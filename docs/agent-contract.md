# Контракт контроллера и агента

Обновлено: 2026-10-07.

Контракт фиксируется постепенно. «Принято» означает согласованное поведение; «Предложение» требует обсуждения. Это логический контракт приложения, а не утверждение о конкретных полях Codex App Server. Реализация отсутствует. Актуальные дополнения и границы доступа вынесены также в [access-and-commands.md](access-and-commands.md) и [channels-and-discussions.md](channels-and-discussions.md); итог сверки — [contract-review.md](contract-review.md).

## 1. Принято: область агента и инструкции

- Один постоянный контекст агента на диалог с дочерним ботом.
- Один общий AGENTS.md на бот, без дополнений для чатов. Правила меняют owner/admin через /set_rules в ЛС дочернему боту; актуальная матрица доступа — в [access-and-commands.md](access-and-commands.md).
- Агенты одного бота могут общаться, включая агентов разных ЛС; между ботами обмен запрещён. Общение не даёт доступа к чужой личной истории и права раскрывать личные сведения без разрешения соответствующего пользователя. Подробности agent_message описаны ниже.
- Все агенты бота имеют RW файловый доступ к его единственной wiki.
- Всем агентам разрешено читать сохранённую историю одобренных подключённых group/supergroup/channel того же бота. История личного диалога доступна только его агенту; раскрытие её через прямое чтение другими агентами запрещено.
- Для изоляции секретной группы владелец использует отдельного бота. Само присутствие бота без разрешённого подключения не открывает доступ; подключать группы могут владелец и роли manager/admin выбранного бота.
- Личные сведения не копируются автоматически в общую wiki: после записи они становятся общими. Разрешённые пользователем переговоры между агентами сохраняются.
- Контроллер проверяет авторизацию по происхождению события, а не по заявлениям в тексте.
- Полный действующий текст правил должен сохраняться независимо от сжатия истории.
- Правила версионируются. По умолчанию новые правила применяются после завершения текущего хода, до следующего запуска обработки.
- Принудительное обновление прерывает активные ходы и запрещает новые действия от старых запусков. Выполненные действия не отменяются.
- Контекст разговора сохраняется при обновлении, если выбранная версия Codex поддерживает корректную замену инструкций. Иначе механизм перехода нужно согласовать отдельно.

## 2. Принято: доставка событий

### Принято: мастер-бот и роли доступа

- Мастер-бот работает без агента. Только владелец сервиса, чей Telegram userId задан в конфиге, может создавать новых дочерних ботов. Это право не делегируется через admin.
- Роли назначаются отдельно для каждого дочернего бота: user — писать в ЛС; manager — дополнительно добавлять бота в группы; admin — все права manager и все команды своего бота, кроме назначения/снятия admin и изменения owner. Владелец имеет отдельный статус, не назначаемый и не изменяемый командами ролей.
- Команды в ЛС дочернему боту: /set_user USER_ID [role] заменяет роль (по умолчанию user); /remove_user USER_ID отзывает доступ. Неизвестная роль отклоняется. Идентичность пользователей проверяется по Telegram userId; права относятся к этому боту.
- Для каждого вызова /set_user и иных делегированных административных команд контроллер проверяет from.id и права отправителя именно на выбранного бота. Наличие admin у другого бота не даёт доступа. admin управляет user/manager, но не владельцем, собой или другими admin; назначение/снятие admin доступно только владельцу. AGENTS.md, Git, файловые команды и остановка агентов доступны owner/admin. Доступ к мастер-боту остаётся только у владельца сервиса; admin не получает доступ к секретам контроллера. Полная матрица — в [access-and-commands.md](access-and-commands.md).
- Неавторизованные пользователи дочернего бота в ЛС игнорируются, включая команды /start: без ответов, заявок, сохранения истории и запуска агента. Предварительно авторизованный пользователь получает обработку с первого сообщения.
- При /remove_user роль удаляется, действия личного агента блокируются и активный ход прерывается; затем полностью удаляются личный агент, его контекст, история, заметка, очередь, задачи/срабатывания и состояния кнопок/карточек. Это заменяет прежнее сохранение истории до 30-дневной очистки. Повторный доступ требует новой авторизации и создаёт диалог с нуля.
- При блокировке дочернего бота пользователем в ЛС выполняется та же полная очистка диалога, но назначенная роль сохраняется. Разблокировка сама не запускает агента: после нового сообщения авторизованного пользователя создаётся новый диалог без повторного разрешения владельца. Общая wiki/Git и уже отправленные Telegram-сообщения остаются, как при очистке группы.
- При добавлении в группу инициатор проверяется по my_chat_member. Владелец, manager или admin данного бота могут подключить группу; при неразрешённом добавлении контроллер вызывает leaveChat, не сохраняет переписку и не создаёт агента. Все участники одобренной группы могут обращаться к агенту независимо от ролей ЛС.
- Эти роли — доступ к боту и его администрированию, отдельно от permits конкретных кнопок. Управление ролями выполняется контроллером без LLM.
- Роль admin приложения не означает администратора Telegram-группы: права проверяются независимо. Проверка доступа в ЛС применяется также к callback до передачи агенту.
- Политика доступа и служебных событий согласована для v1. Заявки, пересылка /start и кнопки принятия/отклонения исключены в пользу явных команд владельца/admin.
- Форумные группы в v1 не поддерживаются независимо от роли добавившего пользователя. При добавлении в группу с is_forum=true контроллер не подключает её, не создаёт агента и вызывает leaveChat.
- Если подключённая группа стала форумом, при обнаружении is_forum=true контроллер прекращает обработку, блокирует новые действия и вызывает leaveChat. Проверка относится к текущему состоянию Telegram (данные chat в обновлениях/актуальный getChat), а не к отдельному гарантированному событию включения форума. Если сервер остановлен, выход возможен после восстановления и обнаружения изменения.
- Архитектура агентов по темам, маршрутизация тем, история и расписание форумов отложены до следующих версий. Предложения об одном агенте на группу/тему не являются принятыми решениями v1.
- Обычные группы имеют агента; каналы и нефорумные супергруппы могут подключаться пассивно без агента. Форумы запрещены. Новая модель и расширения инструментов: [channels-and-discussions.md](channels-and-discussions.md).
- При превращении подключённой обычной группы в супергруппу контроллер прекращает обработку старого диалога и запрещает новые действия, затем выходит из новой супергруппы по её новому chatId. Для обнаружения учитываются migrate_to_chat_id/migrate_from_chat_id и фактический тип чата. Перенос агента, контекста, заметки, расписания и истории на новый chatId в v1 не выполняется; старый диалог отключается согласно правилам отзыва доступа к чату.
- При удалении бота из подключённой группы, включая выход по ограничениям v1, данные диалога удаляются полностью. Сначала контроллер блокирует действия старого агента и прерывает активный ход, затем очищает очередь, отменяет/удаляет задачи и срабатывания, удаляет агента, контекст Codex, локальную заметку, историю группы, состояния кнопок и служебных карточек. Старые исполнения и callback не должны восстановить удалённый диалог.
- Повторное добавление проходит проверку инициатора и типа группы заново; создаётся новый агент/контекст как при первом подключении. Прежние задачи не восстанавливаются, громкий режим изначально выключен.
- Общая wiki бота и её Git-история сохраняются, в том числе сведения, ранее перенесённые из удалённой группы. Автоматическое вычищение происхождения из общих статей не выполняется. Уже отправленные сообщения Telegram этой очисткой не удаляются.

- Свободный агент запускается сразу, без общего окна сбора сообщений. Альбомы — согласованное исключение, описанное ниже.
- Пока агент занят, события ожидают в памяти приложения; постоянной очереди в БД нет.
- При освобождении допускается передача накопленных событий одним пакетом без дополнительной задержки.
- Потеря очереди и автоматического продолжения активной обработки при сбое принята для первой версии.
- История Telegram хранится в БД 30 дней; отложенные задачи хранятся в БД.
- В подключённой группе прямые триггеры принимаются при наличии места в ограниченной очереди; обычные сообщения запускают агента только во время громкого режима. Переписка сохраняется в историю независимо от режима.
- Агент может закончить обработку без отправки сообщения.

### Принято: редактирование и удаление входящих сообщений

- Последняя версия сообщения и дата редактирования сохраняются в БД. Редактирование само по себе не включает/продлевает громкий режим; добавленное при правке упоминание бота не создаёт новый триггер.
- Если сообщение ещё ожидает передачи в очереди, его содержимое заменяется актуальной короткой версией без отдельного события.
- Если сообщение передано в незавершённый основной ход, включая пачки через steer, создаётся одно событие message_edited в обычной очереди. Оно содержит актуальное сообщение в принятом сокращённом формате и editDate, а не только ID и не полный сырой Telegram JSON. При необходимости агент вызывает read.
- Последующие правки до передачи уведомления обновляют его содержимое и editDate, не создавая дублей. После передачи уведомления дальнейшие правки того же сообщения не создают новых уведомлений в рамках того же основного хода; БД обновляется всегда.
- Сообщения, только прочитанные через history/read, не считаются входящими сообщениями активного хода для этой механики. Зависимости от всей прочитанной истории не отслеживаются. После завершения хода редактирование само по себе агента не запускает.
- Уведомление позволяет агенту учесть важную правку или проигнорировать опечатку; не отменяет выполненные действия и уже отправленные ответы. Передача во время ожидания через steer зависит от ранее запланированной проверки runtime.
- В обычных ЛС и группах Bot API не сообщает об удалении пользователем. Входящий message_deleted в v1 не вводится. deleted_business_messages относится к бизнес-подключениям, не к нашим обычным чатам.
- Когда сообщение удаляет сам контроллер через инструмент, локальная запись обновляется по подтверждённому результату операции. Удалённые пользователями сообщения могут остаться в локальной истории до 30-дневной очистки; автоматическое обнаружение не обещается. Удаление не считается автоматической отменой расписания или откатом действий.

### Принято: технический сбой основного агента

- При техническом сбое контроллер прекращает индикатор и напрямую отправляет ошибку в текущий чат. Это сообщение не ставится в очередь агента и не вызывает новый ход. Диагностика не раскрывает токены и внутренние секреты.
- Очередь событий пострадавшего агента в памяти очищается; уже начатая пачка автоматически не повторяется. Выполненные внешние действия не отменяются. Очистка очереди не удаляет обычную сохранённую историю сообщений.
- Для межагентских сообщений, потерянных из очищенной очереди или незавершённой активной пачки, контроллер отправляет уведомление каждому непосредственному агенту-отправителю. Уведомление означает сбой обработки, не подтверждение доставки/исполнения поручения. Не вводятся requestId, обязательные ответы или ожидание подтверждения отправителем.
- Уведомления отправителям доставляются как события их агентов через общую очередь; прямое сообщение об ошибке в пострадавший Telegram-чат остаётся вне очереди. Ошибка не пересылается далее как новая просьба, чтобы не создавать циклы уведомлений о сбое.
- Асинхронное уведомление о сбое обязательно содержит agentId пострадавшего агента, а не только описание: например {"eventType":"agent_error","agentId":"a2","error":"agent_failed","description":"The target agent failed while processing messages. Your request may not have been completed."}. Description на английском; идентификатор принадлежит тому же боту. RequestId и личные chatId/userId не добавляются.
- Принудительное обновление инструкций не считается техническим сбоем само по себе. Возможность сообщить об ошибке при остановленном контроллере/недоступном Telegram не гарантируется; постоянная очередь аварийных уведомлений в этом решении не вводится.
- Исключение из потери событий: срабатывания планировщика сохраняются как невыполненные/пропущенные в БД, включая события из незавершённой активной пачки. Правила карточек и повторов описаны ниже; обычная пачка сообщений не переигрывается.

### Принято: громкий режим групп, первая версия

- По умолчанию выключен. Прямой триггер автоматически включает его до двух минут после этого триггера.
- Триггеры: упоминание текущего бота, reply на его сообщение и разрешённое нажатие его кнопки в этом чате. Проверки доступа контроллера сохраняются.
- Каждый новый триггер заново устанавливает срок: время последнего триггера + 2 минуты, и сбрасывает лимит 10 обычных сообщений громкого режима.
- В течение окна обычные новые сообщения передаются агенту как в ЛС; при занятости действует очередь в памяти и передача накопленного пакета.
- Агент учитывает, что сообщение может быть адресовано другим участникам, и может промолчать или участвовать по собственной инициативе.
- Обычные сообщения, ответы бота и внутренние события не продлевают окно.
- Агент не включает, не продлевает и не выключает режим инструментом. Ранняя отписка отложена за пределы v1.
- По истечении окна новые обычные сообщения только сохраняются в историю; уже начатый ход завершается без прерывания.
- Ожидающие обычные события после истечения окна больше не запускают агента. Прямые обращения из очереди обрабатываются независимо от окна.
- Состояние режима хранится в памяти контроллера; после перезапуска режим выключен.
- Для ЛС окно не применяется: разрешённые сообщения и так активируют агента.

Громкий режим отсчитывается от получения триггера контроллером, не от начала обработки агентом; ожидание очереди его не продлевает. Альбом проверяется после сборки по принятому ниже правилу; повторная доставка того же Telegram update не является новым триггером. Отдельной реакции на обновления Live Location нет.

### Принято: сборка альбомов

- Каждый элемент сразу сохраняется в историю.
- Контроллер собирает элементы по (botId, chatId, albumId).
- Пакет становится готовым после 1 секунды без новых элементов либо через 3 секунды после первого элемента — что наступит раньше.
- Сохраняются отдельные messageId; готовые элементы передаются одним пакетом, когда агент свободен.
- В группе альбом активирует агента, если содержит обращение к боту или reply на сообщение бота, либо обрабатывается в громком режиме. Вне громкого режима альбом без прямого триггера только сохраняется. Сборка альбома сохраняется в обоих режимах; окно громкого режима проверяется в момент готовности пакета, не по времени первого фото. Если окно закончилось, альбом без собственного прямого триггера в очередь не поступает, даже если первые элементы пришли внутри окна.
- Поздний элемент сохраняется и передаётся как дополнение с тем же albumId, если этот альбом активировал агента; при занятости действует обычная очередь.
- Таймер не гарантирует полноту альбома: Telegram не передаёт сигнал завершения.
- Обычные сообщения не ждут сборки альбома. Альбом не резервирует место в очереди: ставится после готовности, поэтому более позднее обычное сообщение может быть передано раньше альбома. Служебные подсказки о сборке и дополнительные инструкции агенту не вводятся.

### Принято: Live Location

- Активная Live Location обозначается live:true внутри location.
- Обновления заменяют сохранённую версию и сами не запускают агента. Маршрут из промежуточных координат не накапливается.
- Агент может читать последнюю полученную позицию через read и назначать следующую проверку одноразовой отложенной задачей.
- Сценарий проверки каждую минуту и уведомления о приближении поддерживается через расписание в БД. Специальный инструмент маршрутов в v1 не подключается; это пример поручения, а не обязательная функция.
- Для оценки свежести нужны время последнего обновления и сведения о состоянии трансляции; точная схема read ещё обсуждается.

## 3. Предложение: данные запуска

Контроллер передаёт неизменяемые сведения об области исполнения отдельно от текста событий:

```json
{
  "botId": "b1",
  "agentId": "a1",
  "chatId": -100123,
  "runId": "r17",
  "rulesVersion": 3
}
```

Эти сведения привязываются контроллером к вызовам инструментов. Агент не выбирает botId или runId в аргументах каждого вызова. Точные типы идентификаторов и способ передачи зависят от адаптера Codex и пока не утверждены.

Принятое ограничение: chatId/userId личных диалогов не раскрываются другим агентам через межагентные события, список агентов и сведения о личных агентах. Собственному агенту ЛС доступны chatId и userId текущего собеседника; скрывать их от него не требуется. Контроллер проверяет область независимо от знания идентификатора.

## 4. Принято: входной пакет событий

Агент получает непосредственно упорядоченный JSON-массив событий, без обёртки events. Одиночное обращение — массив из одного элемента. turn/start и turn/steer используют одинаковый формат содержимого. В RPC массив сериализуется в текст входного элемента Codex; это не замена нативной схемы input App Server. Полный Telegram JSON по умолчанию не включается.

```json
[
  {
    "eventType": "message",
    "messageId": 150,
    "date": "2026-10-03T10:15:00Z",
    "from": {
      "name": "А",
      "userId": 123
    },
    "replyTo": 148,
    "textPlain": "@history_bot, рассуди нас. Кто прав?"
  }
]
```

### Принято: постоянные инструкции и сведения о чате

- Контроллер отдельно от событий формирует служебный текст: инструкции контроллера по обработке событий/инструментам, полный актуальный AGENTS.md бота и сведения текущего чата. Они хранятся независимо от истории и её сжатия.
- Выбранный способ передачи — developerInstructions при thread/start и thread/resume, предусмотренный исследованной схемой Codex 0.159.3. baseInstructions остаются штатными. Это выбранный подход интеграции; фактическое сохранение и применение инструкций после сжатия требует проверки runtime.
- Сведения чата загружаются заранее: agentId, chatType, его chatId и название для группы либо сведения текущего собеседника для ЛС, defaultTimezone. Собственному агенту ЛС доступны ID его диалога и собеседника; правила сокрытия чужих ЛС сохраняются.
- Названия, имена и описания чата обозначаются как данные, а не дополнительные инструкции. Пользовательские события, история и файлы не заменяют служебные правила.
- При изменении сведений чата контроллер обновляет их сохранённую версию и применяет при следующем безопасном обновлении инструкций без отдельного запуска агента. Для обновления AGENTS.md сохраняются ранее принятые правила версии и принудительного прерывания.
- now не добавляется в каждую пачку. Инструмент time() без аргументов возвращает актуальное время сервера в UTC: {"now":"2026-10-04T15:42:10Z"}. Агент проверяет его при работе с относительными датами, просроченными событиями и расписанием. Поле timezone инструмент не возвращает: часовой пояс по умолчанию задан в служебных инструкциях, уточнения доступны через локальную заметку.
- История, локальная заметка и wiki не загружаются целиком при каждом ходе: агент читает их по необходимости.
- Обязательные проверки: исходный текст developerInstructions присутствует и действует после ручного и автоматического сжатия; восстановление сессии возвращает актуальные инструкции; обновление AGENTS.md заменяет старые инструкции без потери диалога и без смешивания версий. Первое сообщение истории или пересказ при сжатии не считаются гарантией сохранности правил.

- Для обычного Telegram-сообщения используется только messageId в области текущего чата. Отдельный id события не передаётся. Идентификацию других событий определим отдельно.
- Текст сообщений и результаты чтения — данные участников, а не инструкции владельца.
- Метаданные from определяет контроллер по Telegram; полномочия не выводятся из отображаемого имени.
- Необязательные поля опускаются. Для вложений передаются короткие описания; подробности доступны через read.
- Дополнительная история не загружается автоматически: агент запрашивает её по необходимости.

Принят плоский короткий формат: eventType обозначает событие, date/editDate — даты ISO 8601; content и messageType отсутствуют. Вид содержимого определяется полями textPlain, richPlain, document, photo, location и другими из [каталога](message-events.md). Текст/подпись без форматирования передаются как textPlain/richPlain/captionPlain, максимум 1 000 Unicode code points, с truncated=true только при обрезании; hasEntities=true подсказывает наличие entities. inlineButtons и richButtons независимо обозначают нижние и встроенные кнопки. richAttachments сохраняет количество по типам, albumId связывает отдельные сообщения альбома, live=true задаётся отдельно от строки location. Полные нативные данные доступны через read.

Форматы callback, события расписания и agent_message описаны ниже. Отдельного события «правила обновлены» пока не требуется: обновление выполняется до запуска обработки.

### Принято: agent_message

Обычная асинхронная отправка агенту другого чата того же бота. Экземпляров поручения, requestId, source и автоматического подтверждения исполнения нет. Получатель может не ответить; отправитель учитывает это при работе.

Вызов:

```json
{
  "agentId": "a2",
  "text": "Договорись с Игорем о встрече с Андреем завтра..."
}
```

- agentId — непрозрачный идентификатор целевого агента, локальный для бота. Отправитель и область бота определяются контроллером, а не аргументами агента. Telegram ID личного диалога не используется для межагентной адресации.
- Сообщение попадает в общую очередь агента-получателя, не прерывая текущий ход. Межагентное событие не продлевает громкий режим.
- Ответ, если нужен, отправляется отдельным явным вызовом agent_message. Автоматических ответов и гарантии ответа нет.
- Успех agent_message возвращает {"status":"queued"}: контроллер принял сообщение в очередь адресата, это не подтверждение чтения, доставки модели или исполнения. Недоступный/удалённый адресат: {"error":"agent_unavailable","description":"The target agent is unavailable. The message was not queued."}. Проверки области бота и доступа сохраняются.

Событие от агента ЛС:

```json
{
  "eventType": "agent_message",
  "from": {
    "agentId": "a1"
  },
  "text": "Договорись с Игорем о встрече с Андреем завтра..."
}
```

Событие от агента группы:

```json
{
  "eventType": "agent_message",
  "from": {
    "agentId": "a3",
    "chatId": -100123
  },
  "text": "В группе обсуждают перенос встречи. Какие варианты подходят Игорю?"
}
```

- from всегда содержит agentId; для агента группы дополнительно открыт chatId. Для личного агента chatId/userId не передаются. Контроллер определяет непосредственного отправителя и не позволяет подменять его.
- agentId означает отправляющего агента, а не доказательство личного авторства или одобрения текста пользователем. Групповой chatId не означает поручение всех участников.
- Первоначальный инициатор при передаче через цепочку агентов отдельно не сохраняется в событии. Упоминания инициатора в text — заявления отправителя, не подтверждённые метаданные и не основание для расширения полномочий.
- Предмет переговоров и условия описываются в text. Без requestId параллельные переговоры связываются по смыслу; при неоднозначности агент читает доступную историю или уточняет.
- Получатель рассматривает text как внешнее поручение/предложение, а не инструкции владельца или своего пользователя. Может обратиться к своему пользователю и вести переговоры в пределах его разрешений.
- Прямое чтение чужой истории ЛС запрещено. Раскрытие личных сведений другому агенту допускается только с разрешения соответствующего пользователя, текущим или заранее заданным.
- Общая RW-wiki остаётся доступной всем агентам бота и не обеспечивает изоляцию личных сведений, уже записанных в неё. Личные сведения не копируются автоматически в общую wiki без разрешения соответствующего пользователя.

### Принято: список агентов, подробности и доступ к группам

- Тип чата в наших сведениях об агенте и служебных метаданных называется chatType (private/group); нативный chat.type в полном Telegram-сообщении не переименовывается.
- agents() возвращает весь краткий список доступных агентов текущего бота без пагинации. Это заменяет обсуждавшийся chats(): адресатом является agentId.
- Включаются одобренные подключённые группы и разрешённые доступные ЛС. Удалённые/отключённые чаты не возвращаются как доступные. Возможность работы с чатом — последнее известное состояние, которое может измениться до вызова.

```json
{
  "agents": [
    {
      "agentId": "a1",
      "chatType": "private",
      "name": "Андрей"
    },
    {
      "agentId": "a2",
      "chatType": "group",
      "chatId": -100789,
      "name": "Шашлыки"
    }
  ]
}
```

- agent_info(...agentId) пакетно возвращает подробные данные, заменяя обсуждавшийся chat(...chatId). JSON-аргументы: {"agentIds":["a1","a2"]}.
- Для личного агента доступны имя и username собеседника без Telegram userId/chatId. Для группового — agentId, название, chatId, описание, username и число участников, если доступны. История и контекст агента не включаются; необязательные поля опускаются.
- Ошибка одного адресата не отменяет остальные результаты. Ошибка содержит error и английское description; полная схема сведений принята в разделе agent_info/members.
- members({userIds}) предназначен для доступных сведений и роли выбранных участников текущей группы; схема ответа принята ниже. Групповые userId не скрываются, но не предоставляют доступ к ЛС. Telegram гарантирует getChatMember для других пользователей только боту-администратору; недоступность данных — допустимый результат.
- Отдельный users() и отдельная таблица всех замеченных пользователей для v1 не требуются. Контроллер хранит внутреннее соответствие agentId, chatId и userId собеседника ЛС; Telegram ID не раскрываются через сведения о личном агенте. Данные отправителей живут вместе с сообщениями 30 дней; метаданные подключённого диалога и заметка — до его удаления, роли хранятся отдельно.
- history, read и download получают необязательный chatId: без него текущий чат, с ним только одобренный подключённый group/supergroup/channel того же бота. Чужой личный диалог, чат другого бота и неподключённая группа отклоняются контроллером. Прежняя область messageId — выбранный чат, а не глобальный идентификатор.
- Наличие личного агента в списке разрешает межагентное обращение, но не чтение его истории. Раскрытие группового chatId позволяет запрашивать групповую историю; изменение/отправка сообщений в соседних группах напрямую пока не утверждены.

### Принято: подробные ответы agent_info и members, 2026-10-05

- agent_info({agentIds:[...]}) возвращает {agents:[...]} в порядке запроса, с результатом/ошибкой каждого элемента независимо. Только агенты текущего бота. Неизвестный адресат: {agentId,error:"agent_not_found",description} с английским описанием.
- Сведения ЛС: agentId, chatType:"private", name, известный username. Чужие личные chatId/userId скрыты. Свой личный агент знает ID своего диалога/собеседника из служебных инструкций. Контекст, notes, история и инструкции другого агента не входят в ответ.
- Сведения группы: agentId, chatType:"group", chatId, name, известные description, memberCount, botStatus. Сведения обновляются через Telegram; неизвестные необязательные значения опускаются. botStatus — статус бота в Telegram, не роль приложения.
- agent_info включает известный pinned_message в полном формате сообщения и available_reactions в согласованном нативном формате. Пустой список означает запрет реакций; отсутствие поля в успешно полученных сведениях Telegram — доступность стандартных emoji. Ошибка получения актуальных сведений даёт error/английское description для элемента, а не неполный успех, который можно принять за разрешение всех реакций.
- members({userIds:[...]}) возвращает {members:[...]} в порядке запроса. Область — только текущая группа, без chatId для другого чата. В ЛС — ошибка с английским description. Без userIds не возвращается полный список участников; такой вызов не поддерживается.
- Успех участника: userId, name, известный username, status и customTitle. status — нативный статус Telegram, не user/manager/admin приложения. Для известного временного ограничения/блокировки добавляется untilDate в ISO 8601; бессрочная дата не выдумывается. Полный набор отдельных прав участника не выдаётся в v1.
- Недоступность элемента: {userId,error:"member_unavailable",description}. Telegram не гарантирует получение сведений о других пользователях, если бот не администратор. При действиях контроллер независимо проверяет права бота и доступ пользователя.

```json
{
  "agents": [
    {"agentId":"a1","chatType":"private","name":"Андрей","username":"DPOHVAR"},
    {"agentId":"a2","chatType":"group","chatId":-123456789,"name":"Шашлыки","description":"Планируем поездки и встречи","memberCount":12,"botStatus":"administrator","available_reactions":[{"type":"emoji","emoji":"👍"}]},
    {"agentId":"missing","error":"agent_not_found","description":"The agent is not available for this bot."}
  ]
}
```

```json
{
  "members": [
    {"userId":123,"name":"Андрей","username":"DPOHVAR","status":"administrator","customTitle":"Организатор"},
    {"userId":456,"name":"Игорь","status":"member"},
    {"userId":789,"error":"member_unavailable","description":"Telegram could not provide this member's details."}
  ]
}
```

### Принято: кнопки и callback

Одинаковая механика применяется к нижней inline-клавиатуре и кнопкам внутри rich-содержимого. Агент задаёт Telegram-совместимые кнопки непосредственно, без отдельного словаря или маркеров размещения.

```json
{
  "text": "☐ Короткий",
  "callback_data": "[route]short"
}
```

- Агент заполняет callback_data, в rich HTML/Markdown — атрибут data тега tg-button. Формат [btnGroup]key обозначает окончательный одиночный выбор; key без префикса группы — повторяемое действие. Группа распознаётся только по префиксу в начале строки.
- key и btnGroup — непустые строки длиной не более 20 Unicode code points каждая; символы [ и ] внутри запрещены. Пустой ключ, пустая группа и незакрытая скобка недопустимы. Полный callback_data должен помещаться в 64 байта UTF-8; Unicode-лимиты полей сами по себе этого не гарантируют. Идентификаторы не обрезаются.
- Группа ограничена одним сообщением: одинаковое имя в разных сообщениях не связывает их. В одном rich-сообщении группа может объединять кнопки из разных блоков и клавиатуры под сообщением.
- Группа может содержать одну кнопку. Например, {"text":"Отменить поездку","callback_data":"[cancel]cancel"} принимается один раз и блокируется без добавления иконки. Повторные нажатия не запускают агента.
- Первое разрешённое нажатие атомарно закрывает группу в состоянии контроллера. Все её кнопки становятся неактивными; выбранная сохраняет отметку выбора.
- Контроллер подтверждает callback без ожидания агента, обновляет интерфейс и передаёт агенту одно событие принятого выбора. Ошибка обновления интерфейса не открывает группу снова.
- Повторные, устаревшие и неразрешённые нажатия не передаются агенту и не продлевают громкий режим. Контроллер подтверждает их с подходящим уведомлением.
- Полей check и showCheckboxIcon нет. Агент сам ставит префикс ☐, ☑ или ☒ в подпись групповой кнопки. Только при наличии такого префикса контроллер управляет иконкой: ☐ — можно выбрать, ☑ — выбрано, ☒ — не выбрано и неактивно. Без префикса иконка не добавляется. Подписи действий без группы не изменяются.
- Контроллер использует Telegram disabled:{} для блокировки обычных и rich-кнопок. Выбранная кнопка закрытой группы тоже неактивна.
- Состояние кнопок хранится в существующей записи исходящего сообщения; отдельная таблица кнопок и версии не нужны. read возвращает актуальные кнопки с иконками/disabled; отдельное синтетическое состояние выбора не выдаётся.
- До сетевых ожиданий контроллер атомарно устанавливает минутную блокировку для (botId, chatId, messageId, btnGroup) и сохраняет закрытые кнопки. Таймер защищает от быстрых кликов; актуальное сохранённое disabled защищает от поздних и после перезапуска. Ошибка обновления Telegram не откатывает закрытие группы.
- Для нового выбора агент задаёт новый btnGroup либо новое сообщение. Закрытая группа не открывается под прежним именем. Удаление группы превращает новую кнопку в действие; старый callback с группой отклоняется.
- Полученный callback_data сверяется с текущими сохранёнными кнопками, их активностью и разрешениями. Содержимое callback не перезаписывает нашу текущую запись. Если записи сообщения нет (включая удаление после 30 дней), callback отклоняется как устаревший без запуска агента.
- Проверки доступа выполняются до закрытия группы; подробные правила permits описаны ниже.

Принятое событие:

```json
{
  "eventType": "button",
  "messageId": 150,
  "from": {
    "name": "А",
    "userId": 123
  },
  "key": "short",
  "text": "Короткий",
  "btnGroup": "route"
}
```

prompt не передаётся: при необходимости агент вызывает read(messageId). text содержит подпись кнопки без управляемой иконки; rich-подпись нормализуется в простой текст. Для кнопки-действия btnGroup отсутствует.

Основание для адаптера: [RichMessageButton](https://core.telegram.org/bots/api#richmessagebutton), [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton), [CallbackQuery](https://core.telegram.org/bots/api#callbackquery). Префикс группы — соглашение нашего приложения о содержимом callback_data.

### Принято: permits на кнопки

- В БД permits хранится как синтетическое свойство записи отправленного сообщения рядом с Telegram-структурой. В Telegram свойство не передаётся; в callback_data разрешения не кодируются.
- Пермиты применяются только в групповых чатах. В личных сообщениях они не используются; общая авторизация пользователя бота сохраняется.
- permits — объект правил по полному callback_data, без разделения на группы и действия:

```json
{
  "permits": {
    "[route]short": [
      123
    ],
    "[route]*": [
      123,
      456
    ],
    "cancel": [],
    "*": null
  }
}
```

- Это не регулярные выражения: без * правило точное; единственная * допустима только в конце и задаёт префикс. Квадратные скобки — обычные символы. * совпадает с любой строкой.
- Приоритет: точное совпадение, затем совпавший префикс максимальной длины, затем *. Применяется одно правило; списки пользователей не объединяются.
- Массив Telegram userId разрешает нажатие только указанным пользователям; [] запрещает всем; null разрешает всем в рамках общей авторизации бота. Пермит не расширяет общий доступ.
- При первой отправке отсутствие permits означает общий доступ. Если объект передан, но совпадения нет, нажатие запрещено. Общий доступ явно выражается через {"*":null}.
- permits передан в edit — полностью заменяет прежний объект; отсутствует — прежние разрешения сохраняются, в том числе после удаления кнопок. При редактировании rich агент сам следит за встроенными кнопками и сохраняемой нижней клавиатурой и передаёт актуальные разрешения. Контроллер v1 не парсит разметку для проверки обязательности обновления permits. Риск ошибочного применения старого правила (включая "*":null) принят. Проверки актуальной кнопки, активности и действующих permits при callback сохраняются.
- Редактирование только содержимого без изменения кнопок сохраняет permits. Автоматическое обновление иконок/disabled контроллером после выбора также сохраняет permits и не требует участия агента.
- Сначала проверяются реальный отправитель callback, общая авторизация, наличие текущего сообщения и кнопки, точное совпадение данных и активность; затем permits. Неразрешённое нажатие не закрывает группу и не запускает агента.

### Принято: дополнительные возможности кнопок

- В v1 предусмотрены callback (callback_data, в разметке data), ссылка (url) и копирование текста (Telegram copy_text, в разметке type=copy_text). У кнопки ровно одно действие; группировка применяется только к callback.
- Общие поля: text, необязательный style (primary, success, danger) и Telegram disabled:{}; в rich-разметке блокировка выражается type=disabled.
- Для rich callback-кнопок дополнительно доступен style:link. Произвольные цвета не предусмотрены.
- Нижние кнопки располагаются по строкам в reply_markup.inline_keyboard; rich-кнопки — внутри текста или tg-button-row.
- Агент может менять подписи и стили, добавлять, удалять и переставлять кнопки, блокировать отдельные кнопки или группу и удалять все кнопки. Изменение подписи или стиля не сбрасывает выбор.
- Нажатия ссылок и копирования не создают callback, не закрывают группы и не продлевают громкий режим.
- Inline-вызов бота и кнопки inline-переходов отложены за пределы v1. inline_query/chosen_inline_result не запускают агента. Это не затрагивает принятые callback-кнопки inline-клавиатуры. Mini Apps и Telegram Login остаются возможными расширениями. Клавиатура ввода ReplyKeyboardMarkup в v1 не рассматривается.

### Принято: события расписания

```json
[
  {
    "eventType": "scheduled",
    "taskId": "t1",
    "scheduledAt": "2026-10-04T07:00:00Z",
    "text": "Напомни пользователю позвонить маме."
  }
]
```

- taskId идентифицирует задачу; повторные срабатывания cron используют тот же taskId.
- scheduledAt — назначенное время срабатывания в UTC, даже если обработка началась позднее.
- Для cron-события дополнительно передаётся timezone из задачи (часовой пояс IANA, например Asia/Nicosia). scheduledAt и lastScheduledAt остаются в UTC. Смещение конкретного времени не заменяет timezone. Для одноразового at отдельное поле timezone не требуется. Cron-выражение в событии не дублируется; при необходимости агент получает его через tasks(taskId).
- text — сохранённая полная инструкция. description в событии не дублируется.
- Срабатывание запускает агента; само по себе не отправляет сообщение в Telegram. Агент выбирает действия и может промолчать.
- При занятости агента событие ждёт освобождения и не прерывает текущий ход.
- Задача выполняется с актуальными правилами бота. Событие расписания обрабатывается независимо от громкого режима и не продлевает его.
- Отложенные задачи сохраняются в БД независимо от 30-дневной истории сообщений. Срабатывания остаются восстанавливаемыми до успешной обработки; очередь в памяти не является единственным источником расписания.

### Принято: очередь расписания и восстановление после простоя

- Сообщения чата и события планировщика используют общую очередь текущего агента. При его занятости все события ожидают освобождения; готовый пакет передаётся без дополнительной задержки.
- Очередь остаётся в памяти. Срабатывания планировщика дополнительно сохраняются в БД до успешной обработки, включая состояние активной попытки; при сбое становятся пропущенными и допускают повтор. Это заменяет прежний срок сохранения только до передачи агенту. Сообщения чата не получают постоянную очередь.
- Просроченная одноразовая задача at передаётся после запуска сервера. Агент сам решает, выполнять её, сообщить об опоздании или промолчать.
- Новые cron-срабатывания за время остановки сервера пропускаются и не восстанавливаются. После запуска расписание продолжается с ближайшего будущего времени.
- Cron-событие, уже ожидавшее до остановки, сохраняется и передаётся после запуска. Оно не считается новым срабатыванием за время простоя.
- Для одной cron-задачи допускается одно ожидающее событие. Новые срабатывания объединяются с ним по taskId, а не по тексту инструкции. Разные задачи не объединяются.
- Объединённое событие сохраняет место первого срабатывания в общей очереди. Например, «сообщение А → cron t1 → сообщение Б → cron t1» становится «сообщение А → cron t1 (2 срабатывания) → сообщение Б».
- Уже выполняющееся событие не объединяется с новыми срабатываниями. Пока событие данного taskId в обработке, новые срабатывания накапливаются в БД вне общей очереди и не передаются агенту, даже если во время ожидания субагентов допускается steer с другими событиями. После завершения обработки накопленное событие может войти в обычную очередь. Для одной задачи не допускаются одновременные попытки.
- Если задача не в обработке, но агент занят другими событиями, её срабатывания накапливаются в общей очереди и схлопываются по прежнему правилу. Например, четыре ожидающих срабатывания передаются как одно событие с occurrences=4.
- scheduledAt содержит время первого срабатывания. При объединении добавляются lastScheduledAt (последнее срабатывание) и occurrences (общее число, включая первое). Для одиночного срабатывания эти дополнительные поля опускаются.
- occurrences учитывает только реально созданные срабатывания, а не пропущенные за время остановки сервера.
- Для четырёх срабатываний, накопившихся за четыре минуты во время предыдущей обработки, следующее событие имеет occurrences=4: одно актуальное срабатывание и три дополнительных пропущенных. Значение «3 пропуска» не включает уже завершённое предыдущее событие. scheduledAt/lastScheduledAt относятся только к новой накопленной группе.
- Актуальное время агент получает через инструмент системного времени по ранее принятому правилу, без now в каждой пачке.
- expiresAt в v1 не вводится: решение об актуальности просроченного поручения принимает агент.

Пример объединённого события:

```json
{
  "eventType": "scheduled",
  "taskId": "t2",
  "scheduledAt": "2026-10-03T12:00:00Z",
  "lastScheduledAt": "2026-10-03T12:04:00Z",
  "timezone": "Asia/Nicosia",
  "occurrences": 5,
  "text": "Проверь актуальные сведения и обнови сводку."
}
```

## 5. Предложение: выход агента

### Принято: типы исходящих сообщений, v1

- Текст с форматированием, ссылками и упоминаниями.
- Rich-сообщение со структурированным содержимым, медиа и встроенными кнопками.
- Фото, документ, видео, анимация, аудио, голосовое, стикер.
- Геопозиция, место (venue), контакт.
- Опрос/викторина и дайс.
- Альбомы как группа связанных медиа. Кнопки для альбома отправляются отдельным сообщением после него: sendMediaGroup не принимает reply_markup.
- Пересылка и копирование существующих сообщений с учётом ограничений Telegram.
- Отправка видеокружков, Live Photo и Live Location отложена. Чтение входящей Live Location сохраняется.
- Нативные чеклисты отложены: sendChecklist требует business_connection_id и отправку от имени подключённого аккаунта. Счета, платные медиа и игры в v1 не включаются.
- Отправка аудио/видео не подразумевает поддержку их генерации.

### Принято: размещение кнопок

- Агент самостоятельно выбирает встроенные кнопки rich-содержимого или нижнюю inline-клавиатуру. Rich-сообщение может одновременно содержать оба варианта.
- Общая механика callback_data, групп и состояния действует независимо от размещения.
- Для текста используется нижняя inline-клавиатура. Клавиатура ввода не включается.
- Принятый пример отправки rich и кнопок приведён ниже; полная схема send/edit для всех типов ещё обсуждается. Актуальные правила выхода и очистки приведены в access-and-commands.md.

### Принято: отправка rich и кнопок без парсера разметки контроллера

- Агент передаёт rich_message с нативным Telegram html, markdown или blocks (ровно один формат). Нижняя клавиатура передаётся как reply_markup.inline_keyboard. Контроллер подставляет chat_id назначения: необязательный chatId либо текущий чат, с проверкой доступа.
- HTML/Markdown отправляется без переписывания разметки: нет специальных атрибутов key/btnGroup и маркеров размещения кнопок. Агент сразу заполняет data и подписи с иконками, если они нужны.
- После отправки контроллер сохраняет структурированный Message из ответа Telegram. В rich_message кнопки представлены JSON-объектами; контроллер обходит эту структуру и разбирает только короткий callback_data.
- Для автоматического изменения rich-кнопок контроллер изменяет сохранённую структуру и преобразует её в InputRichMessage.blocks. Выходные и входные блоки требуют адаптера; исходный HTML/Markdown не парсится контроллером.
- Успешный send возвращает агенту messageIds — массив, в том числе для одного сообщения. permits — дополнительное синтетическое поле приложения, которое сохраняется в БД и исключается из запроса Telegram.

Пример одного сообщения с обоими размещениями кнопок:

```json
{
  "rich_message": {
    "html": "<h2>Настройка поездки</h2><p>Выберите маршрут:</p><tg-button-row><tg-button type=\"callback_data\" data=\"[route]short\">☐ Короткий</tg-button><tg-button type=\"callback_data\" data=\"[route]scenic\">☐ Живописный</tg-button></tg-button-row><p>Ниже выберите транспорт.</p>"
  },
  "reply_markup": {
    "inline_keyboard": [
      [
        {
          "text": "☐ Пешком",
          "callback_data": "[transport]walk"
        },
        {
          "text": "☐ На машине",
          "callback_data": "[transport]car"
        }
      ],
      [
        {
          "text": "Подробнее",
          "callback_data": "details"
        },
        {
          "text": "Открыть карту",
          "url": "https://example.com/map"
        }
      ]
    ]
  },
  "permits": {
    "[route]*": [
      123
    ],
    "[transport]*": [
      123

```

```json

    170
  ]
}
```

- Публикация в Telegram выполняется только явными инструментами, а не автоматической отправкой финального текста Codex.
- Один ход допускает ноль, один или несколько вызовов отправки.
- Завершение хода без отправки означает, что агент решил промолчать.
- Финальный текст не требует повторять отправленные сообщения; отдельный JSON-отчёт о каждом ходе не вводится.
- Контроллер получает статус completed / failed / interrupted из протокола исполнения и не определяет успех по свободному тексту агента.

## 6. Инструменты

### Принято: сокращённое представление rich-сообщения

- В событиях, history и search rich использует общий краткий формат сообщения: richPlain (пустая строка для rich без текста), richAttachments с количеством вложений по типам и richButtons=true при наличии встроенных кнопок. inlineButtons=true независимо обозначает нижнюю inline-клавиатуру.
- richPlain извлекается из текстовых блоков в порядке чтения, с переносами строк между блоками, без оформления и подписей кнопок. Если текста нет, richPlain="" сохраняет признак вида. Даже без обрезания это извлечённый текст, а не полное rich-содержимое. Структура блоков, файловые ID и подробные метаданные в короткий вид не входят.
- При превышении общего лимита текста выдача обрезается и содержит truncated=true. Лимит — 1 000 Unicode code points; полное содержимое доступно через read.
- Короткий вид вычисляется при сохранении по структурированным блокам Telegram и пересчитывается при редактировании. Для поиска сохраняется полный извлечённый текст до обрезания. Полная структура, вложения и кнопки доступны через read.

```json
{
  "eventType": "message",
  "messageId": 170,
  "date": "2026-10-04T12:30:00Z",
  "from": {
    "name": "Андрей",
    "userId": 123
  },
  "richPlain": "Предлагаю встретиться здесь.\nПервый вариант — офис.\nДругие варианты — в карусели.",
  "richAttachments": {
    "photo": 4
  },
  "richButtons": true,
  "inlineButtons": true
}
```

### Принято: единый send для сообщений и альбомов

- Отдельного send_album нет. send отправляет одно сообщение или один альбом; необязательный chatId выбирает текущий чат либо подключённый пассивный канал/супергруппу. Отправка в чужой чат с агентом запрещена.
- Ровно один вариант содержимого: text, rich_message, photo, document, video, animation, audio, voice, sticker и другие принятые типы; массив media верхнего уровня обозначает альбом. Контроллер выбирает подходящий метод Telegram, включая sendMediaGroup.
- rich_message.media описывает вложения внутри одного rich-сообщения и не означает альбом. Ограничения размеров, форматов и совместимости типов альбома проверяются согласно Telegram API.
- Остальные параметры близки к Telegram: caption, reply_parameters, reply_markup и т. п., где они поддерживаются выбранным типом. uploads, file_sources и permits — синтетические поля приложения, не передаются Telegram.
- Альбом не допускает reply_markup и permits; кнопки отправляются отдельным следующим вызовом send.
- Для нескольких независимых сообщений агент делает несколько вызовов send; отдельного пакетного отправителя в v1 нет.
- Успех всегда возвращает {"messageIds":[170]}; альбом — {"messageIds":[171,172]} в порядке отправленных элементов. Это заменяет прежний одиночный результат messageId.
- До отправки проверяются локальные пути, источники файлов и разрешения. Известный отказ возвращает короткую ошибку, например {"error":"file_not_accessible"}.
- Если запрос мог быть выполнен, но результат доставки неизвестен, возвращается {"error":"delivery_unknown"}. Такой исход не означает гарантированную неудачу; автоматический повтор может создать дубликат. Правило относится и к альбому.

### Принято: forward и copy

- Оба инструмента отправляют в текущий чат или разрешённый пассивный чат. chatId — необязательное назначение, fromChatId — необязательный источник; каждое отсутствующее поле независимо означает текущий чат агента. messageIds (1–100 ID строго по возрастанию) относятся к источнику. Источник и назначение проверяются независимо по правилам доступа. Контроллер выбирает одиночный метод для одного ID и пакетный для нескольких.
- Контроллер проверяет область источника: текущий чат либо одобренный подключённый group/supergroup/channel того же бота. Чужие ЛС, группы другого бота и неподключённые чаты запрещены. Для проверки доступа достаточно разрешённого chatId; наличие каждого messageId в локальной 30-дневной истории не требуется. Наличие сообщения и возможность операции проверяет Telegram.
- forward сохраняет указание источника, copy создаёт копию без ссылки на оригинал. Файлы не скачиваются. Контроллер выбирает одиночный или пакетный метод Telegram; пакетные методы сохраняют группировку альбомов.
- Оба принимают disable_notification и protect_content. copy одного сообщения дополнительно допускает caption, parse_mode либо caption_entities, show_caption_above_media, reply_parameters, reply_markup и синтетические permits по общим правилам кнопок. Произвольная замена основного текста через copy не предусмотрена.
- copy нескольких сообщений допускает remove_caption; новые подписи, reply_parameters, кнопки и permits для пакета не допускаются. Варианты remove_caption и новой caption взаимоисключающие.
- Успех: {"messageIds":[301,302]} — ID новых сообщений в чате назначения. Telegram может пропустить недоступные сообщения пакета; результат может быть короче запроса, нельзя сопоставлять источник и результат по позиции при пропусках. Отдельная карта соответствий в v1 не вводится.
- Недопустимые аргументы и источник отклоняются до вызова Telegram. Ограничения пересылки/копирования типов и защищённого контента определяет Telegram. Неопределённый результат доставки — delivery_unknown, без автоматического повтора, как у send.

Пример forward:

```json
{
  "fromChatId": -1001234567890,
  "messageIds": [
    171,
    172,
    173
  ],
  "disable_notification": true
}
```

Пример copy одного фото с новой подписью и кнопками:

```json
{
  "fromChatId": -1001234567890,
  "messageIds": [
    171
  ],
  "caption": "Предлагаю встретиться здесь. Подходит?",
  "reply_markup": {
    "inline_keyboard": [
      [
        {
          "text": "☐ Подходит",
          "callback_data": "[meeting1]yes"
        },
        {
          "text": "☐ Другой вариант",
          "callback_data": "[meeting1]no"
        }
      ]
    ]
  },
  "permits": {
    "[meeting1]*": [
      123,
      456
    ]
  }

```

Пример copy альбома без подписей:

```json
{
  "fromChatId": -1001234567890,
  "messageIds": [
    171,
```

Нативные методы: [forwardMessage](https://core.telegram.org/bots/api#forwardmessage), [forwardMessages](https://core.telegram.org/bots/api#forwardmessages), [copyMessage](https://core.telegram.org/bots/api#copymessage), [copyMessages](https://core.telegram.org/bots/api#copymessages).

У forward нет reply_parameters и reply_markup: пересылка с кнопками или reply одним вызовом не поддерживается. Можно отправить отдельное сообщение с кнопками в ответ на результат пересылки. copy одного сообщения поддерживает одновременно reply_parameters и reply_markup; message_id в примере reply относится к чату назначения. Для callback-кнопок действуют общие правила permits.

### Принято: file_sources для повторной отправки

- При использовании Telegram file_id агент передаёт file_sources: массив {messageId,fileId,chatId?}. Без chatId источник относится к текущему чату; явно допускаются одобренные подключённые group/supergroup/channel того же бота. Для вложенного reply используется ID внешней сохранённой записи.
- Каждый используемый file_id должен иметь доступный источник; контроллер выполняет проверки принадлежности и области как в download. Поле работает для одиночного вложения, rich_message.media и альбома.
- Для локальных uploads проверяются пути; HTTP/HTTPS URL не требуют file_sources. Известные секретные Telegram URL не выдаются агенту согласно правилам контроллера.
- file_sources не передаётся Telegram. Хранение исходящих сообщений после copy/forward определено в разделе ниже; отдельная система происхождения файлов в v1 не вводится. Разрешения не выводятся из одного знания file_id.

```json
{
  "document": "document-file-id",
  "caption": "Вот план поездки",
  "file_sources": [
    {
      "chatId": -100789,
      "messageId": 200,
      "fileId": "document-file-id"
    }
  ]
}
```

### Принято: метаданные отправителей и срок жизни заметки группы

- Отдельный постоянный справочник участников группы в v1 не вводится. Доступные Telegram-поля отправителя (id, first_name, last_name, username, is_bot либо sender_chat и относящиеся к отправителю поля) сохраняются внутри записи сообщения и удаляются вместе с ней по 30-дневному сроку истории.
- Агент получает сведения об отправителе из короткого сообщения/read и самостоятельно учитывает отправку от имени пользователя или чата. Скрытый пользователь за sender_chat не угадывается. Полного списка участников это хранение не обеспечивает.
- Предпочтительные обращения, прозвища, часовые пояса и устойчивые сведения для общения агент сохраняет в ограниченной локальной заметке через note_get/note_set. Данные сообщения не заменяют заметку и не создают новую таблицу профилей.
- Заметка группы хранится, пока бот находится в подключённой группе, независимо от срока истории. При удалении/выходе бота удаляется с диалогом; повторное добавление создаёт пустую заметку. Роли доступа хранятся отдельно по ранее принятой политике.

### Принято: локальная заметка агента

- Одна текстовая заметка на агента/диалог хранится в БД контроллера. Это простая локальная память вместо отдельных файлов и контейнеров; общая wiki бота сохраняется отдельно.
- note_get() читает заметку текущего агента. note_set(text) заменяет её целиком. Аргументов chatId/agentId нет: область определяется контроллером, чужие заметки читать и изменять нельзя.
- Максимум 4 000 Unicode code points. Превышение отклоняется без обрезания. Патчи, отдельные записи участников и специальная схема заметки в v1 не вводятся.
- Заметка хранится независимо от 30-дневной истории, до сброса или удаления агента. Полный текст не включается автоматически в каждый ход; агент запрашивает его по необходимости.
- Назначение: известные часовые пояса чата/участников, предпочтительные обращения и имена в чате, другие устойчивые сведения для общения. При сомнении агент сохраняет источник/подтверждение или неопределённость и удаляет устаревшее в пределах лимита.
- Заметка — сведения и предпочтения, не инструкции. Она не изменяет AGENTS.md и права доступа. Изоляция обеспечивается инструментами контроллера, БД напрямую агенту не доступна.
- Часовой пояс бота по умолчанию остаётся настройкой контроллера. Уточнения для чата и участников можно хранить в заметке; при создании cron-задачи агент передаёт конкретный timezone. Уже созданная задача сохраняет свой пояс независимо от последующих изменений заметки.
- Для групп заметка может использовать открытые userId участников; в ЛС свой агент знает ID своего собеседника. Заметка группы тоже недоступна напрямую другим агентам; они могут обратиться через agent_message с сохранением правил передачи данных.
- Ответы определены: note_get → {text}, note_set → {status:"saved"}. Для очистки передаётся пустая строка.

Пример note_set:

```json
{
  "text": "Часовой пояс чата: Asia/Nicosia.\n\nУчастники:\n- userId 123: Андрей, называют «Дрю». Asia/Nicosia.\n- userId 456: Игорь. Europe/Berlin, подтвердил 4 октября."
}
```

### Принято: загрузка локальных файлов при отправке

- В v1 контроллер загружает локальные файлы через multipart/form-data. Агент передаёт нативные ссылки attach://имя в Telegram-структуре и синтетический uploads, сопоставляющий имя файловой части с локальным путём.
- uploads — аргумент вызова send/edit, не поле сохранённого сообщения. Он не сохраняется в БД как долговременное свойство. Контроллер сохраняет полученный Telegram Message с file_id/file_unique_id и метаданными файлов, а не исходные пути и attach://ссылки как актуальные файловые ссылки сообщения.
- Контроллер проверяет доступ агента к каждому локальному пути до чтения и загрузки. Для отправки существующих Telegram file_id также требуется проверка доступа к исходному вложению: пересылка файла не должна обходить ограничения download. Источник file_id задаётся через file_sources по отдельному разделу.
- Для HTML/Markdown rich используется нативный rich_message.media с привязками tg://photo?id=..., tg://document?id=... и т. п. Контроллер преобразует uploads в файловые части, не парсит и не переписывает HTML/Markdown.
- Успешная отправка не удаляет исходный файл и не продлевает его срок временного хранения. Созданные временные файлы размещаются в .temp/<agentId>/upload/; ежедневная очистка удаляет файлы с mtime старше 24 часов. Нужное надолго агент копирует вне .temp в wiki. Файлы wiki отправкой не удаляются.
- После завершения загрузки можно удалить только технические временные копии, специально созданные контроллером для запроса. Агентский исходник остаётся до обычной очистки.
- Возвращённый Telegram file_id сохраняется и может использоваться для повторной отправки без исходного локального файла, с прежними проверками доступа.
- Будущий транспорт через публичный HTTPS URL отложен. Для агента контракт локального uploads остаётся тем же; контроллер может выбрать подходящий транспорт. Multipart остаётся доступным, поскольку URL-загрузка имеет иные ограничения размеров и поддержки типов.
- При будущем HTTPS-транспорте путь может содержать bot_id/agent_id/upload/имя, но эти компоненты не являются авторизацией. Параметр доступа должен быть непредсказуемым токеном, не просто хешем файла; URL истекает вместе с временным файлом. Знание URL даёт доступ к содержимому, поэтому URL не публикуется как обычный результат инструмента.

Пример агентского вызова:

```json
{
  "rich_message": {
    "html": "<p>Сгенерированное изображение:</p><img src=\"tg://photo?id=result\"/>",
    "media": [
      {
        "id": "result",
        "media": {
          "type": "photo",
          "media": "attach://result"
        }
      }
    ]
  },
  "uploads": {
    "result": "/workspace/.temp/agent-1/upload/result.png"
  }
}
```

Основание: [InputRichMessage](https://core.telegram.org/bots/api#inputrichmessage), [Sending files](https://core.telegram.org/bots/api#sending-files).

### Принято: замена компонентов сообщения через edit

- Агент заменяет компоненты целиком: текст, rich-содержимое, подпись, медиа или нижнюю inline-клавиатуру. Замены фрагмента строки, отдельного rich-блока и JSON patch в v1 нет.
- edit принимает messageId и необязательный chatId по правилам доступа к текущему или пассивному чату и только компоненты, которые нужно изменить. Отсутствующие компоненты сохраняются контроллером; это семантика нашего инструмента, а не обещание о поведении отсутствующих полей Telegram API.
- text заменяет весь текст; rich_message заменяет всё rich-содержимое. Они не передаются одновременно. Нижняя клавиатура сохраняется, если reply_markup отсутствует.
- caption заменяет подпись к медиа, media — одно вложение через подходящий метод Telegram с сохранением исходного типа. photo→photo, video→video, document→document и т. д.; text→rich, rich→text и любые другие переходы между типами запрещены, даже если Telegram их допускает. Это ограничение инструмента v1, не ограничение Telegram.
- reply_markup.inline_keyboard заменяет нижнюю клавиатуру целиком. Пустой массив удаляет её, не затрагивая встроенные rich-кнопки.
- Встроенные кнопки изменяются передачей нового rich_message целиком; старые блоки/кнопки не дополняют новую структуру автоматически. Контроллер сохраняет актуальную структуру по ответу Telegram и механику закрытых групп. Проверка необходимости обновления permits в rich лежит на агенте, без парсера разметки в v1.
- permits передан — заменить целиком; не передан — сохранить. При удалении всех кнопок прежние правила бездействуют, но не удаляются автоматически; агент может явно очистить их через permits:{}. В ЛС permits не применяется.
- Если агенту нужно изменить небольшой фрагмент, он при необходимости вызывает read(messageId) и передаёт обновлённый компонент целиком.
- Контроллер выбирает editMessageText, editMessageCaption, editMessageMedia или editMessageReplyMarkup. Автоматическая блокировка групп после callback остаётся отдельной механикой контроллера.
- Все изменения сохраняют исходный тип сообщения. Альбом редактируется по messageId одного элемента, также без смены типа и без изменения состава альбома. Частичный успех описывается updated/failed/unknown по разделу результатов инструментов.

Пример замены только текста:

```json
{
  "messageId": 170,
  "text": "Поездка подтверждена."
}
```

Пример замены только нижних кнопок в группе:

```json
{
  "messageId": 170,
  "reply_markup": {
    "inline_keyboard": [
      [
        {
          "text": "Отменить поездку",
          "callback_data": "[cancel]cancel"
        }
      ]
    ]
  },
  "permits": {
    "[cancel]*": [
      123
    ]
  }
}
```

Пример удаления нижней клавиатуры и правил (если встроенных кнопок нет):

```json
{
  "messageId": 170,
  "reply_markup": {
    "inline_keyboard": []
  },
  "permits": {}
}
```

### Принято: компактные инструменты Git

- git_changes() возвращает commits — строки «короткий SHA + сообщение» локальных коммитов вне отслеживаемой remote-ветки, от старых к новым, и files — объект «относительный путь → added/modified/deleted» для всех незакоммиченных изменений, включая staged, unstaged и untracked. Переименование показывается удалением старого и добавлением нового пути. Чистое состояние: {"commits":[],"files":{}}.
- git_sync({message}) добавляет все изменения wiki в индекс, включая новые файлы и удаления, создаёт коммит при наличии изменений, затем выполняет обычный push. Без новых изменений commit пропускается, но существующие неопубликованные коммиты отправляются. Нет pull, merge, разрешения конфликтов или force push.
- Успех: {"commit":"a1b2c3d Update meeting arrangements","push":"completed"}; без нового коммита commit=null. При ошибке push локальный коммит остаётся, следующий вызов может отправить его без создания дубликата. При ошибке commit push не выполняется.
- Ошибка push: {"commit":"a1b2c3d Update meeting arrangements","push":"failed","error":"push_rejected","description":"The commit was created locally, but push was rejected. Manual synchronization is required."}.
- Ошибка commit: {"commit":null,"push":"skipped","error":"commit_failed","description":"Commit failed. Push was not attempted. Fix the reported issue and retry."}. Description на английском поясняет конкретную причину. commit=null означает отсутствие нового коммита, причина отказа передаётся отдельно.
- Область — wiki текущего бота. Один коммит может включать правки разных агентов; защита от параллельного редактирования в v1 не вводится. Репозиторий/remote/ветка и секреты не выбираются произвольными аргументами агента.
- Агентские инструменты не выполняют fetch. Административная команда /git_setup выполняет fetch и принудительное восстановление remote-ветки. commits определяется по последнему известному состоянию отслеживаемой remote-ветки и не обещает свежего состояния сервера. При расхождении истории сервер может отклонить обычный push; владелец синхронизирует репозиторий вручную.

```json
{
  "commits": [
    "a1b2c3d Add meeting arrangements"
  ],
  "files": {
    "index.md": "modified",
    "meetings/office.md": "added",
    "old-plan.md": "deleted"
  }
}
```

Приняты аргументы read: {messageIds:[170,171], chatId?}. Без chatId используется текущий чат; явно разрешена одобренный подключённый group/supergroup/channel того же бота. Чужие ЛС запрещены. chatId подключённых group/supergroup/channel агент получает через chats(), подробности — через chat_info. agents()/agent_info описывают только чаты с агентами. Правила полного ответа read приняты в следующем разделе.

### Принято: read — хранение и полное представление

- read({messageIds, chatId?}) возвращает {messages:[...]}. Результаты соответствуют порядку запроса. Успешный элемент — подробное сообщение с нативными названиями Telegram, без content. Ошибка элемента — {messageId,error,description}, description на английском; она не отменяет остальные результаты. Нативный message_id при успехе и наш messageId при ошибке сохраняются намеренно.
- Для принятого сообщения разрешённого диалога БД хранит полученный Message максимально близко к оригиналу: исходные числовые даты, полное содержимое и полученные метаданные. Короткий вид и read — разные проекции этой записи; отсутствие поля в выдаче не означает удаления из БД. История хранит последнюю редакцию 30 дней, не архив всех версий.
- read сохраняет message_id, from, sender_chat, author_signature, text/entities, caption/caption_entities, rich_message, полные объекты вложений, media_group_id, reply_to_message, forward_origin, external_reply, quote, reply_to_story, reply_to_checklist_task_id, reply_to_poll_option_id и via_bot при наличии.
- В read сохраняются has_media_spoiler, has_protected_content, show_caption_above_media, link_preview_options и полная reply_markup. Редкое содержимое и служебные поля сохраняют полученную структуру; их наличие не обещает поддержку отправки или специальных действий. Это правило не открывает исключённые маршруты.
- Все полученные варианты photo, thumbnails и файловые метаданные, включая file_id/file_unique_id, размеры, длительность и размер файла, сохраняются в БД и read. read ничего не скачивает. Короткая форма показывает только согласованные сведения каталога.
- date/edit_date и даты отправки внутри reply/сведений о пересылке преобразуются в ISO 8601 при выдаче. Длительности, live_period, смещения/длины entities и другие нативные числовые значения не превращаются в строки; их единицы сохраняются. Не используется безусловное преобразование всех чисел, похожих на timestamp.
- chat внешнего сообщения хранится для маршрутизации/авторизации, но не выдаётся read: область задаётся запросом. Сведения источника внутри forward_origin/external_reply сохраняются. reply_to_message возвращает один полученный уровень с содержимым и файлами; отсутствующий исходник не восстанавливается выдуманными данными. Для чтения старого reply и download используется messageId внешней сохранённой записи.
- from в БД/read сохраняет полученные поля пользователя, а короткое представление содержит краткие сведения. sender_chat и author_signature сохраняются; короткая форма использует единый from с userId либо chatId по правилам следующего раздела. Наличие sender_chat не раскрывает скрытого пользователя.
- sender_boost_count, effect_id, is_from_offline, sender_tag и suggested_post_info не выдаются через read, но сохраняются в полученной исходной записи, если сообщение принято. Это исключения из проекции; каналы и нефорумные супергруппы принимаются по пассивной модели, остальные специальные маршруты остаются ограниченными.
- Неподдерживаемые маршруты business/guest/ephemeral/topics/channel direct messages отклоняются целиком до записи обычной истории. Их business_connection_id, guest_query_id, receiver_user, ephemeral_message_id, direct_messages_topic и связанные признаки нельзя просто удалить и обработать остаток как обычный диалог. Проверяется контекст маршрута обновления/внешнего Message; такие сведения о процитированном источнике не дают ему отдельного доступа.
- Необязательные отсутствующие поля опускаются, не заполняются null. Полный текст/rich не обрезается по лимиту короткой формы. Нативные type/text/entities и вложенные структуры не переименовываются в eventType/textPlain.
- permits и известные reactions — синтетические данные, добавляемые в read. Закрытые группы хранятся контроллером для отсечения повторных callback, но отдельное поле buttonSelections или аналог не выдаётся. Выбор виден через иконки и disabled, если иконки есть; без них восстановление выбора из сообщения не гарантируется. Короткие inlineButtons/richButtons вычисляются из актуального состояния.

### Принято: отправитель короткого сообщения

- from — единый объект: пользователь {userId,name,username?}, чат {chatId,name,username?}. Прежний from.id заменён на from.userId. name — доступное имя пользователя или название чата; отсутствующий username опускается.
- При наличии Telegram sender_chat он имеет приоритет: сопутствующий from не интерпретируется как реальный пользователь. Иначе используется Telegram from. При неизвестном отправителе from опускается.
- Известный author_signature передаётся отдельно как authorSignature. Подпись не подтверждает личность пользователя.
- from.chatId — автор сообщения, не чат доставки. Знание этого ID не открывает историю: сохраняются проверки подключённой области. Для подключения каналов и пассивных супергрупп действует [channels-and-discussions.md](channels-and-discussions.md).
- Полный read сохраняет нативные from/sender_chat/author_signature. Идентификаторы from агентских сообщений по-прежнему описывают agentId и разрешённый групповой chatId, не выдуманного инициатора-пользователя. Авторизация контроллера проверяет исходные поля Telegram, не текст или нормализованное заявление агента.

```json
{
  "eventType":"message",
  "messageId":190,
  "date":"2026-10-05T12:30:00Z",
  "from":{"chatId":-1001234567890,"name":"Новости компании"},
  "authorSignature":"Редакция",
  "textPlain":"Встреча переносится на пятницу."
}
```

### Принято: отсутствующие сообщения и якоря

- read и download возвращают message_not_found с английским description для конкретного элемента, если доступная исходная запись отсутствует; остальные элементы пакета обрабатываются независимо в порядке запроса. Проверка области доступа выполняется до поиска, без раскрытия сведений из запрещённых чатов.
- history с явно заданным отсутствующим messageId возвращает ошибку; автоматический переход к последним сообщениям не выполняется. Агент может отдельно запросить history с messageId=null.
- Не различаем «сообщение никогда не сохранялось» и «удалено по сроку хранения», если соответствующей записи уже нет. Отсутствующая запись не означает доказанного удаления сообщения в Telegram.
- Пример: {"error":"message_not_found","description":"The message is not available in stored history. It may have expired. Use history with messageId=null to retrieve recent messages."}. Для поэлементного read/download сохраняются идентификаторы запрошенного элемента рядом с error/description.

### Принято: history и search

- Оба инструмента возвращают короткий формат сообщений; подробности агент получает через read. Область: текущий чат или одобренный подключённый group/supergroup/channel того же бота по необязательному chatId. Чужие ЛС недоступны.
- history считает смещения по сохранённым сообщениям, а не арифметикой Telegram ID. Указанное messageId имеет позицию 0, границы from/to задают интервал [from,to). Результат — от старых сообщений к новым.
- history с messageId:null использует позицию после последнего сохранённого сообщения. from:-20,to:0 возвращает последние 20 сообщений. Отсутствующий ненулевой якорь возвращает message_not_found по разделу отсутствующих сообщений; автоматического перехода к последним сообщениям нет.

```json
{
  "messageId": 150,
  "from": -10,
  "to": 5
}
```

```json
{
  "messageId": null,
  "from": -20,
  "to": 0
}
```

search принимает необязательные фильтры и размер порции:

```json
{
  "chatId": -100789,
  "text": [
    "шашлык",
    "дожд"
  ],
  "senderId": 123,
  "types": [
    "text",
    "photo"
  ],
  "since": "2026-10-01T00:00:00+03:00",
  "until": "2026-10-04T00:00:00+03:00",
  "limit": 20
}
```

- text — массив буквальных подстрок без учёта регистра. Все элементы должны присутствовать в одном сообщении. ["шашлыки под дождём"] ищет непрерывную фразу внутри сообщения; ["шашлык","дожд"] — обе подстроки в любом порядке, включая «шашлыки» и «дождём». Это не равенство всему тексту, не поиск целых слов и не морфологический поиск. Пустые элементы отклоняются.
- Поиск выполняется по тексту, подписи и сохранённому текстовому представлению rich-содержимого, без OCR и анализа файлов. Ищется последняя сохранённая редакция, не предыдущие версии.
- Разные фильтры объединяются через И; внутри types достаточно совпадения с одним типом. Фото с текстовой подписью может соответствовать photo и text.
- senderId — единое числовое поле автора: положительный ID пользователя либо отрицательный Bot API ID отправителя-чата. При наличии sender_chat используется он, а не сопутствующий технический from. Внешний chatId определяет область поиска, senderId — автора; знание ID не расширяет доступ. В текущих ЛС свой агент знает userId собеседника. Частный chatId совпадает с ID соответствующего пользователя и не обозначает отдельный вид автора. Формат подтверждён официальной документацией https://core.telegram.org/api/bots/ids.
- since включительно, until исключительно; временной фильтр относится ко времени отправки сообщения. Даты задаются с явным часовым смещением или Z. Даты агентского контракта — строки ISO 8601 с часовым смещением или Z; согласование имён полей в примерах описано в contract-review.md.
- Результаты search идут от новых к старым, по времени сообщения, затем messageId. limit задаёт максимальный размер страницы, не общее количество результатов. По умолчанию limit=20; дополнительной жёсткой верхней границы приложения в v1 нет.
- Ответ содержит messages и, при наличии следующей страницы, nextCursor. Отсутствие nextCursor означает окончание выдачи. total и отдельный подсчёт всех совпадений в v1 не возвращаются.
- Для определения продолжения контроллер запрашивает limit+1 совпадений и возвращает не более limit.

Продолжение поиска:

```json
{
  "cursor": "opaque-token"
}
```

- Курсор непрозрачен для агента. При продолжении другие аргументы не передаются: курсор содержит чат, фильтры, размер страницы, границу начала поиска, позицию последнего результата и срок действия.
- Курсор подписан контроллером; поисковая сессия и результаты отдельно в БД/памяти не сохраняются. Продолжение заново выполняет поиск; проверяются подпись, срок и текущие права доступа, включая область бота и агента.
- Срок действия — один час с первого запроса, без продления при перелистывании. Просроченный курсор возвращает cursor_expired; агент начинает новый поиск.
- Курсор действует после перезапуска при сохранении ключа подписи. Ключ подписи хранится контроллером и не передаётся агентам.
- Новые сообщения после первого запроса не добавляются в продолжение поиска. Полный снимок результатов не создаётся: редактирование и очистка истории могут изменить оставшиеся совпадения.
- Найденное messageId можно использовать как якорь history для чтения обсуждения вокруг результата.

### Принято: скачивание и временное хранение

- download — отдельный инструмент. Агенту не нужно предварительно искать файл в каталоге кеша.
- Скачанные файлы размещаются в .temp/<agentId>/download/. Ежедневная очистка удаляет временные файлы с mtime старше 24 часов; это не жёсткий срок удаления ровно через сутки.
- Повторный вызов для уже доступного файла возвращает существующий локальный путь без повторного скачивания.
- Для долгосрочной работы агент сохраняет нужный файл в wiki. Файлы wiki не очищаются вместе с временным хранилищем.
- После очистки файл можно скачать повторно, если сведения о вложении и сам файл Telegram ещё доступны. Очистка 30-дневной истории может удалить сведения, необходимые для такого вызова.

### Принято: безопасность файлов и Telegram-токенов

- Скачивание выполняется контроллером через download с проверкой доступа к выбранному сообщению и принадлежности fileId; проверки предшествуют выдаче любого кешированного пути.
- Telegram-токены доступны только контроллеру. Агент не получает их через инструменты, окружение, файлы конфигурации или логи. Прямой доступ к БД и секретам контроллера запрещён.
- Ссылки Telegram для скачивания содержат токен и не передаются агенту. download возвращает только локальный путь к готовому файлу или ошибку.
- Telegram file_id привязан к боту, не переносится на другого бота. file_unique_id может совпадать у разных ботов, но не позволяет скачивать файл. Новый токен другого бота не даёт доступа по нашему file_id; перевыпуск токена того же бота не создаёт изоляцию агентов.
- Telegram не знает внутренние права агентов одного бота. Их проверяет контроллер, а не getFile.
- Файловая изоляция реализуется песочницей среды исполнения, без контейнеров. Агент не должен видеть временные файлы чужих личных диалогов, чужие сессии, БД или секреты контроллера. Общая wiki текущего бота остаётся доступной RW согласно принятой модели.
- Дедупликация кеша внутри бота не означает общего файлового доступа: песочница и контроллер предоставляют файл только после проверки полномочий вызывающего агента. При необходимости одному физическому кешированному файлу соответствуют разные доступные агентам пути.
- Рабочий каталог или AGENTS.md сами по себе не обеспечивают изоляцию. При реализации требуется выбрать поддерживаемую песочницу и проверить запрет чтения чужих файлов и секретов, включая обход через штатные файловые/командные инструменты. Это принятое требование, а не утверждение о уже проверенной конфигурации Codex.

Основание для Telegram-привязки файлов: [Sending files](https://core.telegram.org/bots/api#sending-files), [getFile](https://core.telegram.org/bots/api#getfile).

Возраст всех временных файлов считается по mtime. Повторное чтение или выдача существующего файла через download не обновляет mtime; изменение файла меняет отсчёт. Кеш изолирован по боту; file_unique_id можно использовать для сопоставления файлов внутри него, а скачивание выполняется по file_id. Одновременные запросы одного файла ожидают одну загрузку; готовый путь выдаётся только после её успешного завершения. Файловая доступность кеша дополнительно ограничивается песочницей агента, как описано выше.

### Принято: пакетный download по сохранённому сообщению и fileId

Единая схема для одного и нескольких вложений:

```json
{
  "files": [
    {
      "messageId": 152,
      "fileId": "photo-file-id"
    },
    {
      "messageId": 200,
      "fileId": "document-from-reply-id"
    }
  ]
}
```

- fileId берётся из нативного file_id в результате read. Нумерация attachment больше не используется.
- Необязательный chatId задаётся на уровне всего вызова, а не каждого файла. Без него используется текущий диалог; явно разрешены только одобренные подключённые группы того же бота. Чужие ЛС и другие боты недоступны.
- Право читать историю соседней группы включает скачивание её вложений. Контроллер проверяет область чата, наличие сохранённой записи messageId и принадлежность fileId этой записи до обращения к кешу или Telegram.
- Поиск выполняется только внутри указанного сохранённого сообщения, включая вложенные rich-блоки, reply_to_message и файловые сведения external_reply, если они действительно получены. Текст с упоминанием fileId не считается файловым объектом. Поиск по всей базе и отдельный глобальный индекс файлов не нужны.
- Для вложения из reply, цитаты или пересланного источника агент использует messageId ВНЕШНЕГО сохранённого сообщения, через которое файл доступен. Нельзя подставлять ID вложенного оригинала: он может отсутствовать в нашей БД, относиться к другому чату или источнику. Под «текущим сообщением» здесь понимается выбранная доступная запись-контейнер, а не обязательно последнее событие.
- Если старый original message_id доступен отдельно в выбранном чате, его можно использовать только как самостоятельную сохранённую запись; наличие ID внутри reply само по себе этого не гарантирует.
- Знание fileId не заменяет проверки доступа: идентификатор мог попасть в текст, межагентный обмен или остаться в контексте после очистки истории. Попадание в кеш тоже не даёт дополнительного доступа.

Пример скачивания файла из соседней группы:

```json
{
  "chatId": -100789,
  "files": [
    {
      "messageId": 200,
      "fileId": "document-from-reply-id"
    }
  ]
}
```

Здесь 200 — сохранённое сообщение с reply, даже если вложенный reply_to_message.message_id равен 50.

Ответ:

```json
{
  "files": [
    {
      "messageId": 152,
      "fileId": "photo-file-id",
      "path": "/tmp/b1/photo-a.jpg"
    },
    {
      "messageId": 200,
      "fileId": "document-from-reply-id",
      "error": "file_unavailable"
    }
  ]
}
```

Порядок результатов соответствует запросу. Ошибка одного файла не отменяет успешные результаты остальных. Ответ не содержит байты файлов. Явно заданные messageId позволяют скачать известные элементы альбома без ожидания или обещания полноты альбома. Дополнительной жёсткой границы количества файлов приложения в v1 нет.

### Другие возможности агента

Генерация изображений выполняется встроенной возможностью Codex за лимиты подписки; её серверная доступность требует проверки.

### Принято: файловая wiki v1

```text
wiki/
  index.md
  topics/
  attachments/
```

- index.md — краткая карта знаний со ссылками; topics/ — тематические статьи со взаимными ссылками; attachments/ — файлы для долгосрочного хранения. raw/ и log.md отсутствуют, историю правок хранит Git.
- Все агенты одного бота имеют RW файловый доступ к его wiki; другие боты изолированы. Защита от параллельного редактирования и отдельные права разделов в v1 не вводятся. AGENTS.md бота управляется владельцем отдельно, не включается в общую RW wiki как редактируемая агентом инструкция.
- ingest/query/lint — процедуры в инструкциях, а не отдельные API. Агент использует штатные файловые инструменты Codex.
- ingest добавляет знания, указывает источник и обновляет статьи/индекс/ссылки; query ищет сведения в файлах и готовит ответ с источниками; lint проверяет ссылки, противоречия и дублирование.
- Запись в общую wiki не отменяет ранее принятой границы личных данных: личные сведения не переносятся туда автоматически без разрешения.

### Принято: schedule, tasks и cancel_tasks

schedule создаёт задачу. Обязательны description (короткое описание для списка) и text (полная инструкция для будущего хода). Инструкция должна быть достаточной после сжатия контекста; сведения можно дополнительно получать через read, history и wiki.

Ровно один вариант расписания:

- at — одноразовый момент в ISO 8601 с явным часовым смещением или Z.
- cron и timezone — повторяющееся расписание из пяти полей (минута, час, день месяца, месяц, день недели), с точностью до минуты и явным часовым поясом IANA.

everySeconds не предусмотрен. Бот, чат и агент определяются текущей областью исполнения контроллера, не аргументами агента.

Одноразовый вызов:

```json
{
  "at": "2026-10-04T10:00:00+03:00",
  "description": "Позвонить маме",
  "text": "Напомни пользователю позвонить маме."
}
```

Повторяющийся вызов:

```json
{
  "cron": "0 9 * * 6,0",
  "timezone": "Asia/Nicosia",
  "description": "Утренняя сводка по выходным",
  "text": "Прочитай wiki и отправь краткую сводку актуальных событий в этот чат."
}
```

Ответ schedule:

```json
{
  "taskId": "t1"
}
```

tasks() возвращает краткий список без text:

```json
{
  "tasks": [
    {
      "taskId": "t1",
      "description": "Позвонить маме",
      "at": "2026-10-04T10:00:00+03:00"
    },
    {
      "taskId": "t2",
      "description": "Утренняя сводка по выходным",
      "cron": "0 9 * * 6,0",
      "timezone": "Asia/Nicosia"
    }
  ]
}
```

tasks(...taskId) получает несколько полных задач одним вызовом. Представление вариативных аргументов в JSON:

```json
{
  "taskIds": [
    "t1",
    "t2"
  ]
}
```

schedule возвращает {"taskId":"t1"}. tasks с явно заданными taskIds возвращает массив tasks в порядке запроса: полные записи с text либо поэлементные ошибки, например {"taskId":"missing","error":"task_not_found","description":"The task does not exist or is no longer available."}. Ошибка одной задачи не мешает прочитать остальные; область текущего агента/диалога проверяется контроллером.

cancel_tasks(...taskId) принимает тот же пакет идентификаторов:

```json
{
  "taskIds": [
    "t1",
    "t2"
  ]
}
```

Ответ:

```json
{
  "results": [
    {
      "taskId": "t1",
      "status": "cancelled"
    },
    {
      "taskId": "t2",
      "status": "cancelled"
    }
  ]
}
```

- Для одноразовой задачи отменяется ожидающий запуск; для cron — всё расписание и уже ожидающие срабатывания.
- Отмена не прерывает ход, который уже начал выполнять событие.
- Отмена удаляет запись задачи и её ожидания. Повторный cancel_tasks отсутствующего taskId — безопасный успех status=cancelled, как в примере результата. Не различаем «ранее отменено» и «не существовало»; удалённые задачи ради этого не хранятся. Правило не расширяет область доступа инструмента.
- Контроллер проверяет отмену перед передачей события агенту, включая события из очереди в памяти.
- Отдельного пропуска одного срабатывания cron в v1 нет. Отмена означает отмену задачи целиком.
- Повторяющаяся задача остаётся активной до отмены. Для условного наблюдения, например Live Location, агент может назначать следующую одноразовую проверку после текущей вместо использования cron.

### Принято: невыполненные задачи и текстовые уведомления

- Технический сбой оставляет события из очищенной очереди и незавершённого основного хода невыполненными независимо от стадии. Выполненные внешние действия не откатываются; риск повторения принят в v1.
- Контроллер отправляет простое текстовое уведомление в текущий чат задачи, без очереди агента, кнопок и редактирования сообщений. Уведомление содержит taskId, причину, описание задачи, время и cron/timezone при наличии; инструкция остаётся в исходном диалоге и доступна через /task.
- Для cron уведомление отправляется только при первом сбое периода непрерывных сбоев. Накопление новых пропусков/повторные неудачи не создают и не обновляют уведомления. После успешной обработки ранее сбоившей задачи следующий сбой снова может создать уведомление. Флаг подавления хранится с задачей в БД и не сбрасывается перезапуском. Новые ожидания, возникшие во время успешной попытки, не считаются выполненными автоматически.
- Пропуски продолжают учитываться в БД и отображаются /tasks или /task; отсутствие нового уведомления не означает успех. Новые cron-срабатывания за время остановки/выключения не создаются по прежнему правилу.
- /retry_task атомарно проверяет состояние: уже в очереди/обработке — текст «Событие обрабатывается», без дубля. Иначе ставится одно объединённое невыполненное событие с retry=true. Будущее cron-срабатывание также может объединиться с накопленными пропусками.
- /cancel_task удаляет задачу и ожидающие срабатывания, не прерывая уже начатый ход. В группе управление расписанием доступно владельцу/manager/admin; в ЛС — текущему авторизованному собеседнику и владельцу, в пределах текущего диалога.
- В v1 completed основного хода подтверждает все переданные ему события расписания, включая steer. failed/interrupted оставляет их невыполненными. Субагентская ошибка сама не означает сбой успешно завершившегося основного хода. complete_tasks отложен в v2.
- Политика восстановления согласована в разделе «Восстановление после перезапуска контроллера», календарные правила — в разделе «Croner для Node и календарные правила». Их реализация требует проверки. Старые карточки, их состояния, callback и лимиты rich-карточек больше не входят в v1.

### Принято: текстовые команды расписания

- /tasks [FROM-TO] — краткий список задач текущего диалога с taskId, description, at либо cron/timezone и актуальными пропусками. /task TASK_ID — сведения выбранной задачи. /retry_task TASK_ID и /cancel_task TASK_ID выполняют по одному действию.
- Команды возвращают текст без кнопок и редактирования. Пагинация списков — явный диапазон, например /tasks 11-20; диапазон включительный и позиции начинаются с 1. Порядок задач сохраняет созданное ранее правило createdAt/taskId. Это текущий список, не снимок между вызовами.

### Принято: служебные события чата

- Добавление/удаление бота, изменение его прав, названия группы и закрепление сообщений обновляют состояние чата и доступную историю без запуска агента. Актуальные сведения доступны через agent_info.
- Удаление бота или отзыв доступа прекращает обработку чата и запрещает новые действия в нём. Служебные события не включают и не продлевают громкий режим.
- Отдельная автоматическая реакция агента на вступление, например приветствие, в v1 не вводится. Активация остаётся по обращению, допустимому callback, расписанию или межагентскому сообщению.

### Принято: область удаления и закрепление

- Удаление разрешено в текущем чате агента или подключённом пассивном канале/супергруппе по необязательному chatId. Чужой чат с агентом недоступен для удаления. Ограничение только сообщениями самого бота не вводится: возможность удаления определяется правами и ограничениями Telegram. Аргументы delete — {messageIds,chatId?}; успешный ответ — {status:"completed"} по разделу простых инструментов.
- pin({messageId,disable_notification?}) и unpin({messageId}) включаются в v1 для текущего чата. В группах необходимы права администратора can_pin_messages. Снятие всех закреплений отдельным инструментом пока не принято. Точные схемы ответов ещё обсуждаются.
- Полный список закреплённых сообщений через Bot API получить нельзя. agent_info включает доступное pinned_message из getChat — закреплённое сообщение с наиболее поздней датой отправки, не временем закрепления. В v1 используем только это сообщение, без локального списка закреплений.

### Принято: пожелания к индикатору и доступности агента; исполнение требует проверки

- Желаемое соответствие: typing («печатает») — основной агент занят, новые сообщения копятся в очереди; upload_photo («отправляет фото») — идёт генерация изображения, но основной агент доступен для обработки новых сообщений; отсутствие индикатора — основной агент доступен для новых сообщений. Отдельный инструмент activity агенту не требуется.
- typing имеет приоритет над upload_photo. Блокирующая основной агент генерация показывается как typing. При фоновой генерации и обработке основным агентом новой пачки тоже показывается typing; после освобождения основного агента возвращается upload_photo, если генерация ещё идёт.
- Обычная работа субагентов и фоновые задачи сами по себе индикатор не меняют. Фоновая генерация изображения, в том числе у субагента, — исключение и может включать upload_photo, когда основной агент доступен. Это заменяет прежние правила приоритета генерации и полного исключения активности субагентов.
- При завершении, ошибке или прерывании обработки контроллер прекращает обновление индикатора. Telegram держит chat action не более пяти секунд и может очистить его при отправке сообщения; во время активной обработки контроллер обновляет его повторно. Мгновенное выключение отдельным chat action Bot API не предусмотрено.
- Исследованная схема установленного Codex 0.159.3 содержит imageGeneration, уведомления item/started и item/completed, collabAgentToolCall с tool=wait и идентификаторы threadId/turnId/item. Наличие схемы не подтверждает фактическую доступность параллельной обработки. Генерации предполагается учитывать по ID; события субагентов должны быть связаны с породившим их диалогом без раскрытия данных других чатов.
- Нет активного хода — пачка передаётся через turn/start. Для активного хода, ожидающего субагентов, предлагается turn/steer с expectedTurnId, если эксперимент подтвердит пробуждение. Завершённый ход определяется turn/completed; незавершённое ожидание не означает возможность второго turn/start. Отсутствие событий/разрыв соединения не доказывает освобождение агента.

Проверки до реализации окончательного алгоритма очереди и индикатора:

1. Основной агент запускает долгого субагента и входит в wait; передать новую пачку через turn/steer. Проверить ответ до завершения субагента, сохранение исходной задачи и продолжение после результата субагента.
2. Проверить порядок событий wait/steer/возобновления работы: как надёжно выключать и возвращать typing. Подтверждение приёма steer само по себе не считается началом обработки; завершение субагента само по себе тоже не означает работу основного агента.
3. Запустить реальную встроенную генерацию через выбранный серверный App Server с ChatGPT-подпиской. Проверить начало/завершение/ошибку imageGeneration, сохранение файла и отправку в Telegram. Поддержка генерации данным маршрутом остаётся неподтверждённой.
4. Во время прямой генерации основного агента отправить turn/steer. Проверить возможность ответа до готовности изображения без отмены генерации. Если вызов блокирует обработку, проверить генерацию у субагента и доступность основной нити в это время.
5. Проверить доступность событий генерации субагента, одновременные генерации и сброс индикатора при ошибке, прерывании и отключении процесса. Не обещать желаемое соответствие статусов до этих проверок.

### Принято: реакции и их представление в read

- react работает в текущем или разрешённом пассивном чате: {messageId,chatId?,reaction:[ReactionType]}. Нативные типы: emoji с emoji и custom_emoji с custom_emoji_id; paid ботом не поддерживается. Пустой reaction снимает собственную реакцию. Telegram разрешает боту не более одной реакции и определяет доступность реакции на конкретном сообщении; для альбома применяется первое неудалённое сообщение.
- agent_info включает available_reactions из getChat: список разрешённых реакций; отсутствие поля означает все стандартные emoji-реакции Telegram, пустой список — реакции отключены. Это не разрешение на произвольный Unicode emoji. Custom emoji допустим при наличии на сообщении либо явном разрешении администраторами; автоматически пересланное сообщение канала использует ограничения канала.
- Перед каждым react обязательный getChat не выполняется. Настройки могли измениться, окончательное решение принимает Telegram. Отказ имеет error и английское description; агент может запросить актуальную информацию о чате и выбрать другую реакцию.
- События реакций не запускают агента и не продлевают громкий режим, в том числе реакции на сообщения бота. Контроллер обновляет БД только для уже сохранённых сообщений, не восстанавливает старые записи и не продлевает 30-дневный срок хранения.
- Для получения message_reaction и message_reaction_count бот должен быть администратором, а события явно включены в allowed_updates. Отключения privacy mode недостаточно. События реакций ботов не приходят; после успешного react собственное состояние сохраняется контроллером. Анонимные счётчики могут приходить с задержкой в несколько минут.
- read включает синтетический reactions только при наличии известных сведений. Короткие события/history/search не дополняются реакциями. Отсутствие reactions или его отдельных полей означает отсутствие сведений, а не отсутствие реакций.
- counts — массив нативных ReactionCount: {type:ReactionType,total_count:number}. countsComplete=false означает неполные наблюдаемые количества, полученные из изменений отдельных участников; полный снимок анонимных счётчиков имеет countsComplete=true на момент снимка. Полнота снимка не гарантирует актуальность после него.
- users — известные реакции участников: {userId,reactions:[ReactionType]} либо {actorChatId,reactions:[ReactionType]} для источника от имени чата. Полные профили не дублируются. Отсутствие участника не доказывает отсутствие его реакции; собственные реакции бота представлены отдельно в own.
- own — подтверждённая реакция бота; [] означает подтверждённое снятие. updatedAt — время последнего учтённого изменения в ISO 8601 UTC. Сведения могут быть неполными или устаревшими, например при позднем предоставлении прав или пропущенных событиях. Неизвестные количества не превращаются в нули, состояние own не используется для предположений о полном числе реакций.

Пример react:

```json
{
  "messageId": 170,
  "reaction": [
    {
      "type": "emoji",
      "emoji": "👍"
    }
  ]
}
```

Пример синтетического поля в read:

```json
{
  "message_id": 170,
  "text": "Встречаемся завтра в 18:00",
  "reactions": {
    "counts": [
      {
        "type": {
          "type": "emoji",
          "emoji": "👍"
        },
        "total_count": 3
      },
      {
        "type": {
          "type": "emoji",
          "emoji": "❤"
        },
        "total_count": 1
      }
    ],
    "countsComplete": false,
    "users": [
      {
        "userId": 123,
        "reactions": [
          {
            "type": "emoji",
            "emoji": "👍"
          }
        ]
      }
    ],
    "own": [
      {
        "type": "emoji",
        "emoji": "👍"
      }
    ],
    "updatedAt": "2026-10-04T12:30:00Z"
  }
}
```

Если известна только собственная реакция, reactions может содержать только own и время известного изменения; counts/users не добавляются как пустые массивы по умолчанию.

Основание: [Update](https://core.telegram.org/bots/api#update), [setMessageReaction](https://core.telegram.org/bots/api#setmessagereaction), [ChatFullInfo](https://core.telegram.org/bots/api#chatfullinfo), [ReactionCount](https://core.telegram.org/bots/api#reactioncount).

### Принято: лимиты и экономия контекста

- Текст одного сообщения в сокращённом представлении ограничен 1 000 Unicode code points. При превышении textPlain/richPlain/captionPlain обрезается и добавляется truncated=true. Полное содержимое доступно через read; поиск использует полный извлечённый текст.
- Текст agent_message ограничен 8 000 Unicode code points. Превышение отклоняется с error и английским description, без обрезания.
- Дополнительные жёсткие лимиты количества сообщений в history/read/search и файлов в download в v1 не вводятся. Это не отменяет ограничения Telegram API и другие ранее принятые ограничения инструментов.
- Для экономии контекста инструкция агенту рекомендует history до 100 сообщений за вызов, search по 20 результатов (limit по умолчанию 20), read до 20 сообщений и download до 20 файлов. Это рекомендации, а не верхние границы: агент выбирает размер запроса по задаче.
- Например, поручение прочитать последние 500 сообщений допустимо выполнить одним history либо несколькими вызовами. Контроллер не отклоняет запрос только из-за превышения рекомендованного количества.
- read возвращает полное содержимое сообщений без сокращения текста/rich-блоков по лимиту короткого представления. Отдельный жёсткий лимит объёма ответа в этом обсуждении не принят.

### Принято: ответы простых инструментов

- note_get() возвращает {"text":"..."}; отсутствующая заметка — {"text":""}. note_set({text}) возвращает {"status":"saved"}.
- pin, unpin и react возвращают {"status":"completed"} после успешного ответа Telegram.
- delete({messageIds:[170,171],chatId?}) удаляет пакет в текущем или разрешённом пассивном чате и возвращает {"status":"completed"} при успешном ответе Telegram на пакет. Это не точный отчёт об удалении каждого ID: Telegram может пропускать отсутствующие сообщения. Нативные ограничения пакета и прав Telegram сохраняются.
- При отказах используются error и обязательное английское description по общим правилам; неопределённый результат внешнего действия не представляется подтверждённым успехом.

### Принято: результаты и ошибки инструментов

- Успех возвращает полезные данные без обязательной обёртки ok/result, например {"messageIds":[301]}.
- Каждая ошибка, включая ошибку отдельного элемента пакета, содержит error (короткий машинный код) и обязательное description на английском. Description объясняет причину и доступный следующий шаг; агенту не нужен отдельный справочник кодов.
- Description формируется контроллером и не раскрывает секреты, внутренние трассировки или сведения из недоступных чатов. Полезные разрешённые пути результатов download сохраняются; диагностические внутренние пути не выдаются.
- Известный отказ означает, что действие не выполнено. Ошибки аргументов требуют исправления запроса; неизменённый запрос не повторяется без причины.
- Временный отказ может содержать retryAfterSeconds. Повтор внешнего действия допустим только при уверенности, что оно не выполнено. Короткие безопасные повторы могут выполняться контроллером без нового хода агента.
- delivery_unknown означает неизвестный результат отправки: сообщение могло быть доставлено. Ни контроллер, ни агент не повторяют отправку автоматически. Проверка истории может помочь, но отсутствие локальной записи не доказывает отсутствие отправки.
- Пакетные read/download возвращают результаты каждого элемента в порядке запроса; ошибки элементов имеют те же error/description. Для forward/copy остаётся массив новых messageIds без карты соответствия пропущенных источников.
- edit возвращает messageId и updated — массив подтверждённо изменённых компонентов, например {"messageId":170,"updated":["text","reply_markup"]}. При частичном отказе добавляются failed — компоненты с известным отказом, error и английское description: {"messageId":170,"updated":["text"],"failed":["reply_markup"],"error":"edit_failed","description":"The text was updated, but the keyboard update failed. Retry only reply_markup."}.
- Компоненты с неопределённым результатом перечисляются в unknown, а не failed: отсутствие подтверждения не означает отсутствие изменения. updated/failed/unknown описывают компоненты запроса и не пересекаются; пустые failed/unknown опускаются. При смешанных результатах description объясняет, что подтверждено и что нельзя повторять автоматически. Сохраняется замена компонента целиком; общий отказ не скрывает успешные изменения.
- Сырые ошибки Telegram переводятся в краткие коды и понятные описания. Полный набор кодов не фиксируется как справочник для агента.

```json
{
  "error": "invalid_argument",
  "description": "messageIds must be in strictly increasing order. Correct the order and retry."
}
```

```json
{
  "error": "rate_limited",
  "description": "Telegram rejected the request due to a rate limit. The action was not performed. Retry after at least 12 seconds.",
  "retryAfterSeconds": 12
}
```

```json
{
  "error": "delivery_unknown",
  "description": "Telegram confirmation was not received. The message may have been sent. Do not resend automatically, as this may create a duplicate."
}
```

Ранее приведённые сокращённые примеры с одним error подразумевают обязательное description согласно этому разделу.

### Предложение: общие правила инструментов

- Область текущего бота, чата и запуска определяется контроллером.
- Ответ содержит минимальные данные, необходимые для следующего решения: идентификатор/результат либо короткую ошибку.
- Ошибка инструмента не должна выглядеть как успешное действие.
- Вызовы старого запуска после принудительного обновления правил отклоняются.
- Инструменты не раскрывают токены Telegram, Git и Codex.

## 7. Результат сверки и оставшиеся вопросы

Актуальный перечень расхождений, незавершённых схем и проверок исполнения находится в [contract-review.md](contract-review.md). Уже согласованные правила не требуют повторного утверждения. Отложенные возможности не входят в список обязательных решений для v1.

### Принято: уточнение send/edit и состояния кнопок, 2026-10-05

- send содержит ровно один вариант: text, rich_message, photo, document, animation, video, audio, voice, sticker, location, venue, contact, dice, poll либо media (альбом). Подпись к медиа — caption, не второй вариант text.
- location:{latitude,longitude}, venue:{latitude,longitude,title,address}, contact:{phone_number,first_name,last_name?}, dice:{emoji?}, poll:{question,options:[...]} — наши оболочки, разворачиваемые в аргументы метода Telegram. Необязательные нативные параметры допускаются там, где поддерживаются выбранным типом.
- parse_mode/ entities взаимоисключающие для текста, parse_mode/caption_entities — для подписи. Без них текст обычный.
- В send media — массив альбома; в edit media — один объект InputMedia для замены вложения. uploads/file_sources/permits остаются синтетическими полями, чат назначения выбирается по правилам необязательного chatId, результат {messageIds:[...]}.
- Универсальный edit v1 ограничен текстом, rich, подписью, поддерживаемым Telegram медиа и inline-клавиатурой. Изменение геопозиции/опроса и другие специальные действия не добавляются неявно; их методы требуют отдельного решения.
- buttonSelections отклонён как лишнее поле. Агент получает выбранный ключ в событии; read показывает актуальные иконки/disabled, без отдельного списка выбранных групп.
- permits в edit отсутствует — прежний объект сохраняется. Агент отвечает за актуальность правил после изменения rich и/или нижней клавиатуры. Контроллер не проверяет необходимость обновления через парсер в v1, но проверяет действующие разрешения на каждом callback.

### Принято: edit с сохранением типа, 2026-10-05

- Редактирование в текущем или разрешённом пассивном чате с сохранением исходного типа: текст→текст, rich→rich, фото→фото и т. д. Нельзя перейти между текстом/rich/медиа или разными видами медиа. Для другого вида агент отправляет новое сообщение.
- Замена text/caption включает оформление: без новых entities/parse_mode (или caption_entities/parse_mode) текст обычный, старые entities не переносятся. Пустой caption удаляет подпись; пустой text недопустим.
- При замене media отсутствие media.caption сохраняет прежнюю подпись и её entities; явная media.caption заменяет подпись с новым оформлением, media.caption="" удаляет её. Контроллер подставляет сохраняемые сведения в нативный запрос. Нельзя одновременно передавать верхний caption и media.caption; если передан media, подпись задаётся только внутри media.
- Нижняя клавиатура сохраняется при отсутствии reply_markup; inline_keyboard:[] удаляет её. Полная замена rich не сохраняет старые встроенные кнопки или блоки автоматически.
- Разрешены совместные изменения совместимых компонентов и permits. Контроллер использует один Telegram-вызов, где возможно; общая атомарность нескольких вызовов не обещается, ошибки возвращают updated/failed/unknown.
- Элемент альбома меняется по собственному messageId без изменения его типа/состава альбома. Изменение геопозиции, остановка опроса и другие специальные операции не входят в универсальный edit v1. Сохранение типа само по себе не разрешает неподдерживаемую Telegram операцию.

### Принято: административные команды и ручное подключение ботов

- Мастер доступен только владельцу сервиса из конфигурации и не использует агента. Боты регистрируются токеном через /newbot TOKEN [OWNER_ID], владелец по умолчанию — владелец сервиса. Managed Bots/MTProto не требуются; владельцем в сервисе считается назначенный пользователь, не автоматически обнаруженный владелец BotFather. getMe проверяет токен и Telegram ID; повтор того же ID обновляет токен без удаления данных.
- /bots показывает зарегистрированных в БД ботов; /set_owner @BotName USER_ID меняет владельца выбранного бота в сервисе. Эти команды только для владельца сервиса. /pause_bot и возобновление бота отложены за пределы v1; /disable_bot и /enable_bot в v1 не реализуются. /pause_agent в v1 также не вводится.
- /delete_bot @BotName ничего не удаляет: возвращает сведения и две полные команды с реальным BOT_ID. /delete_bot @BotName BOT_ID удаляет подключение и связанные данные бота, оставляя файловую wiki/Git; /delete_bot @BotName BOT_ID all удаляет все данные, включая wiki. Username и ID должны соответствовать зарегистрированному боту. Это удаление из сервиса, не удаление аккаунта Telegram.
- В ЛС дочернего бота owner/admin использует /rules для получения AGENTS.md файлом. /set_rules требует reply на файл правил; /set_rules force применяет согласованное принудительное обновление. Эти команды обрабатывает контроллер, файл правил не попадает агенту как обычное поручение.
- /users [FROM-TO] — роли пользователей, доступ владельцу/admin. /set_user USER_ID [role] и /remove_user USER_ID — в пределах ранее согласованных полномочий: admin не меняет себя/других admin/владельца и не назначает admin. Владелец управляет всеми ролями.
- /agents [FROM-TO] — список агентов для owner/admin. /stop_agent AGENT_ID в группе выходит и удаляет диалог по принятому правилу. Для ЛС останавливает агента и удаляет все связанные данные диалога, но сохраняет назначенную роль: следующее сообщение авторизованного пользователя создаёт личного агента заново. Постоянного запрета и /enable_agent для ЛС нет.
- /transfer_owner USER_ID — передача владения текущим дочерним ботом его нынешним владельцем, не операция BotFather. /leave в группе доступна owner/admin и очищает диалог по принятому правилу.
- /users, /agents, /tasks поддерживают диапазоны вида 11-20. Размер страницы и порядок закреплены в разделе «Страницы и ответы административных команд». Некорректный диапазон — текстовая ошибка, без кнопок/уточняющего диалога.
- Административные команды не передаются агенту и не включают громкий режим. Каждая команда выполняет одно действие; ответ текстовый, кроме явно принятого файла /rules. Удаление бота реализуется полной командой с проверочным ID, без кнопок подтверждения. Команда с токеном не хранится в обычной истории/логах, токен не выдаётся агентам.

### Принято: загрузка правил по reply без состояния приглашения

- /set_rules (либо /set_rules force) в reply на файл загружает правила из этого файла. Это не отменяет возможной предшествующей обычной обработки файла агентом.
- Команда без reply на файл возвращает текст: «Отправьте AGENTS.md файлом в ответ на ваше сообщение /set_rules». Отдельное приглашение/его ID/таймер в БД не хранятся.
- Файл в reply на собственную команду /set_rules перехватывается контроллером до активации агента. Проверяются текущие права owner/admin, ЛС с выбранным ботом, автор исходной команды (тот же пользователь), текущий чат, полный допустимый текст команды /set_rules или /set_rules force без постороннего текста и отсутствие пересылки исходной команды. Проверяется структурированный reply_to_message, не quote.
- force определяется исходной командой. Ошибка чтения/проверки не запускает агента и не заменяет прежние правила. Не вводится одноразовость или срок: повторные файлы в ответ на ту же команду допустимы, каждый раз проверяются действующие права owner/admin. Это уточняет прежнее правило /set_rules только в reply на файл.


### Принято: рабочая директория и файловые команды — 2026-10-06

Каждый бот сразу получает собственную рабочую директорию. Git опционален. LLM Wiki — организация файлов и правила работы, которые предварительно задаёт владелец; контроллер не требует специальной структуры wiki. Правила бота AGENTS.md и секреты хранятся отдельно от доступной RW директории.

Все следующие команды доступны owner/admin в ЛС дочернему боту, обрабатываются контроллером без агента. Пути относительны рабочей директории; абсолютные пути, выход наружу (включая через ссылки), доступ к .git, секретам и управляемому файлу правил запрещены.

- /ls [директория]: непосредственные файлы и поддиректории с размерами; по умолчанию корень.
- /cat путь: имя и текст файла в pre; если не помещается в сообщение, предложить /download, не выдавать незаметно обрезанный текст.
- /download путь: отправить файл документом.
- /upload путь: сохранить документ, на который отвечает команда; без такого reply предложить отправить файл ответом на собственную команду /upload. Проверки отправителя/чата/реального reply аналогичны /set_rules. Файл-ответ перехватывается до агентской обработки. Создавать родительские директории, существующий файл заменять атомарно; ответ сообщает о создании или замене.
- /rm путь: удалить файл или директорию рекурсивно без подтверждения; удаление корня запрещено. Восстановление незакоммиченных данных не обещается.
- /mv путь1 путь2: оба пути задаются отдельными entities code; точное назначение, без неявного перемещения внутрь директории. Существующее назначение — ошибка без перезаписи. Родительские директории создаются.
- /edit путь и один pre-блок: путь задаётся entity code; полностью записать буквальное содержимое pre в UTF-8 атомарно, создавая родителей. Без pre создать/очистить пустой файл. Для длинного содержимого используется /upload.

Для /cat, /download, /upload весь остаток после команды считается путём. Обычные файловые операции не вводят блокировок параллельного редактирования агентами.

### Принято: /git_setup — 2026-10-06

Синтаксис: /git_setup [branch [remoteUrl [token]]]. Без аргументов показывает текущие настройки, скрывая токен (можно показать его наличие). Любой вызов с branch принудительно заменяет рабочую директорию точным состоянием указанной remote-ветки. Только branch использует прежние URL и токен; branch remoteUrl использует прежний токен; три аргумента задают новые значения. Если необходимых сохранённых настроек нет, операция возвращает ошибку.

Сначала проверить доступ к remote и существование ветки, не меняя текущие файлы и настройки при ошибке этой проверки. Затем fetch и принудительное восстановление ветки, без merge/pull. Теряются незакоммиченные изменения, неопубликованные коммиты и отсутствующие в remote файлы, включая игнорируемые. Подтверждение не требуется. Новые настройки сохраняются только после успешной синхронизации; полный откат при сбое самой замены файлов этим правилом не обещается.

На время замены приостановить всех агентов бота и исключить другие файловые/Git-операции. После операции продолжить работу с уведомлением, что директория обновлена и ранее прочитанные данные могли устареть. Это специальная защита административной синхронизации, а не общая блокировка редактирования wiki.

Токен принимает контроллер до сохранения истории и передачи агенту. Хранить отдельно от рабочей директории и .git/config; исключить из логов, ответов и ошибок. По возможности удалить исходную команду из Telegram; удаление не гарантирует удаления ранее показанных уведомлений. AGENTS.md также не заменяется синхронизацией.

В ЛС owner/admin доступны /git_changes и /git_sync сообщение коммита с той же семантикой, что у агентских инструментов. Агентские git_changes()/git_sync() не выполняют fetch/pull/force push. Если Git не настроен, возвращают error=git_not_configured и английское description, например: {"error":"git_not_configured","description":"Git is not configured for this bot. Ask the bot owner to run /git_setup."}. Не считать отсутствие настройки чистым репозиторием и не инициализировать Git автоматически из агентского инструмента.


### Принято: восстановление после перезапуска контроллера — 2026-10-06

- Обычная очередь событий находится в памяти и теряется при остановке; восстановление обычных сообщений не выполняется.
- Сохранённые контексты агентов возобновляются при следующем событии, с актуальными служебными инструкциями и правилами бота.
- Прерванная активная попытка расписания считается невыполненной. Сохранённые невыполненные срабатывания повторно поступают в обычную очередь; восстанавливается существующее срабатывание, новая запись задачи не создаётся.
- Если внешнее действие выполнено, но успех не записан до сбоя, повторная обработка может повторить действие. Этот риск принят для v1; гарантия exactly-once не предоставляется.
- Сохранённое до остановки cron-срабатывание и накопленный счётчик восстанавливаются. Новые срабатывания за время остановки не восстанавливаются и не увеличивают счётчик. После запуска новые срабатывания объединяются с восстановленным по обычным правилам, учитывая уже согласованное ожидание завершения активной обработки задачи.
- Второй экземпляр контроллера с той же БД не запускается одновременно с первым.
- Подключение агента действует только для запустившего его экземпляра контроллера. После перезапуска прежние подключения не могут выполнять инструменты и другие внешние действия через контроллер. Если процесс агента пережил контроллер, он не получает полномочий нового экземпляра; контекст возобновляется новым процессом. Проверка действительности подключения применяется перед выполнением действий.


### Принято: .temp и ежедневная очистка — 2026-10-06

- Внутри рабочей директории бота выделена .temp/<agentId>/ с download/ для скачанных файлов и upload/ для созданных файлов отправки. generated/ и отдельные .download/.upload не используются как каноническая структура.
- Агент может создавать любые дополнительные поддиректории и временные файлы внутри собственной .temp/<agentId>/. В инструкции указывается путь и предупреждение: рассчитывать на доступность временного файла можно не более суток; нужное надолго сохранять вне .temp.
- Все временные файлы, включая скачанные, созданные контроллером и произвольные файлы агента, очищаются по mtime старше 24 часов. Изменение файла обновляет отсчёт; чтение и повторный download готового файла его не продлевают.
- Одна ежедневная служебная задача контроллера удаляет историю старше 30 дней и временные файлы старше 24 часов, затем пустые поддиректории. Отдельная защита файлов, используемых текущими операциями, в v1 не вводится. Неудавшееся удаление повторяется при следующей ежедневной очистке; ошибки с путями и причинами собираются в одно уведомление владельцу каждого затронутого бота, без раскрытия секретов.
- Из-за ежедневной периодичности файлы могут фактически храниться до 48 часов после mtime; 24 часа — порог для очистки, не гарантия точного удаления. Для истории аналогично возможен дополнительный интервал до суток. Возраст истории считается от первого получения внешнего сообщения контроллером; редактирование не продлевает срок, см. раздел срока истории ниже.
- Агент имеет RW-доступ к своей .temp/<agentId>/; чужие временные директории ему не открываются. Доступное вложение соседней группы download размещает в директории запрашивающего агента. Дедупликация загрузки не должна предоставлять доступ к чужой приватной директории; конкретный способ повторного использования кеша определяется при реализации.
- Владелец может работать со всей .temp файловыми командами. Файловые границы и изоляция остаются действующими.
- .temp принудительно исключается из git_changes и git_sync, независимо от .gitignore. /git_setup сохраняет .temp при замене рабочих файлов и отклоняет remote-ветку, содержащую .temp. Прежнее правило удаления игнорируемых файлов при /git_setup имеет это явное исключение.
- Очистка истории не удаляет сохранённые срабатывания планировщика, notes и постоянные рабочие файлы/wiki. Notes сохраняются по ранее принятому жизненному циклу диалога.


### Принято: /cleanup_temp и отчёт очистки — 2026-10-06

Ошибки ежедневного удаления временных файлов сообщаются в ЛС владельцу от соответствующего дочернего бота. Отчёт содержит все просроченные файлы, оставшиеся после очистки, их относительные пути и причины ошибок; предлагает /cleanup_temp для повторной очистки и /rm путь для удаления отдельного файла независимо от возраста. Если список не помещается в одно сообщение, обрезать с явной отметкой; файл с полным отчётом в v1 не прикладывается.

/cleanup_temp доступна owner/admin в ЛС дочернему боту. Немедленно повторяет очистку временных файлов по актуальному mtime старше 24 часов, сохраняя свежие файлы; историю не очищает. Результат возвращается напрямую в ответе команды, без дополнительного уведомления. Файлы, изменённые после прежнего отчёта, проверяются заново и не удаляются, если больше не просрочены.


### Принято: уточнение ролей — 2026-10-06

manager наследует все права user; admin наследует manager и получает все команды дочернего бота, кроме назначения/снятия admin и изменения owner; owner имеет все права своего бота. Назначение admin остаётся только owner, передача владения — только owner. Мастер-бот остаётся доступен только владельцу сервиса. Актуальные права и команды собраны в [access-and-commands.md](access-and-commands.md); эта матрица заменяет прежние ограничения команд только владельцем. Содержание уведомлений очистки по-прежнему отправляется владельцу, не всем admin. Приватность истории и область агентских инструментов не меняются.


### Принято: каналы и пассивные супергруппы — 2026-10-07

Полная модель в [channels-and-discussions.md](channels-and-discussions.md). Документ заменяет прежний запрет всех супергрупп и текущую-чату-only область инструментов: необязательный chatId разрешает чтение подключённых group/supergroup/channel и запись/изменения в пассивных каналах/супергруппах, но не в чужом чате с агентом и не в чужих ЛС. Приняты chats(), chat_info(), /chats, /leave_chat и discussion-объект для search/history. message_thread_id обычных комментариев сохраняется и не означает автоматически форум; форумные маршруты остаются запрещены. Callback в пассивных чатах агенту не передаётся.


### Принято: выбор модели агента — 2026-10-07

Команды доступны только admin/owner дочернего бота, обрабатываются контроллером без запуска агента; остальные пользователи не получают через команды модель агента или каталог моделей. В пассивных чатах команды не выполняются. agentId должен принадлежать текущему боту.

- /get_model [agentId]: текущая модель выбранного агента; без аргумента — агента текущего чата. Если назначена другая модель на следующий ход, показать её отдельно как ожидающую применения.
- /set_model MODEL [agentId]: назначить модель выбранному агенту; без agentId — текущему. Свободному агенту — со следующего хода, занятому — после завершения текущего хода. Не запускать и не прерывать ход; steer внутри старого хода модель не меняет. Уже выполняющихся субагентов автоматически не переключать.
- /get_model default: показать дефолтную модель текущего бота.
- /set_model MODEL default: изменить дефолт только для новых агентов. Существующие агенты сохраняют свои конкретные модели.
- /models: доступный каталог из model/list, без жёстко заданного перечня. Каталог не гарантирует разрешённость успешного inference для аккаунта; ошибка выбора/использования объясняется явно, скрытая подмена модели не предполагается.

При создании агент получает конкретное значение текущего default. Модель, default и ожидающее изменение сохраняются контроллером в БД отдельно от истории и компактации; выбранная модель передаётся при новом turn/start того же thread. Историю и контекст не сбрасывать. Если текущий reasoning не поддерживается новой моделью, использовать её default reasoning и сообщить об этом в ответе. Смена модели с контекстом, resume/компактацией и субагентами требует проверки на выбранной версии runtime.

Это выбор модели внутри используемой Codex-авторизации, не переключение аккаунта. Источник возможностей: https://learn.chatgpt.com/docs/app-server (model/list, turn/start, ограничения turn/steer).


### Принято: лимит очереди и громкого режима — 2026-10-07

- Громкий режим действует 2 минуты и максимум 10 обычных сообщений после активации; заканчивается по первому достигнутому пределу, независимо от размера очереди. Прямой триггер (упоминание, reply, кнопка) обновляет время и сбрасывает счётчик; сам прямой триггер не расходует эти 10 сообщений. Счётчик расходуется при приёме события, не после ответа агента.
- Для каждого агента в памяти допускается максимум 10 ожидающих событий чата: сообщения, события редактирования и callback входят в один лимит. Уже обрабатываемая пачка не входит. Межагентные события и события планировщика в этот лимит не входят; лимит байтов и межагентных отправок в v1 не вводится.
- При переполнении новые сообщения/редактирования сохраняются в обычной истории, но событие не ставится в очередь. Контроллер ведёт краткий счётчик пропущенных событий и при следующей передаче сообщает агенту их количество и возможность прочитать историю. Служебное уведомление не хранит полный список пропущенных сообщений и не считается их исполнением.
- Callback при заполненной очереди сразу отклоняется ответом «Агент занят, попробуйте позже». Не фиксировать выбор, не закрывать группу и не блокировать кнопки. Проверка места и принятие callback должны быть согласованы с фиксацией выбора, чтобы не принять выбор без события.
- Очередь остаётся непостоянной: история и новый межагентный журнал не используются для автоматического восстановления потерянных обычных событий после остановки.

### Принято: журнал межагентных сообщений — 2026-10-07

- Успешно поставленные в очередь agent_message записываются в БД на 7 дней от момента постановки. Одна отправка — одна запись: botId, agentId отправителя и получателя, время, полный текст. Для каждого участника отображается соответствующее направление. Журнал не подтверждает исполнение и не является постоянной очередью; автоматической повторной доставки из него нет.
- /agent_messages AGENT_ID [FROM-TO] доступна только admin/owner текущего бота. AgentId проверяется в пределах бота. По умолчанию последние 10 записей, порядок от новых к старым; позиции с 1, диапазон включительный. Одна позиция допустима: /agent_messages a1 11.
- Вывод: заголовок a1 → a2 DateTime и текст сообщения для каждой записи, входящие и исходящие вместе. Если выдача не помещается в одно текстовое сообщение Telegram, обрезать даже посреди записи, добавив явную отметку. Файл не прикладывать; полный текст в БД остаётся. Запрос одной позиции также может быть обрезан.
- Лимиты agent_message по длине текста и проверки принадлежности боту остаются; ограничения частоты отправок в v1 нет. Неограниченное накопление межагентных событий является принятым риском v1. Срок 7 дней применяется ежедневной очисткой, аналогично другим данным: возможен дополнительный интервал до суток между проверками.


### Принято: отсчёт срока истории — 2026-10-07

История хранится 30 дней от первого получения сообщения контроллером. В БД сохраняется отдельная дата первого получения; повторное получение и редактирование не обновляют её. Telegram date и edit_date сохраняются отдельно для отображения и фильтров поиска. При редактировании обновляются последняя версия и дата редактирования, но не срок хранения.

Вложенное сообщение reply хранится как часть внешнего сообщения по сроку внешней записи, даже если оригинал старше 30 дней. Это не продлевает срок отдельно сохранённой записи оригинала и не восстанавливает его самостоятельную историю. Задержавшееся сообщение не удаляется сразу из-за старой даты отправки.

Ежедневная очистка удаляет записи, полученные более 30 дней назад; фактическое хранение может превышать порог на интервал между очистками до суток. Notes, расписание/невыполненные срабатывания и постоянные рабочие файлы не удаляются этой очисткой. Межагентный журнал сохраняет собственный срок 7 дней от успешной постановки.


### Принято: Croner для Node и календарные правила — 2026-10-07

Контроллер работает на Node.js; библиотека расписаний — croner. Конкретная версия закрепляется при реализации, календарные примеры и DST проверяются на ней. Приняты правила Croner, а не nnCron или системного crontab. Источники: https://croner.56k.guru/usage/pattern/ и https://croner.56k.guru/usage/examples/.

- Агентский cron — пять полей (минуты, часы, день месяца, месяц, день недели), точность до минуты. Секунды и год библиотека поддерживает, но в агентский интерфейс v1 не включаются.
- Timezone задаётся IANA-именем, например Asia/Nicosia. Воскресенье — 0 или 7, также допустимы имена дней.
- При одновременном ограничении дня месяца и недели действует OR. Для явного AND допускается + перед полем дня недели; прежнее предложение отклонять сочетание полей не принимается.
- При переходе DST вперёд несуществующее локальное время пропускается. При переходе назад повторяющееся локальное время запускается один раз при первом наступлении.
- Календарные расширения Croner доступны: например L для последнего дня месяца и MON#2 для второго понедельника. Правила и примеры включаются в инструкции агенту; собственные несовместимые правила не вводятся.
- Примеры: 0 9 * * SAT,SUN — 09:00 по выходным; 0 9 1 * MON — первое число или понедельник; 0 9 1 * +MON — первое число только если понедельник; 0 9 * * MON#2 — второй понедельник; 0 9 L * * — последний день месяца.

Croner используется также для одноразовых at: конкретный момент с явным offset/Z преобразуется в Date. Агентский контракт сохраняет отдельные варианты at и cron, без маскировки разового события cron-выражением.

Библиотека отвечает за вычисление дат/таймеры, а контроллер — за БД, очередь, накопление и объединение срабатываний, ошибки и восстановление. Callback только регистрирует срабатывание, не ожидает завершения агента. Библиотечная защита overlap, пропускающая новые запуски пока агент занят, не применяется вместо нашего учёта пропусков.

После перезапуска просроченный at обрабатывается контроллером: сохранённое невыполненное событие ставится в очередь, а не передаётся Croner как таймер прошедшей даты. Одноразовое событие сохраняется до успешной обработки по принятому правилу, даже если таймер уже сработал. Новые cron-срабатывания за время остановки не восстанавливаются; ранее сохранённые невыполненные срабатывания восстанавливаются независимо от таймеров.


### Принято: порядок альбомов и громкий режим — 2026-10-07

Альбом собирается независимо от передачи обычных сообщений: готов через 1 секунду после последнего полученного элемента, но не позже 3 секунд от первого. Очередь не задерживается и место для альбома заранее не резервируется. Порядок событий у агента может отличаться от порядка отправки, это штатная ситуация без служебных подсказок.

Готовый альбом — одно событие для лимита 10 ожидающих событий чата и, при приёме по громкому режиму, одно сообщение из его бюджета 10. Громкий режим и наличие места проверяются при готовности. Если окно истекло во время сборки, альбом без собственного прямого триггера только сохраняется в историю; время первого элемента не резервирует право доставки. Прямой триггер внутри альбома обрабатывается по правилам триггеров и сбрасывает бюджет, не расходуя бюджет обычных сообщений.

Поздние элементы сохраняются по прежнему правилу и могут передаваться дополнением с тем же albumId для альбома, который уже активировал агента, с проверкой лимита очереди. Telegram-сообщения в истории остаются отдельными, а агрегированный пакет не заменяет их. Жёсткая гарантия полноты альбома не предоставляется.


### Принято: компактные служебные ответы — 2026-10-07

Служебные ответы стараться писать компактно. Длинные текстовые ответы /tasks, /task, /users, /agents, /chats, /ls, /agent_messages и других служебных команд обрезаются до одного допустимого сообщения Telegram с явной отметкой; обрезка посреди записи допустима. Отчёт ошибок очистки также обрезается, файл с полным отчётом не отправляется. Списки можно запрашивать меньшим диапазоном. Это правило относится к ответам контроллера, не к произвольным сообщениям агента.

Исключения: /rules и /download возвращают файл по назначению команды; /cat при слишком длинном содержимом предлагает /download, не выдавая незаметно обрезанный файл. При обрезке оформленного служебного текста учитывать границы UTF-16 entities, удалять/сокращать выходящие за текст entities и не ломать пары Unicode; отметка обрезания тоже входит в допустимый размер. Отдельный лимит количества entities приложения в v1 не вводится. Служебное оформление минимальное: pre для содержимого файла, code для команд и путей; избегать лишних фрагментов форматирования. Соблюдаются ограничения Telegram по длине текста, UTF-16 offset/length и вложенности entities. Числовой предел количества entities официальной документацией Bot API в текущей проверке не подтверждён; не фиксировать непроверенное число как гарантию API.


### Принято: без маршрутизации в v1 — 2026-10-07

Время в пути в сценарии Live Location — пример поручения агенту, а не обязательная функция контроллера. В v1 сервисы маршрутов и отдельный инструмент оценки времени в пути не подключаются. Работа с полученными координатами и расписанием сохраняется; отдельный обязательный сценарий расстояния вместо маршрутов не вводится.


### Принято: пользовательские MCP вне v1 — 2026-10-07

Подключение пользовательских MCP для бота/агента и команды /mcp_* не реализуются в v1. Предложения HTTP-прокси, Bearer/OAuth-настройки и фильтров пользовательских MCP отложены. Это не отменяет инструменты нашего контроллера: способ предоставления этих инструментов Codex (MCP или иной поддерживаемый механизм) выбирается при реализации. Встроенный веб-поиск использует согласованный ниже режим live.


### Принято: встроенный веб-поиск live — 2026-10-07

Для всех агентов v1 встроенный веб-поиск Codex настраивается в режиме live. Команды переключения режима и индивидуальные настройки поиска в v1 не вводятся. Пользовательские MCP остаются вне v1. Доступность поиска в выбранном App Server с фактической авторизацией проверяется при интеграции; это решение о конфигурации, а не результат live-теста.


### Принято: permits и отсутствующая запись при edit — 2026-10-07

- Если edit передаёт permits вместе с rich_message и/или reply_markup, новый объект сохраняется при подтверждённом успешном изменении хотя бы одного из этих компонентов. Отказ другого компонента не отменяет эту замену. Если ни rich, ни клавиатура не были подтверждённо изменены, прежние permits сохраняются; неизвестный результат не считается подтверждённым успехом.
- При частичном сбое агент получает updated/failed/unknown и английское description, затем должен попытаться исправить сообщение и разрешения с учётом подтверждённых изменений. Это не безусловный автоматический повтор всего запроса. Дополнительная временная блокировка callback до сверки не вводится; риск рассогласования до исправления принят.
- Если edit меняет только permits без rich_message/reply_markup, сохраняется ранее согласованная самостоятельная замена синтетического свойства; новая оговорка относится к совместному изменению разрешений и кнопок/rich.
- Если исходная запись удалена из локальной истории и контроллер не располагает данными, необходимыми для проверки типа, прав и сохранения отсутствующих компонентов, edit возвращает ошибку с английским description. Контроллер не угадывает исходное содержимое. Наличие старого сообщения внутри reply само по себе не восстанавливает исходную запись и состояние permits. Срок истории ради редактирования не продлевается.


### Принято: исходящие записи copy/forward — 2026-10-07

- Полный Message, возвращённый Telegram, сохраняется обычным способом с файловыми метаданными.
- При одиночном copy, если исходное сообщение есть в БД, контроллер формирует запись нового сообщения из исходника с учётом применённых изменений. Запись явно отмечается как восстановленная контроллером, а не полученная целиком от Telegram. Идентичность, чат назначения и происхождение копии не переносятся слепо из исходника. Формат технической отметки определяется при реализации.
- Для пакетных copy/forward без надёжного соответствия исходных и новых ID записи не выдумываются и не сопоставляются по позиции. Успешный результат отправки сохраняет messageIds, но read/download нового сообщения могут возвращать message_not_found, если его содержимое не было сохранено из надёжного источника.
- Вложение можно повторно использовать через доступное исходное сообщение и file_sources, пока соответствующая запись доступна. Отдельная система происхождения файлов в v1 не нужна.

Перед открытием темы обсуждения проверять уже зафиксированные решения и примеры. Продолжать обсуждение только при конкретном пробеле, противоречии или необходимом улучшении; согласованную семантику заново не обсуждать.


### Принято: страницы и ответы административных команд — 2026-10-07

- Все команды списков с пагинацией принимают диапазон FROM-TO или одиночную положительную позицию N (например, /agents 5). Это не меняет смысл числовых аргументов других команд: USER_ID, CHAT_ID и другие идентификаторы остаются идентификаторами.
- По умолчанию выдаются позиции 1–10. /users сортируется по userId, /agents — по времени создания от старых к новым, /bots и /chats — по числовому ID. /tasks сохраняет ранее согласованный порядок createdAt/taskId. /agent_messages сохраняет последние 10 записей от новых к старым.
- Ответ показывает фактический диапазон и общее количество, например 11–20 / 83. Диапазон частично за концом возвращает доступную часть; полностью за пределами — «Записей нет». Это текущие списки без снимка/курсора между вызовами.
- Ошибки синтаксиса аргументов возвращаются сразу контроллером, без передачи агенту, выполнения действия или уточняющего диалога.
- Все ответы на команды, включая ошибки и файлы, отправляются как reply на сообщение команды. Для загрузки файлом в ответ на /set_rules или /upload ответ адресуется сообщению с файлом, которое выполнило операцию. Автоматические уведомления не являются ответами на команды и под это правило не подпадают.


### Принято: один аккаунт Codex в v1 — 2026-10-07

Владелец сервера самостоятельно авторизуется на сервере через Codex CLI. Все дочерние боты и агенты v1 используют эту единую авторизацию. Подключение отдельных аккаунтов пользователей, передача их Codex-токенов через Telegram и команды управления аккаунтами в v1 не вводятся. Регистрация Telegram-ботов и их владельцы остаются независимыми от аккаунта Codex. Учётные данные Codex остаются служебными данными вне агентской RW-директории и не раскрываются агентам. Фактическая работа App Server, веб-поиска и генерации изображений с этой авторизацией требует ранее запланированных интеграционных проверок.
