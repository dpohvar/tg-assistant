# Views, overlays and events

[Widget handbook](../widgets.md) · [Getting started](getting-started.md) · [JSX](jsx.md) · [State](state.md) · [Runtime](runtime.md)

A view binds one exported component to one Telegram message. `set_widget_view({widgetId,component,send:{}})` creates a message; `target:{chatId,messageId}` binds an authorized existing bot message. `send:{guestRequestId}` answers a guest request, and `target:{inlineMessageId}` binds an owned inline publication. Agent-created durable views use JSON props. `get_widget` returns component names, targets, props, statuses and errors; `list_widgets` includes quota. `delete_widget_view` detaches one view, while `delete_widget` removes the instance and saved state.

Inside a component, `useView()` exposes `id`, `target`, `props`, last confirmed `message`, `status`, `error`, `parent`, and `user`. A public view has `user === null`; a recipient-only view identifies its recipient. `view.mount(<Other {...props}/>)` updates the retained view: changed props preserve component state; changing the component remounts it. Pass `{force:true}` to remount deliberately. `view.mount()` retries its retained node, including after a view error. `view.unmount()` removes its binding. `view.closeOverlay()` removes the current private overlay and safely does nothing on a public view. `view.getOverlays()` returns the public view's overlays.

`useWidget()` offers `mount(targetOrViewId,node,{force?})`, `unmount`, `closeOverlays`, `getView`, `notifyAgent`, and `requestAgent`. `widget.mount` creates a new message view; `useViews()` subscribes to the instance's current list. Editing a public parent first closes its private overlays. An overlay is kept per user per parent and expires after 20 minutes of inactivity; private overlays are removed on server restart. Ordinary views retain their saved binding identity across restart and can be repainted by a later store update.

An ordinary group or supergroup button can call `event.overlay(<Game playerId={event.from.id}/>)` to open or update a recipient-only view. The same user's next call on that parent updates their overlay; another user gets a separate overlay. `event.respond(...)` answers the callback. **Inline mode cannot create overlays or new ephemeral messages:** an inline publication has no usable ordinary group chat address. Guest views also have no ordinary chat/message address for `event.overlay`. Render shared controls in the inline or guest message itself and enforce player identity in button handlers. A widget may mount a new recipient-only message in an ordinary chat using an explicit authorized `{chatId,receiverUserId}` target.

In a private chat, the same `event.overlay(<Game />)` opens a virtual child view and edits the parent message in place. `useView()` inside the child has `user` set to the chat user and `parent` set to the original view. `view.closeOverlay()` restores the original rendering; reopening can read the widget's persisted store. A changed parent projection closes the virtual child before publishing the parent. Virtual children have no separate Telegram address, are not stored in the database, and disappear on restart; the parent is then repainted. A render with unchanged parent output keeps the child open, including store updates from game controls. Rich message bodies can be edited this way; Telegram's native dice and sticker body replacement rules still apply.

A standalone recipient-only message in a group can use the same virtual child behavior. Mount the parent with `set_widget_view({widgetId,component:"GameInput",target:{chatId,receiverUserId}})`; `event.overlay(...)` then edits that same ephemeral message, and `view.closeOverlay()` restores its launcher. Only the designated recipient can activate the view. The bot must be an administrator to [send proactively](https://core.telegram.org/bots/api#ephemeral-messages-and-commands). Otherwise Telegram requires a callback or reply to an ephemeral message within 15 seconds, and runtime code must provide that fresh identifier. Ephemeral messages can disappear from clients; the saved widget state remains until the widget is removed.

`useOnMessage(callback)` runs after every confirmed send or edit. `useOnReply(callback,{disabled?})` receives replies to this view; active handlers receive them instead of the chat agent. `useOnReaction(callback,{disabled?})` receives identified reaction changes. `useDice()` reads the last confirmed native dice result as `[value,emoji]`. Hooks unregister on unmount. Callback buttons are valid only while present in the last confirmed render.

`widget.notifyAgent({text})` queues a `widget_message`. `widget.requestAgent({text,data?,responseSchema?},{timeoutMs?,signal?})` waits for a JSON reply; give it a deadline or AbortSignal. The agent receives a `widget_request` and replies with `answer_widget_request({requestId,result})`. Cancelling an unstarted request removes it from the queue. A Telegram edit failure leaves a view in `error`; a confirmed deleted or inaccessible message detaches it. Errors are reported to the owner only on the first occurrence to avoid repeated interruptions. See [agent contract](../agent-contract.md#widget-tools) for the tool schemas.
