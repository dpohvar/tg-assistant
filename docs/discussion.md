# Telegram-ассистент на Codex: результаты обсуждения

Обновлено: 2026-10-03. Начало обсуждения: 2026-10-02.

Документ фиксирует текущее обсуждение. Принятые решения, предложения и открытые вопросы разделены. Реализация и проверки интеграции ещё не выполнены.

## Цель и вариант размещения

Желаемый продукт — сервис на сервере владельца платформы, куда пользователи подключают собственных Telegram-ботов и аккаунты ChatGPT/Codex.

Если условия или возможности подключения ChatGPT не позволяют такой сервис, рассматривается личный сервер с аккаунтом владельца. Обновление 2026-10-07: в v1 используется один аккаунт владельца сервера, авторизация выполняется им через Codex CLI; подключение пользовательских аккаунтов отложено. Несколько дочерних ботов и мастер-бот приняты как модель организации данных; прежний вариант без мастер-бота заменён новой моделью.

Обязательное требование: генерация и редактирование изображений через стандартную подписку ChatGPT/Codex. Отдельный API-ключ и отдельная оплата Image API не рассматриваются как запасной вариант.

## Агенты и события

- У каждого диалога с ботом один постоянный контекст агента. Поддерживаются ЛС и группы.
- Личный диалог владельца с ботом обслуживает основной агент бота.
- Агент решает, промолчать ли, отправить одно или несколько сообщений, запустить субагента, создать отложенную задачу или выполнить другие доступные действия.
- Агенты одного бота могут общаться, включая агентов разных личных диалогов, и спрашивать о происходящем в подключённых группах. Общение не даёт права читать чужую личную историю или раскрывать личные сведения без разрешения соответствующего пользователя. Это уточняет первоначальную модель всегда авторизованного обмена данными.
- Агенты разных ботов не могут общаться между собой. История, wiki и внутренние инструменты изолированы по боту.
- В группах упоминание бота, reply на его сообщение и разрешённое нажатие его кнопки обрабатываются как прямые триггеры. Каждый триггер автоматически включает громкий режим до двух минут после последнего триггера: в этом окне агент получает обычные сообщения и может отвечать или промолчать. Обычные сообщения окно не продлевают. По истечении окна они только сохраняются в историю, а ожидающие обычные события больше не запускают агента; текущий ход завершается. Ранняя отписка агентом в v1 отсутствует. Режим хранится в памяти и выключается при перезапуске. Полное правило — в [agent-contract.md](agent-contract.md).

## Контроллер

### Мастер-бот и доступ пользователей

Принята новая модель: бот — общая область данных и доверия, агент — отдельный контекст чата внутри неё.

- Мастер-бот не управляется агентами. Создавать новых дочерних ботов через него может только владелец сервиса; его Telegram userId задаётся в конфиге. Делегированные admin не могут создавать ботов.
- У каждого дочернего бота один общий AGENTS.md и возможность зарегистрировать одну wiki.
- Между ботами данные изолированы. Внутри бота wiki общая, но прямое чтение чужих ЛС запрещено; межагентная передача личных сведений ограничена разрешениями пользователя. Личные сведения не копируются автоматически в общую wiki без разрешения соответствующего пользователя.
- Список авторизованных пользователей дочернего бота изначально содержит только владельца. Владелец может добавлять пользователей для общения в ЛС.
- Настройка выполняется через мастер-бота. Роли отдельного дочернего бота: user — ЛС; manager — ЛС и подключение групп; admin — дополнительно управление user/manager. Владелец — отдельный неизменяемый через роли статус; только он управляет admin, AGENTS.md, аккаунтами, токенами и настройками бота.
- В подключённой группе обращаться к боту могут все участники, независимо от списка для ЛС.
- Неавторизованные ЛС и команды, включая /start, молча игнорируются без истории, агента и Codex. Заявки на доступ и их уведомления не создаются. Предварительная авторизация позволяет работать с первого сообщения.
- /set_user USER_ID @BotName [role] назначает/заменяет роль, по умолчанию user; /remove_user USER_ID @BotName отзывает доступ. Для каждой административной команды контроллер проверяет реального отправителя и его права именно на выбранного бота. admin одного бота не получает прав на другие и не может изменять владельца, себя или других admin.
- При добавлении в группу контроллер проверяет инициатора по my_chat_member: владелец, manager или admin выбранного бота могут её подключить. При неавторизованном добавлении бот выходит; переписка не сохраняется и агент не запускается. Telegram не предоставляет настройки «добавлять может только владелец».
- Форумные группы запрещены в v1: даже разрешённый пользователь не может подключить их. При is_forum=true бот выходит без создания агента. Если подключённая группа стала форумом, контроллер при обнаружении прекращает её обработку и выходит. Поддержка тем и выбор архитектуры отложены до следующих версий.
- В v1 разрешены только обычные группы (type=group); супергруппы (type=supergroup), включая нефорумные, подключать запрещено. При добавлении бот выходит. При миграции обычной группы в супергруппу контроллер отключает прежний диалог и выходит из новой супергруппы; переноса контекста, истории и расписания на новый chatId нет.
- При удалении/выходе бота из подключённой группы сначала блокируются действия и прерывается ход, затем полностью удаляются агент, контекст, история группы, заметка, очередь, задачи, состояния кнопок и карточек. Повторное подключение — с нуля и с новой проверкой доступа. Общая wiki/Git и ранее отправленные сообщения Telegram сохраняются.
- Блокировка бота пользователем в ЛС полностью очищает личный диалог тем же способом, сохраняя назначенную роль. После разблокировки новое сообщение создаёт агента с нуля без повторной авторизации. /remove_user также полностью очищает диалог, но удаляет роль; дальнейшее подключение требует нового разрешения. Общая wiki/Git сохраняются.

Предлагается при подключении явно объяснять, что сведения всех чатов одного бота могут передаваться между ними. Межагентная передача данных не превращает просьбу участника группы в команду владельца и не даёт права менять настройки.

Для получения контекста группы нужен доступ к обычным сообщениям. Предлагаемая настройка Telegram: выключить Privacy Mode у дочернего бота и добавлять его обычным участником, без обязательных административных прав. Получение сообщений контроллером и активация Codex — разные операции.

Предусмотрена прослойка по образцу teletale / joan-world, но проще и с акцентом на надёжность и экономию токенов.

Принятые требования:

- Свободный агент реагирует сразу. Общей задержки для сбора сообщений нет. Исключение — альбомы: контроллер ждёт 1 секунду после последнего элемента, максимум 3 секунды после первого, и передаёт собранные элементы пакетом. Элементы сразу сохраняются в историю. Поздние элементы активировавшего агента альбома передаются дополнением; таймер не гарантирует полноту. Детали фиксируются в [agent-contract.md](agent-contract.md).
- Если агент занят, новые события встают в очередь.
- Если стандартные средства Codex обеспечивают требуемую обработку очереди, следует использовать их.
- Иначе контроллер хранит очередь и передаёт накопленные события после освобождения агента. Группировка допускается только за время занятости агента, без дополнительного ожидания.
- MCP или другие инструменты должны иметь простые контракты и компактные результаты.

Предлагается оставить контроллеру транспорт Telegram, маршрутизацию, хранение событий и истории, очередь, расписание, восстановление, авторизацию и выполнение внешних действий. Решения о содержании ответов и необходимости загрузить контекст остаются у агента.

### Очередь и отложенные задачи: первая версия

Принято упрощение:

- Очередь событий хранится только в памяти приложения, не в БД.
- История сообщений хранится в БД независимо от очереди.
- На агента выполняется одна обработка одновременно; остальные события ожидают в памяти.
- После перезапуска старые обращения автоматически не восстанавливаются из истории.
- Очередь ограничивается по количеству событий; при переполнении новые обращения явно отклоняются. Конкретный лимит пока не выбран.
- При штатном завершении приложение по возможности заканчивает текущую работу.
- Владелец может повторить запрос после сбоя.
- Отложенные задачи и расписание хранятся в БД и сохраняются после перезапуска.
- Контракт расписания: schedule создаёт задачу с description и полной инструкцией text; at задаёт одноразовый запуск, cron + timezone — повторяющийся с точностью до минуты. everySeconds не нужен. tasks(...taskId) возвращает полные выбранные задачи, без аргументов — краткий список без text. cancel_tasks(...taskId) отменяет задачи целиком вместе с ожидающими срабатываниями, не прерывая уже начатый ход. Событие scheduled содержит taskId, scheduledAt и text. Примеры и ещё открытые детали восстановления — в [agent-contract.md](agent-contract.md).
- Сообщения и расписание используют общую очередь агента в памяти; ожидающие события планировщика дополнительно сохраняются в БД до успешного завершения обрабатывающего их основного хода. Просроченные at передаются после запуска. Новые cron-срабатывания за время остановки пропускаются, но ранее ожидавшие сохраняются. При занятости агента cron-срабатывания одной задачи объединяются по taskId на месте первого события, с occurrences и lastScheduledAt; выполняющийся запуск не объединяется. Агент сам оценивает актуальность по времени, expiresAt в v1 не нужен.
- Cron-событие включает timezone отдельным полем; scheduledAt и lastScheduledAt остаются в UTC. Для at отдельный timezone не требуется. Само cron-выражение доступно через tasks, а не дублируется в событии.

Приняты риски очереди в памяти: потеря ожидающих обращений и внутренних событий, потеря автоматического продолжения активного задания, частичное выполнение действий и возможные повторы при повторной доставке или повторном запросе.

Постоянная очередь с состояниями pending / processing / done обсуждалась, но не выбрана для первой версии. Правило о сохранении необработанных событий сверх срока истории не требует отдельного хранения очереди в БД в принятом варианте.

Предстоит определить жизненный цикл процессов Codex после сбоя контроллера, чтобы старый и новый исполнитель не работали одновременно. Поведение активного хода и точный механизм исполнения сохранённых отложенных задач ещё не определены.

## Правила агентов

- Для каждого бота один общий AGENTS.md. Локальных дополнений для чатов нет.
- Правила меняет только владелец через мастер-бота, а не администраторы или участники групп. Точный интерфейс пока не определён.
- Проверка владельца выполняется контроллером по Telegram user ID.
- Сжатие контекста не должно приводить к потере основных правил.
- Разрешения на генерацию изображений описываются в общем AGENTS.md бота.

Предлагается хранить правила и устойчивое состояние отдельно от контекста Codex и предоставлять их при восстановлении. Техническое обеспечение запрета генерации изображений, а не только текстовая инструкция, пока не проверено.

## История Telegram

Типичный сценарий:

```text
А: арбуз — это ягода!
Б: нет! Арбуз это овощ.
А: @БОТ, рассуди нас. Кто прав?
```

Агент получает обращение, определяет необходимость дополнительного контекста, загружает предшествующие сообщения и отвечает.

Предложенные пользователем инструменты:

### history(messageId, from, to)

Читает историю текущего чата относительно опорного messageId, позволяя загружать её постранично. Возвращает короткое представление: текст и несколько метаданных.

Принятая семантика (полный контракт, включая messageId=null и search, — в agent-contract.md):

- from и to — смещения по порядку сохранённых сообщений, а не арифметика Telegram message ID;
- интервал [from, to), опорное сообщение имеет смещение 0;
- результат отсортирован хронологически;
- отсутствующая или очищенная история обозначается явно.

```text
history(150, -20, 0)    // 20 сообщений перед опорным
history(150, -40, -20)  // предыдущая страница
history(150, 0, 10)     // опорное и следующие 9 сообщений
```

### read(...messageId)

Получает подробную информацию по одному или нескольким сообщениям. Агент вызывает его только когда короткой истории недостаточно.

Предлагаемый результат: полный сохранённый текст, форматирование, автор, сведения об ответе, кнопках и вложениях. Файлы предоставляются по необходимости; полный Telegram JSON не передаётся по умолчанию.

### Ограничения истории

История — локальный архив сообщений, полученных контроллером. Bot API не предоставляет произвольную загрузку старой переписки до подключения бота. Получение обычных сообщений группы и фильтрацию активации необходимо настроить отдельно.

Принято для первой версии:

- История хранится в БД только 30 дней, затем очищается.
- Лимит объёма не вводится: размер зависит от количества и активности чатов.
- Важно сохранять факт редактирования сообщения. Обсуждённый способ — текущая версия и время последнего редактирования edit_date, без накопления всех версий.

Точная точка отсчёта 30 дней и периодичность очистки пока не определены.

### Вложения и ответы на старые сообщения

Обсуждённые факты Telegram: сообщение содержит file_id и метаданные вложения, а не постоянную ссылку скачивания. getFile выдаёт путь для скачивания; ссылка действует не менее часа и может быть получена повторно. file_unique_id не подходит для скачивания.

Если пользователь отвечает на старое вложение, Telegram может включить исходное сообщение в reply_to_message вместе с file_id. Тогда файл можно получить даже после удаления старой записи из нашего архива. Это не гарантировано: поле исходного сообщения необязательное.

Предложения, пока не утверждённые отдельно:

- Не скачивать вложения автоматически; сохранять file_id и метаданные, скачивать по запросу агента.
- Старое сообщение из reply сохранять как вложенный контекст нового сообщения на срок хранения новой записи.
- Предусмотреть отдельную очистку скачанных файлов.

## Telegram-инструменты и управление

Агент должен поддерживать широкий набор полезных действий Bot API, включая rich-сообщения, вложения, кнопки, редактирование и обработку нажатий.

Принятый набор исходящих сообщений v1: текст, rich, фото, документ, видео, анимация, аудио, голосовое, стикер, геопозиция, место, контакт, опрос/викторина, дайс; также альбомы, пересылка и копирование. Видеокружки, Live Photo, отправка Live Location и нативные чеклисты отложены; счета, платные медиа и игры не включены. Агент сам выбирает встроенные rich-кнопки и/или нижнюю inline-клавиатуру. После альбома кнопки отправляются отдельным сообщением. Подробности — в [agent-contract.md](agent-contract.md).

Кнопки используют нативный callback_data формата [btnGroup]key либо key для повторяемого действия; в rich-разметке это атрибут data. Поле showCheckboxIcon исключено: контроллер меняет только явно добавленные агентом префиксы ☐/☑/☒. Вместо версий новый выбор получает новое имя группы; минутная блокировка защищает быстрые клики, сохранённое disabled — поздние. Контроллер не парсит исходный HTML/Markdown, а работает со структурированным ответом Telegram и адаптером блоков для редактирования.

Пермиты кнопок хранятся в БД как синтетическое permits у сообщения. Правила задаются точными callback_data или префиксами с одной конечной *, с приоритетом точного совпадения и самого длинного префикса. Массив userId ограничивает доступ, [] запрещает всем, null разрешает в рамках общей авторизации. В ЛС пермиты не используются. При редактировании кнопок в группе агент обязан передать актуальный полный объект permits; изменение только содержимого и автоматическая блокировка контроллером сохраняют права.

Редактирование v1 заменяет явно переданные компоненты целиком (текст/rich, подпись, медиа, нижнюю клавиатуру); отсутствующие сохраняются. Патчей фрагментов текста и отдельных rich-блоков нет. Группа может состоять из одной кнопки: [cancel]cancel принимается один раз и блокируется, без повторной активации агента.

Обсуждавшийся предварительный набор, кроме history и read:

- send — сообщения, rich-контент, вложения и кнопки;
- edit — изменение отправленного сообщения;
- schedule — отложенные события;
- agent_message — сообщение другому агенту.

Принят agent_message(agentId, text): асинхронная отправка в общую очередь целевого агента того же бота, без requestId/source, обязательного ответа и автоматического подтверждения исполнения. Входящее событие содержит type:agent_message, text и from с agentId; для группового агента дополнительно открыт chatId, для личного Telegram chatId/userId скрыты. Контроллер подтверждает непосредственного отправителя; это не доказательство одобрения текста пользователем. Ответ — отдельный явный вызов. Полный контракт — в [agent-contract.md](agent-contract.md).

agents() возвращает весь краткий список доступных личных и групповых агентов без пагинации. agent_info(...agentId) возвращает имя/username личного собеседника без его числовых Telegram ID либо подробности группы с chatId. Они заменяют ранее обсуждавшиеся chats()/chat(). Все агенты могут читать историю одобренных подключённых групп текущего бота через history/read/download с необязательным chatId. Личная история доступна только агенту её диалога. Для изоляции секретной группы создаётся отдельный бот. Личные сведения не копируются автоматически в общую wiki.

Уточнение: свой агент ЛС знает chatId и userId текущего собеседника; они скрываются от других агентов. history использует смещения по сохранённым сообщениям [from,to), с якорем messageId или null для позиции после последнего сообщения. search ищет по массиву подстрок text (все должны встретиться), автору, типам и датам; limit задаёт страницу, total не возвращается. Продолжение — подписанный непрозрачный курсор со сроком один час, без отдельного хранения поисковых сессий. Подробности — в [agent-contract.md](agent-contract.md).

Принята локальная память: одна заметка на агента/чат в БД, до 4 000 символов. note_get() читает её, note_set(text) заменяет целиком; чужую область инструментам указать нельзя. Хранятся часовые пояса, обращения и устойчивые сведения о собеседниках. Заметка не удаляется с 30-дневной историей, сохраняется до сброса/удаления агента и не включается автоматически в каждый ход. Она не заменяет AGENTS.md и не меняет права. Файловая память и контейнеры для этого не используются; timezone бота по умолчанию остаётся настройкой контроллера.

Принят пакетный download: files содержит messageId и fileId (из Telegram file_id); необязательный chatId общий для вызова. Контроллер проверяет доступ к сохранённому сообщению и ищет fileId только среди его файловых объектов, включая rich и reply. Для вложенного/пересланного оригинала указывается messageId внешнего сохранённого сообщения, не внутренний ID источника. Доступ к групповой истории включает скачивание вложений соседних групп того же бота; чужие ЛС недоступны. Кеш не отменяет проверки прав.

Скачивание выполняет контроллер; Telegram-токены и содержащие их URL не выдаются агентам. file_id привязан к конкретному боту, но Telegram не разграничивает агентов внутри него. Файловый доступ изолируется песочницей, без контейнеров: чужие временные файлы ЛС, сессии и секреты недоступны. Общая wiki сохраняет RW-доступ. Кеш до суток от завершения загрузки без продления; повторные/одновременные запросы не скачивают файл заново, но каждый вызов проверяет права. Реальные границы песочницы потребуется проверить при реализации.

Отправка локальных файлов в v1 — multipart/form-data. Агент передаёт attach://имя и uploads (имя → локальный путь); контроллер проверяет пути и формирует загрузку без парсинга rich-разметки. uploads не сохраняется в записи сообщения БД; сохраняются файловые идентификаторы и структура, возвращённые Telegram. Исходники не удаляются после успеха: временные generated-файлы живут не более суток без продления, долгосрочные копируются в wiki. HTTPS-публикация отложена, её контракт прозрачен агенту; для доступа нужен непредсказуемый истекающий токен, multipart сохраняется как запасной транспорт.

Принят единый send для одиночного сообщения и альбома: контроллер выбирает метод Telegram по полю содержимого, media верхнего уровня означает альбом, rich_message.media — вложения одного rich. Успех всегда возвращает messageIds массивом. Альбом не принимает кнопки/permits. Повторная отправка через file_id требует file_sources с доступными messageId/fileId и необязательным chatId, как download. Неопределённый результат доставки — delivery_unknown, без автоматического повтора.

Точные схемы пока не утверждены. Предлагается автоматически определять текущего агента и чат, чтобы не повторять их в аргументах. Callback следует быстро подтверждать на уровне контроллера, а выбранное действие передавать агенту через очередь.

Владелец должен иметь возможность в ЛС получить список агентов, отправить сообщение выбранному агенту, изменить настройки и синхронизировать wiki. Точные команды не определены.

Inline-вызов бота отложен за пределы v1 как отдельная тема. В v1 inline_query/chosen_inline_result не запускают агентов; кнопки inline-клавиатуры с callback продолжают поддерживаться. Маршрутизация, авторизация и публикация результатов инлайн-запросов будут обсуждаться в следующих версиях.

## Wiki: первая версия

Основа — подход [LLM Wiki](https://gist.githubusercontent.com/karpathy/442a6bf555914893e9891c11519de94f/raw/ac46de1ad27f92b28ac95459c782c07f6b8c964a/llm-wiki.md): агент постепенно поддерживает связанную файловую базу знаний.

Принятые решения:

- У каждого бота одна wiki; все агенты этого бота имеют RW-доступ к ней через файловую систему. Wiki других ботов недоступны.
- Разделы с отдельными правами R / RW / без доступа откладываются за пределы первой версии.
- raw/ отсутствует: основной источник информации — Telegram.
- log.md отсутствует: историю изменений хранит Git.
- Защита от параллельного редактирования в первой версии отсутствует.

Принятая структура v1:

```text
wiki/
  index.md
  topics/
  attachments/
```

Агент использует файловые инструменты Codex для поиска, чтения и изменения материалов. Если файловый доступ окажется непригодным, допустим доступ через специальный инструмент.

Процедуры описываются в инструкциях агенту и выполняются штатными файловыми инструментами Codex, без отдельных API:

- ingest — извлечь знания из сообщений, указать источник, обновить статьи, индекс и ссылки;
- query — найти материалы и ответить с указанием источников;
- lint — проверить ссылки, противоречия и дублирование.

index.md — краткая карта знаний со ссылками; topics/ — тематические статьи со взаимными ссылками; attachments/ — файлы для долгосрочного хранения. AGENTS.md бота остаётся отдельно управляемой владельцем инструкцией, не общей RW-статьёй wiki.

Предлагается сохранять в статьях происхождение утверждений: ссылки на Telegram-сообщения либо chatId/messageId. После очистки архива источник может стать недоступен; политика сохранения важных источников пока не выбрана.

Знания wiki и сведения чатов доступны всем агентам того же бота и могут использоваться в его подключённых чатах. Для отдельной границы доступа создаётся другой бот.

## Git: первая версия

Агенту предоставляются две операции через контролируемые инструменты:

| Инструмент | Поведение |
| --- | --- |
| git_changes() | Неопубликованные коммиты строками и объект путь → статус всех незакоммиченных файлов, включая staged/unstaged/untracked |
| git_sync(message) | Коммит всех изменений wiki и обычный push в настроенную ветку |

Принятые границы:

- Pull отсутствует. При необходимости владелец синхронизирует репозиторий вручную.
- Автоматическое разрешение конфликтов отсутствует.
- Force push не используется.
- Если push не прошёл, локальный коммит сохраняется; следующий вызов повторяет отправку.
- git_sync добавляет все изменения wiki в индекс, включая новые файлы и удаления. Ответ компактный: commit — строка «SHA + сообщение» либо null, push — completed/failed/skipped; при отказе добавляются error и английское description. При ошибке commit push пропускается.
- Один коммит может включать изменения разных агентов.
- Параллельные правки могут перезаписать друг друга; это принятое ограничение первой версии.

Предлагается фиксировать репозиторий, ветку и remote в настройках контроллера, не предоставляя произвольные аргументы Git. Токен Git хранится у контроллера. Если изменений нет, git_sync отправляет существующие неопубликованные коммиты, если они есть.

Fetch в v1 отсутствует. Список неопубликованных коммитов опирается на последнее известное состояние отслеживаемой remote-ветки. Push остаётся обычным, сервер может отклонить его при расхождении истории; синхронизация выполняется владельцем вручную. Полные примеры компактных ответов — в agent-contract.md.

## Codex и генерация изображений: что требует проверки

Не следует смешивать обычную авторизацию Codex через ChatGPT и preview-маршрут использования ChatGPT OAuth через публичный Responses API.

- [Документация встроенной генерации](https://learn.chatgpt.com/docs/image-generation) описывает расход лимитов Codex на изображения.
- [Preview-ограничения](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations) публичного маршрута включают отсутствие генерации изображений и ряда hosted-инструментов. Этот маршрут не подходит для обязательного требования проекта.
- [Документация подключения планов пользователей](https://developers.openai.com/siwc/token-sharing-open-source) не подтверждает автоматически доступность массового сервиса на чужом сервере; для удалённо размещённых или платных приложений указана отдельная заявка.
- [Self-hosted VMs](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) описывает перенос авторизации для собственного удалённого исполнителя.

Критическая проверка: обычный Codex App Server на сервере с ChatGPT-авторизацией вызывает встроенную генерацию изображения, сохраняет результат и предоставляет его для отправки в Telegram. Проверка ещё не выполнена. Нельзя считать эту связку подтверждённой только на основании доступности генерации в других клиентах Codex.

## Дополнения: принятые решения

Приняты ответы планировщика: schedule → {taskId}; tasks(taskIds) возвращает записи либо поэлементный task_not_found с английским description в порядке запроса. cancel_tasks отсутствующего taskId безопасно возвращает cancelled; удалённые задачи не хранятся ради различения причин отсутствия.

Закрыт вопрос метаданных участников: сведения отправителя сохраняются в самих сообщениях и удаляются с 30-дневной историей, отдельного постоянного справочника нет. Предпочтительные обращения и часовые пояса — в локальной заметке. Notes группы живёт, пока бот находится в подключённой группе, и удаляется при выходе вместе с диалогом. Тип отправителя (пользователь/чат) агент учитывает по переданным полям.

Приняты ответы простых инструментов: note_get → {text}, без заметки пустая строка; note_set → status:saved; pin/unpin/react/delete → status:completed после успешного ответа. delete принимает messageIds и действует в текущем чате; ответ не гарантирует поэлементное удаление отсутствовавших сообщений. Ошибки по общему контракту.

Принят результат edit: messageId и updated для подтверждённых компонентов; при частичном отказе failed, при неизвестном исходе unknown, плюс error и английское description. Агент может исправить только отклонённую часть, неизвестный исход не означает неуспех. Компоненты по-прежнему заменяются целиком.

Принят time() без аргументов: {"now":"2026-10-04T15:42:10Z"}, текущее системное время сервера в UTC. Timezone остаётся в инструкциях/заметке, не дублируется в ответе инструмента.

Принято отсутствие сообщений: read/download возвращают поэлементный message_not_found с английским description, не прерывая остальной пакет; history с отсутствующим явным якорем возвращает ошибку без перехода к последним сообщениям. Причины «никогда не сохранялось» и «истекло хранение» не различаются без данных. Проверка доступа сохраняется и не раскрывает чужие чаты.

Принят ответ agent_message: {"status":"queued"} подтверждает только локальную постановку в очередь, без ожидания чтения/исполнения. Недоступный адресат возвращает agent_unavailable с английским description. Асинхронное событие ошибки обязательно содержит agentId пострадавшего агента; формат agent_error описан в agent-contract.md, без requestId и раскрытия личных Telegram ID.

Приняты правки входящих сообщений: ожидающее сообщение обновляется в очереди; для уже переданного в активный основной ход создаётся одно message_edited с актуальным сокращённым содержимым и editDate. Повторные правки обновляют ожидающее уведомление; после его передачи новые уведомления по тому же сообщению в рамках хода не создаются. Громкий режим не продлевается, правка после завершения хода сама агента не запускает. message_deleted в v1 отсутствует: обычный Bot API не сообщает пользовательские удаления. Удаления контроллером обновляют БД по подтверждённому результату, внешние удаления могут оставаться в истории до очистки.

Принято управление расписанием через /tasks текущего чата без агента: одна rich-карточка, список по 10 задач и подробности с возвратом на ту же страницу. Описание в списке до 100 символов; инструкция отображается до 6 000, вся служебная карточка — до 8 000 Unicode code points с пометкой сокращения, без изменения задания в БД. Пагинация инструкции отложена. Действия доступны manager/admin/владельцу в группе, собеседнику/владельцу в ЛС; проверка при каждом нажатии. Изменение задачи — удалить и создать; успешная одноразовая задача удаляется. Удаление отменяет ожидания и блокирует карточку, но не прерывает активный ход.

Принята семантика расписания v1: completed основного хода подтверждает все переданные срабатывания; failed/interrupted оставляет их невыполненными, даже если отдельное действие уже сделано. complete_tasks() отложен в v2. Пока taskId обрабатывается, новые cron-срабатывания копятся вне общей очереди и могут попасть в неё только после окончания попытки; другие события могут передаваться через steer, если проверка runtime подтвердит это. Если агент занят другой задачей, cron копится в общей очереди с объединением по taskId. Четыре накопленных срабатывания означают occurrences=4, то есть одно текущее и три дополнительных пропуска.

Принят простой отказ при техническом сбое основного агента: контроллер напрямую сообщает ошибку в текущий чат, прекращает индикатор и очищает очередь; обычную пачку не повторяет. Отправители потерянных межагентских сообщений получают события о сбое без подтверждений доставки. Срабатывания расписания — исключение: сохраняются до успешной обработки и после сбоя считаются пропущенными даже при частично выполненном действии. Риск дубликатов принят в v1. Одна обновляемая карточка на taskId в исходном чате, «Пропущено N срабатываний с {дата}», кнопки повтора/отмены; повтор имеет retry=true. Уже ожидающее/выполняющееся событие не дублируется, успешная обработка меняет кнопки на неактивную «Обработано». Cron может автоматически объединять пропуски со следующим срабатыванием; отмена удаляет задачу и ожидания без прерывания активного хода. Детали — в agent-contract.md.

Принят простой вход: JSON-массив событий без обёртки, одинаковый для start/steer. Служебные инструкции контроллера, полный AGENTS.md, сведения текущего чата и defaultTimezone передаются отдельно через developerInstructions при создании/восстановлении сессии; baseInstructions штатные. Исходный текст хранится независимо от сжатия; сохранность после compaction и замена при обновлении требуют проверки runtime. Системное время доступно агенту через инструмент, now в каждой пачке не передаётся. История, заметка и wiki читаются по необходимости.

Вопрос служебных событий и прав доступа закрыт для v1: события обновляют состояние без запуска агента; удаление бота/отзыв доступа прекращает работу чата; автоматических приветствий нет. Владелец сервиса из конфига создаёт ботов; роли user/manager/admin действуют отдельно для каждого бота. Неавторизованные ЛС молча игнорируются, заявок нет. Проверки выполняет контроллер; роли приложения не заменяют права Telegram-группы. pin/unpin действуют в текущем чате, в agent_info доступно одно pinned_message; полный список закреплений не ведём.

Принято пожелание к индикаторам: typing означает занятость основного агента и накопление очереди; upload_photo — генерацию изображения при доступном для новых сообщений основном агенте; отсутствие статуса — доступность агента. Занятость имеет приоритет. Генерация у субагента может влиять на индикатор как исключение. Возможность steer во время wait/генерации, события возобновления, генерация через серверный App Server с подпиской и наблюдение дочерней генерации требуют экспериментов; сценарии записаны в agent-contract.md. Желаемое поведение пока не считается технически подтверждённым.

Приняты реакции: react ставит/снимает реакцию только в текущем чате; available_reactions доступен через agent_info. Наблюдаемые реакции обновляют БД без запуска агента и без продления срока истории. В read добавляется синтетический reactions с нативными counts, countsComplete, известными users, собственной own и updatedAt. Отсутствие сведений не означает отсутствие реакций. Получение событий реакций требует администратора и явного allowed_updates. Подробный контракт и примеры находятся в agent-contract.md.

Приняты два лимита длины: краткий текст сообщения — 1 000 Unicode code points с truncated=true при обрезании; agent_message — 8 000, превышение отклоняется без обрезания. Количества сообщений history/read/search и файлов download не ограничиваются дополнительными жёсткими лимитами приложения: умеренные размеры запросов задаются рекомендациями в инструкции агенту, а агент выбирает загрузку целиком или частями по задаче.

Приняты правила результатов инструментов: успех без обязательной обёртки; каждая ошибка имеет error и обязательное английское description с причиной и следующим шагом. Пакетные чтение/скачивание возвращают результаты поэлементно. Частичный edit сообщает updated/failed/unknown; схема определена в agent-contract.md. delivery_unknown не допускает автоматической повторной отправки. Подробности и примеры находятся в agent-contract.md.

Приняты forward и copy: источник задаётся необязательным chatId, назначение всегда текущий чат агента; messageIds — массив 1–100 ID. Проверяется разрешённость исходного чата, наличие сообщений в локальной истории не требуется. Допустим текущий чат или подключённая одобренная группа того же бота; чужие ЛС запрещены. Поддерживаются альбомы и частичный результат пакетных операций. copy одного сообщения позволяет заменить подпись и добавить кнопки с permits. Полный контракт и примеры находятся в agent-contract.md.

Список оставшихся решений и необходимых проверок приведён в [contract-review.md](contract-review.md). Основной источник подробного контракта — [agent-contract.md](agent-contract.md); каталог message-events.md показывает варианты содержимого и не расширяет область v1.

## Плоский короткий формат, 2026-10-05

Принята плоская структура без content/messageType. Общие поля: eventType, messageId, date, editDate?, from, replyTo?, inlineButtons?. Содержимое определяется по textPlain/richPlain/document/photo/location и другим принятым полям каталога. Для подписи используется captionPlain; текстовые поля ограничены 1 000 code points с truncated=true только при обрезании, hasEntities — наличие исходных entities. richButtons обозначает встроенные кнопки, richAttachments хранит количества по типам. albumId сохранён; координаты location — строка, live — отдельный признак. Остальные типы и примеры зафиксированы в message-events.md. Это заменяет ранее обсуждавшиеся объект content и plainText.

## Хранение Message и полный read, 2026-10-05

Согласовано хранить принятый Message близко к оригиналу, включая исходные timestamp, форматирование, все варианты фото/thumbnails и метаданные файлов. Короткий вид и read — проекции, не причина удалять данные из БД. read возвращает messages в порядке запроса: нативное сообщение при успехе либо messageId/error/английское description. Даты отправки/редактирования выдаются строками, длительности и остальные нативные числа сохраняются. Полные reply, пересылки, rich, кнопки и служебные данные доступны по принятой политике; внешний chat скрыт. sender_boost_count/effect_id/is_from_offline/sender_tag/suggested_post_info хранятся, но не выдаются. Неподдерживаемые маршруты отклоняются целиком, не маскируются удалением их полей. Синтетические permits, состояния выбора и известные реакции добавляет контроллер. Полный перечень — в agent-contract.md.

## Отправитель короткого сообщения, 2026-10-05

Принят единый from: {userId,name,username?} либо {chatId,name,username?}. sender_chat приоритетен, скрытая личность не угадывается; неизвестный from опускается. authorSignature передаёт известную подпись без подтверждения личности. ID автора-чата не даёт права читать его историю. Полный read сохраняет нативные поля Telegram. Короткие примеры обновлены с id на userId.

## Уточнение send/edit и кнопок, 2026-10-05

Приняты Telegram-подобные аргументы send с одним вариантом содержимого и оболочками location/venue/contact/dice/poll. Оформление parse_mode и entities/caption_entities взаимоисключающее. media — альбом в send, один объект замены в edit. Универсальный edit v1 не включает геопозицию и специальные действия опросов. Отдельный buttonSelections не нужен; закрытые группы остаются внутренним состоянием контроллера. При замене rich с итоговыми кнопками нужен полный permits, без итоговых кнопок не нужен; оставшаяся нижняя клавиатура также считается. Отсутствие permits в rich-edit не открывает общий доступ. Проверку условия без парсера rich ещё нужно технически определить.

## Окончательное уточнение edit и permits, 2026-10-05

Это решение заменяет прежнее обязательное наличие permits при rich-edit: если permits не передан, он сохраняется; агент отвечает за актуальность правил обеих разновидностей кнопок. Контроллер проверяет callback, но не парсит rich для проверки необходимости обновления. Риск старых правил принят в v1. edit сохраняет тип (текст→текст, rich→rich, фото→фото и т. д.). Оформление заменяется вместе с текстом/подписью. При замене media без caption прежняя подпись и entities сохраняются, пустая подпись удаляет её. Одновременные совместимые изменения возвращают частичные результаты по общему контракту; переходы типов, геопозиция и специальные действия опросов не включаются.

## Подробности диалогов и участников, 2026-10-05

Приняты agent_info({agentIds}) → {agents:[...]} и members({userIds}) → {members:[...]} с порядком запроса и независимыми ошибками элементов. Личные ID других диалогов скрыты. Групповые сведения включают chatId, описание, число участников, статус бота, известное закрепление и разрешённые реакции; ошибка обновления не выдаётся как неполный разрешающий ответ. members работает только в текущей группе, возвращает имя/username/Telegram-статус/известный титул и временный untilDate; без ID полный список не запрашивается. Отдельные права участников в v1 не выдаются. Полные схемы — в agent-contract.md.

## Упрощение администрирования и уведомлений

Последние решения заменяют прежние предложения административных кнопок/rich-карточек: одна команда — одно действие и текстовый ответ, /rules возвращает файл, /set_rules требует reply на файл. /delete_bot без ID показывает сведения и полные команды; с проверочным BOT_ID оставляет wiki, с BOT_ID all удаляет всё. /users, /agents, /tasks имеют аргумент диапазона, например 11-20. Отключение ЛС-агента удаляет его данные и останавливает его, сохраняя роль; новое сообщение создаёт агента заново. Сбой задачи уведомляется текстом в её чате; cron — только первый сбой, без новых сообщений при накоплении до успешной обработки. После успеха следующий сбой снова допускает уведомление. Подробности в agent-contract.md; прежняя карточка задач исключена из v1.


## Уточнение команд остановки — 2026-10-06

Принято /stop_agent вместо /disable_agent с прежним поведением: в группе бот выходит и удаляет данные диалога; в ЛС данные диалога удаляются, роль сохраняется, следующее сообщение авторизованного пользователя создаёт агента заново. Ответ команды явно сообщает об удалении данных. /pause_agent не вводится. Временная пауза всего бота называлась бы /pause_bot, но в v1 она и команда возобновления не нужны; прежние /disable_bot и /enable_bot исключены из v1.


## Рабочие файлы и настройка Git — 2026-10-06

Приняты собственная директория каждого бота сразу, опциональный Git и организация LLM Wiki владельцем. В ЛС владельца доступны /ls, /cat, /download, /upload, /rm без подтверждения, /mv с двумя code entities, /edit с путём code и содержимым pre, /git_changes, /git_sync и /git_setup [branch [remoteUrl [token]]]. /git_setup без аргументов показывает настройки без токена; с веткой выполняет fetch и принудительное восстановление remote-ветки с потерей локальных изменений и неопубликованных коммитов. Прежние URL/token используются для пропущенных аргументов. Проверка remote до изменения, сохранение настроек после успеха, приостановка агентов и уведомление об обновлении директории приняты. Токен исключается из истории приложения, агентского входа и логов, хранится вне рабочей директории. Агентские Git-инструменты не выполняют fetch и возвращают git_not_configured с английским description, если Git не настроен. Полные правила в agent-contract.md.


## Восстановление после перезапуска — 2026-10-06

Принято: обычная очередь теряется, контексты возобновляются при следующем событии, прерванные попытки расписания считаются невыполненными, сохранённые срабатывания и счётчики восстанавливаются без создания новых задач. Cron за время остановки пропускается. Повтор внешнего действия при сбое до записи успеха допустим в v1. Одновременно работает один контроллер для БД; подключения старых процессов агентов после перезапуска недействительны, новый контроллер возобновляет контексты новым процессом. Полные правила в agent-contract.md.


## Временные файлы и ежедневная очистка — 2026-10-06

Принята структура .temp/<agentId>/upload и download внутри рабочей директории бота, с произвольными дополнительными временными поддиректориями агента. Возраст всех временных файлов определяется mtime. Одна задача раз в сутки удаляет историю старше 30 дней и временные файлы старше 24 часов; ошибки удаления объединяет в уведомление владельцу. Точный предел 24 часа не гарантируется: при ежедневной очистке файл может храниться до 48 часов после mtime. .temp исключается из Git, сохраняется при /git_setup, remote с .temp отклоняется. Собственная временная директория доступна агенту RW, соседние групповые вложения размещаются в директории запрашивающего агента без открытия чужих приватных файлов. Владелец имеет доступ через файловые команды. Отсчёт возраста истории принят 2026-10-07: от первого получения контроллером без продления редактированием.


## Ручная очистка временных файлов — 2026-10-06

Принята /cleanup_temp только для владельца в ЛС дочернему боту: повторная очистка .temp по актуальному mtime старше 24 часов без очистки истории. Ошибки автоматической очистки отправляются в ЛС владельцу соответствующим ботом со всеми оставшимися устаревшими файлами, причинами и предложениями /cleanup_temp или /rm путь. Длинный отчёт по уточнению 2026-10-07 обрезается с отметкой, без файла. Ручной запуск отвечает напрямую без дублирующего уведомления.


## Актуальные роли — 2026-10-06

Принято наследование user → manager → admin → owner. Manager включает ЛС и личные задачи user, подключение групп и управление групповыми задачами. Admin может все команды своего бота, кроме назначения/снятия admin и изменения owner, включая правила, файлы, Git, остановку агентов и /leave. Owner имеет все права своего бота. Мастер только для владельца сервиса. Актуальная матрица в [access-and-commands.md](access-and-commands.md); прежние ограничения owner-only заменены. Приватность чужих ЛС сохраняется.


## Каналы и пассивные супергруппы — 2026-10-07

Модель и принятые расширения вынесены в [channels-and-discussions.md](channels-and-discussions.md). Все агенты своего бота читают пассивные чаты и могут писать/изменять в них, но не в чужом чате с агентом. Manager/admin/owner подключают каналы/супергруппы. Форумы запрещены; миграция обычной группы по-прежнему приводит к выходу и очистке. Приняты chats/chat_info и /chats, /leave_chat. Search/history с discussion:{chatId,messageId} выбирают обсуждение по источнику автоматически пересланной публикации и цепочкам replies, а не текущей привязке. Полнота 30-дневной истории не гарантируется. Кнопки и команды в пассивных чатах не запускают агента; уведомления о потере доступа не отправляются. Rich-кнопки при пересылке disabled по проверке пользователя.


## Выбор модели — 2026-10-07

Приняты /get_model [agentId], /set_model MODEL [agentId], /get_model default, /set_model MODEL default и /models, только admin/owner. Без ID текущий агент, адресный ID только того же бота. Default влияет только на новых агентов. Смена занятого применяется со следующего хода; текущая и ожидающая модели отображаются отдельно. Настройка хранится в БД, контекст сохраняется, командой ход не запускается и не прерывается. Полные правила в agent-contract.md.


## Ограниченная очередь и межагентный журнал — 2026-10-07

Приняты громкий режим до 2 минут/10 обычных сообщений с обновлением по прямым триггерам и очередь до 10 ожидающих событий чата, включая редактирования/callback. При переполнении сообщения остаются в истории, агент получает краткий счётчик пропусков; callback отклоняется без фиксации выбора. Межагентные и планировщик в лимит не входят. Agent_message без ограничения частоты, принятый текст журналируется 7 дней без повторной доставки. /agent_messages AGENT_ID [FROM-TO] или одна позиция доступны admin/owner, выдача от новых к старым, по умолчанию 10, длинный текст обрезается с отметкой без файла. Полные правила в agent-contract.md.


## Срок истории — 2026-10-07

30 дней считаются от первого получения сообщения контроллером; Telegram date/editDate используются отдельно для поиска и отображения. Редактирование и повторное получение срок не продлевают. Вложенный reply хранится по сроку внешней записи независимо от возраста оригинала, не восстанавливая отдельную историю оригинала. Очистка раз в сутки.


## Библиотека расписаний — 2026-10-07

Выбран croner для Node.js, для cron и одноразовых at. Приняты пять cron-полей, IANA timezone, OR дня месяца/недели и явное AND через +, календарные расширения, пропуск DST gap и один запуск при DST overlap. Callback регистрирует срабатывание; БД/очередь/накопление и восстановление контролирует приложение. Просроченный at после перезапуска ставится в очередь самим контроллером. Конкретная версия и DST-проверки — при реализации. Полный контракт в agent-contract.md.


## Порядок сборки альбомов — 2026-10-07

Альбом готов после 1 секунды без новых элементов, максимум через 3 секунды от первого, и только тогда ставится в очередь. Обычные сообщения его не ждут; служебных подсказок и специальных инструкций нет. Для очереди и громкого режима готовый альбом считается одним событием. Громкий режим проверяется при готовности; истёкшее во время сборки окно не сохраняется по первому фото. Без собственного прямого триггера такой альбом только сохраняется.


## Компактные служебные ответы — 2026-10-07

Принято обрезать длинные текстовые служебные ответы до одного сообщения с отметкой, включая отчёт очистки; писать компактно. Файл отчёта не отправляется. /rules и /download остаются файловыми командами, /cat при превышении размера предлагает /download.


## Entities служебных ответов — 2026-10-07

Принято минимальное оформление (pre для файла, code для команд/путей), корректировка entities при обрезке с учётом UTF-16 и правил вложенности Telegram. Отдельный лимит количества entities в v1 не вводится; официальное числовое ограничение не подтверждено текущей проверкой Bot API.


## Пользовательские MCP — 2026-10-07

Пользовательские MCP, команды подключения, авторизация Bearer/OAuth и настройки MCP отдельных агентов отложены за пределы v1. Наши контроллерные инструменты сохраняются; это не запрет их реализации через MCP.
