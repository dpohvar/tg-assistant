# План реализации Telegram Assistant v1

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. Делегирование этим планом не предписывается.

**Goal:** Реализовать контроллер Telegram-ботов с агентами Codex по согласованному контракту v1.

**Architecture:** Один процесс Node принимает Telegram updates, хранит данные в SQLite и управляет Codex app-server через JSON-RPC stdio. Контроллер проверяет полномочия инструментов; Codex применяет файловую/сетевую песочницу. События чатов находятся в RAM, задачи и результаты их попыток — в БД.

**Tech Stack:** Предлагаемые технические решения: JavaScript ESM, Node 24, встроенные fetch и node:test; SQLite через небольшой адаптер node:sqlite; Croner 10.0.1 и Temporal polyfill 0.5.1; Codex 0.159.3. Node 24.18.1 проверен на Alpine-стенде. node:sqlite в этой ветке ещё experimental: драйвер скрыт за storage-адаптером, его пригодность проверяется первым этапом. Telegram SDK не требуется: прямой клиент нужен для rich и новых полей API.

**Spec:** [Контракт](../../agent-contract.md), [события](../../message-events.md), [команды](../../access-and-commands.md), [каналы](../../channels-and-discussions.md). Более поздние принятые уточнения имеют приоритет над историческими предложениями. Этот план не меняет продуктовый контракт.

## Global Constraints

- Один аккаунт ChatGPT, авторизация на сервере через Codex CLI. Мастер-бот без агента, доступен только владельцу сервиса.
- Бот — граница изоляции; общая RW wiki; чужие ЛС и чужие временные каталоги закрыты.
- 10 ожидающих событий чата; межагентные события и расписание вне лимита. Очередь не восстанавливается из истории после рестарта.
- История 30 дней от первого получения; межагентный журнал 7 дней; temp и служебные исходники изображений старше 24 часов по mtime очищаются раз в сутки.
- Громкий режим 2 минуты/10 сообщений; альбом 1 секунда тишины, максимум 3 секунды, одно событие.
- Cron — пять полей с IANA timezone; at — ISO с явным смещением. Только проверенный UTC/Temporal-адаптер, без нативного DST-планирования Croner.
- Обычные группы и ЛС имеют агента; нефорумные супергруппы и каналы пассивны. Форумы запрещены.
- Git опционален. Агентские операции без fetch/pull/force push; .temp всегда исключена.
- Без пользовательских MCP, inline-вызова, маршрутов, контейнеров как границы агентов и complete_tasks в v1.
- Linux — сервер; Windows — отладка. Нельзя заменять ограниченный профиль Codex полным доступом ради прохождения проверки.

## Review Focus

1. Сбой после успешного Telegram-действия: вернуть известный результат со storage_failed, не повторять запрос (этап 4).
2. Старый thread после force/restart не может выполнять действия от имени нового запуска (этапы 2 и 7).
3. Совпадающие messageId разных чатов не смешивают историю и полномочия (этапы 1 и 3).
4. Callback при заполненной очереди не закрывает группу кнопок и не занимает место (этап 4).
5. Пропущенные cron-срабатывания при живом сервере и во время остановки учитываются по разным правилам (этап 6).


## Схема данных

Предлагается одна SQLite БД, foreign_keys=ON, WAL; миграции по версии. Индексы/секреты не располагаются в wiki. Не хранить все необработанные updates бессрочно.

| Таблица | Ключ и основные данные |
|---|---|
| bots | botId; Telegram bot ID/username, ownerId, rulesVersion, defaultModel, ссылка на секрет |
| roles | (botId,userId); user/manager/admin, owner определяется bots |
| chats | (botId,chatId); chatType, доступ/права, описание, linkedChatId, известные сведения |
| agents | agentId; botId/chatId unique, model, threadId, threadRulesVersion, notes, lifecycle |
| messages | (botId,chatId,messageId); receivedAt, date/editDate, нормализованный полный JSON, текст для поиска, автор, reply, forward_origin |
| button_state | ключ сообщения; permits и закрытые группы, срок привязан к сообщению |
| agent_messages | ID журнала; botId/fromAgentId/toAgentId, date, text; очистка через 7 дней |
| tasks | taskId; agentId, description/text, at либо cron/timezone, createdAt, признак уведомлённого сбоя |
| task_firings | taskId + внутренний ID попытки; scheduledAt, последние накопленные срабатывания, счётчик, pending/processing/failed |
| generated_images | зарегистрированный путь; botId/agentId/threadId, источник нативного события; очистка mtime |
| git_settings | botId; branch/remote, ссылка на секрет; токен вне .git/config |
| polling_offsets | botId; Telegram offset; не является журналом заданий |
| schema_migrations | версия и дата |

Индексы: messages по bot/chat/date/messageId, receivedAt, senderId, replyTo; источник автоматической пересылки по channelId/postId; task_firings по taskId/status. Telegram edits изменяют сохранённое сообщение без продления receivedAt. Внутренние номера попыток не добавляются в согласованные события агента. Кеш download восстанавливается по имеющимся файлам; uploads не сохраняется в БД.

## Интерфейсы модулей

Внутренние интерфейсы не меняют публичные имена инструментов.

```js
// scope создаёт контроллер, аргументы модели его не заменяют.
// generation — поколение запуска; controllerId — текущий экземпляр процесса.
const scope = { botId, agentId, chatId, threadId, generation, controllerId };
await telegram.call(botId, method, args);             // объект Bot API result
await codex.request(method, params);                  // JSON-RPC result
queue.enqueue(agentId, event, source);                // accepted | full
await tools.invoke(scope, name, args);                // контрактный JSON результата
await access.assertRead(scope, targetChatId);
await access.assertWrite(scope, targetChatId);
await lifecycle.assertCurrent(scope);                 // перед внешним действием
```

DB transaction синхронна; не держать её во время сетевого await. Все операции используют botId из scope, а не ищут глобально по одному messageId/fileId. Clock внедряется для тестов; инструмент текущего времени отдаёт UTC ISO.

## Выполнение и приёмка

Каждый этап: сначала предметные проверки его риска, затем минимальная реализация, unit/integration gate, сверка с контрактом и ограниченная живая проверка только затронутого поведения. Примеры выше — конкретные assertions, fixture создаётся рядом с тестом; это не тесты, уже существующие в репозитории. В тестах token передаётся отдельно, raw HTTP URL/CLI auth не пишутся в отчёт.

Команды проекта после этапа 1: `npm test` для unit/integration; `npm run test:live -- <scenario>` для явно выбранного bounded сценария. Общий fake suite не считается Telegram/Codex приёмкой. Коммиты и push выполнять только при отдельном разрешении пользователя; план не авторизует публикацию.

Порядок зависимостей: 1 → 2 → 3 → 4 → 5 → 6 → 7 → 8. Первый пользовательский результат — после этапа 2; полный сценарий с картинкой — после этапа 5. Начинать с этапа 1, а не со всей матрицы команд.
