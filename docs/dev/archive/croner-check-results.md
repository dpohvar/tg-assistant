# Проверка Croner — 2026-10-07

Проверена точная версия **10.0.1**, зафиксированная в `tools/croner-check/package-lock.json`. Среды: Windows / Node 26.8.2 и WSL Ubuntu / Node 22.20.0. Alpine не проверен. Это проверка доверенной библиотеки контроллера, без запуска агента; агентская песочница здесь не участвует.

## Результат

Основной набор: **10 успешных, 2 неуспешных проверки** в обеих средах. Итоговый совместный запуск с диагностикой: **13 успешных, 4 неуспешных из 17**; четыре неуспешных проверки относятся к двум проблемам DST. Подтверждены пять полей с минутной точностью, валидация, диапазоны/шаги, выходные, имена дней, воскресенье 0/7, OR и явное +AND, L/#/W, високосные даты, IANA timezone, одноразовый Date с Z/offset, отмена таймера, пропуск прошедших cron после пересоздания и новые срабатывания при незавершённом async callback с protect:false.

Дополнительная диагностика воспроизвела расхождения ниже в обеих средах. Реальный одноразовый таймер и его отмена также прошли. DST моделировался встроенными Node mock timers: Date и setTimeout движутся шагами 30 секунд с освобождением event loop. Это не ожидание реального календарного перехода. Диагностические тесты содержат проверки отсутствия повторов и намеренно завершаются ошибкой на найденном дефекте.

## Несовпадения с принятыми правилами

1. **Весна: nextRun/nextRuns и таймер расходятся.** Для `30 3 * * *`, Asia/Nicosia, от `2026-03-28T23:00:00Z` следующий результат — `2026-03-29T01:30:00Z`, то есть 04:30 местного времени вместо отсутствующего 03:30. Фактический моделируемый таймер этот день пропустил и сработал 30 марта в 03:30. Аналогично America/New_York: отсутствующее 02:30 8 марта отображается как 03:30, но callback пропускается. Следовательно, нельзя без дополнительной проверки использовать nextRun как достоверное отображение следующего срабатывания.

2. **Осень: дата в прошлом и повторные callback.** Для `30 3 * * *`, Asia/Nicosia, от `2026-10-25T01:05:00Z` nextRun возвращает `2026-10-25T00:30:00Z` — раньше точки отсчёта. При запуске таймера в 00:45Z до перехода диагностика получила 60 лишних callback между 01:00:30Z и 01:30Z, затем одно правильное на следующий день. При запуске в 01:05Z после перехода — 50 лишних callback, затем правильное на следующий день. Число лишних вызовов относится к шагу моделирования 30 секунд, а не к гарантированной частоте на реальном сервере.

Отдельная попытка диагностики осеннего перехода New York застряла внутри продвижения mock timers и была остановлена. Она не считается завершённой проверкой; достаточно независимо воспроизведённого случая Nicosia.

Исходный код версии объясняет возможность повторов: расчёт происходит через локальные календарные поля, а `_checkTrigger` допускает callback, если вычисленная цель уже в прошлом, после чего снова планирует таймер. Это объяснение по коду, не проверка реальной частоты повторов. Источники: [Croner 10.0.1, croner.ts](https://github.com/Hexagon/croner/blob/10.0.1/src/croner.ts), [date.ts](https://github.com/Hexagon/croner/blob/10.0.1/src/date.ts).

## Следствие для проекта

**Нативный DST-механизм Croner 10.0.1 не прошёл проверку.** Ниже описан проверенный адаптер, сохраняющий библиотеку и согласованные правила. Исходники зависимости не исправлялись; её повторяющиеся таймеры с IANA timezone не используются.

Не проверены состояния БД, схлопывание очереди, счётчики пропусков и восстановление задач приложения: их реализации в репозитории ещё нет. Пересоздание библиотечного таймера не заменяет такую проверку.

## Повторение

В `tools/croner-check`: `npm ci --ignore-scripts`, затем `npm test` для адаптера. `npm run test:native` воспроизводит исходные дефекты и ожидаемо заканчивается ошибкой. Неуспешные DST assertions сохранены, а не заменены фактическим ошибочным поведением.

## Адаптер — принято после проверки, 2026-10-07

Использованы Croner **10.0.1** и `@js-temporal/polyfill` **0.5.1**, обе версии закреплены без диапазонов в package.json и lockfile. Экспериментальный код: [zoned-cron.mjs](../tools/croner-check/zoned-cron.mjs); проверки: [adapter.test.mjs](../tools/croner-check/adapter.test.mjs).

Алгоритм:

1. Croner с `timezone: UTC`, `mode: 5-part`, `paused: true` перебирает календарные кандидаты. UTC здесь временно кодирует локальные поля календаря, а не целевой момент исполнения.
2. Temporal переводит кандидата в часовой пояс задачи с `disambiguation: earlier`. Повторяющееся время сопоставляется первому наступлению.
3. Проверка обратного преобразования в локальные поля отсеивает несуществующее время: при весеннем переходе earlier сдвигает его назад, поэтому поля не совпадут. Кандидаты не позже абсолютной точки отсчёта тоже пропускаются.
4. Рассчитанный реальный момент передаётся Croner как одноразовый Date с `timezone: UTC`, `maxRuns: 1`. Перед регистрацией события вычисляется следующий момент от фактического текущего времени. Работа агента не ожидается.

Для at не нужен перебор календаря: абсолютный Date также запускается в UTC. Это сохраняет явно заданный offset/Z, в том числе второе наступление осеннего часа. Просроченный at восстанавливается контроллером по прежнему правилу, а не этой библиотекой.

Все пользователи расчёта следующего cron-срабатывания — таймер, список задач, восстановление после остановки — должны использовать один адаптер, а не прямой `Cron.nextRun` с IANA timezone. Счётчики пропусков и состояние выполняющейся задачи остаются обязанностью контроллера.

### Покрытие

Основные прежние регрессии сначала запущены на нативном Croner: 7 прошли, 9 не прошли из 16. После подключения адаптера все 16 прошли. Итоговый расширенный набор включает 38 проверок:

- Весенний/осенний переход Nicosia и New York, даты до первого наступления и после него, перезапуск во втором часе.
- Получасовые переходы Lord Howe; пропуск целой локальной даты Apia в 2011 году.
- Ежеминутные расписания и первый существующий момент после пропуска, отсутствие второго исполнения повторяющихся минут.
- Сравнение с независимым обходом реальных UTC-минут через Intl: семь окон переходов, три расписания в каждом, без Temporal-преобразования кандидатов в эталоне.
- Моделируемые таймеры в восьми окнах переходов; точное совпадение scheduledAt и времени callback, отсутствие лишних callback.
- Синтаксис L/#/W/+AND, OR, шаги, диапазоны, високосный день, обычные зоны, минутная граница.
- Отмена, незавершённый async callback, обработка ошибки callback, пропуск простоя при пересоздании, точный одноразовый UTC-момент во втором осеннем часе.

Итог: **38 из 38 проверок прошли на обеих платформах**, exit code 0. Проверка выполнялась на Windows / Node 26.8.2 и WSL Ubuntu / Node 22.20.0. Логи: `.runtime-check/adapter-red.txt`, `adapter-windows.txt`, `adapter-linux.txt`. DST проверен моделируемыми часами, не ожиданием реальных сезонных переходов. Ранее реальный одноразовый таймер Croner и отмена прошли отдельно.

### Границы результата

Адаптер остаётся изолированным прототипом: приложения и его БД/очереди в репозитории ещё нет. Alpine и полный интеграционный путь не проверены. Тесты покрывают перечисленные случаи, а не все исторические переходы всех зон. Данные часовых поясов предоставляет Intl среды исполнения; их актуальность и полнота на Alpine требуют отдельной проверки.

Поиск защищён от бесконечного перебора: после 10 000 отвергнутых календарных кандидатов возвращается явная ошибка, а не неверная дата. Это технический предохранитель прототипа; ошибка должна идти через обычный путь технического сбоя. В callback требуется быстро зарегистрировать событие; для ошибки предоставляется onError. Блокировки БД, схлопывание событий и восстановление незавершённых действий этим кодом не реализованы.
