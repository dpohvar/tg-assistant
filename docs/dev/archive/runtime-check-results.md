# Проверки Codex App Server — 2026-10-07

Проведены реальные запросы к Codex App Server 0.159.3 с CLI-авторизацией ChatGPT, без отдельного API-ключа. Модель по умолчанию в каталоге — gpt-6.1-sol. Пользовательская конфигурация Codex не изменялась; использован отдельный CODEX_HOME без пользовательских MCP, plugins и skills.

Среда проверки — Ubuntu в WSL, Linux musl-бинарник Codex. Основной сервер проекта будет Alpine Linux; нативный Windows используется для отладки. Это проверка Linux-профиля доступа и протокола, **не live-приёмка на Alpine**. Telegram не подключался.

## Песочница

Проверен именованный профиль tg-check с approval_policy=never. Он не расширяет :workspace, поскольку требуется ограничить и чтение. Доступ:

- :minimal — read для системных средств исполнения;
- рабочая директория текущего бота — write;
- её .temp — deny;
- более конкретная .temp/a1 — write;
- каталоги установленного Codex и Node — read;
- остальные файлы не открываются, включая контроллер, auth и sessions.

Сеть команд выключена. Встроенные web search и image generation при этом работали: их запросы выполняются отдельно от сетевого доступа shell-команд. Сетевая политика будущих дополнительных инструментов этим тестом не проверяется.

В WSL используется встроенный в пакет bubblewrap; App Server сообщил, что системный bwrap не найден и используется bundled fallback. Конфигурация профиля и canary сохраняются в локальных артефактах. На Alpine требуется проверить системные зависимости, user namespaces/seccomp и фактическое применение того же профиля на его ядре. Описание профилей и платформенного enforcement: [официальная документация](https://learn.chatgpt.com/docs/permissions).

Нативные Windows-пробы не прошли:

- unelevated отказался: restricted read требует elevated backend;
- elevated отказался: установленная версия требует effective :root read.

Широкое чтение для обхода отказа не включалось. Для отладки с проверенными Linux-границами доступен WSL; эквивалентность нативной Windows-песочницы не подтверждена.

## Следствия для контроллера

- Генерацию в фоне можно организовать через субагента и steerable wait. Простая прямая генерация не показала обработку новых сообщений до её завершения.
- Одного thread/status active/idle недостаточно: в ожидании субагента основной thread оставался active. Для открытия очереди нужны item/started и item/completed для wait, а для изображения — imageGeneration с привязкой дочернего thread к основному.
- Во время ожидания с генерацией возможен upload_photo; если основной обрабатывает новое сообщение, typing должен иметь приоритет. Это вывод для дальнейшего согласования реализации статусов, а не результат реальной отправки chat action в Telegram.
- Завершение субагента наблюдается до последующих item основного: статус можно включать по началу фактической работы основного, а не только по уведомлению о готовности субагента.
- Замена developerInstructions через resume не прошла проверку. Нельзя считать её рабочей на основании наличия поля в схеме. Создание нового thread с новой версией правил работает; способ сохранения нужного контекста при такой замене необходимо определить отдельно.

## Стенд и воспроизведение

[prepare-runtime-check.py](../tools/prepare-runtime-check.py) создаёт fixture, профиль и выполняет обязательную проверку файловых границ; при отказе не выдаёт passed. Опционально копирует CLI-auth в отдельный controller home с правами 0600. Путь источника задаётся оператором, токены не печатаются.

[codex-runtime-check.mjs](../tools/codex-runtime-check.mjs) запускает отдельный stdio App Server, проверяет gate перед inference, сохраняет RPC-события и результаты. Использует installed native tools, а не MCP-имитацию. Поддерживает catalog, sandbox, image, image-save, image-background, subagent, instructions, instructions-resume, instructions-resume-config, instructions-fresh, web. Для modes resume сначала нужен instructions; для image-save — файл предыдущего image-сценария.

Пример запуска на Linux с уже установленными Node и Codex:

```sh
python3 tools/prepare-runtime-check.py --root /absolute/check-root --codex /absolute/codex --node /absolute/node --auth-file /operator/codex-home/auth.json
node tools/codex-runtime-check.mjs image /absolute/codex /absolute/check-root/control-home /absolute/check-root/fixture/bot /absolute/check-root/results/image
```

Артефакты текущего запуска: .runtime-check/results/ в рабочей директории (исключены из Git). Содержат events.jsonl, report.json, timeline.json, эффективный профиль и PNG. Временная копия auth после проверок удаляется; исходная CLI-авторизация не изменяется.

На первоначальных запусках обнаружены ошибки стенда: синтаксис профиля, путь/наличие Node в PATH и слишком узкая текстовая инструкция для .upload. Они исправлены; итоговые успешные пробы выполнены после исправлений. Успех этих исправлений не распространяется на не прошедшую замену инструкций через resume.


## Уточнение: base64 и контекст агента

Повторная проверка исходных response_item показала, что агент сохранил результат генерации через code-mode store/load и сформировал apply_patch программно из переменной JavaScript. Сам модельный текст вызова exec с декодированием имел длину 371 символ; большой diff в уведомлении fileChange не равен объёму текста, написанного моделью.

Однако первый вызов генерации содержал if(!r.content) text(r). Реальный результат имел image_url, и агент вывел весь объект как текст. Code-mode обрезал вывод: сообщение предупреждало об исходных 431 135 токенах до обрезки; сохранённый результат custom_tool_call_output занимал около 40 тысяч символов, а не полные 1,7 МБ. Таким образом, в этом тесте часть base64 всё же попала в контекст из-за ненужного текстового вывода. Обработка байтов в JavaScript сама по себе этого не требует.

Последний запрос теста image имел 44 331 inputTokens; накопленные totalTokens=146 249 суммируют запросы хода и не являются размером одного текущего контекста. Эти числа включают инструкции, инструменты и прочие данные; они не измеряют отдельно цену изображения или base64.

Для следующих тестов требуется не печатать image_url/base64 через text/notify: сохранять объект в code-mode и выводить только путь/статус либо корректно передавать изображение через image/generatedImage. Наличие image-вложения всё равно имеет собственную токенную стоимость, даже без текстового base64.

## Проверка генерации и save_image в одном JavaScript-блоке — 2026-10-07

Живой сценарий `image-export` выполнен на том же WSL Linux / Codex 0.159.3 с прежним профилем `tg-check`: сеть shell отключена, служебный CODEX_HOME недоступен агенту, общая wiki и собственная `.temp/a1` доступны. Проверка Alpine по-прежнему не выполнена.

Контроллер зарегистрировал `save_image` через `thread/start.dynamicTools`; запросы пришли как `item/tool/call`. Агент вызвал нативную генерацию и оба сохранения внутри одного `functions.exec`: результат генератора оставался в переменной JavaScript, путь извлекался из `output_hint`, наружу выводились только результаты сохранения. `image_url` и base64 не печатались, `image()` и `generatedImage()` не вызывались. App Server уведомление `imageGeneration` по-прежнему содержит байты; исключение их из контекста не исключает их из транспорта и сырых диагностических логов.

Результат: PNG 1 165 413 байт сохранён в `.temp/a1/generated/exec-3cd85d4c-706e-4a9a-a052-533355501f1a.png` и `wiki/images/exec-3cd85d4c-706e-4a9a-a052-533355501f1a.png`. Обе копии и native savedPath имеют SHA-256 `860451b020c952bfaed511a44f820505a3d9745d1ee44f423abe3bf97f053a5c`. Исходник оставлен на месте. Дополнительно чтение обеих копий проверено через `codex sandbox -P tg-check`, их хеши совпали.

| Измерение | Предыдущий image | Новый image-export |
|---|---:|---:|
| Input tokens последнего запроса | 44 331 | 16 360 |
| Накопленные totalTokens за ход | 146 249 | 81 098 |
| Накопленные cachedInputTokens | 113 280 | 63 488 |
| Текстовые результаты с base64 | 1 | 0 |
| Размер самого длинного сериализованного tool output, символов | 40 241 | 309 |

В этих двух прогонах последний input уменьшился примерно на 63%, накопленные токены — на 45%. Это не контролируемый бенчмарк и не измерение стоимости генерации: различались изображение, инструкции и число шагов. Выгода от отсутствия base64 в текстовом контексте подтверждена непосредственно содержимым response_item.

Начальный exec использовал yield_time_ms=1000, затем агент сделал три `wait`, включая два коротких. Поэтому один JavaScript-блок не означает один запрос к модели. Для дальнейшей инструкции стоит рекомендовать более длинное ожидание exec/wait; экономия от этого отдельно не проверялась.

Прототип [save-image-probe.mjs](../tools/save-image-probe.mjs) принимает только savedPath, зарегистрированный завершённой генерацией вызывающего thread. Направления: обычные директории wiki (включая корень `.`) либо `.temp/a1` и её поддиректории. Служебные скрытые директории wiki, чужая `.temp`, абсолютные пути, `..` и symlink отклоняются. Совпадающий повторный экспорт возвращает прежний путь; другое содержимое не перезаписывается. [Тесты](../tools/save-image-probe.test.mjs) выполнены на Windows и Linux. Это тестовый адаптер: защита от конкурентной подмены файловых путей и привязка дерева субагентов к постоянному agentId требуют реализации в приложении.

Извлечение пути из текстового output_hint работает в проверенной версии, но это не структурированное поле savedPath: при изменении шаблона подсказки потребуется обновление. Если подсказка отсутствует, сценарий должен вернуть ошибку без попытки вывести base64. Thread теста: `01a115f7-a5b0-7300-9b82-36be4d3ea3b8`; артефакты `.runtime-check/results/image-export/`. Временная копия CLI-auth удалена после теста.

## save_image у нативного субагента и удаление сессий — 2026-10-07

Проверки выполнены в прежнем WSL Linux окружении, Codex 0.159.3, профиль `tg-check`, без расширения песочницы и без Telegram-вызовов. Инструмент `save_image` передан только основному thread через dynamicTools; нативный субагент унаследовал его и вызвал самостоятельно. Контроллер связал дочерний thread с постоянным агентом `a1` по наблюдаемому `subAgentActivity(kind=started)` от разрешённого родителя; пути не авторизовались по одному утверждению модели.

### Фоновая генерация с сохранением

- Основной thread: `01a11614-686b-7e53-beb6-aa48a81989b8`; субагент: `01a11614-c583-7691-9801-fb41bbe804d2`.
- Генерация началась в 11:17:10.285 UTC. Ответ основного агента STEER_ACK получен в 11:17:12.869 UTC, завершение изображения — в 11:17:25.116 UTC. Основной ответил во время генерации, не дожидаясь субагента.
- Оба `item/tool/call` для `save_image` пришли от субагента, не от основного агента. Файл сохранён в `.temp/a1/generated/` и `wiki/images/`.
- PNG 991 840 байт; исходник и обе копии имеют SHA-256 `30e8e773bb68b41e5f724c6f58773ab8fe39e679851f8e2eea97b6d52e44739a`. После удаления сессий обе копии отдельно прочитаны через `codex sandbox -P tg-check`, хеши совпали.
- При первом запуске родитель попытался назвать субагента `image-save`; Codex отклонил дефис. Родитель самостоятельно исправил имя на `image_save` и продолжил. В воспроизводимом сценарии следует сразу использовать допустимое имя.

### thread/delete завершённого дерева

После завершения основного и дочернего хода вызван `thread/delete` только для основного thread. Получены `thread/deleted` для обоих. Оба существовавших rollout JSONL физически исчезли; файлов с этими ID нет ни в sessions, ни в archived_sessions. `thread/read` возвращает thread not loaded, `thread/resume` — no rollout found. Проверка после перезапуска App Server также не восстановила сессии.

В SQLite проверено отсутствие строк для этих ID: метаданные threads, dynamic tools, spawn edges, проекции turn/item history и другие таблицы с идентификаторами thread. Это удаление логических записей; физическое уменьшение размеров самих SQLite-файлов не проверялось.

Исходник в CODEX_HOME/generated_images и обе экспортированные копии остались на месте. Следовательно, thread/delete не заменяет согласованную очистку исходников генерации по отдельному реестру.

### thread/delete при работающем субагенте

Основной thread `01a11615-649f-7153-b120-5046595297fc`, дочерний `01a11615-983a-7342-b10c-13afc504bceb`. У дочернего запущена команда `sleep 45; printf child-finished > .temp/a1/delete-active-marker.txt`. После item/started команды вызван thread/delete основного без предварительного interrupt — для проверки поведения самого удаления.

API принял вызов, дочерняя команда завершилась с exitCode=-1 примерно через 59 мс, получены оба thread/deleted. После 50 секунд с живым App Server файл-маркер не появился, rollout-файлы не восстановились. Метаданные/история обоих thread удалены; resume после перезапуска отклонён.

Это проверка отмены конкретной локальной команды, а не гарантия отката уже выполненных внешних действий или отмены запроса к генератору изображений. Согласованное отсечение инструментов старого запуска контроллером сохраняется.

### Согласованная последовательность interrupt → delete

Дополнительный сценарий `delete-interrupt`: основной thread `01a11617-e57d-7ec0-ac15-5c5d002e57a6`, дочерний `01a11618-051c-7fe1-b781-d13f8381482f`. После начала дочерней команды вызван turn/interrupt основного; получен turn/completed с прерванным ходом. На момент последующего вызова thread/delete команда субагента ещё не имела item/completed. Удаление остановило её с exitCode=-1 (длительность около 147 мс) и удалило оба thread.

После 50 секунд файл-маркер не появился, rollout-файлы не восстановились. После нового перезапуска App Server resume всех шести удалённых сессий отклонён, их SQLite-метаданные и история отсутствуют. Следствие: interrupt основного в этой проверке не заменил остановку дочерней работы; сохраняется согласованный порядок отсечения старых инструментов, interrupt и delete.

## Динамическая смена модели — 2026-10-07

В прежней песочнице WSL Linux / Codex 0.159.3 выполнены `model-switch` и `model-resume`. Проверена доступность gpt-6.1-sol и gpt-6-sol по текущему model/list; использован поддерживаемый обеими effort=low. Основной thread во всех шагах один: `01a11634-6127-7450-bc41-e2265a71f844`.

1. На gpt-6.1-sol дано контрольное значение MODEL_MEMORY_LANTERN_73924 для хранения только в диалоге и developerInstructions с окончанием CHECK_MODEL_RULE.
2. Следующий turn/start с model=gpt-6-sol сохранил значение и правило без нового thread или сброса контекста.
3. На новом ходе gpt-6.1-sol создан model_old (`01a11634-8b57-75f0-9601-4fe578be4b35`) без model override. Основной завершил ход, пока дочерний выполнял нативный sleep на 40 секунд.
4. Основной переключён на gpt-6-sol через следующий turn/start. Уже работающий model_old сохранил gpt-6.1-sol до завершения. Новый model_new (`01a11634-adda-7f60-965b-7fa4d363c797`) без model override унаследовал gpt-6-sol. На момент переключения работа старого субагента ещё не завершилась.

6. App Server остановлен и запущен заново. Thread возобновлён без model и без повторной передачи developerInstructions; следующий turn/start тоже не задавал model. Сохранились gpt-6-sol, контрольное значение и правило.

Модели проверены по thread/read и фактическим turn_context в rollout, не по самоописанию агента. В аргументах обоих spawn_agent отсутствовал model override. Дочерние rollout включают исторические turn_context родителя из fork: для дочерней модели проверялся собственный ход, а не все унаследованные записи.

После исправления распознавания весь сценарий повторён успешно; исходный результат сохранён в model-switch-initial и не считается успешной проверкой переключения с активным субагентом.

Сохранение одного контрольного значения не обещает безошибочного воспроизведения всех деталей после сжатия.
