# Telegram-стенд — 2026-10-07

Живые проверки на выделенном временном боте. Токен читается из игнорируемого локального файла; в документацию и результаты API он не записывается. Код стенда: [telegram-check.py](../tools/telegram-check.py). Это отдельный API-прототип, без Codex и без БД/очереди приложения. Все сообщения помечены как тестовые.

## Подтверждено API

- getMe: бот подключён, can_read_all_group_messages=true. Webhook отсутствует; события получаем через getUpdates.
- ЛС доступны. Два подготовленных групповых чата Telegram определяет как supergroup; бот в обоих administrator. Обычная group пока отсутствует. Имена чатов не определяют их тип.
- sendMessage с HTML, editMessageText, reply_parameters.
- sendRichMessage с HTML и reply_markup.inline_keyboard; Telegram возвращает rich_message.blocks с JSON-кнопками.
- Редактирование rich через структурированные blocks в editMessageText.
- disabled:{} принято для rich и inline. После callback rich-кнопки [probe]rich answerCallbackQuery прошёл, editMessageText с одновременным disabled для обеих кнопок общей группы прошёл. В callback присутствовали message_id, data и rich_message. Пользователь подтвердил отметки ☑/☒: rich выглядит заблокированной, inline выглядит обычной, но нажатие ничего не делает. В сохранённом ответе inline содержит только text и disabled:{}, без callback_data; нового callback при последующем нажатии не обнаружено. Для inline нельзя обещать такой же визуальный вид disabled, как у rich; иконка остаётся полезной.
- copyMessage rich-сообщения с reply_parameters и новой inline-клавиатурой; forwardMessage rich-сообщения. При отдельной проверке активного источника forward вернул rich-кнопку disabled:{} без callback_data и без нижней клавиатуры. Copy также сохранил rich-кнопку как disabled:{}: подтверждено полным Message после editMessageReplyMarkup копии. Сам copyMessage возвращает только MessageId, поэтому отсутствие полей в его ответе не доказывает отсутствие этих полей в сообщении.
- editMessageReplyMarkup меняет нижнюю клавиатуру отдельно, сохраняет rich и принимает стиль primary.
- Повторная изолированная проверка inline disabled: sendMessage без rich и иконок с двумя строками кнопок принят. Message 25 содержит «Активная» с callback_data и «Без действия» с disabled:{} без callback_data. Это отдельное подтверждение поддержки структуры в API; визуальный серый вид не гарантируется. Официальный changelog Bot API 10.3 от 24 августа 2026 отмечает добавление disabled в InlineKeyboardButton: https://core.telegram.org/bots/api#inlinekeyboardbutton.
- Пользователь проверил обе кнопки Message 25: активная вызвала уведомление «Стенд получил нажатие», disabled выглядит активной, но ничего не делает. Такое поведение пользователя устраивает; disabled оставляем в контракте, серый вид не обещаем.
- Активная inline-кнопка копии прислала callback с data=copy_probe и message_id=10. Повторная попытка с работающим слушателем успешно подтверждена answerCallbackQuery; пользователь увидел уведомление. Первое нажатие произошло после завершения четырёхминутного слушателя; событие получено при его перезапуске, но answerCallbackQuery вернул истёкший срок. Это неуспешная попытка стенда, а не дефект inline/copy; временное мерцание клиента не означает подтверждения callback.
- callback_data проверен на ASCII и кириллице: 64 UTF-8 байта принимаются, 65/66 байт отвергаются с BUTTON_DATA_INVALID.
- Входящее редактирование пользовательского сообщения получено как edited_message: прежний message_id, исходный date, edit_date и полный новый text. Приход реакций пользователя на сообщения бота подтверждён: message_reaction содержит chat, message_id, user, date, old_reaction и new_reaction. Это подтверждение событий Bot API, а не сохранения/триггеров будущего приложения.
- В двух супергруппах: отправка/reply, pinChatMessage/getChat/unpinChatMessage, setMessageReaction с 👍, sendChatAction typing/upload_photo, deleteMessage тестового сообщения. Все ответы успешны. getChat при закреплении возвращает pinned_message.
- multipart sendDocument и getFile: скачанный документ байт-в-байт совпал с исходником по SHA-256.
- multipart sendMediaGroup: два отдельных сообщения с фото в одном альбоме. Это проверка исходящей отправки, не времени прихода пользовательского альбома.
- Входящий пользовательский альбом: четыре отдельных Message (21–24) с одним media_group_id, все получены в одном ответе getUpdates. Каждое фото имеет четыре PhotoSize; максимальные 853×1280 скачаны через getFile, получены четыре JPEG размером 145–259 КБ. Анализ и SHA-256 сохранены в `.runtime-check/telegram-album-analysis.json`. Точную задержку между элементами этот ответ не показывает: date имеет секундную точность, а индивидуальные времена прихода не записаны. Согласованную политику сборки 1 секунда тишины / максимум 3 секунды не меняем. Это не проверка самого сборщика контроллера.
- multipart sendRichMessage: HTML с локальными медиа через attach:// и rich_message.media принят; ответ содержит heading, paragraph, photo, paragraph, slideshow, buttons. Пользователь подтвердил правильное отображение rich, фото и карусели (одинаковые синие изображения — намеренный fixture). Кнопки ссылки и copy_text приняты API; фактическое копирование текста ещё не подтверждено.
- Канал: getChat подтверждает linked_chat_id в обе стороны; бот administrator. Успешны публикация/редактирование, pin/unpin, реакция бота 👍, удаление отдельного временного поста и multipart-публикация rich с фото. Получена автоматическая пересылка в супергруппу: is_automatic_forward=true, forward_origin.type=channel, forward_origin.chat.id=ID канала и forward_origin.message_id=2. ID корня в группе — 9, то есть отличается от ID публикации. Также пришёл корень rich-публикации с сохранённым rich_message.
- Cross-chat reply из ЛС на публикацию канала через reply_parameters.chat_id/message_id принят. Ответ Message содержит external_reply.
- Прототип поиска обсуждения по захваченным верхнеуровневым сообщениям: [telegram_discussion_probe.py](../tools/telegram_discussion_probe.py). Шесть offline-проверок пройдены: рекурсивная цепочка с непоследовательным порядком входа, изоляция канала/чата, отказ ручной пересылки как корня, обрыв при неизвестном родителе, отличие пустого обсуждения от отсутствующего корня, отсечение чужого chat в reply. На живых данных найдены корень 9 и все пять комментариев: 11→9, 12→11, 13→9, 14→9, 15→14; у всех message_thread_id=9. Это подтверждает рекурсивный обход двух веток, но не является реализацией search или проверкой индексов БД. Живой результат: `.runtime-check/telegram-discussion-analysis.json`.
- Анонимные реакции канала получены через message_reaction_count для публикации 2: 👍 total_count=2, 🔥 total_count=1. Одну 👍 ранее поставил бот. Событие содержит сводные счётчики, без пользователей; оно пришло позже комментариев. По [Update](https://core.telegram.org/bots/api#update) такие обновления группируются и могут задерживаться до нескольких минут. Сохраняем снимок известных счётчиков, не прибавляем total_count как дельту; отсутствие нового события не означает нулевые реакции.

## Дополнительный сценарий: новая загрузка при rich edit

По запросу пользователя проверено одно Message 27 в ЛС:

1. sendRichMessage: «генерирую фото», rich-кнопка «продолжить».
2. Callback → multipart editMessageText: «фото готово», slideshow из двух фото, rich-кнопка «добавить ещё». Оба фото загружены как attach://red и attach://green.
3. Callback → multipart editMessageText: «фото добавлено», slideshow из трёх фото. Первые два заданы существующими file_id из ответа первого edit; только третий загружен как attach://blue.

Оба edit успешны, message_id остался 27. API вернул сначала два, затем три элемента slideshow; file_id и file_unique_id первых двух не изменились, порядок сохранён. Пользователь подтвердил визуально: красное и зелёное фото остались, синее добавилось; сценарий работает как ожидалось.

Таким образом, editMessageText с rich_message поддерживает multipart-загрузку новых файлов одновременно с сохранением прежних через file_id. Это полная замена описания rich: старые фото должны присутствовать в новой структуре. Не проверялось и не обещается автоматическое добавление к прежнему slideshow без передачи старых элементов. Файлы изображения для стенда созданы локально, генерация Codex в этом сценарии не запускалась.

Код: [telegram_carousel_probe.py](../tools/telegram_carousel_probe.py). Артефакты: `.runtime-check/telegram-carousel-state.json`, telegram-carousel-log.txt и записи multipart в telegram-results.jsonl. Загрузка первого edit содержит два файла, второго — один. Предыдущий общий слушатель остановлен перед запуском, отдельный слушатель карусели завершился после успешного второго edit.

## Оставшиеся проверки

После визуальной проверки пользователь выбрал новый набор иконок состояний: ⬜️ (enabled), ✅ (check), ⬛️ (disabled). Канонический контракт, его примеры и повторные запуски telegram-check.py используют их. Старые ☑/☒ выше описывают фактически выполненный первоначальный тест и не переписываются как новое наблюдение.

- Пользовательская проверка ссылки/copy_text.
- Повторные/одновременные нажатия и permits с вторым пользователем. Закрытие группы в этом стенде хранится в памяти одного процесса; это не проверка БД или атомарности будущего приложения.
- Ошибки частичных операций и ограничения файлов; отдельная проверка нижней клавиатуры copy без явного reply_markup.
- Сохранение событий и поиск в БД приложения; обычная группа. Канал, связанные комментарии и анонимные счётчики реакций проверены на уровне платформы/прототипа.

Артефакты в игнорируемой `.runtime-check/`: telegram-results.jsonl, telegram-listener.txt, telegram-listener-2.txt, telegram-listener-3.txt. Первый слушатель ограничен четырьмя минутами, второй — пятнадцатью (`listen 900`), третий — тридцатью (`listen 1800`). Повторный запуск возможен после остановки предыдущего. Первый и второй завершились по лимиту; третий получил накопленные события канала и продолжает принимать комментарии. Тестовые сообщения оставлены для визуальной проверки. Стенд не удаляет и не изменяет пользовательские сообщения и прежние закрепления; закреплённое им тестовое сообщение затем открепляется.
