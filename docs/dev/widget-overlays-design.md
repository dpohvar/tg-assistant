# Эфемерные представления виджетов: базовая концепция

Статус: согласованная основа для дальнейшего проектирования и реализации. Это не описание уже доступного API и не разрешение начинать реализацию. Текущий контракт находится в [Widgets](../widgets.md) и [Hidden correspondence](../ephemeral.md); результаты экспериментов — в [отчёте об оверлеях](ephemeral-overlay-verification.md).

## Назначение и границы

Один виджет имеет общее состояние, публичные вьюхи и личные эфемерные оверлеи поверх публичных сообщений. Обработчики самого виджета управляют интерфейсом без обращения к агенту на каждое нажатие.

Используем обычный Telegram Bot API. Переход на MTProto отложен. Для обычной группы, где присутствует бот, предусматриваем личные интерфейсы игроков. В гостевом режиме сохраняем существующее одно публичное сообщение и последовательную игру; вызов открытия оверлея возвращает явную ошибку о недоступности операции, без публичного запасного ответа.

## Модель вьюх

- `render(state, view)` используется для публичных сообщений и оверлеев.
- У каждой вьюхи есть собственный `id`, адрес `target` и параметры `props`.
- У публичной вьюхи `view.parent === null`. У оверлея `view.parent` ссылается на публичную вьюху в том же замороженном снимке.
- В публичном API используем `parent`, а не отдельный `parentViewId`. Внутри хранения и межпроцессной передачи связь представляется ID; ссылки собираются при подготовке снимка для кода виджета.
- Глубина ограничена двумя уровнями: публичная вьюха → оверлей. Вложенных оверлеев нет.
- `ctx.views` — замороженный словарь всех вьюх собственного виджета по ID, включая оверлеи. Пример получения родителя: `ctx.views[id].parent`.
- Для адреса оверлея нужны `chatId`, `receiverUserId`, `ephemeralMessageId`. Получатель задаётся контроллером; выбор игрока в `props.playerId` не меняет получателя и не предоставляет прав на чужие действия.
- Лимит: один активный оверлей на пользователя в каждой публичной вьюхе. Один пользователь может иметь оверлеи в нескольких публичных вьюхах, в том числе в разных чатах.

`parent`, `props` и остальные поля снимка нельзя менять напрямую. Ссылки на родителя не являются изменяемыми объектами платформы.

## Открытие и переключение экрана

В обработчике нажатия:

```js
await event.overlay({
  props: {
    screen: "game",
    playerId: event.user.id,
  },
});
```

- В публичной вьюхе метод открывает оверлей нажавшему пользователю либо обновляет его существующий оверлей этой вьюхи.
- Внутри оверлея метод переключает тот же личный интерфейс, сохраняя публичного родителя.
- `props` заменяются целиком; параметры публичной вьюхи не изменяются.
- Метод возвращает `WidgetView` созданного или обновлённого оверлея.
- Создание остаётся привязанным к событию нажатия; произвольное создание из `ctx` без события в базовый API не включено.

Экран, выбранный игрок, страница и фильтры списка — примеры параметров `props`. Общее состояние игры хранится в состоянии виджета отдельно от существования личного интерфейса.

## Обновление без нового нажатия

```js
const exists = await ctx.updateView(viewId, {
  props: {screen: "list"},
});
```

- Метод работает для публичных вьюх и оверлеев.
- Заменяет `props` целиком и запускает рендер выбранной вьюхи. Для частичного изменения вызывающий передаёт `{...view.props, screen: "list"}`.
- Для оверлея редактирует существующее эфемерное сообщение, не создавая новое.
- Может использоваться обработчиком или по таймеру; операции выполняются последовательно с другими действиями виджета.
- Возвращает `true`, если вьюха существует; `false`, если уже закрыта или истекла. Закрытую вьюху не восстанавливает.
- Если результат рендера не изменился, запрос редактирования в Telegram не отправляется.
- Автоматическое обновление не продлевает срок активности пользователя.

При обновлении общего состояния рендер вызывается также для активных оверлеев. Прежний результат не отправляется повторно. Таблица и просмотр чужой игры могут обновляться автоматически; кнопка обновления остаётся способом явно запросить актуальный рендер.

## Поиск и закрытие

Произвольная выборка выполняется обычным JavaScript, без специального языка фильтров по `props`:

```js
const lists = Object.values(ctx.views).filter(
  view => view.parent !== null && view.props.screen === "list"
);

for (const view of lists) {
  await ctx.closeOverlay(view.id);
}
```

Согласованные операции:

| Вызов | Действие |
|---|---|
| `ctx.closeOverlay(overlayId)` | Закрыть один оверлей |
| `ctx.closeOverlay(publicViewId)` | Закрыть все оверлеи этой публичной вьюхи, сохранив её сообщение |
| `ctx.closeOverlays()` | Закрыть все оверлеи собственного виджета |
| `ctx.closeOverlays({parentViewId})` | Закрыть оверлеи выбранной публичной вьюхи |
| `ctx.closeOverlays({receiverUserId})` | Закрыть оверлеи пользователя во всём виджете |
| `ctx.closeOverlays({parentViewId, receiverUserId})` | Закрыть оверлей пользователя у выбранного родителя |
| `event.closeOverlay()` | Закрыть только оверлей нажавшего пользователя в текущей публичной вьюхе |

В аргументах массового закрытия `parentViewId` — ID фильтра, а не дополнительное поле `WidgetView`. Указанные фильтры применяются совместно. Повторное закрытие отсутствующего оверлея ничего не делает.

Для нажатия внутри оверлея `ctx.closeOverlay(event.view.id)` и `event.closeOverlay()` эквивалентны. Для нажатия в публичной вьюхе первый вызов закрывает оверлеи всех её пользователей, а второй — только нажавшего пользователя.

## Неактивность и очистка

- Оверлей закрывается после 20 минут неактивности получателя.
- Активностью считаются его открытие и действия: кнопки, переключения, ручное обновление. Изменения общего состояния, фоновые рендеры и переключение по таймеру активностью не считаются.
- Закрытие удаляет локальную привязку, прекращает рендер и обслуживание старых кнопок и отправляет запрос удаления сообщения в Telegram.
- Доставка удаления в клиент не гарантирована; локальная недействительность не зависит от видимого исчезновения сообщения.
- Удаление публичной вьюхи закрывает все дочерние оверлеи.
- Закрытие оверлея не удаляет прогресс игрока. Позднее нажатие в публичном меню позволяет открыть новый личный интерфейс на основе сохранённого состояния.
- Очистка и нажатия должны обрабатываться последовательно с остальными действиями виджета.

## Редактирование публичного родителя

Общее правило применяется независимо от причины рендера: `ctx.updateView()`, изменение состояния или `ctx.render()`.

1. Вычислить новое содержимое публичной вьюхи.
2. Если содержимое не изменилось, не редактировать сообщение и сохранить оверлеи.
3. Если требуется редактирование, закрыть все связанные оверлеи, затем редактировать публичное сообщение.

Закрытие включает локальное отключение старых кнопок и запросы удаления эфемерных сообщений. Прогресс игры сохраняется. Если последующее редактирование публичного сообщения завершилось ошибкой, оверлеи автоматически не восстанавливаются.

Поэтому публичное меню, служащее основой личных интерфейсов, следует сохранять неизменным, а обновляемую общую таблицу публиковать отдельной вьюхой.

## Применение к Wordle

В обычной группе предусматриваем одновременную игру разных пользователей. Две публичные вьюхи:

- Общая таблица результатов, обновляющаяся по мере игры, включая появление первой зелёной буквы после проверки попытки.
- Неизменное меню `#main`, поверх которого открываются личные экраны.

| Экран | Содержимое и переходы |
|---|---|
| `#main`, публичный | «Начать/продолжить игру» → личный `#game`; «Посмотреть игры» → личный `#list` |
| `#list`, оверлей | Таблица игроков с кнопками перехода в `#game` выбранного игрока; «Обновить», «Назад» |
| `#game`, своя игра | Поле, клавиатура, «Назад» |
| `#game`, чужая игра | Поле без клавиатуры; «Обновить», «Назад» |

«Назад» удаляет оверлей и возвращает исходный публичный `#main`, в том числе из просмотра чужой игры. После завершения игры результат можно оставить в оверлее с кнопкой «Назад». Проверка права на игровой ход выполняется в обработчике, а не только скрытием клавиатуры.

Гостевое представление сохраняет текущую модель с одним публичным сообщением и последовательными ходами. Возможный конфликт игры одного пользователя через обычное и гостевое представления одного виджета осознанно отложен.

## Протокольные ограничения и оставшиеся вопросы

Пятнадцать секунд относятся к созданию нового эфемерного ответа после подходящего действия, а не к редактированию уже созданного сообщения. Для редактирования используется сохранённый адрес оверлея. Telegram может самостоятельно потерять эфемерное сообщение; закрытие клиента и состояние интерфейса нельзя считать надёжно наблюдаемыми платформой. См. [условия отправки](https://core.telegram.org/bots/api#ephemeral-messages-and-commands), [редактирование](https://core.telegram.org/bots/api#editephemeralmessagetext), [удаление](https://core.telegram.org/bots/api#deleteephemeralmessage).

До плана реализации отдельно определить:

- хранение личных вьюх и поведение после перезапуска контроллера;
- последствия штатного Revert/исчезновения оверлея в клиенте при последующем автоматическом рендере;
- обработку ошибок и неопределённого результата создания, редактирования и удаления, включая защиту от повторного использования эфемерного ID и старых кнопок;
- точный порядок рендера родителя и дочерних вьюх при одном обновлении, чтобы закрытый оверлей не был вновь отредактирован из ранее составленного списка;
- изменения контракта, сериализации, событий, прав и поведения остановки виджета, а также проверки совместимости со старыми обработчиками `render(state)`.

Эти пункты не являются уже выбранными решениями. Документ фиксирует базовую модель и принятые интерфейсы, а не полную спецификацию реализации.
