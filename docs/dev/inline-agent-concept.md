# Inline-вызов агента и публикация виджетов

Обновлено: 2026-10-18.

Документ фиксирует принятый дизайн, предложения и открытые вопросы без полного лога обсуждения. Реализация ведётся в отдельном worktree; результаты проверок находятся в [итоговом отчёте](inline-widget-verification.md), [калибровке](inline-calibration-results.md) и [матрице типов](inline-media-matrix-verification.md). Принятое решение не означает автоматически успешную live-проверку.

## 1. Цель

Вызывать агента через inline-режим Telegram, выбирать подготовленный им результат и публиковать его в текущий чат. Результат может быть текстом, rich-сообщением или стартовой карточкой будущего виджета.

Подготовка ответа агентом может занимать дольше времени ожидания одного inline-запроса. Поэтому каждый запрос выдачи получает отдельный ответ, а агент работает асинхронно между запросами.

## 2. Принятые решения

- В качестве исходного механизма запуска рассматривается пагинация inline-выдачи — «двухсекундный барабан».
- Принятый порог паузы — **2 секунды**, с запасом на задержки и сбои сети. После живых замеров пользователь решил сохранить его; эксперимент с меньшими значениями больше не требуется (§46).
- Точка отсчёта паузы: серверное время начала отправки страницы с конкретным курсором. Это эвристика, которая не гарантирует различение намеренной прокрутки и запоздалой автоподгрузки (§46).
- После запуска поручения запрос страницы ожидает готовность до 5 секунд и отвечает раньше, если результат появился. Иначе возвращается один пункт «Агент думает» с новым курсором. Значение предварительное и требует отдельной проверки в живом эксперименте; общий час не продлевается (§47).
- Повтор действующего курсора текущей версии обслуживается по её актуальному состоянию, без истории полных страниц и повторного запуска агента. После завершённой выдачи, а также для неизвестного, чужого, отменённого, потерянного или истёкшего курсора возвращается пустая завершающая страница (§48).
- При любой ошибке answerInlineQuery прекращается обслуживание именно связанной с этим вызовом версии, её буфер освобождается, поздний set_inline_results отклоняется. Уже записанные перед отправкой кнопки остаются в БД на случай фактической доставки. Начатая агентская работа не прерывается, автоматической повторной отправки нет (§49).
- Ошибка записи кнопок в БД также прекращает обслуживание соответствующего inline-запроса: готовая страница не отправляется, буфер освобождается, поздний результат не принимается (§49).
- Предел количества страниц барабана не вводится; действует общий час жизни версии. В живом эксперименте, помимо порогов 2 и 5 секунд, нужно откалибровать число служебных строк, при котором прекращается автоподгрузка следующей страницы, на разных устройствах (§46).
- На пару `{botId, userId}` обслуживается одно текущее inline-поручение. Новый начальный запрос немедленно заменяет текущую версию, даже при том же тексте: прежнее ожидающее поручение по возможности снимается из очереди, уже начатая работа не прерывается, поздние результаты не выдаются и их кнопки/действия не регистрируются. Прокрутка по курсору продолжает прежний запрос. Новая версия отдельно проходит двухсекундный порог (§37, §43).
- Принят `set_inline_results({requestId, results})`: агент передаёт весь готовый список одним вызовом; каждый вариант содержит title, необязательные description и message с содержимым и кнопками. При отсутствии message подставляется нейтральное сообщение с крестиком (§42). Контроллер проверяет версию и владельца, назначает технические идентификаторы и готовит выдачу; сам вызов не публикует сообщение в чат (§38).
- Область inline-результатов расширяется на все нативные возможности, которые не требуют самостоятельной новой подсистемы: медиа по file_id и внешним URL, article, контакты, геопозиции и места, доступные поля оформления и InputMessageContent, кроме invoice. Telegram Games и счета на оплату явно исключены (§56). Исходники предоставленного Wordle не меняются, миграция проверяется на текущем обработчике; о найденных проблемах совместимости сообщать пользователю (§9, §56).
- После настройки агента или передачи фото/файла в ЛС пользователь сам начинает новый inline-запрос. Отдельной кнопки возврата, сохранения текста для возврата и автоматического возобновления прежнего requestId не требуется (§57).
- Приняты матрица рядов message.buttons и прежний словарь message.permits: точные ключи, префиксные шаблоны, null либо массив userId. Для action-кнопок логический key/group отделён от непрозрачного btnId; плоский buttons означает один ряд, каждый rich buttons-блок задаёт отдельный ряд (§50).
- Приняты отдельные сроки хранения: первоначальные action-кнопки — 30 дней от первой регистрации перед выдачей; inline-снимки — 30 дней от последней подтверждённой правки. Владение сохраняется на срок зависимостей и по правилу §51; действующие виджеты и view не очищаются вместе с историей или стартовыми кнопками.
- Буферные сообщения не удаляются автоматически после выдачи, отмены или истечения inline-запроса. Для временных файлов и истории буфера действует общая очистка. Недоступный file_sources даёт file_not_accessible без принятия результата; агент может исправить источник в пределах срока запроса (§52).
- Явное отключение/удаление агента, утрата назначения собеседнику или права его обслуживать закрывают соответствующие inline-запросы. Готовый невыданный буфер освобождается, поздние результаты отклоняются; включение агента не восстанавливает прежний requestId. Временный сбой выполнения не равен отключению (§53).
- Готовность inline-ответа определяется только успешно принятым set_inline_results для текущего requestId. Окончание хода агента и переход к фоновой работе не завершают ожидание: барабан продолжает отдавать «Агент думает» на запросы страниц (§40).
- Подготовка и готовые результаты inline-запроса хранятся только в памяти в пределах одного общего часа от создания версии: expiresAt = createdAt + 1 час. Готовность, прокрутка и модельные ходы срок не продлевают; новый начальный запрос заменяет прежний раньше. После перезапуска запрос теряется и не восстанавливается; тот же вопрос в новом начальном запросе обрабатывается заново. Кнопки записываются в БД только перед выдачей страницы, в которую они включены (§43).
- Первоначальное событие агенту: `{eventType: 'inline', requestId, query, expiresAt, chatType?}`. from не передаётся: автор — текущий собеседник личного агента. chatType передаёт известный тип чата вызова без его адреса; нативный пользователь по-прежнему проверяется контроллером (§44).
- Первый успешно принятый set_inline_results окончательный: accepted при первом приёме, already_set при повторе без изменения результата; ошибка одного варианта отклоняет весь список. Пустой results завершает ожидание строкой «Работа завершена» с нейтральным message ✖️ без кнопок и пустым next_offset (§45).
- Уточнение или сообщение о невозможности выполнить поручение тоже передаётся обычным set_inline_results: title/description объясняют ситуацию в выдаче, message задаёт содержимое при выборе. Такой ответ завершает ожидание текущего запроса; отдельный set_inline_status и динамическая замена верхней кнопки для этого не нужны (§41).
- Для файлов/изображений в inline-результате uploads, attach:// и локальные пути запрещены. Агент явно загружает файл обычным send в буферный чат, читает отправленное сообщение и передаёт file_id с file_sources. Буфер выбирает пользователь; по умолчанию — ЛС автора inline-поручения с disable_notification: true. Контроллер не делает скрытую загрузку; порядок работы включается в подсказку агенту (§39).
- Ложные срабатывания при отличении автоматической загрузки от ручной прокрутки пока допустимы. Пауза является эвристикой, а не доказательством действия пользователя.
- Целевой сценарий: опубликовать стартовую карточку Wordle с одноразовой кнопкой **«Начать»**; после нажатия агент получает событие и превращает именно это опубликованное сообщение в виджет.
- Для inline-выдачи принято `cache_time: 0`. Группа кнопок одноразова глобально для заготовки: первое допустимое принятое нажатие закрывает `{botId, tipId, group}`, например удалением соответствующих btn-записей. Повторная публикация той же заготовки не даёт независимый запуск этой группы. Это ограничивает приём действий, а не число отправленных сообщений. Закрытие группы согласовывается с приёмом события: отказ очереди не должен расходовать кнопку без события.
- Сохранение принятого события и закрытие группы выполняются в одной транзакции базы. Событие содержит адрес публикации, пользователя, action, агентский маршрут и идентификаторы; после фиксации оно передаётся очереди агента. Ошибка транзакции не расходует группу и не создаёт события. Переданным событие считается с момента приёма в очередь агента; подтверждение модельного runtime, начало или завершение обработки не требуются. После этого автоматической повторной доставки нет, даже если событие потеряется при перезапуске очереди или агент его не обработает. Такой риск принят; пользователь может подготовить и опубликовать новую карточку.
- После принятого нажатия ошибка агента или инструментов не открывает группу автоматически. Агент сам решает, исправить ли существующий виджет, повторить подключение или подготовить новую кнопку с новыми идентификаторами и действием повтора. Старые кнопки группы остаются недействительными; платформа не создаёт новую игру автоматически после частичного сбоя.
- Inline-поручение получает агент личного диалога пользователя с этим ботом. Подготовленный результат сохраняет выбранный agentId, «Начать» направляется тому же агенту, который становится владельцем виджета. Если личного агента нет, inline-выдача показывает кнопку перехода к боту для начала личного диалога и обычной настройки агента; агент автоматически из inline-запроса не создаётся. Явный выбор другого агента в первой версии не вводится.
- Содержимое стартовой карточки, её inline-клавиатуру и доступность кнопок определяет подготовивший результат агент; кнопка может быть публичной. Ограничения «только автор inline-запроса» по умолчанию не вводятся. Допустимое нажатие направляется тому же агенту с данными нажавшего пользователя и адресом публикации; агент решает, подключать ли виджет. Нажавший пользователь не становится автоматически владельцем виджета и не меняет агента-получателя события.
- Для модельного inline-нажатия принят тип `eventType: 'button'` с `eventId`, `inlineMessageId`, `from`, сохранённым `action`, `btnId`, `tipId` и необязательным `btnGroup`. Обычные button-события сохраняют messageId, key и text; у inline-варианта неизвестные адреса и фиктивные key/text не добавляются. Игровые кнопки подключённого виджета продолжают обрабатываться его runtime, без автоматического события модели.
- Принят `read({inlineMessageId})` с оболочкой `{messages: [...]}`. При отсутствии сохранённого содержимого возвращается элемент с `message_not_found` и пояснением. Частичное известное представление имеет `partial: true`, полное — `partial: false`; отсутствующие поля не считаются пустыми. После правки с неизвестным результатом возвращается последнее подтверждённое представление с `deliveryUnknown: true`. Это чтение данных контроллера с проверкой владельца, без выдуманных адресов и метаданных Telegram.
- Принят `edit({inlineMessageId, ...})` для явно заданных компонентов обычной inline-карточки с проверкой владельца, даже без полного исходного снимка (§34). Через обычный адрес chatId/messageId агенту запрещены правки сообщений с `via_bot`, включая клавиатуру, rich-кнопки, permits и подключение нового view; удаление сохраняется по обычным правам (§35).
- В краткие сообщения добавить необязательный `viaBot`: username из message.via_bot без @, например `"bold"`; при отсутствии username — `true`. Поле показывает происхождение содержимого без read и не заменяет отправителя from (§36).
- Для рассматриваемой модели нескольких публикаций Wordle сохраняем общий `state`, включая одного общего активного игрока. Разные чаты видят участников и изменения одной игры; отдельный выбор активного игрока для каждого сообщения пока не вводится.
- Ошибка рендера или публикации одного подключённого `view` не препятствует обновлению остальных и не откатывает общее состояние. `onError` получает ошибку и конкретное отображение. Неудавшееся отображение остаётся подключённым; следующая операция рендера, включающая это отображение, снова пытается его обновить.
- Принята сигнатура `onError(ctx, error, event)`. Для операций отображений ошибка содержит `code`, `message`, `operation` (`render`, `attach`, `replace`, `detach`) и снимок проблемного `view`, если он есть. `event` — исходное событие, если оно есть; его `event.view` обозначает источник действия, а `error.view` — отображение с ошибкой. Отсутствующие событие или отображение не заменяются фиктивными объектами.
- При ошибке замены `error.view` содержит снимок нового отображения, которое не удалось подключить, а `error.previousView` — снимок сохранённой прежней привязки. Оба имеют форму `{id, target, props}`; новый снимок в ошибке не означает успешного подключения. Для остальных операций `previousView` отсутствует.
- Если при обработке ошибки отображения сам `onError` выбрасывает исключение, рекурсивно его не вызываем: сохраняем исходную и вторичную ошибки, работа виджета и других отображений продолжается, согласованный результат исходной операции не меняется. Уведомление агенту об этой паре ошибок подчиняется правилу сохранённой ошибки отображения.
- Каждое `view` хранит последнюю ошибку, не обработанную в `onError`, в служебном `lastError`. Агент уведомляется только при переходе от отсутствия ошибки к первой записи. Последующие необработанные ошибки обновляют запись без новых уведомлений, независимо от их кода. Успешное изменение агентом отдельного отображения сбрасывает только его ошибку; успешное изменение общего состояния или handler сбрасывает ошибки всех отображений виджета. Чтение, неудачная попытка изменения, автоматические рендеры, таймеры и нажатия ошибки не сбрасывают. Ошибка управляющей попытки возвращается агенту непосредственно в ответе инструмента.
- У самого виджета также есть служебный `lastError` для необработанных ошибок общего обработчика, таймеров и lifecycle, включая ошибку `onViewDelete` после отвязки. Первая запись уведомляет агента, последующие только заменяют ошибку. Успешное изменение агентом общего состояния или handler очищает общий `lastError` и ошибки всех отображений; изменение отдельного отображения очищает только его ошибку. Это метаданные контроллера, отдельные от пользовательского `state`.
- Необработанная ошибка `attach`, когда подключённого view ещё нет, сохраняется в `widget.lastError` со снимком кандидата в `error.view`, без создания фиктивного отображения. Сведения о возможной первой публикации с неизвестным результатом хранятся отдельно от `lastError`, доступны владельцу через `get_widget` и `/widget show` и переживают перезапуск. Обработка или сброс ошибки не удаляет эти сведения и не запускает повторную отправку.
- `delete_widget_view({viewId})` также удаляет служебную запись кандидата с неизвестным адресом с проверкой владельца. Для такого кандидата операция только забывает сведения: Telegram-сообщение не меняется, хуки удаления и повтор отправки не запускаются. Найденное сообщение сначала подключается обычным `set_widget_view` с новым viewId, затем запись кандидата удаляется отдельно. Удаление всего виджета удаляет и эти записи.
- Успешное восстановление из `stopped` через `update_widget`, включая вызов без новых полей, очищает прежние ошибки виджета и его view после успешного `onInit`. Новые ошибки последующих рендеров сохраняются заново. Неудачная попытка запуска ошибки не очищает; чтение и ререндер уже активного виджета без изменения handler/state также не считаются восстановлением.
- При обычном рендере все типы событий, включая кнопки, могут ожидать в очереди с действующими ограничениями её размера. Перед выполнением кнопки проверяются неизменность идентичности подключённого `view` и наличие точного `callback_data` среди кнопок последнего успешно опубликованного содержимого именно этого отображения. Недопустимое нажатие игнорируется с пустым подтверждением. По проверенному текущему коду короткого таймера подтверждения нет; сохраняем отсутствие такого таймера. Ответ даётся через `event.respond` или возвращаемое значение обработчика, первый ответ имеет приоритет. Поздний/повторный ответ после уже выбранного подтверждения пропускается без ошибки и повторной отправки.
- При неопределённом результате обычной публикации view и состояние сохраняются, ошибка проходит через обычные `onError`/`lastError`, а кнопки только этого отображения игнорируются с пустым подтверждением до подтверждённого обновления. Следующий запрошенный рендер обязательно публикует актуальное содержимое, обходя кеш прежнего успешного хеша. Успех снимает неопределённость, но сам по себе не очищает `lastError`; остальные view работают, отдельного цикла повторов нет.
- При неопределённом результате первой отправки нового сообщения возвращается `delivery_unknown` с известными `widgetId`, ID кандидата `viewId` и `chatId`, без выдуманного `messageId`. Виджет и остальные отображения сохраняются; кандидат без адреса не считается подключённым view и не отправляется повторно автоматически, включая рендеры и перезапуски. Сведения о попытке сохраняются в служебной диагностике. Достоверно найденное сообщение можно позднее подключить через `target`; уже известный адрес первой публикации возвращается в диагностике ошибки последующего этапа.
- Дополнительное отображение может показывать результаты без возможности начать игру.
- Выбран единый `render(state, view)`. Название `view` принято: второй аргумент описывает конкретное отображение в сообщении и содержит его параметры. Несколько экспортированных функций рендера как отдельный контракт не выбираем; вспомогательные функции внутри модуля допустимы. Структура `view` — `{id, target, props}`.
- В render передаётся отдельный снимок view, рекурсивно замороженный через Object.freeze, включая target, props и вложенные объекты/массивы. Прокси и отдельный механизм перехвата записей не нужны. Общее state этим решением не замораживается (§54).
- События от сообщения получают `event.view` той же формы `{id, target, props}`: контроллер фиксирует снимок источника при приёме события в очередь и передаёт его обработчику только для чтения. Ожидание не меняет источник; актуальность привязки проверяется перед обработкой. У событий агента и общих таймеров `event.view` отсутствует.
- Виджет может существовать без единого `view`. Удаление последнего отображения не удаляет виджет и его общее состояние; позднее можно подключить отображение к тому же состоянию.
- Приняты состояния виджета `active | stopped`. `stopped` означает системную/аварийную остановку с сохранением состояния, отображений и причины; ручная остановка отдельным методом агенту не предоставляется. Ошибка отдельного отображения, `lastError` и отсутствие отображений сами по себе не останавливают виджет. Для прекращения работы агент удаляет виджет, для восстановления вызывает `update_widget`. Ранее отключённые регистрации при миграции становятся `stopped` и не запускаются автоматически.
- При остановке виджета очищается вся очередь его ещё не выполненных событий, включая сохранённые события. Новые события в `stopped` не принимаются на последующее выполнение; callback подтверждается без текста. После возобновления или перезапуска отброшенные события не воспроизводятся. Управляющие операции агента остаются доступны отдельно от исполнения событий виджета.
- При запросе остановки сразу закрывается приём новых событий и очищается очередь, затем контроллер дожидается завершения уже выполняющегося обработчика и связанного рендера, включая публикацию. Следующий обработчик из очереди не запускается. Только после завершения текущей работы заканчивается остановка и отключаются кнопки: поздняя публикация не должна вернуть их активность.
- При штатной остановке после завершения текущей работы вызывается `onStop(ctx)` один раз для текущего запущенного экземпляра. Независимо от успеха хука контроллер очищает оставшиеся таймеры, освобождает runtime и отключает кнопки. Ошибка хука фиксируется и не отменяет остановку; повторная остановка `stopped` хук не вызывает. После возобновления начинается новый цикл работы со своим завершающим `onStop`.
- При зависшем завершении или нарушении heartbeat выполняется единая аварийная остановка runtime агента: закрывается приём событий, виджеты этого runtime переводятся в `stopped`, их очереди очищаются и процесс принудительно завершается. Сохраняются последнее подтверждённое состояние, отображения и причина остановки; кнопки отключаются по возможности. Хуки в аварийной ветке не гарантируются. Агент получает одно уведомление со списком затронутых виджетов; повторные проверки той же аварии его не дублируют. Остальные runtime не затрагиваются, остановленные виджеты сами не возобновляются. Текущие значения таймаутов сохраняются (§55).
- Остановка сохраняет сообщения и привязки отображений, но контроллер отключает все обычные и rich-кнопки. Ошибка обновления кнопок не отменяет локальную остановку. При возобновлении рендер обновляет те же отображения и восстанавливает доступные кнопки без создания новых `view`.
- Возобновление не замораживает и не сдвигает реальное время: загружается handler, вызывается `onInit` для восстановления таймеров из `state`, затем обновляются отображения. `onCreate` повторно не вызывается, контроллер не воспроизводит пропущенные срабатывания пачкой. Ошибка инициализации оставляет виджет в `stopped`.
- Таймеры общие для всего виджета, не принадлежат отдельным `view` и продолжают работать без отображений. Подключение или отключение отображения само по себе не перезапускает и не останавливает эти таймеры. При отсутствии отображений рендерить сообщения некуда; последующее подключение показывает актуальное состояние.
- Параметры отображения меняются повторным подключением того же сообщения: успешно принятая замена отключает старое `view` и создаёт новое с новым идентификатором. Отдельная операция изменения `props` не нужна; при замене в рамках того же виджета его состояние, таймеры и остальные отображения сохраняются.
- Одно сообщение может иметь только одно подключённое view. Подключение к другому виджету возвращает `view_conflict` с `ownerAgentId`, `widgetId` и `viewId` существующей занятой привязки, сохраняя сообщение и привязку. Доступ нескольких агентов к одному каналу разрешает им публиковать собственные виджеты, но каждый управляет только своими регистрациями и отображениями. Автоматического переноса между виджетами нет; чужое отображение отключает его владелец.
- Замена ждёт завершения текущего рендера старого `view`, включая отправку в Telegram, независимо от успеха или ошибки. Операции рендера и замены одного отображения должны быть упорядочены, чтобы старый рендер не перезаписал новое отображение.
- Ошибка замены обрабатывается в `onError`, старая привязка сохраняется. Неопределённый результат публикации пока считаем ошибкой и также сохраняем старое `view`; это не является гарантией отката уже выполненного изменения в Telegram.
- Замена `view` упорядочивается с событиями виджета: уже принятые события, стоящие в очереди перед заменой, обрабатываются раньше неё. Замена использует актуальное после них состояние; принятые действия не отбрасываются только из-за предстоящей замены отображения.
- События кнопок, поступающие во время замены отображения, отсекаются: callback подтверждается без текста, обработчик не вызывается и событие не воспроизводится после завершения замены, в том числе при её ошибке. После успешной замены накопленные нажатия старого `view` не переходят новому даже при совпадении `callback_data`.
- Отсечение кнопок начинается при принятии валидной операции замены в очередь, после проверки аргументов, прав и конфликта привязки. Ранее принятые события выполняются перед ней. Отсечение включает ожидание текущего обработчика/рендера и заканчивается после окончательного успеха или ошибки; несколько уже принятых замен того же сообщения не создают промежуточного окна приёма кнопок. Запрещённый или невалидный запрос отсечение не включает; другие отображения работают по обычным правилам.
- Reply и реакции сохраняются в очереди при успешной или неудачной замене `view` того же сообщения внутри того же виджета. Исходный `event.view` не подменяется, обработчик использует текущее состояние; перед выполнением проверяется непрерывная принадлежность сообщения виджету вместо сохранения прежнего `view.id`. Явная отвязка, удаление, передача другому виджету и остановка запрещают выполнение старого события; повторное подключение его не оживляет.
- `poll` и `poll_answer` сохраняются при замене view, если тот же опрос с тем же `pollId` непрерывно связан с тем же сообщением и виджетом. Исходный `event.view` сохраняется; потеря связи опроса, явная отвязка, смена виджета или остановка запрещают старые события. Наблюдения и голоса разных опросов одного виджета хранятся раздельно по `pollId`.
- При отключении `view` Telegram-сообщение остаётся с последним содержимым, обновления прекращаются и отключаются все кнопки любых типов: как нижняя inline-клавиатура, так и встроенные rich-кнопки. Удаление сообщения — отдельная операция; общее состояние, таймеры и другие отображения сохраняются.
- При ошибке отключения кнопок `view` всё равно отключается локально. После отключения игнорируются все события, источником которых является это `view`, а не только нажатия кнопок. Ошибка операции передаётся в `onError` единожды; поздние события отключённого отображения не вызывают повторных ошибок или рендеров.
- Удаление всего виджета прекращает работу обработчика и общих таймеров, отключает все его `view` по согласованным правилам и удаляет общее состояние. Сообщения в Telegram остаются с отключёнными кнопками, насколько удалось выполнить их обновление; ошибка Telegram не сохраняет виджет работающим.
- Для удаления работающего виджета сначала выполняется согласованная остановка, затем удаляются регистрации отображений и общее состояние. У уже остановленного виджета `onStop` повторно не вызывается. Удаление отдельного Telegram-сообщения отвязывает только соответствующее `view`, не удаляя виджет и остальные отображения; даже после удаления последнего сообщения состояние и таймеры активного виджета сохраняются.
- Потеря доступа к сообщению и `message_not_found` для существующего отображения обрабатываются как удаление его `view`, а не как ошибка рендера: отвязка без вызова `onError`, записи новой ошибки рендера и автоматического уведомления агенту. Для работающего виджета вызывается необязательный `onViewDelete(ctx, event)` со снимком `event.view` и причиной `event.reason`. Если хука нет, дополнительных действий нет. Форма причины различает подтверждённое удаление, отсутствие сообщения и потерю доступа.
- Принято разделение операций: отдельно создать виджет без отображений, подключать или заменять `view`, отключать отдельное отображение и удалять весь виджет. В обсуждении используем имена `create_widget`, `set_widget_view`, `delete_widget_view`, `delete_widget`; точные аргументы ещё уточняются.
- Принят `update_widget({widgetId, handler?, description?, state?})`: опущенные поля сохраняются, переданный `state` заменяет состояние целиком, переданный handler загружает новую версию кода. Все существующие `view`, их идентификаторы, адреса и `props` сохраняются. Каждое успешное обновление вызывает ререндер всех отображений. Для `stopped` любой вызов, включая только описание или `{widgetId}`, является попыткой запуска через `onInit`; при успехе виджет становится `active`. Отдельные stop/resume-методы и команды не вводятся.
- `description` — описание самого виджета для агента. Оно обязательно при `create_widget`; при `update_widget` опционально, переданное значение заменяет описание, а отсутствие поля сохраняет прежнее, в том числе при замене handler. Изменение только описания не переинициализирует работающий экземпляр, но вызывает ререндер всех отображений.
- Обновление handler или явно переданного `state` работающего виджета после подготовки упорядочивается в очереди: завершить предшествующую работу, вызвать старый `onStop` и очистить ресурсы экземпляра, применить параметры, вызвать новый `onInit`, рендерить сохранённые view. `onCreate` не повторяется. При успешной замене очередь сохраняется, новые события ждут; при ошибке `onInit` виджет останавливается и очередь очищается. У `active` изменение только описания или вызов без новых полей лишь рендерят view, у `stopped` запускают инициализацию.
- Если обновление принято, ошибки рендеров отдельных отображений возвращаются в результате `{widgetId, renderErrors: [{viewId, code, message}]}` без отката общего обновления и успешных публикаций. Без ошибок массив пуст. Ошибка подготовки/применения самого обновления возвращается как ошибка операции; потеря сообщения остаётся штатной отвязкой, а не записью в `renderErrors`.
- Новая версия handler компилируется, аргументы и формат переданного состояния проверяются до остановки старого экземпляра и изменения регистрации. Ошибка этой подготовки возвращается агенту напрямую; неудачное обновление не изменяет прежний handler, состояние, статус, отображения и ошибки. Работающий экземпляр продолжает обычную работу.
- Сбой `onInit` при создании или замене останавливает конкретный виджет, сохраняя регистрацию и отображения. Частичные изменения `ctx.state`, сделанные до исключения, сохраняются без отката; следующая инициализация получает это изменённое состояние. Ошибка записывается в `widget.lastError` и возвращается агенту в ответе операции с `widgetId`, этапом `onInit` и статусом `stopped`, без отдельного дублирующего события.
- Приняты методы чтения `list_widgets()` и `get_widget({widgetId})`. Список содержит краткие сведения и числовой `canCreate` — сколько ещё виджетов агент может создать с учётом текущих квот и доступности runtime, как в существующем API. Полная карточка содержит пользовательское состояние, ошибки и отображения. Чтение видит мигрированные и остановленные регистрации, не запускает их runtime и не сбрасывает ошибки.
- Сохраняется `widget_event({widgetId, name, data?})`: пользовательское событие агента принимается в общую очередь с источником `agent`, без `event.view`; ответ подтверждает приём, а не результат выполнения. Lifecycle-хуки через имя события не вызываются, в `stopped` событие отклоняется без накопления. Отдельный агентский `render_widget` убирается: его роль выполняет `update_widget({widgetId})`, а `ctx.render()` внутри Wordle сохраняется.
- Для `set_widget_view` приняты два взаимоисключающих режима: `send` для нового сообщения и `target` для существующего. Содержимое формируется рендером, а `send` содержит только параметры доставки. При опущенном `chatId` используется текущий чат агента.
- По поручению пользователя принято убрать `target.kind`: обычное сообщение определяется полем `messageId`, inline-сообщение — `inlineMessageId`. Поля разных вариантов нельзя смешивать; неоднозначные, пустые и некорректные адреса отклоняются, а не угадываются. В полном адресе обычного сообщения есть `chatId` и `messageId`; в полном inline-адресе — только `inlineMessageId`.
- При первом рендере перед отправкой нового сообщения `view.target` содержит известный `chatId`, а `messageId` отсутствует. После успешной отправки последующие рендеры получают полный адрес; `view.id` и `props` сохраняются. При подключении существующего сообщения адрес сразу полный. Неполный адрес допустим только в контексте рендера до отправки, но не во входном `target` операции подключения.
- Обязательна совместимость именно с предоставленным игровым Wordle: неизменённый обработчик и ранее сохранённые игры продолжают работать без повторной публикации сообщений или сброса состояния. Требования определяются фактическими зависимостями игры; сохранение всего исторического API, включая неиспользуемый ею `ctx.message`, не требуется.
- Методы агента, их аргументы и ответы можно обновить. Новый API обязан позволять обнаруживать и управлять ранее созданными виджетами по прежнему `widgetId`; сохранение старых имён инструментов не требуется. При изменении хранения предусматривается автоматическая миграция существующих регистраций и их сообщений в модель `view`.
- На этапе текущего обсуждения реализация не начинается; уточняются сценарий и контракт интеграции.

## 3. Предлагаемый механизм inline-выдачи

1. Пользователь вводит `@bot` и поручение, например: «Опубликуй виджет Wordle в этом чатике, со специальной кнопкой для старта».
2. На запросы при наборе текста возвращаем пункты `⬇️ Scroll to send command [hh:mm:ss]` по шкале 6,6,20,20… и курсор следующей страницы. Время формирования страницы указывается в UTC; старые строки сохраняют прежнюю отметку.
3. Если следующая страница запрашивается слишком быстро, продолжаем возвращать предложение прокрутить, без передачи поручения агенту.
4. Когда запрос следующей страницы проходит правило паузы в 2 секунды, передаём текущую версию поручения агенту. После успешного приёма в очередь немедленно выдаём отдельную строку `⬇️ Command sent to agent` с новым курсором.
5. После запуска поручения каждый запрос следующей страницы ожидает готовность до 5 секунд: готовые варианты возвращаются сразу при появлении, иначе выдаётся один пункт «Агент думает» с новым курсором (§47). Это ожидание результата, не проверка занятости агента: конец хода и выполнение фоновой задачи его не завершают. Значение предварительное, требуется живой эксперимент.
6. После успешного set_inline_results возвращаем подготовленные варианты на подходящем запросе страницы и завершаем пагинацию пустым `next_offset`.

Это серверный протокол поверх `offset`/`next_offset`, а не отдельные Telegram-события «ввод закончен» и «пользователь сделал скролл».

Служебные пункты предыдущих страниц остаются в выдаче. Метод редактирования уже показанного пункта не предусмотрен; нельзя рассчитывать на обновление по повторному `id`.

## 4. Целевой сценарий Wordle

1. Через описанный механизм агент получает поручение подготовить публикацию Wordle.
2. Агент готовит вариант отправки сообщения **«Wordle»** с inline-клавиатурой, например кнопкой **«Начать»**, и сам определяет её доступность, в том числе публичную. Кнопка принадлежит отправляемому сообщению, а не интерфейсу выбора результата.
3. Пользователь выбирает результат. Telegram публикует стартовую карточку в выбранном чате.
4. Пользователь, допущенный правилами кнопки, нажимает «Начать». Это может быть другой участник чата, если агент сделал кнопку публичной. Контроллер получает callback с идентификатором пользователя, данными кнопки и `inline_message_id`.
5. Подготовивший карточку агент получает событие нажатия с адресом публикации, данными кнопки, нажавшим пользователем и связью с исходным поручением/результатом.
6. Агент решает выполнить запуск и подключает обработчик Wordle и начальное состояние к этой карточке. Рендер виджета заменяет её игровым полем и игровыми кнопками; владельцем остаётся подготовивший результат агент.
7. Дальнейшие игровые действия обрабатываются механизмом виджетов; обращение к модели для каждого нажатия не требуется.

Желаемый переход одного сообщения:

```text
Wordle                 Wordle запускается…       Игровое поле Wordle
[ Начать ]      →                          →     [ игровые кнопки ]
```

Промежуточный статус «Wordle запускается…» — предложение по интерфейсу, не отдельное согласованное требование.

## 5. Предложения по интеграции

- Принято сохранять связь подготовленного результата с исходным поручением и личным агентом пользователя. Событие «Начать» направляется тому же агенту; выбор и переход к боту при отсутствии агента описаны в §25.
- Поддержать адрес сообщения как один из двух вариантов: обычный `chatId + messageId` либо `inline_message_id`. Не подставлять фиктивный `chatId` для inline-публикаций.
- Одноразовость «Начать» обеспечивать сохранённым состоянием контроллера и атомарным принятием запуска, а не только удалением кнопки в Telegram.
- Принята глобальная одноразовость группы в пределах заготовки: повторные публикации одного tipId не дают независимых запусков закрытой группы. Новая независимо подготовленная заготовка получает собственный tipId.
- Подтверждать callback быстро; создание виджета выполнять через событие агента. После принятия запуска убирать или блокировать стартовую кнопку.
- Уметь привязывать экземпляр к карточке при первом callback. Не делать получение `chosen_inline_result` обязательным условием работы.
- Проверять связь кнопки с подготовленной заготовкой и правила доступа, выбранные агентом. Публичная кнопка допускает нажатие другого пользователя, без платформенного запрета по несовпадению с автором поручения. Конверт события принят в §32; формат токенов и интерфейс подготовки inline-результата ещё уточняются. Для подключения виджета принят `set_widget_view`.

Сейчас в проверенной реализации `set_widget` подключается к известному обычному сообщению по `chatId + messageId`; обработчик callback виджетов требует `message`. Для описанного сценария нужны расширения хранения, адресации, проверки происхождения карточки и маршрутизации событий. Текущие инструменты не объявляются уже совместимыми с inline-сообщениями.

## 6. Границы Telegram, которые учитываем

- Inline-запрос содержит текст, пользователя, курсор и иногда тип чата/геолокацию. В нём нет `chatId` назначения, истории, reply-контекста, вложений или массива `entities`. «В этом чатике» означает место публикации, выбранное клиентом, а не автоматически доступный агенту диалог.
- Клиенты могут загружать следующие страницы автоматически. Задержки сети и обработки влияют на измеряемую паузу.
- Новые страницы дополняют выдачу. Пустая следующая страница в проверенных исходниках клиентов прекращает пагинацию; на пустые страницы ожидания полагаться нельзя.
- Обычные служебные пункты «Прокрутите»/«Агент думает» остаются выбираемыми inline-результатами. При выборе валидного текстового результата Telegram отправляет заранее заданное input_message_content в исходный чат; отдельный send или разрешение контроллера в этот момент не требуются. Показываемые title/description не определяют отправляемый текст. У InlineQueryResultArticle нет флага disabled или операции «при выборе ничего не отправлять»; обязательный input_message_content задаётся заранее, у InputTextMessageContent message_text имеет длину 1–4096. Пустая строка не является документированным способом отменить публикацию. См. [InlineQueryResultArticle](https://core.telegram.org/bots/api#inlinequeryresultarticle), [InputTextMessageContent](https://core.telegram.org/bots/api#inputtextmessagecontent).
- Уведомление chosen_inline_result относится к уже выбранному и отправленному результату, а не к запросу разрешения перед публикацией; использовать его для запрета отправки служебного пункта нельзя. Для барабана принят нейтральный message с крестиком (§42); невозможно обещать, что случайное нажатие строки ничего не опубликует. Удаление или последующая замена публикации не дают гарантии отсутствия исходной отправки и не принимаются как скрытый механизм отмены.
- Кнопка над выдачей имеет только действия перехода в личный диалог или открытия Mini App. Это не универсальная callback-кнопка запуска; надёжную замену её text/start_parameter при пагинации не предполагаем. В проверенном Android switch_pm сохраняется, если верхняя кнопка уже была установлена; Desktop читает параметры из последующего ответа. Межклиентской гарантии изменения нет. Для уточнений используем обычные результаты (§41).
- Опубликованное inline-сообщение можно редактировать по `inline_message_id`, включая rich-содержимое и активные кнопки. Inline-публикация сама по себе не подключает получение переписки чата.
- `chosen_inline_result` не гарантирован. Для карточек только с rich-кнопками описан случай отсутствия `inline_message_id` в feedback при наличии этого ID в последующем callback.
- Числовой предел ожидания `answerInlineQuery` не закреплён в актуальном описании Bot API. Около 10 секунд — практический ориентир из документации клиентской библиотеки, не гарантированный бюджет. `cache_time` задаёт кеширование ответа, а не время на вычисление.

## 7. Открытые вопросы

Основной сценарий, API виджетов, миграция, события нажатий, смена версии поручения, готовность через set_inline_results, буферная отправка медиа и нейтральный крестик согласованы. Основные существующие механики виджетов сохраняются, кроме явно согласованных в этом документе изменений; текущие таймауты приняты в §55. Оставшиеся детали реализации не требуют нового проектирования этих механизмов.

Основные правила обслуживания inline-запроса согласованы: общий час и хранение в памяти (§43), ошибки Telegram/БД (§49), схема кнопок (§50), сроки хранения (§51), очистка буфера (§52) и отключение агента (§53). Граница доставки button по приёму очередью и отсутствие повторной доставки после этого остаются принятыми.

Область inline-результатов определена критерием пользователя: поддержать все возможности, если они не создают существенных сложностей реализации (§56). Внешние URL входят в этот объём с нативными ограничениями Telegram. Telegram Games и счета на оплату явно исключены пользователем из текущего объёма; неподдержанные нагрузки отклоняются при валидации.

Исходный Wordle не адаптируется под отдельное табло или части интерфейса. Проверяется неизменённый текущий игровой виджет; все его view получают полный существующий рендер. Возможность нового render(state, view) остаётся для новых виджетов. О выявленной несовместимости Wordle сообщать пользователю, не исправлять её скрытой правкой игры.

Возвращение после настройки агента или передачи фото в ЛС выполняет сам пользователь новым inline-запросом (§57). Отдельный механизм возврата, сохранения исходного поручения ради возврата или автоматического продолжения requestId не нужен. Создание обработчика/состояния до публикации остаётся выбором агентского сценария. Обязательных продуктовых развилок в рамках обсуждённого сценария больше нет; остаются подготовка реализации и проверки ниже.

Точную форму диагностики неизвестной первой публикации и разбивку длинных /widget list/show можно определить при подготовке реализации в пределах согласованной семантики. Параметры доставки send и явный notify_agent сохраняют существующее поведение, если для уже принятых изменений не потребуется адаптация. Новые ограничения или самостоятельный механизм подавления явно отправленных уведомлений не вводятся. Read-only view/props и рекурсивная заморозка согласованы в §54.

Отдельно от обсуждения дизайна остаются проверки: реальная пагинация Desktop/Android/iOS и калибровка trigger/wait/числа строк барабана, разные типы результатов на одной странице и при переходе от барабана к медиа (§58), копирование/повторные публикации, reply/реакции и Guest Mode в неизвестном чате, обязательная миграция настоящего Wordle со старой версии на новую. Калибровки выполняются в ходе реализации в отдельном worktree. Проверки не считаются уже выполненными и не заменяются одним согласованием документа.

## 8. Несколько публикаций: выбранная модель рендера

Практический пример — предоставленный архив `wordle-widgets-2026-10-16.tar.gz`. В нём `widget.tsx` и `nerdle.tsx` используют общий `createGame` из `shared.mjs`. Одна функция `render(state)` выбирает меню с результатами либо игровое поле с клавиатурой. Состояние содержит партии `players`, общие `activeId`, `mode` и таймер бездействия. Игровые действия выполняются callback-обработчиками `menu`, `view`, `key`, `control` и другими.

Принята модель: один виджет, одно состояние и очередь событий; несколько публикаций, в том числе в разных чатах. Новые обработчики могут показывать одинаковое поле несколькими сообщениями, клавиатуру отдельным сообщением и табло результатов в другом месте. Создание независимой игры выполняется create_widget, подключение существующей — set_widget_view. Предоставленный Wordle остаётся без изменения исходника и показывает полную карточку в каждом view.

### Принято: единая точка входа

Выбран предложенный пользователем второй вариант с принятым названием второго аргумента: `render(state, view)`. Функция вызывается для конкретной публикации с общим состоянием виджета и описанием этой публикации. Внутри можно разделять код на `renderWords`, `renderKeyboard`, `renderResults` и другие вспомогательные функции.

Результат потенциально зависит от конкретной публикации, поэтому одинаковость отображений нельзя предполагать только по имени функции или совпадению части настроек.

### Принято: структура `view`

Название описания публикации `view` и структура `{id, target, props}` приняты: `view` соответствует одному Telegram-сообщению, пользовательские параметры называются `props`. Служебные поля отделены от произвольной JSON-конфигурации автора виджета:

```ts
view = {
  id: 'view-123',
  target: {inlineMessageId: '...'},
  props: {part: 'results', compact: true}
};
```

Адрес обычного сообщения: `{chatId, messageId}`; inline-сообщения: `{inlineMessageId}`. Принято обходиться без `kind` и определять вариант по имени поля идентификатора. Служебные `id` и `target` назначает контроллер; `props` задаются при подключении публикации. До первой отправки нового сообщения `target` содержит только `chatId`, после неё — полный адрес. `part`, `compact`, язык и другие ключи `props` — соглашения конкретного виджета, а не обязательные режимы платформы. Для inline-публикации нельзя обещать наличие обычного `chatId`.

Принято передавать `view` только для чтения, рекурсивно замораживая отдельный снимок через Object.freeze (§54). `props` описывают представление, а партии, выбранный игрок и таймеры остаются в общем `state`. Подключение публикации не должно повторно инициализировать игру.

### Принято: ошибка обновления отдельного отображения

При обновлении нескольких подключённых отображений ошибка вычисления рендера или отправки результата в Telegram для одного из них не прерывает обновление остальных. Изменённое общее состояние сохраняется; успешные обновления сообщений не откатываются. Например, запрет редактирования в одном из трёх чатов не останавливает игру и обновление двух других публикаций.

В `onError(ctx, error, event)` проблемное отображение передаётся в `error.view` по принятому ниже контракту. Отображение не отключается автоматически: следующая операция рендера, включающая его, повторяет попытку с актуальным состоянием. Отдельный фоновый цикл повторных попыток этим решением не вводится. Правила явной замены и отключения сохраняются: неуспешная замена оставляет старую привязку, а явное отключение выполняется локально даже при ошибке Telegram.

### Принято: контракт ошибки отображения

Сохраняется сигнатура обработчика `onError(ctx, error, event)`. Ошибка операции отображения содержит:

```ts
error = {
  code: 'telegram_api_error',
  message: '...',
  operation: 'render', // render | attach | replace | detach
  view: {id, target, props}
};
```

`error.view` описывает отображение, для которого операция завершилась ошибкой. `event`, если он есть, остаётся исходным событием; `event.view` указывает источник действия. Эти ссылки не подменяют друг друга: при нажатии в чате А и ошибке обновления публикации в чате Б `event.view` относится к А, а `error.view` — к Б.

Если конкретного отображения у ошибки нет, поле `error.view` отсутствует. Если операция не вызвана событием, аргумент `event` отсутствует. Сведения об источнике или ошибочной публикации не берутся из последнего обработанного события. Для первого рендера до отправки снимок может содержать принятый неполный `target: {chatId}`.

При `operation: 'replace'` поле `error.view` содержит новое отображение, которое пытались подключить, а `error.previousView` — сохранённое прежнее. Оба снимка имеют форму `{id, target, props}`; новый ID в диагностике не означает подключения нового view. Для остальных операций `previousView` отсутствует.

### Принято: ошибка самого `onError`

Для ошибок отображений исключение из `onError` не приводит к повторному вызову этого хука. Сохраняются обе ошибки, исходная и ошибка обработчика, как одна необработанная ошибка отображения. Уведомление агенту отправляется только при первой записи `lastError` по правилу ниже. Виджет и остальные отображения продолжают работать. Неуспешная замена оставляет прежнюю привязку, явное отключение остаётся выполненным локально, а ошибка рендера не откатывает общее состояние. Правила аварий всего runtime рассматриваются отдельно.

### Принято: сохранённая ошибка отображения вместо частых уведомлений

По предложению пользователя выбирается одно сохранённое значение `lastError` на отображение. Это служебное состояние контроллера, отдельное от общего пользовательского `state` игры и от `view.props`; менять игровой Wordle ради него не требуется. Запись доступна агенту при чтении сведений об отображении и сохраняется между перезапусками.

Правила:

- Ошибка, обработанная в `onError`, не создаёт новую запись необработанной ошибки. Отсутствие хука или ошибка самого хука оставляют исходную ошибку необработанной; во втором случае к ней прикладывается вторичная ошибка.
- При первой записи в ранее пустой `lastError` агент получает одно уведомление.
- Если `lastError` уже заполнен, следующая необработанная ошибка заменяет его значение последней ошибкой, без нового уведомления. Смена кода, текста, пользователя или исходного события это правило не меняет.
- Успешный автоматический рендер, обработанный следующий сбой, таймер, нажатие, течение времени и перезапуск сами по себе сохранённую запись не очищают. Виджет продолжает работать по остальным принятым правилам.
- Успешное изменение агентом отдельного `view` сбрасывает только его `lastError`. Успешное изменение общего пользовательского состояния или handler виджета сбрасывает ошибки всех его отображений. После сброса новая первая необработанная ошибка снова может породить уведомление.
- Чтение данных и неудачная попытка управляющего изменения ничего не сбрасывают. Ошибка самой попытки возвращается агенту непосредственно в ответе инструмента; неудачная попытка исправления не должна заново разрешать повторное уведомление о сохранённой проблеме.

Таким образом, повторные таймеры и клики не запускают агента, пока запись заполнена. Интервалы подавления, группировка по кодам и периодические сводки не нужны. Обычные игровые `ctx.api.notify_agent`, например результат партии Wordle, не подавляются этим правилом. Явные отправки из пользовательского `onError` ещё требуют отдельного уточнения. Необработанная ошибка подключения без созданного view сохраняется в общем `widget.lastError`; сведения о возможной публикации с неизвестным результатом учитываются отдельно по §23.

### Принято: необработанная ошибка на уровне виджета

Добавляется служебный `lastError` на уровне виджета, отдельно от пользовательского `state`, для необработанных ошибок общего обработчика, таймеров и lifecycle, а также `onViewDelete`, когда отображение уже отвязано, и `attach`, когда view ещё не создан. Ошибка рендера конкретного подключённого отображения по-прежнему хранится в его собственном `lastError`; один лишь `event.view` не делает общую ошибку обработчика ошибкой публикации.

Правило уведомления такое же: первая запись при пустом значении уведомляет агента, последующие только заменяют сохранённую ошибку, обработанная в `onError` ошибка новой записи не создаёт. Снимок удалённого отображения можно сохранить в диагностике ошибки без восстановления привязки. Успешное изменение агентом общего состояния или handler сбрасывает общий `lastError` вместе с ошибками отображений; изменение отдельного отображения очищает только его ошибку. Чтение и неудачная попытка изменения ошибок не очищают. Общая ошибка сохраняется между перезапусками, как и ошибка отображения; полный список сбрасывающих управляющих операций уточняется вместе с API.

Успешное восстановление из `stopped` через `update_widget` также очищает общий `lastError` и ошибки всех отображений. Старые записи очищаются после успешного `onInit`, до фиксации новых ошибок последующего рендера. Если `onInit` снова завершается ошибкой, предыдущая запись заменяется последней ошибкой по обычному правилу и не очищается как при успешном восстановлении.

### Принято: очередь событий во время обычного рендера

Принято сохранять все типы событий, включая кнопки, в очереди во время обычного рендера, в рамках действующих ограничений очереди. Перед выполнением события кнопки проверяется, что исходный `view` по-прежнему подключён с тем же идентификатором и в последнем успешно опубликованном содержимом этого отображения есть кнопка с точно таким же `callback_data`. Если кнопка исчезла, событие игнорируется с подтверждением без текста. Проверка относится к конкретной публикации, включая её обычные и rich-кнопки, и повторяется перед каждым обработчиком: предыдущий обработчик мог снова изменить сообщение.

Это решение не отменяет отсечение кнопок при замене `view`: совпадение `callback_data` у нового отображения не разрешает выполнить старое нажатие. Ожидание обычного рендера и правила событий при замене рассматриваются отдельно.

По проверенному текущему коду `events.mjs` допустимость callback проверяется при получении обновления; одной такой проверки недостаточно для принятой очереди. `render.mjs` сохраняет `buttonNames` после успешной публикации. Для новой модели такой список нужен на каждом отображении, а проверка — также непосредственно перед выполнением отложенного обработчика. Обычная ошибка рендера не должна подменять список кнопками неотправленного результата. При неопределённом результате действует принятое правило §20: кнопки данного view игнорируются до подтверждённой публикации, сохранённый набор остаётся историей, следующий рендер обходит кеш.

Совпадение `callback_data` означает сохранение действия при обычном рендере. Обработчик всё равно проверяет допустимость действия по текущему состоянию и пользователю; например, Wordle не должен принимать ход чужого игрока только из-за наличия кнопки. Приложениям, для которых одноимённая кнопка означает новое несовместимое действие, потребуется различать такие действия в `callback_data`.

Для callback, который ждёт в очереди, сохраняется ожидание обработчика ради его `event.respond({text, showAlert})` или возвращаемого значения. По проверенному текущему коду короткого таймера подтверждения нет, и пользователь выбрал сохранить это поведение: новый таймер на 2 секунды не вводится. Первый ответ имеет приоритет; поздний или повторный `event.respond` после уже выбранного подтверждения завершается без ошибки и повторной отправки. Ожидание само по себе не удаляет допустимое событие из очереди. Пустые подтверждения при отсечении или отклонении события сохраняются по отдельным принятым правилам. В Wordle ответы кнопок используются для пояснений и отказа в чужом ходе, поэтому ответы обработчика сохраняются.

### Принято: замена отображения

Для новых параметров повторно подключаем то же сообщение с новыми `props`. При успешной замене старое `view` отключается, создаётся новое с новым идентификатором; адрес Telegram-сообщения сохраняется. Отдельная операция изменения `props` не нужна. При подключении к тому же виджету его состояние и таймеры сохраняются, остальные отображения не затрагиваются.

Перед заменой ждём завершения уже выполняющегося рендера старого `view`, включая его публикацию: успех и ошибка одинаково завершают ожидание. Замена и рендеры этой публикации упорядочиваются; новые рендеры старого `view` не должны обходить ожидающую замену и позднее перезаписывать новое отображение.

Замена стоит в общей очереди операций и событий виджета. Уже принятые события, поставленные раньше неё, выполняются перед заменой; для нового отображения используется состояние после этих событий. Их не отбрасываем из-за предстоящего отключения старого `view`. При этом по-прежнему требуется дождаться начатого рендера старой публикации.

Принято: новые события кнопок, поступающие во время замены, не ставятся на последующую обработку. Callback подтверждается без текста; обработчик и изменение состояния по этому нажатию не выполняются. При неудачной замене эти нажатия также не воспроизводятся. Отсечение начинается при принятии валидной операции замены в очередь после проверок аргументов, прав и конфликта привязки, включает ожидание текущего исполнения и завершается после окончательного результата операции. Ранее принятые события выполняются перед заменой. При нескольких уже принятых заменах того же сообщения отсечение действует до завершения всех таких операций без промежуточного окна. Запрещённый или невалидный запрос сам по себе отсечение не включает. Это правило относится к замене отображения; автоматическое отсечение кнопок во время любого обычного рендера не принято.

Reply и reaction во время замены сохраняются в очереди по принятому правилу §14: смена `view.id` при непрерывной принадлежности сообщения тому же виджету их не отменяет. Для poll/poll_answer дополнительно требуется непрерывное сохранение того же `pollId` по §18. По текущему `src/widgets/events.mjs` реакции и опросы частично обновляют внутренние проекции до передачи события в очередь; наблюдения реакций того же сообщения не сбрасываются только из-за замены view, наблюдения разных опросов хранятся отдельно.

Исходный снимок `event.view` у ожидающего reply/reaction не заменяется новыми `id` или `props`; это согласованное исключение из проверки прежнего подключённого `view.id`. Явная отвязка или смена виджета-владельца сообщения всё равно запрещает старое событие. Агентские и таймерные события не следует отсекать как нажатия данного отображения.

Если замена завершается ошибкой, вызывается `onError(ctx, error, event)` с `error.operation: 'replace'`, прежняя привязка сохраняется. `error.view` описывает неудавшееся новое отображение, `error.previousView` — сохранённое старое. Неопределённый результат публикации пока обрабатывается тем же способом: считаем его ошибкой и сохраняем старое `view`. Сохранение локальной привязки не означает, что сообщение в Telegram гарантированно не изменилось; распределённый откат этим решением не обещается.

Для Wordle несколько публикаций с `{part: 'words'}` показывают общее поле, `{part: 'keyboard'}` — клавиатуру, `{part: 'results'}` — результаты без старта, `{part: 'game'}` — полную карточку. Названия и набор представлений пока являются примерами.

### Принято: источник события в `event.view`

События от конкретного сообщения получают `event.view` той же формы `{id, target, props}`, что передаётся рендеру. Контроллер фиксирует снимок идентичности, адреса и параметров источника при приёме события в очередь; обработчик получает его только для чтения. Изменения состояния и ожидание в очереди не подменяют источник. Актуальность привязки проверяется перед вызовом обработчика по согласованным правилам рендера, замены и отключения.

```ts
event.view = {
  id: 'view-123',
  target: {chatId: -1001234567890, messageId: 456},
  props: {part: 'keyboard'}
};
```

У событий агента и общих таймеров `event.view` отсутствует: они не получают фиктивное отображение или источник предыдущего события. В Wordle обработчик может определять по `event.view.props.part`, с какого отображения пришло нажатие; неизменённый старый обработчик просто не использует новое поле. Сохранять `ctx.message` ради игры не требуется.

### Действия табло результатов

Отсутствие кнопки старта и полностью пассивное табло — разные режимы. В текущем `resultsTable` есть кнопки `view:<playerId>`; обработчик `view` меняет общий активный выбор при отсутствии активного таймера. Это существующее поведение Wordle сохраняется. Отдельное табло без старта или полностью пассивное представление остаётся возможностью новых обработчиков, а не требованием изменить предоставленную игру. При маршрутизации callback необходимо проверять кнопки конкретной публикации, а не объединение кнопок всех отображений виджета.

### Принято: отключение отображения

При явном отключении `view` сохраняем Telegram-сообщение с последним содержимым, прекращаем его обновления и отключаем все кнопки любых типов, включая URL, копирование и другие действия. Правило охватывает нижнюю inline-клавиатуру и все встроенные rich-кнопки. Изменение затрагивает активность кнопок, остальное содержимое сообщения сохраняется. Удаление самого сообщения — отдельная операция. Общее состояние, таймеры и другие отображения сохраняются.

Принят вариант 1 обработки ошибки: если обновление Telegram завершилось ошибкой, привязка всё равно отключается локально. После отключения все события от этого `view` игнорируются: callback, ответы, реакции и другие связанные с ним события, когда они доступны контроллеру. Они не передаются обработчикам виджета или агенту как действующие события этого отображения, не меняют состояние и не запускают рендер. Это не останавливает общие таймеры и события других отображений.

Ошибка операции отключения передаётся в `onError` единожды. Поздние нажатия и другие игнорируемые события не вызывают дополнительных вызовов `onError`. Внешний вид сообщения может остаться прежним, а клиентские действия вроде URL-кнопок и копирования могут продолжить работать, пока сообщение не исправлено: локальная фильтрация событий не отключает действия на стороне клиента.

### Принято: удаление всего виджета

Удаление работающего виджета сначала выполняет согласованную остановку: закрытие приёма, очистку очереди, завершение текущей работы, `onStop` и обязательную очистку ресурсов с отключением кнопок. У уже остановленного виджета повторного `onStop` нет. Затем удаляются регистрации отображений и общее состояние. Telegram-сообщения сохраняются как последние снимки с отключёнными кнопками, насколько удалось выполнить обновление. Ошибки Telegram не оставляют привязки активными и не отменяют удаление виджета. Детали собственного удаления из обработчика и отдельных ошибок ещё требуют уточнения.

### Совместимость собственного удаления Wordle

Игровой `finish` уже выполняет `await ctx.render()`, затем `await ctx.api.delete_widget({widgetId: ctx.widgetId})`. В проверенном текущем `manager.delete` собственный вызов после фиксации намерения удаления не ждёт завершения всей очистки; полная операция выполняется асинхронно. Это поведение необходимо сохранить для совместимости: обработчик не должен ждать остановки, которая сама ждёт его завершения.

В новой модели собственный вызов подтверждает принятие удаления, закрывает приём событий и очищает очередь, позволяет текущему обработчику закончиться, затем выполняет внутреннюю очистку, отключение кнопок всех view и удаление регистрации. Прямой вызов агента может дождаться завершения операции. Отдельного собственного `stop_widget` для этого не требуется. Финальное содержимое публикуется до запроса удаления, как уже делает Wordle.

### Принято: удаление сообщения отвязывает только его отображение

Когда контроллер узнаёт об удалении Telegram-сообщения, его отсутствии или потере доступа к нему, соответствующее `view` отвязывается от виджета. Обновлять кнопки отсутствующего или недоступного сообщения при этой отвязке не требуется. Общий `state`, другие отображения и таймеры активного виджета сохраняются; удаление последнего сообщения само по себе не удаляет и не останавливает виджет. Повторная информация о том же событии не должна повторять отвязку.

В проверенном `controller.mjs` текущий агентский `delete` после удаления сообщения вызывает `widgets.delete` и удаляет всю регистрацию виджета. В новой модели эту ветку необходимо заменить на отвязку конкретного отображения. Это требование к будущей реализации, а не уже изменённое поведение.

Обнаружение удаления ограничено Telegram: в перечне Bot API `Update` нет общего события удаления обычных сообщений; `deleted_business_messages` относится к подключённым business-аккаунтам. Удаление через собственный API контроллер знает непосредственно; внешнее удаление может обнаружиться позднее при попытке обновления. Не каждая ошибка редактирования доказывает удаление, но по принятому решению классифицированная потеря доступа также приводит к отвязке с собственной причиной. Контракт не обещает мгновенного уведомления при удалении вручную.

### Уточнение: обнаружение отсутствующего сообщения при публикации рендера

При реальном вызове Telegram `edit*` можно получить `Bad Request: message to edit not found`. Проверенный официальный `Client.cpp` формирует этот ответ через `check_message(..., "message to edit", ...)`; проверка также возвращает его при отсутствии доступа к сообщению (`!have_message_access(chat_id)`). Следовательно, это сигнал «не найдено или недоступно», а не безусловное доказательство физического удаления.

Классифицированные `message_not_found` и потеря доступа к сообщению/чату существующего отображения приводят к отвязке как при удалении, а не к `onError` рендера или новому `lastError`. Причина отвязки при этом сохраняет различие между случаями. Невозможность изменить конкретный тип содержимого, неверный payload, ограничения частоты и транспортные ошибки сами по себе потерей доступа не считаются и остаются в обычной обработке ошибок. Точный перечень ответов Telegram для этих категорий предстоит определить при реализации и проверках.

Само вычисление `render(state, view)` ничего не сообщает о существовании сообщения. В текущем `render.mjs` при совпадении `renderHash` запрос в Telegram вообще пропускается, поэтому такой рендер не обнаружит удаление. Поведение и точные ответы редактирования по `inlineMessageId` нужно проверить отдельно на реальном клиенте/API, без переноса гарантий обычного адреса на inline.

### Принято: `onViewDelete(ctx, event)`

Для удаления, отсутствия сообщения и потери доступа используется один необязательный lifecycle-хук `onViewDelete(ctx, event)`. Второй аргумент — объект события вместо отдельных позиционных аргументов; это позволяет расширять сведения без изменения сигнатуры. Основа события:

```ts
event = {
  view: {id, target, props},
  reason: 'access_lost'
};
```

Для `reason` используются различимые значения: `message_deleted` — подтверждённое удаление, `message_not_found` — сообщение не найдено при обновлении, `access_lost` — обнаруженная потеря доступа. `event.view` — снимок отвязанного отображения только для чтения. Дополнительные сведения о времени обнаружения или ответе Telegram можно позднее добавить необязательными полями; они пока не требуются.

Сначала контроллер фиксирует отвязку, затем для работающего виджета выполняет хук в общей последовательности операций, без вложенного вызова пользовательского обработчика посреди текущего рендера. Это служебное lifecycle-событие контроллера после отвязки, а не разрешение выполнять обычные события отключённого источника. Остальные отображения продолжают обновляться. Отсутствие хука означает штатную отвязку без дополнительных действий; агент автоматически не вызывается. При необходимости сам хук может изменить состояние, обновить оставшиеся публикации или явно уведомить агента.

Повторная информация об одной и той же утрате сообщения не повторяет отвязку и вызов хука. Ошибка хука не восстанавливает привязку; если она не обработана, сохраняется в общем `widget.lastError` с исходным снимком для диагностики. При обычном `delete_widget_view`, замене отображения и удалении всего виджета этот хук не вызывается. У `stopped` выполняется только отвязка, без запуска обработчика и без отложенного вызова после возобновления.

### Принято: состояния виджета `active | stopped`

Сохраняется отдельное состояние остановки всего виджета с названием `stopped` вместо `disabled`. В `active` виджет обрабатывает события и выполняет таймеры. В `stopped` исполнение обработчиков и таймеров прекращается, но пользовательское состояние, handler, регистрации отображений и причина остановки сохраняются; виджет доступен агенту для управления и последующего возобновления.

`stopped` предназначен для системных/аварийных случаев, когда исполнение невозможно или запрещено: например, сбой `onInit`, авария runtime, нарушение heartbeat или отключение агента. Отдельного публичного метода ручной остановки нет; для прекращения работы агент использует `delete_widget`, для исправления и повторного запуска — `update_widget`. Ошибка одного отображения и заполненный `lastError` сами по себе виджет не останавливают. Отсутствие отображений тоже не означает остановку: таймеры тогда продолжают работать. Удалённый виджет не является третьим сохранённым статусом: его регистрация и общее состояние удаляются.

В проверенном текущем `manager.mjs` старый `disabled` используется для ошибок, аварии runtime, отключения агента и прерванного создания; `controller.mjs` при отключении агента вызывает `disableOwner`. При миграции старый `active` сохраняется, `disabled` переводится в `stopped` с сохранением причины. Ранее отключённые регистрации автоматически не запускаются; явный `update_widget` может восстановить их с проверкой текущих разрешений.

### Принято: очередь событий остановленного виджета

При остановке очищаются все ещё не выполненные события виджета: нажатия, reply, реакции, опросы, агентские и внутренние события, включая события таймеров. Правило охватывает оперативную и сохранённую очередь; очистка должна сохранять силу после перезапуска, чтобы старые события не появились вновь.

В состоянии `stopped` новые события не накапливаются для будущего исполнения. Callback подтверждается без текста, обработчики не вызываются. При возобновлении виджет начинает принимать новые события; очищенные и отброшенные ранее события не воспроизводятся. Восстановление таймеров через `onInit` по актуальным срокам состояния не является воспроизведением старого события таймера.

Это правило не блокирует отдельные управляющие операции агента: чтение регистрации, исправление состояния/handler, управление отображениями, возобновление и удаление. Конкурирующие управляющие изменения должны учитывать незавершённую остановку и не обходить её упорядочивание.

### Принято: граница остановки текущего исполнения

При запросе остановки контроллер сразу закрывает приём новых событий виджета и очищает ожидающие события. Уже выполняющийся обработчик и его рендер, включая публикацию в Telegram, завершаются в обычном порядке — успехом или ошибкой. Следующее событие на исполнение не извлекается. Затем контроллер завершает остановку и отключает кнопки всех сохранённых отображений.

Начатое действие не считается отменённым только из-за внутреннего запроса остановки: его уже выполненные внешние эффекты не обещается откатить. После завершения остановки старая публикация не должна заново активировать кнопки. Для зависшего исполнения применяется принятая ниже общая аварийная остановка runtime. Этот механизм используется контроллером, а не предоставляется агенту отдельным публичным методом остановки.

### Принято: завершающий хук `onStop`

Принят порядок штатной остановки:

1. Закрыть приём событий и очистить ожидающую очередь.
2. Дождаться текущего обработчика и его рендера, включая публикацию.
3. Один раз вызвать `onStop(ctx)` для текущего запущенного экземпляра.
4. Независимо от успеха хука очистить оставшиеся таймеры, освободить runtime и отключить кнопки.

Ошибка `onStop` фиксируется, но остановка завершается. Повторная остановка уже остановленного виджета хук не вызывает. После последующего возобновления начинается новый цикл работы, который снова может завершиться одним вызовом `onStop`. Для Wordle это сохраняет существующий хук очистки таймера, а контроллер дополнительно освобождает оставшиеся таймеры независимо от результата хука. При зависании хука или всего исполнения применяется общая аварийная ветка ниже.

### Принято: зависшее исполнение, heartbeat и аварийная остановка

В проверенном `host.mjs` runtime привязан к паре `botId + agentId`, а не к одному виджету. Текущий `manager.mjs` ограничивает `retire` значением `WIDGET_LIMITS.teardownMs` (сейчас 5 секунд); превышение вызывает общую ветку аварии runtime. В `manager.failure` останавливаются виджеты этого владельца и отправляется одно уведомление со списком затронутых виджетов. Отдельно `host` следит за heartbeat и памятью процесса.

Принято сохранить границу изоляции runtime агента и ограничить ожидание штатного завершения обработчика/рендера и `onStop`. При превышении срока, а также при нарушении heartbeat проверки применяется одна аварийная ветка:

1. Закрыть приём событий и дальнейшие действия затронутого runtime.
2. Перевести его виджеты в `stopped`, сохранить причину, очистить оперативные и сохранённые ожидающие очереди. Существующие остановленные регистрации не возобновлять.
3. Принудительно завершить процесс runtime; не ждать выполнения пользовательских завершающих хуков.
4. Сохранить последнее подтверждённое состояние и привязки сообщений; отключить кнопки отображений, насколько позволяет Telegram.
5. Отправить агенту одно объединённое уведомление о причине и затронутых виджетах. Повторные heartbeat-проверки или параллельное обнаружение той же аварии не создают новые уведомления.

Область аварии — общий runtime пары `botId + agentId`; виджеты других runtime не затрагиваются. После аварии автоматического возобновления остановленных виджетов нет. Поздние сообщения старого процесса не должны возобновить исполнение или восстановить очищенную очередь. Вызов `onStop` при принудительном завершении не гарантируется, уже выполненные внешние действия не откатываются.

Текущие значения лимитов штатного завершения и heartbeat сохраняются по принятому §55. Изоляция отдельного процесса на каждый виджет не вводится.

### Принято: время и таймеры при возобновлении

Остановка прекращает исполнение, но не замораживает реальное время и не сдвигает пользовательские сроки в `state`. При возобновлении загружается обработчик, вызывается `onInit`, который восстанавливает таймеры по сохранённому состоянию, затем обновляются отображения. Повторный `onCreate` не вызывается, контроллер не воспроизводит пропущенные срабатывания пачкой. Ошибка инициализации оставляет виджет в `stopped`. Ошибки обновления отдельных отображений подчиняются принятой независимой обработке таких ошибок.

Это совместимо с предоставленным Wordle: `onInit` вызывает `armIdle`, а тот сравнивает `idleDeadline` с `Date.now()`. При истёкшем сроке игрок получает `status: 'paused'`, дедлайн очищается; при будущем сроке создаётся таймер на оставшееся время. Это состояние партии внутри игры, отдельное от платформенного `stopped`. Например, остановка на десять минут при оставшихся сорока секундах до бездействия не даёт новых сорока секунд при возобновлении.

### Принято: сообщения и кнопки остановленного виджета

При остановке сообщения остаются с последним содержимым, контроллер отключает все обычные и rich-кнопки после завершения текущего обработчика/рендера и завершающего `onStop`. Регистрации отображений, их идентификаторы и `props` сохраняются, в отличие от отключения отдельного `view`. В состоянии `stopped` новые события от этих публикаций не выполняются и не откладываются; callback подтверждается без текста. Ошибка обновления кнопок не отменяет остановку. При возобновлении рендер из актуального состояния восстанавливает содержимое и доступные кнопки тех же сохранённых отображений. Если редактирование Telegram не удалось, кнопки могут внешне остаться прежними; контроллер всё равно не исполняет события остановленного виджета.

### Принято: операции виджета и отображений

Создание общего виджета и подключение отображений разделяются. Принятое разделение ответственности операций, аргументы пока схематичны:

- `create_widget({handler, description, state})` создаёт виджет без отображений и возвращает `widgetId`; описание виджета `description` обязательно при создании.
- `set_widget_view` подключает новое или существующее сообщение как отображение виджета; повторное подключение того же сообщения заменяет его `view` по принятому правилу. Новый и существующий адреса задаются через `send` и `target` соответственно.
- `delete_widget_view({viewId})` отключает конкретное отображение; для сохранённого кандидата с неизвестным адресом удаляет только служебную запись по §24, без изменения Telegram-сообщения.
- `delete_widget({widgetId})` удаляет виджет со всеми отображениями.

Все операции управления виджетами и отображениями проверяют агента-владельца. Общее разрешение на публикацию в канале не даёт права заменить, отключить, удалить или обновить чужой виджет/view. При подключении сообщения, занятого другим виджетом, действует конфликт §17 с `ownerAgentId`; это относится и к двум разным виджетам одного агента.

Для inline-Wordle агент после события «Начать» создаёт виджет и подключает опубликованную карточку по `inlineMessageId`. Для общего табло в другом сообщении подключает новое `view` к тому же `widgetId` с параметрами результатов. Если подключение не удалось, созданный виджет может оставаться без отображений; повторное подключение не должно создавать новую игру.

Методы агента можно обновить, включая замену `set_widget` новым набором операций. Новый API должен управлять и ранее созданными регистрациями, а не только новыми. Это отдельное требование от совместимости контекста обработчика Wordle: используемые самой игрой `ctx.api.notify_agent` и `ctx.api.delete_widget` сохраняются. Требования к API управления и миграции описаны в разделе 9. Проверка доступа и дополнительные аргументы нового API ещё уточняются.

### Принято: обновление существующего виджета

Принят `update_widget({widgetId, handler?, description?, state?})`. Метод изменяет существующую регистрацию, включая мигрированную, без создания новой игры или отображений. Опущенные поля сохраняют прежние значения. Переданный `state` заменяет пользовательское состояние целиком, без неявного глубокого слияния. Переданный `handler` означает загрузку новой версии кода, включая случай того же пути после редактирования файла.

`description` описывает сам виджет для агента и обязательно только при создании. При обновлении оно опционально и может заменяться самостоятельно или вместе с handler/состоянием. Если `description` не передано, сохраняется прежнее значение, в том числе при смене handler; не требуется повторять описание только ради загрузки новой версии кода.

`widgetId`, все существующие `view`, их идентификаторы, адреса сообщений и `props` сохраняются. Каждое успешное обновление виджета повторно вызывает `render(state, view)` для всех его подключённых отображений, включая обновление только описания. Публикация результата подчиняется обычным правилам кеширования и независимых ошибок отображений; ререндер не означает пересоздание сообщений или привязок. При отсутствии отображений обновление сохраняется без отправки сообщений.

Любой `update_widget` для `stopped` является явной попыткой запуска: применить переданные параметры, загрузить handler, выполнить `onInit` и рендерить сохранённые отображения. Это относится и к обновлению только описания, и к вызову `update_widget({widgetId})` без новых полей. При успехе виджет становится `active`, таймеры восстанавливаются и кнопки формируются обычным рендером; при сбое `onInit` остаётся `stopped` с сохранением частичных изменений состояния. Проверки владения и разрешений не обходятся. Отдельной операции resume нет.

При успешном изменении общего состояния/handler или успешном восстановлении из `stopped` очищаются прежние общий и view-ошибки. У `active` изменение только описания или вызов без новых полей прежние ошибки не очищают. Новые ошибки последующих рендеров фиксируются заново и возвращаются в `renderErrors`. Порядок смены handler и форма результата при принятом обновлении согласованы ниже; детали отдельных ошибок применения ещё уточняются.

### Принято: результат обновления при ошибке отдельного рендера

Различаются ошибка подготовки/применения обновления и ошибки последующего рендера или публикации отдельных отображений. Если общее обновление принято, но одно из отображений не обновилось, принятое состояние/handler и успешные публикации не откатываются. Агент получает результат:

```ts
{
  widgetId: 'widget-123',
  renderErrors: [{viewId: 'view-3', code: '...', message: '...'}]
}
```

При отсутствии ошибок `renderErrors` пуст. Ошибка подготовки или применения самого обновления возвращается как ошибка операции, а не как успешный результат с `renderErrors`. Потеря сообщения, приводящая к штатной отвязке и `onViewDelete`, в ошибки рендера не включается. Детали момента сброса и записи новых ошибок ещё уточняются; основной lifecycle обновления согласован ниже.

### Принято: подготовка новой версии handler до замены

Новый handler компилируется и аргументы обновления, включая формат переданного состояния, проверяются до остановки старого экземпляра и изменения регистрации. Ошибка подготовки возвращается агенту напрямую и не меняет старый handler, пользовательское состояние, статус, отображения или сохранённые ошибки. Работающий экземпляр продолжает обычную работу; его независимые события и таймеры не считаются запрещёнными изменениями состояния из-за неудачной подготовки.

После успешной подготовки применение обновления упорядочивается с текущими событиями и рендерами виджета. Принятый порядок `onStop` старой версии и `onInit` новой описан ниже; сбой инициализации останавливает виджет с сохранением частичных изменений состояния. Подготовка не обещает заранее обнаружить все ошибки исполнения или выполнить `onInit` без побочных эффектов до замены.

### Принято: lifecycle применения обновления

Для агентского `update_widget` изменение handler или явно переданного пользовательского состояния требует переинициализации работающего экземпляра. Это позволяет восстановить таймеры и ресурсы согласно новому коду/состоянию. У `active` изменение только описания или вызов без новых полей требует ререндера всех отображений, без `onStop` и повторного `onInit`. У `stopped` любой вызов обновления требует попытки запуска через `onInit`.

После успешной подготовки операция применяется в очереди виджета: завершить предшествующие действия и публикации, вызвать `onStop` старого экземпляра и освободить его таймеры/ресурсы, применить обновление, загрузить новый экземпляр и вызвать `onInit`, затем рендерить все сохранённые отображения. `onCreate` повторно не вызывается. При сбое `onInit` действует принятое правило остановки с сохранением частичных изменений состояния.

При успешном обновлении работающего экземпляра `view.id`, привязки и статус `active` сохраняются, новые события ждут завершения обновления в очереди; сам по себе переход к новому экземпляру очередь не очищает. Если инициализация завершается ошибкой и виджет становится `stopped`, очередь очищается по правилу системной остановки. Для исходного `stopped` старого работающего экземпляра нет: повторный `onStop` не нужен, обновление запускает сохранённую/обновлённую версию через `onInit` и при успехе переводит только этот виджет в `active`.

### Принято: сбой `onInit` при создании или замене

Успешная инициализация обязательна для запуска: исключение из `onInit` переводит конкретный виджет в `stopped`, закрывает приём событий, очищает очереди и ресурсы неудачного запуска, отключает кнопки сохранённых отображений по возможности. Обработка ошибки в `onError` не должна разрешать продолжить обычную работу после незавершённого `onInit`. Если очистка зависает или нарушен heartbeat общего runtime, применяется принятая аварийная ветка для этого runtime.

При создании сохраняется созданная регистрация в `stopped`, её `widgetId` возвращается в ошибке: агент сможет прочитать диагностику, исправить или удалить виджет вместо создания дубликата. При замене сохраняются прежний `widgetId` и все отображения, но новый handler остаётся неработающим; автоматического возврата к старому запущенному экземпляру нет.

Принят вариант без отката состояния: изменения `ctx.state`, сделанные неуспешным `onInit` до исключения, сохраняются по обычным правилам нормализации и допустимости состояния. Следующая попытка инициализации получает это частично изменённое состояние. Если агент передал новый `state` при обновлении, хук изменяет именно его; ошибка не возвращает прежнее состояние партии автоматически. Внешние эффекты хука также не откатываются.

Если создание/замена непосредственно вызваны агентом, ошибка возвращается в том же ответе инструмента, без отдельного события агенту. Диагностические поля ошибки:

```ts
{
  code: 'widget_init_failed',
  phase: 'onInit',
  widgetId: 'widget-123',
  status: 'stopped',
  message: '...'
}
```

Ошибка сохраняется в `widget.lastError` и доступна через `get_widget`. Для фоновой инициализации при восстановлении без текущего агентского вызова применяется одно уведомление по правилу первой записи общего `lastError`. Ошибка `onInit` не является успешным обновлением с `renderErrors`; интерфейс инструментов должен сохранять `widgetId`, этап и статус при сериализации ошибки.

### Принято: чтение виджетов агентом

`list_widgets()` возвращает краткий список собственных регистраций агента, включая активные, остановленные, мигрированные и виджеты без отображений. Форма ответа сохраняет существующие верхнеуровневые поля:

```ts
{
  canCreate: 7,
  items: [{widgetId, description, status, viewCount, hasError}]
}
```

`canCreate` — не boolean, а неотрицательное число виджетов, доступных для создания. Эта возможность уже есть в проверенном `manager.list`: при доступном runtime возвращается `Math.max(0, L.widgets - items.length)`, иначе `0`. Новая модель сохраняет смысл расчёта: квота считается по зарегистрированным виджетам, включая `stopped` и виджеты без отображений, а не по числу `view`. Добавление отображения не создаёт ещё один виджет. Действующие значения квот берутся из конфигурации/лимитов приложения, а не из примера ответа.

`hasError` учитывает как общий `lastError`, так и ошибки отдельных отображений. Пользовательский `state` и полные диагностические записи в краткий список не включаются.

`get_widget({widgetId})` возвращает полную карточку: идентификатор, handler, описание, статус и причину остановки, пользовательский `state`, общий `lastError` и список `views` со служебными `id`, `target`, `props`, `lastError`. Чтение не запускает runtime остановленного виджета и не сбрасывает ошибки. Права владельца сохраняются; наличие публикаций в других чатах не передаёт виджет другому агенту. Эти имена и состав ответов приняты.

Отдельно от подключённых `views` карточка также показывает служебные сведения о возможных первых публикациях с неизвестным результатом по §23. Они не исчезают при очистке `lastError` и не увеличивают `viewCount`; точная форма записи ещё уточняется.

### Принято: `send` или `target` в `set_widget_view`

Для отправки нового сообщения передаём `send` с параметрами доставки; для подключения существующего — `target` с его адресом. Должно быть указано ровно одно из полей `send` и `target`. В обоих случаях контент сообщения формируется через `render(state, view)`, а `props` задают представление. `send` не содержит дублирующих полей содержимого.

Для агента выбран адрес без избыточного `kind`: `{messageId, chatId?}` или `{inlineMessageId}`. В первом случае `messageId` — целое число, во втором `inlineMessageId` — непустая строка. `chatId` при наличии — целое число и допустим только с `messageId`. Это различение по именам полей, а не попытка распознать происхождение произвольной строки ID. Полный адрес в результате операции и `view.target` также не содержит `kind`.

Отклоняются с `invalid_argument`: пустой `target`, один `chatId` без `messageId`, одновременные `messageId` и `inlineMessageId`, сочетание `chatId` с `inlineMessageId`, неправильные типы и одновременные `send` и `target`. Для отправки нового сообщения в выбранный чат используется `send: {chatId}`, а не неполный `target`.

```ts
// Новое сообщение в текущем чате агента.
await set_widget_view({widgetId, send: {}, props: {part: 'game'}});

// Существующее сообщение в текущем чате агента.
await set_widget_view({
  widgetId,
  target: {messageId: 456},
  props: {part: 'results'}
});

// Новое сообщение в канале, куда разрешено публиковать.
await set_widget_view({
  widgetId,
  send: {chatId: -1001111111111},
  props: {part: 'results', compact: true}
});

// Новое сообщение в разрешённой соседней супергруппе.
await set_widget_view({
  widgetId,
  send: {chatId: -1002222222222},
  props: {part: 'game'}
});
```

При опущенном `chatId` используется текущий чат вызова агента. Это не неизвестный чат, в котором пользователь набирал inline-запрос. Для ранее опубликованной inline-карточки используется `target: {inlineMessageId}` из события.

Результат успешной операции: `{viewId, target}`, где адрес уже полный и однозначный: `{chatId, messageId}` для обычного сообщения либо `{inlineMessageId}` для inline-сообщения.

При первой отправке без подтверждённого адреса действует принятое правило §22: `delivery_unknown`, отсутствие подключённого view и автоматического повтора, сохранение диагностики с известными идентификаторами. Такой ответ не является успешным `{viewId, target}`. Ошибка после получения адреса должна сохранять этот адрес в диагностике, чтобы агент мог подключить существующую публикацию через `target`.

Принято: перед первым рендером нового сообщения `view.id` и `props` уже назначены, а `view.target` содержит `{chatId}` без `messageId`. После успешной отправки последующие рендеры получают `{chatId, messageId}`; идентификатор отображения и параметры не меняются. При подключении существующего обычного или inline-сообщения адрес сразу полный. Пример одного отображения:

```ts
// Первый рендер перед отправкой нового сообщения.
{id: 'view-123', target: {chatId: -1001234567890}, props: {part: 'results'}}

// Последующие рендеры после успешной отправки.
{id: 'view-123', target: {chatId: -1001234567890, messageId: 456}, props: {part: 'results'}}
```

Это исключение для контекста рендера, а не для входного адреса `set_widget_view`: для нового сообщения по-прежнему используется `send`, а `target: {chatId}` во входных аргументах отклоняется.

Примеры предполагают действующее разрешение владельца виджета на публикацию. В текущем контракте соседняя обычная группа и соседний чат с включённым агентом не являются автоматически разрешёнными адресами; примеры соседней группы относятся к доступной пассивной супергруппе. Допуск публикаций в другие категории чатов требует отдельного решения.

Форма `send`/`target`, отсутствие `target.kind`, выбор текущего чата при опущенном `chatId`, результат `{viewId, target}` и адрес в контексте первого рендера приняты для проектируемого API. Дополнительные параметры доставки ещё уточняются. Эти инструменты пока не реализованы.

## 9. Обратная совместимость

### Область совместимости: предоставленный игровой Wordle

Проверен архив `wordle-widgets-2026-10-16.tar.gz`: игровой `widget.tsx` экспортирует обработчики из `createGame` в `shared.mjs`. Игра и её игровые зависимости не используют `ctx.message`. Он встречается только в отдельном виджете управления словарём `dictionary-admin.tsx`; совместимость этого административного приложения не входит в обязательный объём.

Нужно сохранить работу неизменённого игрового обработчика и ранее созданных игр. Совместимость исполнения всех исторических обработчиков и сохранение всего старого API не являются требованием. При этом существующие регистрации любых виджетов должны оставаться доступны для управления через новый API. В частности, ради Wordle не нужны `ctx.message`, понятие основного отображения, адаптер старого `set_widget` или отдельный режим вызова старого `render`.

Дополнительно подтверждено пользователем: исходный код Wordle и его игровых зависимостей не менять, тестировать текущий предоставленный виджет. При обнаружении проблем обратной совместимости сообщить пользователю конкретное нарушенное поведение и причину; не маскировать проблему адаптацией обработчика или заменой тестового виджета. Исправление совместимости должно выполняться в платформе в рамках принятого контракта; если это невозможно без изменения согласованного поведения, вынести развилку на обсуждение. Успешная миграция ещё не проверена и не заявляется.

### Фактические зависимости игры

- `render(state)` возвращает `rich_message.blocks`, включая таблицы, custom emoji и встроенные кнопки. Его можно вызывать как `render(state, view)`: JavaScript игнорирует лишний аргумент. Неизменённый Wordle показывает полную карточку во всех отображениях; разделение на поле, клавиатуру и результаты потребует доработать сам рендер игры.
- Контекст: `ctx.state`, `ctx.widgetId`, `ctx.render()`, `ctx.setTimeout()`, `ctx.clearTimeout()` и `ctx.enqueue()` с прежними используемыми сигнатурами. Таймер хранится по `widgetId` и формирует событие `idle` с `id` игрока и `deadline`; он не зависит от сообщения.
- События: существующие аргументы `(ctx, event)`, `event.data.from` либо `event.user`, исходная callback-строка в `event.data.data`, данные таймерного события и `event.respond({text, showAlert})`. Метаданные `event.view` добавляются без замены этих данных. Сохранённые кнопки должны продолжать маршрутизироваться в обработчики игры.
- Хуки `onCreate`, `onInit` и `onStop`: первые два восстанавливают значения состояния и таймер, последний снимает таймер. Восстановление и добавление отображений не должны повторно создавать игру или размножать таймеры; миграция не вызывает повторный `onCreate`.
- `ctx.api.notify_agent({text})` используется при завершении партии с включённым уведомлением. `ctx.api.delete_widget({widgetId})` используется обработчиком `finish`; эти вызовы сохраняются.
- `ctx.render()` используется перед уведомлением и перед удалением виджета. В новой модели он публикует актуальное состояние во всех подключённых отображениях; при отсутствии отображений сохраняет состояние без отправки сообщений. `finish` сначала показывает итоговое состояние, затем удаляет виджет с отключением кнопок по принятому правилу.
- Загрузка относительных модулей, файлов словарей и сохранённых снимков кода остаётся работоспособной. Нормализация `state` сохраняет действующие правила, включая удаление объектных `undefined` и превращение массивных `undefined`/пропусков в `null`.

Игра не использует `ctx.api.set_widget`, чтение сообщения или его адреса, replies/reactions/polls. Их исторические контракты не входят в обязательную совместимость с этим примером.

### Принято: новый API управляет старыми регистрациями

Агентские методы и формы их ответов можно заменить. После обновления агент через новый API должен иметь возможность:

- Найти ранее созданный виджет в списке, получить его прежний `widgetId`, состояние, handler, статус и список отображений с их `viewId` и адресами. Отключённые регистрации также доступны для просмотра и управления.
- Передать событие, запросить рендер или изменить состояние в рамках правил соответствующей операции и текущего статуса виджета.
- Обновить handler и описание существующего виджета без обязательного пересоздания. Если новое состояние не передано, сохраняется прежнее; параметры отображений управляются отдельно.
- Подключить дополнительное отображение, заменить или отключить мигрированное отображение через `set_widget_view` и `delete_widget_view`.
- Удалить ранее созданный виджет через `delete_widget` по прежнему идентификатору.

Старые регистрации не становятся доступнее новым владельцам: сохраняются идентичность бота и агента, проверки владения и действующих разрешений. Неизвестный или отключённый обработчик не мешает обнаружить регистрацию, прочитать сохранённое состояние или удалить её; запуск и рендер по-прежнему требуют работоспособного обработчика. Методы чтения `list_widgets`, `get_widget`, `update_widget`, его lifecycle, восстановление `stopped` и результат с `renderErrors` приняты. Для старых `disabled` после миграции используется тот же `update_widget`, без отдельного resume-метода.

### Миграция сохранённых регистраций

По проверенному текущему `src/widgets/store.mjs` адрес единственного сообщения и данные его рендера хранятся в самой записи `widgets`; поиск по сообщению также обращается к ней. Для нескольких отображений нужен переход к отдельным записям публикаций либо эквивалентная миграция хранения. Конкретная схема таблиц пока не выбрана.

Известное сообщение существующего виджета становится одним обычным `view` прежнего `widgetId`, без особого статуса основного отображения. Сообщение не пересылается и не создаётся заново. Сохраняются `botId`, `agentId`, `widgetId`, адрес и параметры доставки, пользовательское состояние, handler и его снимок кода, описание, статус активности/отключения, причина отключения и допустимые сохранённые ожидающие события активных регистраций. В отображение переносится необходимая информация о последнем сообщении, рендере и кнопках: отказ от `ctx.message` в публичном контексте не означает удаления внутренних данных для обновления сообщения. Параметры отображения не добавляются внутрь пользовательского `state`.

Миграция выполняется автоматически до запуска runtime и приёма событий в новой модели, транзакционно и безопасно к повторному запуску. Созданный `viewId` сохраняется и не меняется при повторном старте; новые списки и операции сразу видят мигрированную регистрацию. Существующие callback-данные продолжают разрешаться в тот же виджет и его отображение без повторной публикации кнопок. Сохранённые события активных регистраций не теряются и не переигрываются только из-за смены схемы. У старых `disabled`, переводимых в `stopped`, ожидающие события очищаются по принятому правилу остановленного виджета и не воспроизводятся при будущем возобновлении.

Активные Wordle восстанавливаются, старые `disabled` мигрируют в `stopped` с сохранением причины и без автоматического запуска; повторный запуск не создаёт дубли отображений, сообщений или таймеров. Если адрес сообщения неизвестен из-за неопределённого результата первоначальной отправки, `view` с выдуманным адресом не создаётся и отправка не повторяется автоматически. Такая регистрация и диагностическое состояние неопределённости остаются видимыми агенту. Ошибка миграции не должна запускать runtime с частично перенесёнными данными; исходные регистрации сохраняются для повторной попытки. Точная схема хранения и восстановления ещё предстоит проектированию.

### Проверки перед принятием реализации

Проверить неизменённый Wordle из архива: загрузку зависимостей и словарей, новый запуск через новый API, восстановление сохранённой партии в прежнем сообщении, старые callback-кнопки, отказ в ходе чужого игрока, `event.respond`, промежуточный `ctx.render()`, уведомление агента и `finish`. Отдельно проверить восстановление таймера без дублей, его работу без отображений, подключение нескольких сообщений к одному состоянию и повторный перезапуск после миграции. Проверки `ctx.message` и полного старого API не требуются. Это требования к будущей реализации; проверки совместимости runtime ещё не выполнялись.

На заранее созданных регистрациях отдельно проверить управление новым API: обнаружение и чтение состояния, событие, рендер, обновление handler без сброса состояния, добавление/замену/отключение отображений и удаление. Проверить сохранение идентификаторов, адресов, владения и ограничений доступа, видимость отключённых и неопределённых регистраций, откат неуспешной миграции и повторный старт без дублей.

Проверить чтение: `list_widgets` возвращает `canCreate` и краткие `items`, а `get_widget` — полное состояние и ошибки виджета/отображений. Проверить расчёт доступного создания при свободной и исчерпанной квоте виджетов и недоступном слоте runtime, учёт остановленных и не имеющих отображений регистраций, неизменность `canCreate` при добавлении `view`. Чтение не сбрасывает ошибки и не запускает остановленный runtime; миграция не удваивает число регистраций при расчёте квоты.

Проверить `update_widget`: сохранение опущенных полей и полную замену переданного состояния, новую версию handler по тому же пути, сохранение всех `view.id`, адресов и `props`. После изменения состояния, handler и отдельно только описания рендерятся все подключённые отображения. В `stopped` любой вызов, включая только описание и `{widgetId}`, выполняет `onInit`: успех восстанавливает `active`, таймеры и доступные кнопки, ошибка оставляет `stopped` с диагностикой. Без отображений успешный запуск восстанавливает таймеры без отправки сообщений. Проверить изменение и восстановление ранее мигрированного Wordle без потери партии.

Проверить `description`: обязательно при создании; опущенное при обновлении сохраняется, в том числе при смене handler; переданное заменяется отдельно и вместе с остальными полями. У `active` изменение только описания вызывает ререндер всех view без `onStop`/`onInit` и без очистки прежних ошибок. У `stopped` такое обновление пытается запустить виджет и при успешном восстановлении очищает прежние ошибки. При изменении handler или явно переданного состояния работающего виджета проверить порядок старого `onStop`, очистки ресурсов, применения параметров, нового `onInit` и рендера, без повторного `onCreate`. Успешная замена сохраняет ожидающую очередь; ошибка `onInit` очищает её.

Проверить результат принятого обновления: отказ одного рендера или отправки даёт запись в `renderErrors` с правильным `viewId`, без отката общего изменения и успешных публикаций. Без ошибок массив пуст; ошибка подготовки/применения возвращается ошибкой операции. Штатная отвязка потерянного сообщения не становится ошибкой рендера.

Проверить неудачную подготовку нового handler и невалидного состояния до замены: старый экземпляр не останавливается, его регистрация, отображения и ошибки не меняются неудачной операцией, `onStop` старого и `onInit` нового не вызываются. Отдельно проверить, что ошибка приходит непосредственно в ответе инструмента и не создаёт дубликат уведомления агенту.

Проверить исключение из `onInit` после изменения состояния при создании и замене: виджет остаётся доступен по возвращённому `widgetId` в `stopped`, отображения сохраняются, частичные изменения состояния не откатываются и видны через `get_widget` и после перезапуска. Повторная инициализация получает изменённое состояние. При переданном агентом новом `state` не восстанавливать прежнюю партию автоматически. Проверить запись в `widget.lastError`, диагностические поля ошибки ответа и отсутствие отдельного дублирующего события агенту; фоновое восстановление использует правило первого уведомления.

Проверить состояния: у `active` без отображений таймеры продолжают исполняться; у `stopped` обработчики и таймеры не исполняются, состояние и регистрации сообщений сохраняются. Старый `disabled` мигрирует в `stopped` с прежней причиной и не запускается при повторном старте приложения. Ошибка одного отображения не останавливает остальные и весь виджет.

Проверить удаление всего виджета из `active` и `stopped`: порядок остановки и очистки соблюдается, повторного `onStop` нет, состояние и привязки удалены, сообщения оставлены с отключёнными кнопками по возможности. Отдельно проверить удаление одного сообщения через API контроллера: отвязывается только его `view`, партия, таймеры и остальные отображения сохраняются. Удаление последнего сообщения не удаляет виджет. Подтверждённое удаление, `message_not_found` и классифицированная потеря доступа вызывают `onViewDelete(ctx, event)` с правильным снимком и причиной; они не вызывают `onError` рендера, не записывают новую ошибку рендера и не уведомляют агента автоматически. Повторный сигнал не повторяет отвязку или хук. Сетевая ошибка, ограничение частоты и неверное содержимое не отвязывают публикацию. Проверить отсутствие хука, запрет его вызова в `stopped` и отсутствие вызова при обычном отключении/замене отображения или удалении всего виджета.

Для неизменённого Wordle проверить `finish` с `await ctx.render()` и собственным `await ctx.api.delete_widget`: нет взаимной блокировки, финальное содержимое публикуется перед удалением, очищенная очередь не исполняется, все view отвязываются, сообщения остаются с отключёнными кнопками. Проверить отсутствие публичных stop/resume-инструментов и команд; повторный запуск выполняется только через явный `update_widget`.

Проверить остановку с заполненной оперативной и сохранённой очередью: все ожидающие события очищаются, новые в `stopped` не накапливаются, callback подтверждается без текста. После возобновления и после перезапуска ни одно отброшенное событие не исполняется; управление агентом остаётся доступным. При миграции старого `disabled` его сохранённая очередь также очищается. Проверить сохранение адресов, `view.id` и `props`, отключение обычных и rich-кнопок при остановке и восстановление актуальных кнопок при возобновлении. Ошибка Telegram не отменяет остановку и не разрешает выполнение событий.

Проверить остановку во время выполняющегося обработчика и незавершённой отправки рендера: приём событий закрывается сразу, очередь очищается, текущая работа завершается до финального отключения кнопок. Ни одно следующее событие не начинает обработку, а после завершения остановки поздний старый рендер не активирует кнопки. Проверить этот порядок как при успешном, так и при ошибочном завершении текущей работы.

Проверить завершающий `onStop`: один вызов после текущего обработчика/рендера; повторная остановка `stopped` не вызывает хук, а новый цикл после возобновления допускает следующий вызов. Исключение из хука не отменяет очистку таймеров, освобождение runtime и отключение кнопок. Порядок проверить на неизменённом Wordle и на обработчике с ошибкой в `onStop`.

Проверить общую аварийную ветку отдельно при зависшем обработчике, зависшем `onStop` и нарушении heartbeat. Все виджеты затронутого runtime переходят в `stopped`, процесс завершается, очереди очищаются, последнее подтверждённое состояние и отображения сохраняются, другие runtime продолжают работу. Не требовать вызова `onStop` при принудительном завершении. Повторные проверки и одновременное обнаружение одной аварии дают одно уведомление агенту; поздние сообщения старого процесса не восстанавливают работу. Перезапуск приложения не возобновляет остановленные виджеты.

Проверить возобновление через `onInit` без повторного `onCreate` и без воспроизведения пропущенных срабатываний. Для Wordle проверить обе ветки сохранённого `idleDeadline`: будущий срок восстанавливает таймер на остаток времени, истёкший переводит игрока в игровое `paused` без сброса партии. Ошибка инициализации оставляет виджет `stopped`; подключённые отображения и состояние не пересоздаются.

Для нескольких отображений проверить отказ рендера и отказ отправки одного `view`: остальные обновляются, состояние не откатывается, `onError` указывает ошибочную публикацию и она остаётся подключённой. После устранения причины следующая операция рендера должна показать в ней актуальное состояние.

Проверить контракт `onError(ctx, error, event)`: поля `code`, `message`, `operation`, правильный `error.view` и сохранение исходного события. В сценарии «нажатие в А, ошибка рендера в Б» источники должны различаться. Проверить отсутствие выдуманного `error.view` при ошибке без публикации и отсутствие `event` при операции без исходного события.

Для неудачной замены проверить снимок нового отображения в `error.view` и сохранённого старого в `error.previousView`, включая разные ID и `props` при одинаковом адресе сообщения. Новый снимок не появляется как подключённый view. Для других операций поле `previousView` отсутствует; эти правила сохраняются при неопределённом результате публикации и при исключении из `onError`.

Проверить падение самого `onError`: исходная и вторичная ошибки сохраняются, рекурсии нет, результат замены/отключения не меняется, другие отображения продолжают обновляться. Для `lastError` проверить одно уведомление при первой записи и отсутствие новых уведомлений при повторных таймерах, нажатиях и смене кода ошибки; сохраняется именно последняя необработанная ошибка. Успешный автоматический рендер и перезапуск запись не сбрасывают. Обработанная в `onError` ошибка не создаёт новой записи. Успешное изменение агентом отдельного отображения сбрасывает только его ошибку, изменение общего состояния или handler — ошибки всех отображений. Чтение и неудачное изменение записи не очищают; ошибка попытки доступна в ответе инструмента. После сброса следующая первая ошибка снова уведомляет агента.

Проверить общий `widget.lastError`: ошибки общего обработчика/таймера/lifecycle и ошибка `onViewDelete` после отвязки доступны без живого отображения, сохраняются между перезапусками и уведомляют агента только при первой записи. Ошибка публикации действующего `view` остаётся на уровне отображения. Успешное изменение общего состояния или handler очищает обе категории ошибок; изменение одного отображения не очищает общую ошибку. Снимок уже отвязанного отображения в диагностике не восстанавливает его привязку.

Проверить контекст первого рендера: перед новой отправкой доступен `chatId` без `messageId`, после неё — полный адрес при сохранении `view.id` и `props`; подключение существующего обычного или inline-сообщения сразу даёт полный адрес. Проверить, что неполный адрес в контексте рендера не ослабляет валидацию входного `target` операции подключения.

Во время замены проверить отсечение кнопок с подтверждением без текста: обработчик не вызывается, состояние не меняется, отложенного воспроизведения нет ни после успеха, ни после ошибки. Ранее принятые события перед заменой продолжают выполняться. Reply/reaction сохраняются после успеха и ошибки замены на том же сообщении того же виджета, с исходным снимком и порядком. Явная отвязка с последующим переподключением, передача другому виджету и остановка запрещают выполнение старых событий. Замена view не сбрасывает наблюдения реакций сообщения. Для poll/poll_answer проверить непрерывную связь того же опроса с сообщением и виджетом, сохранение очереди при изменении только view и отсутствие смешивания наблюдений и голосов разных `pollId`.

При обычном рендере проверить очередь всех типов событий и повторную валидацию каждой кнопки перед выполнением: сохранившийся callback выполняется, исчезнувший игнорируется, совпадение только в другом отображении не подходит, замена идентичности источника запрещает выполнение старого нажатия. Проверить `event.respond` и возвращаемый ответ обработчика, приоритет первого ответа и отсутствие короткого таймера: ожидание дольше 2 секунд само по себе не вызывает пустого подтверждения и не удаляет допустимое событие из очереди. Повторный ответ после уже выбранного подтверждения не отправляется и не вызывает ошибку. После обычной ошибки публикации не использовать кнопки неотправленного результата.

Проверить `event.view`: форма `{id, target, props}`, снимок источника при приёме в очередь, отсутствие возможности изменить его из обработчика, отсутствие подмены параметров при ожидании. События разных отображений получают свои источники; события агента и общих таймеров не наследуют `view` последнего нажатия.

### Обязательный сценарий: Wordle до и после обновления

Нужна проверка перехода между двумя версиями приложения с настоящим опубликованным Telegram-сообщением. Создание записи старого формата непосредственно в тестовой базе полезно для автоматических проверок, но не заменяет этот сценарий.

1. Запустить старую версию приложения, опубликовать предоставленный Wordle через её API и начать партию. Сделать ход, зафиксировать версию приложения, `widgetId`, адрес сообщения и состояние партии; проверить, что кнопки работают.
2. Остановить старую версию и запустить новую с той же базой, хранилищем снимков обработчиков и идентичностью бота/агента. Выполнить штатную автоматическую миграцию без пересоздания виджета и сообщения.
3. Через новый агентский API найти прежний `widgetId`, прочитать состояние и получить созданный при миграции `view`. Убедиться, что адрес Telegram-сообщения и прогресс партии сохранены; изменение режима из-за реально истёкшего таймера учитывать отдельно от потери состояния.
4. Нажать сохранившуюся кнопку в прежнем сообщении и продолжить игру. Через новый API передать событие и запросить рендер; изменения должны появляться в том же сообщении. Подключить дополнительное отображение и проверить общность состояния с исходным.
5. Проверить операции нового API над мигрированным виджетом: обновление handler без сброса состояния, замена и отключение дополнительного отображения.
6. Повторно перезапустить новую версию: `widgetId`, идентификаторы оставшихся `view` и адреса сохраняются, дубли сообщений и таймеров не возникают; исходное сообщение продолжает работать.
7. Удалить мигрированный виджет через новый API, проверить отключение кнопок и прекращение обновлений. Зафиксировать результаты до/после обновления и отдельно отметить реально проверенные операции.

Этот сценарий обязателен для приёмки миграции; сейчас он только запланирован и не выполнялся.

## 10. Команда `/widget list`

### Принято: формат карточки виджета

Принят предложенный пользователем формат: вместо единственного `Message` показывать число отображений и их адреса. Карточка:

```text
[code]w81f6ecf6df00455dafb6f619b1489c8b[/code] [i]active[/i]
{описание виджета}
[b]Owner:[/b] [code]{agentId}[/code]
[b]Pending:[/b] 0
[b]Views:[/b] 2
- supergroup [a href="https://t.me/c/111/111"]-1000000000111/111[/a]
- group [code]{inlineMessageId}[/code]
```

Здесь квадратные теги обозначают желаемое оформление: код для идентификаторов без ссылки, курсив для статуса, жирное начертание меток и ссылку для адреса, если она доступна. Реализация может использовать Telegram entities, как текущий `widgets-format.mjs`, без вывода самих тегов: text_link для кликабельного адреса, code для адреса без ссылки. `description` — описание самого виджета, `Owner` — идентификатор агента-владельца, `Pending` — общая очередь виджета, а не сумма отдельных карточек сообщений. Статус использует принятую модель `active | stopped`.

`Views` считает сохранённые подключённые отображения, включая отображения остановленного виджета; уже отвязанные не учитываются. Для виджета без отображений выводится `Views: 0`, без фиктивного адреса сообщения. Одна карточка относится к одному виджету, а не к отдельному view.

### Принято: адреса и пагинация списка

- Для обычного сообщения всегда показывать исходный адрес контроллера `{chatId}/{messageId}` и известный тип чата. Если для группы/канала доступна корректная ссылка на сообщение, сам адрес становится её текстом: `[a href="https://t.me/c/111/111"]-1000000000111/111[/a]`. Отдельный URL рядом не выводить. Если ссылки нет, адрес оформляется кодом. Сохранённый target view и видимые chatId/messageId ради ссылки не менять. При неизвестном типе использовать нейтральное `message {chatId}/{messageId}` без предполагаемого URL.
- Для любого private view ссылки не формировать, включая view в текущем личном диалоге пользователя с ботом. Показывать только `private {chatId}/{messageId}` с адресом кодом. Ссылку на диалог с ботом также не добавлять. Правила видимости самого списка и адресов сохраняются; контекст получателя и Telegram ID бота для формирования таких ссылок больше не нужны.
- Для супергрупп и каналов формировать ссылку на сообщение по известным данным: `https://t.me/<username>/<messageId>` для публичного адреса или `https://t.me/c/<channelId>/<messageId>` для внутреннего адреса. channelId — корректно преобразованный MTProto ID канала/супергруппы, а не отрицательный Bot API chatId; в видимой подписи остаётся исходный Bot API chatId. Сведения о теме учитывать, когда они известны. Ссылка не предоставляет доступ к закрытой группе или каналу.
- Для обычной basic group не подставлять отрицательный chatId в `t.me/c`: этот формат предназначен для каналов/супергрупп. Без достоверной пользовательской ссылки на нужное сообщение оставить `group {chatId}/{messageId}`.
- Если известен только inline-адрес, показывать `group {inlineMessageId}` при достоверно известном типе назначения; иначе `inline {inlineMessageId}`. Из непрозрачного `inlineMessageId` не выводить неизвестные `chatId` или название группы и не конструировать предполагаемый URL.
- Сохранить существующий заголовок диапазона и пагинацию по виджетам, текущие фильтры владельца и порядок списка. Публикации в соседних чатах не меняют владельца и не исключают виджет из его списка. Разбивку длинной выдачи с большим числом отображений ещё нужно определить.

Причина ограничения: у разных аккаунтов одно сообщение в private/basic group может иметь разные messageId; у каналов и супергрупп messageId общий для аккаунтов. См. [Message ID sequences](https://core.telegram.org/api/updates#message-id-sequences). Для ЛС принято единое правило без ссылок, без специальной обработки текущего пользователя.

В текущем коде `formatWidgets(items, start, end, total)` показывает один `Message: chatId/messageId`; это описание будущего изменения команды. Исходники команды и форматтера пока не изменены. Проверки реализации должны охватить оформление полей, несколько и ноль view, `stopped`, сохранение исходного chatId/messageId как подписи ссылки, отсутствие отдельного дублирующего URL, отсутствие ссылок для любых ЛС, публичные/непубличные ссылки каналов и супергрупп, basic group без ложного URL, fallback inline-адреса, отсутствие выдуманного типа назначения, фильтрацию владельца до пагинации и карточку мигрированного Wordle.

## 11. Команда `/widget show WIDGET_ID`

Принято: `/widget list` остаётся кратким обзором, а `/widget show` показывает полную служебную карточку виджета и его отображений.

Общая часть: `widgetId`, статус, описание, `Owner`, `Handler`, `Pending`, `Dropped`, `Created`, общий `Last error`. Для `stopped` дополнительно показывать причину остановки. Вместо единственных общих `Message`/`Topic` показывать список `Views`; привязанные к публикации сведения относятся к соответствующему отображению.

Для каждого `view` показывать `id`, обязательный известный адрес по правилам `/widget list` (chatId/messageId становится ссылкой, если она доступна; в ЛС ссылок нет), JSON `props` и его `Last error`. Ошибки общей логики и ошибок отдельных публикаций выводятся раздельно; в краткой диагностике достаточно кода, этапа/операции и сообщения, без смешивания с ошибкой другого отображения. При отсутствии ошибки — `none`, при отсутствии отображений — `Views: 0`.

Сведения о возможных первых публикациях с неизвестным результатом показывать отдельно от подключённых `Views` и `Last error` по §23. Не выводить выдуманный адрес или подключённое отображение для кандидата без адреса; сброс ошибки не скрывает такую запись. Точное оформление уточняется вместе с составом записи.

Команда остаётся чтением: не запускает остановленный виджет и не очищает ошибки. Существующие правила доступа команды и отсутствие вывода сырого пользовательского `state` сохраняются. Состав карточки принят; лимиты и разбивку длинных `props`/диагностики нужно определить отдельно.

Проверки будущей реализации: общая ошибка и ошибки отдельных отображений показываются раздельно с правильными ID, ссылка/fallback и `props` соответствуют своему view, у `stopped` видна причина остановки. При нуле отображений нет фиктивной карточки сообщения, при отсутствии ошибки выводится `none`. Просмотр сохраняет ошибки и статус, не запускает runtime; карточка ранее созданного Wordle доступна после миграции.

## 12. Принято: аварийный `stopped` и восстановление через `update_widget`

Принято отказаться от ручной остановки виджета агентом и отдельного возобновления: для прекращения работы достаточно `delete_widget`, который сохраняет сообщения с отключёнными кнопками, а `stopped` нужен для системной/аварийной остановки с сохранением диагностики и возможности исправления. Публичные `stop_widget`, `resume_widget`, `/widget stop` и `/widget resume` не вводятся, в том числе в `ctx.api`. Внутренние механизмы остановки, `onStop`, очистка очереди и ресурсов сохраняются для удаления, замены, запрета исполнения и аварий runtime.

Принятые правила обновления:

- `update_widget({widgetId})` допустим без новых полей. Для `stopped` он повторно запускает сохранённый handler с сохранённым состоянием, вызывает `onInit` и рендерит все сохранённые отображения.
- Если переданы handler, state или description, сначала применяются эти параметры по согласованным правилам, затем выполняется запуск. Для `stopped` даже изменение только описания становится явной попыткой запуска.
- Успех инициализации переводит только указанный виджет в `active`, восстанавливает его таймеры и очищает прежние ошибки как результат успешного восстановления. Свежие ошибки отдельных рендеров учитываются отдельно и возвращаются в `renderErrors`; они не отменяют успешный запуск. Остальные виджеты общего runtime сами не возобновляются.
- Сбой `onInit` сохраняет частичные изменения состояния и оставляет виджет в `stopped`, с диагностикой в ответе инструмента без дублирующего события агенту.
- Для уже `active` сохраняется ранее выбранная граница: изменение handler/state переинициализирует экземпляр, изменение только description или вызов без новых полей лишь рендерит все view. Работающий экземпляр не переинициализируется только ради повторной попытки публикации.
- Проверки владения и текущих разрешений остаются обязательными; восстановление не обходит системный запрет исполнения.

Эти правила заменяют ранее обсуждавшиеся отдельные остановку и возобновление. Предыдущая семантика, сохранявшая `stopped` при любом обновлении, не применяется. Для внутреннего перехода остановки по-прежнему действуют согласованные правила очереди, очистки, хуков и отключения кнопок.

## 13. Принято: именованные события агента

Сохраняется `widget_event({widgetId, name, data?})` для вызова пользовательской логики работающего виджета. Метод проверяет владение и статус, принимает событие с контроллерным источником `agent` в общую очередь и возвращает подтверждение приёма, а не результат выполнения обработчика. Служебные lifecycle-хуки не вызываются через произвольное имя события. Например, `name: 'finish'` использует существующую логику завершения Wordle, включая его собственное удаление.

В `stopped` событие отклоняется и не сохраняется для будущего запуска; восстановление выполняется через `update_widget`. Агентское событие не получает фиктивный `event.view` и не представляется Telegram-нажатием. Рабочие ошибки обработчика используют согласованные `onError` и общий `lastError`. Имя метода и эти правила приняты; подтверждение не должно выдавать ещё не выполненное событие за завершённое действие.

Отдельный агентский `render_widget` убирается: работающий виджет повторно рендерится через `update_widget({widgetId})`, остановленный тем же вызовом пытается запуститься. Используемый Wordle `ctx.render()` сохраняется.

Проверить в будущей реализации приём события в очередь с исходными `name`/`data`, системным источником `agent` и отсутствующим `event.view`. Подтверждение приходит до окончания обработчика; ошибка выполнения отражается через согласованную диагностику. Событие в `stopped` не исполняется ни сразу, ни после восстановления; lifecycle-имя отклоняется. Проверить `finish` неизменённого Wordle и отсутствие отдельного агентского инструмента `render_widget` при сохранении `ctx.render()`.

## 14. Принято: reply и реакции при замене отображения

Reply и reaction адресованы Telegram-сообщению и сохраняются при замене view того же сообщения внутри того же виджета.

Reply/reaction остаются в общей очереди и после успеха или ошибки замены, если сообщение непрерывно принадлежит тому же виджету. Перед обработкой проверяется эта принадлежность, а не сохранение прежнего `view.id`. Явная отвязка, удаление сообщения, передача другому виджету или остановка по-прежнему запрещают выполнение; последующее повторное подключение не оживляет старые события. Между разными виджетами очередь не переносится. Кнопки во время замены по принятому правилу отсекаются.

`event.view` остаётся снимком при приёме, даже если его идентификатор заменён. Это явное исключение для reply/reaction из общего правила проверки подключённого `view.id`. Обработчик работает с текущим общим состоянием. Снимок фиксирует локальную привязку при получении обновления, а не гарантированную версию экрана пользователя в момент действия.

Смысл сообщения может измениться: reply с догадкой для игрового поля способен дождаться его превращения в табло результатов. Виджет решает по текущему состоянию и исходным данным, допустима ли такая команда. Проекцию реакций следует сохранять как наблюдение того же сообщения при такой замене; в текущем `events.mjs` она обновляется до постановки события в очередь. Для poll/poll_answer принято дополнительное условие сохранения идентичности опроса по §18.

Проверки будущей реализации: успех и ошибка замены сохраняют порядок reply/reaction; исходный снимок не подменяется; явная отвязка и переподключение, смена владельца сообщения и `stopped` запрещают старое событие; кнопки остаются отсечёнными. Ранее принятые события перед заменой выполняются до неё, агентские и общие таймерные события продолжают обычную очередь.

## 15. Исследовано: reply и реакции для inline-сообщения в неизвестном чате

Проверено по официальной документации и исходнику Bot API 2026-10-17, без живой отправки сообщений. Сам inline-вызов не даёт подписку на сообщения чужого чата. Callback имеет специальный inline-адрес; reply и реакции используют обычные адреса сообщений. У reply нет готового `inline_message_id` для сопоставления с нашим view; одного `via_bot` недостаточно, чтобы определить конкретную публикацию. Нужна достоверная связь адресов, без декодирования непрозрачного ID. См. [Inline bots](https://telegram.org/blog/inline-bots), [Message](https://core.telegram.org/bots/api#message), [CallbackQuery](https://core.telegram.org/bots/api#callbackquery).

Реакции требуют администратора в чате и явной подписки `allowed_updates` на соответствующий тип. В чужом чате без участия бота на них рассчитывать нельзя; анонимные агрегаты могут задерживаться на минуты. См. [Update](https://core.telegram.org/bots/api#update).

Есть отдельный Guest Mode: упоминание бота в отправленном reply может передать ему сообщение с контекстом без членства в поддерживаемом чате. Документация также обещает обращения ответом на собственные сообщения гостевого бота. Распространение этого правила на обычный пользовательский inline-результат без упоминания отдельно не подтверждено. Guest Mode не открывает историю или поток реакций. См. [Guest Bots](https://core.telegram.org/bots/features#guest-bots), [Guest mode protocol](https://core.telegram.org/api/bots/guest-mode).

В текущем `src/widgets/events.mjs` нет обработки `guest_message`, callback без обычного `message` пропускается; reply и реакции ищутся через `byMessage(chatId, messageId)`. Поэтому обнаруженная возможность Telegram ещё не означает её поддержку проектом. Гостевой контекст нельзя автоматически смешивать с обычным чатом по одному числовому ID: [Message.guest_query_id](https://core.telegram.org/bots/api#message) отдельно предупреждает о пространстве адресов.

Остаётся живой тест в поддерживаемой группе и личной переписке без бота: reply на inline-результат с выключенным/включённым Guest Mode, без упоминания и с явным `@bot`; отдельно reply на сообщение, опубликованное через `answerGuestQuery`. Проверить передачу исходного сообщения и возможность достоверно сопоставить его с view, включая rich-содержимое. Этот тест не выполнялся; интеграция Guest Mode пока не принята.

## 16. Принято: снимки в ошибке замены

При неудачной замене `error.view` описывает новое отображение, которое пытались опубликовать, а `error.previousView` — сохранённую прежнюю привязку. Оба поля содержат снимки `{id, target, props}`; наличие нового снимка в ошибке не означает, что новое view подключено. Так `onError` различает неудачную конфигурацию и продолжающее работать отображение. Для других операций `previousView` отсутствует.

## 17. Принято: исключительная привязка сообщения и владение агента

У одного Telegram-сообщения может быть только одно подключённое view. Вызов `set_widget_view` для сообщения того же виджета выполняет принятую замену. Если сообщение уже связано с другим виджетом, операция возвращает конфликт и сохраняет существующую привязку и сообщение; автоматический перенос не выполняется. Это действует и для разных виджетов одного агента.

Несколько агентов могут иметь доступ к одному публичному каналу и публиковать там свои виджеты в разных сообщениях. Каждый агент управляет только собственными виджетами и отображениями: разрешение писать в канал не разрешает менять, отключать или удалять чужую привязку. Проверка владения обязательна также при обращении напрямую по `widgetId` или `viewId`.

Ошибка конфликта содержит машинно читаемые идентификаторы агента-владельца, существующего виджета и его отображения, занимающего сообщение:

```ts
{
  code: 'view_conflict',
  message: 'Message is already bound to another widget',
  ownerAgentId: 'agent-wordle',
  widgetId: 'widget-wordle',
  viewId: 'view-wordle-channel'
}
```

`ownerAgentId` — владелец регистрации, в том числе для виджета в `stopped`, а не последний пользователь кнопки или агент, выполняющий текущую попытку. `widgetId` и `viewId` обозначают существующую занятую привязку, а не виджет или новый кандидат view из отклонённого запроса. Все три поля сохраняются при сериализации ошибки инструмента. Они позволяют инициатору отдельно обратиться к владельцу с просьбой отключить конкретное отображение; сам конфликт не отправляет запрос другому агенту и не отключает его view. Ошибка возвращается вызывающему агенту напрямую, без вызова `onError` чужого виджета. Диагностика конфликта не предоставляет права управления чужой регистрацией.

Для переноса между собственными виджетами агент явно отключает прежнее view, затем подключает сообщение к новому виджету. При разных владельцах прежнее отображение отключает его владелец, затем новый агент выполняет подключение в пределах своих разрешений. Эти две операции не образуют атомарную замену: ошибка второго подключения не восстанавливает уже отключённое старое view.

Исключительность привязки проверяется в общей области сообщений бота, без разделения реестра по агентам. Проверка конфликта и резервирование адреса упорядочиваются до изменения Telegram-сообщения: параллельные подключения двух агентов не должны оба успешно захватить одно сообщение. Права на целевой виджет и операцию проверяются независимо от диагностики конфликта.

Проверки будущей реализации: два агента с доступом к одному публичному каналу успешно публикуют собственные виджеты в разных сообщениях; попытка занять сообщение другого возвращает правильные `ownerAgentId`, `widgetId` и `viewId` существующей привязки, не меняет публикацию, привязку и состояние существующего виджета. Прямые операции с чужими `widgetId`/`viewId` запрещены. Проверить конфликт для `stopped`, разных виджетов одного владельца, сохранение всех трёх полей в ответе инструмента и одновременное подключение к одному свободному сообщению. После отключения владельцем сообщение можно подключить другому виджету с действующими разрешениями; старые события не переносятся новому владельцу.

## 18. Принято: события опросов при замене отображения

`poll` и `poll_answer` сохраняются в очереди при замене view того же сообщения, если тот же опрос с тем же `pollId` остаётся связан с тем же виджетом без разрыва привязки. Изменение только `view.id`/`props` их не отменяет. Исходный `event.view` сохраняется как снимок; если связь опроса исчезла, сообщение явно отвязано, передано другому виджету либо виджет остановлен, старое событие не исполняется и не оживает после повторного подключения. Ошибка замены, сохраняющая старую привязку и опрос, не отменяет очередь.

Наблюдения и голоса разных опросов одного виджета хранятся раздельно по `pollId`. В проверенном текущем `polls.mjs` записи ответов разделены по `widgetId` и голосующему; для нескольких отображений этого недостаточно. Проверки будущей реализации: сохранение порядка событий одного опроса и исходного снимка, отсутствие смешивания голосов разных опросов и запрет переноса старых событий новому владельцу.

## 19. Принято: начало отсечения кнопок при замене

Отсечение новых кнопок конкретного сообщения начинается при принятии валидной операции замены в очередь, после проверки аргументов, прав и конфликта привязки. События, принятые раньше операции, выполняются перед ней по обычным правилам; кнопки, поступившие после её принятия, сразу подтверждаются без текста и не ставятся в очередь, в том числе пока замена ждёт текущего обработчика или рендера.

Отсечение заканчивается после окончательного успеха или ошибки операции; при успехе новые нажатия проверяются относительно нового view, при ошибке — сохранённого старого. Если для сообщения уже принято несколько замен, отсечение продолжается до завершения всех ожидающих замен без промежуточного окна приёма кнопок. Невалидный или запрещённый запрос сам по себе отсечение не включает. Другие отображения и сохранение reply/reaction/poll/poll_answer подчиняются ранее принятым правилам.

Проверки будущей реализации: кнопка перед приёмом замены выполняется в прежнем порядке; кнопка после приёма отсекается уже во время ожидания, а не только во время нового рендера. После успеха/ошибки приём возобновляется для соответствующего сохранённого view. Несколько принятых замен не создают окна между ними; невалидный запрос, отказ в доступе и конфликт с чужим виджетом не мешают кнопкам действующего отображения. Нажатия других сообщений не отсекаются из-за замены одного view.

## 20. Принято: неопределённый результат обычного рендера

Для обновления уже подключённого view без его замены: если результат публикации неопределён, сохранить привязку и состояние, обработать ошибку через обычные `onError`/`lastError`, но до подтверждённой публикации игнорировать кнопки только этого отображения с пустым подтверждением. Контроллер не знает, какое из содержимых отображается в Telegram; снимок последнего успешного набора кнопок сохраняется как история и не подменяется неподтверждённым набором. Это внутреннее состояние доставки, без нового публичного статуса виджета.

Следующий запрошенный рендер этого view должен выполнить публикацию актуального содержимого даже при совпадении с прежним успешным хешем: кеш не подтверждает состояние после неизвестного результата. Подтверждённый успех снимает неопределённость и восстанавливает обработку актуальных кнопок, но сам по себе не очищает сохранённый `lastError`. Другие view продолжают работать; отдельный цикл повторных попыток не добавляется. Явный повтор можно запросить принятым `update_widget({widgetId})`. Правило касается обычного рендера; правила результата операции замены уже описаны отдельно.

Проверки будущей реализации: неизвестный результат не подменяет историю успешных кнопок; новые нажатия и ожидающие кнопки, проверяемые при сохраняющейся неопределённости, игнорируются с пустым подтверждением. Другие отображения продолжают работать. Рендер с прежним успешным хешем реально выполняет публикацию; только её подтверждение снимает неопределённость. Обработанная в `onError` ошибка и перезапуск сами по себе не считаются подтверждением публикации. Успешный автоматический рендер не очищает прежний `lastError`; отдельные повторы без запроса рендера не возникают.

## 21. Принято: сохранить отсутствие короткого таймера callback

Пользователь попросил сохранить текущее значение таймера вместо предложенных 2 секунд. Проверка исходного checkout проекта показала, что короткого таймера автоматического подтверждения нет. Сохраняется именно отсутствие такого таймера; оно не означает числовое значение 0 и немедленный ответ на каждое нажатие.

Текущие свидетельства: `src/widgets/runtime.mjs`, функция `action`, создаёт `event.respond` с защитой первого ответа и после завершения обработчика вызывает его с возвращённым результатом; `src/widgets/service.mjs`, ветка `respond`, дополнительно исключает повторную отправку. `src/controller.mjs` сначала передаёт распознанные widget-callback в этот маршрут; общего фонового таймера подтверждения для него нет. `docs/widgets.md`, раздел State, callbacks and observations, явно указывает отсутствие автоматического короткого срока подтверждения. Таймаут HTTP-запроса Telegram и heartbeat/teardown runtime имеют другое назначение.

Первый выбранный ответ исключает второй ответ на тот же callback. После уже выбранного подтверждения поздний или повторный `event.respond` завершается без ошибки и без повторной отправки в Telegram; он не откатывает изменения состояния и не создаёт новую ошибку виджета. При завершении обработчика используются его возвращённый ответ либо пустое подтверждение, если ответа нет. Отдельные правила немедленного пустого подтверждения отсечённых/недопустимых событий сохраняются. Предыдущие предложения об автоматическом пустом подтверждении после короткого ожидания заменены этим решением.

Проверки будущей реализации: ожидание в очереди и работа обработчика дольше 2 секунд сами по себе не вызывают подтверждение по таймеру; явный ответ или результат обработчика сохраняются, первый ответ выигрывает, повторный пропускается. Проверить эти правила на неизменённом Wordle. В этой задаче проверены исходники и документация; runtime и Telegram вживую не запускались.

## 22. Принято: неопределённый результат первой отправки

Для `set_widget_view({widgetId, send, props})`: если первая отправка могла создать сообщение, но его адрес не получен, возвращать `delivery_unknown` без автоматической повторной отправки. Виджет, его состояние и остальные отображения сохраняются; кандидат с неизвестным адресом не считается подключённым view, не включается в `viewCount` и не отправляется заново при общем рендере или перезапуске.

Ошибка содержит `widgetId`, назначенный кандидату `viewId` и известный `chatId`; `messageId` отсутствует. Сведения о попытке и неопределённом результате сохраняются в служебной диагностике, чтобы агент мог разобраться после прерывания вызова или перезапуска. Это не успешный результат `{viewId, target}` с полным адресом. Ошибка проходит через `onError` с `operation: 'attach'` и снимком кандидата; непосредственный вызов агента получает ошибку инструмента без дублирующего уведомления.

Следующий вызов с `send` является явной новой отправкой и может создать второе сообщение; контроллер не выдаёт такой повтор за безопасное восстановление. Если агент получает достоверный адрес уже созданного сообщения, он может подключить его через `target` с обычными проверками прав и конфликта. Автоматическое обнаружение адреса и восстановление через поздний callback отдельно не обещаются. Если адрес первой публикации уже известен, но не удался последующий этап, известный адрес нужно вернуть в диагностике вместо совета повторно отправить сообщение.

Проверки будущей реализации: неизвестный результат первой отправки не создаёт подключённый view, не увеличивает `viewCount` и не сбрасывает состояние/остальные отображения. Общий рендер и перезапуск не повторяют отправку. Ошибка инструмента сохраняет известные идентификаторы, диагностика переживает перезапуск, прямой ответ не дублируется уведомлением агенту. При известном адресе ошибка последующего этапа возвращает его; подключение по найденному `target` проверяет права и конфликт.

## 23. Принято: ошибки подключения без созданного view

Если подключённого view ещё нет, необработанная ошибка `attach` сохраняется в общем `widget.lastError` со снимком кандидата в `error.view`; ошибки действующих отображений не затрагиваются. Применяются общие правила `onError`, первой записи и сброса: обработанная ошибка не создаёт `lastError`, непосредственная операция агента возвращает ошибку инструмента без дублирующего события. Неудачный кандидат не создаётся как фиктивное подключённое отображение ради хранения ошибки.

Сведения о возможной первой публикации с неизвестным результатом из §22 хранятся отдельно от `lastError`: обработка ошибки в `onError` или последующий сброс ошибки не доказывают отсутствия сообщения. Эти служебные сведения доступны владельцу через `get_widget` и `/widget show`, переживают перезапуск и сами не запускают повторную отправку. Это сведения о незавершённой публикации, а не ещё одна категория уведомлений об ошибке. Состав записи ещё уточняется; её явное удаление через `delete_widget_view` принято в §24.

Проверки будущей реализации: ошибка `attach` без подключённого view записывается на уровне виджета с правильным снимком, а не на другом отображении. Успешный `onError` исключает запись ошибки, но не теряет сведения о возможной публикации. Сброс `lastError` и перезапуск не удаляют эти сведения; они доступны только владельцу и не считаются подключёнными view. Ошибка непосредственного вызова не дублируется уведомлением.

## 24. Принято: закрытие записи о возможной публикации

Существующий `delete_widget_view({viewId})` также используется для удаления служебной записи кандидата с неизвестным адресом, проверяя его владельца. В этом случае операция только забывает сведения о попытке: подключённого view для отвязки нет, неизвестное Telegram-сообщение не удаляется и не редактируется. Ни `onViewDelete`, ни новый запуск/повтор отправки не вызываются. Очистка такой записи не считается доказательством отсутствия сообщения.

Если агент нашёл адрес публикации, сначала подключает её обычным `set_widget_view({widgetId, target, props})`, затем удаляет запись прежнего кандидата по его ID. Это разные операции: неуспешное подключение не удаляет сведения о попытке, успешное подключение само по себе не доказывает, какой именно неизвестной отправке соответствует сообщение. Новое подключение получает обычный новый `viewId`. Если агент решает больше не разбирать попытку, он может удалить только запись. Удаление всего виджета удаляет и его служебные записи.

Отдельный инструмент очистки не вводится; `delete_widget_view` получает явно описанную ветку для существующего кандидата без подключённого view. Диагностика ошибок подчиняется прежним независимым правилам, удаление записи не сбрасывает произвольный `widget.lastError`.

Проверки будущей реализации: владелец удаляет запись кандидата через `delete_widget_view`, другой агент получает отказ. Telegram-запросов, хуков удаления и повторной отправки при очистке нет, остальные view и общий `lastError` сохраняются. Неуспешное подключение найденного сообщения не очищает кандидата; успешное создаёт обычное новое view, после чего кандидат удаляется отдельно. Удаление всего виджета очищает принадлежащие ему записи.

## 25. Принято: личный агент и переход к боту при его отсутствии

Поручение пользователя из inline-режима получает включённый агент его личного диалога с этим ботом. Контроллер определяет его по идентичности бота и пользователя и проверяет действующий доступ. Подготовленный результат сохраняет выбранный agentId; событие «Начать» маршрутизируется этому же агенту, который станет владельцем созданного виджета независимо от места публикации карточки. Это не раскрывает агенту переписку места публикации и не расширяет его разрешения. Явный выбор другого агента через синтаксис запроса в первой версии не вводится.

Если личного агента нет, в inline-выдаче показывается кнопка для перехода к боту и начала личного диалога. При отключённом личном агенте используется тот же переход для его обычного включения. Сам inline-запрос не создаёт и не включает агента автоматически; действующие проверки доступа сохраняются.

Подходящий механизм Telegram — `answerInlineQuery.button` типа `InlineQueryResultsButton` с `text` и `start_parameter`: кнопка размещается над выдачей и открывает личный диалог, передавая параметр `/start`. Её можно показать до появления результатов. Это подтверждено [официальным описанием InlineQueryResultsButton](https://core.telegram.org/bots/api#inlinequeryresultsbutton). Вход в личный диалог и настройка используют обычный сценарий бота. По принятому §57 исходный текст ради возврата не сохраняется, отдельная кнопка возврата не добавляется: пользователь сам начинает новый inline-запрос.

Проверки будущей реализации: пользователи одного бота получают своих личных агентов, результат и «Начать» сохраняют выбранного владельца. При отсутствии агента показывается рабочий переход к этому боту, фонового запуска поручения и автоматического создания агента нет. Для отключённого агента переход не обходит обычные правила включения. Проверить отображение кнопки при пустом наборе результатов на поддерживаемых Telegram-клиентах. Проверена документация Telegram; интерфейс вживую пока не тестировался.

## 26. Принято: агент определяет клавиатуру и доступность запуска

Агент, получивший inline-поручение, сам подготавливает сообщение и inline-клавиатуру и определяет, кому доступны её кнопки. В частности, он может сделать стартовую кнопку публичной. Платформенное ограничение «запускать может только автор исходного inline-запроса» не вводится. Надпись «Начать» — пример подготовленной агентом кнопки, а не обязательное имя действия для любой карточки.

Контроллер сохраняет связь результата и кнопок с подготовившим их агентом, проверяет выбранные им ограничения и передаёт допустимое нажатие событием этому же агенту. Событие содержит данные нажавшего пользователя, исходные данные кнопки, адрес публикации и связь с подготовленным результатом/поручением. Нажатие другого человека не переключает маршрутизацию на его личного агента. На основании события агент решает, заменять ли карточку виджетом, и использует обычные операции создания/подключения. Публичность кнопки не меняет владельца регистрации и не предоставляет нажавшему пользователю общего управления личным агентом.

Пример: Алиса пишет `@Бот опубликуй виджет wordle`; её личный агент готовит карточку с публичной кнопкой. Борис нажимает кнопку опубликованной карточки; событие получает агент Алисы и подключает Wordle к тому же сообщению. Владельцем виджета становится агент Алисы. После подключения игровые действия обслуживаются обработчиком виджета по его правилам, включая общую модель активного игрока Wordle.

Проверки будущей реализации: публичная кнопка принимает нажатие другого пользователя и направляет ровно к подготовившему результат агенту с правильными данными пользователя и публикации. При выбранном агентом ограничении контроллер соблюдает его до передачи события; автоматического ограничения по автору нет. Подключение сохраняет адрес сообщения, владение исходного агента и обычные проверки инструментов. Конверт события принят в §32, формат правил доступа — в §50. Совместимость будущего inline-пути с прежним форматом permits согласована как требование, но ещё не реализована.

## 27. Исследовано: чтение inline-сообщений

В текущем Bot API нет получения полного сообщения по `inline_message_id`. Inline-callback содержит адрес, пользователя и данные кнопки, но не содержимое; успешное inline-редактирование возвращает `True`. Поэтому сохранённая карточка из выдачи не доказывает текущее содержимое публикации. См. [CallbackQuery](https://core.telegram.org/bots/api#callbackquery) и [редактирование сообщений](https://core.telegram.org/bots/api#editmessagetext).

Текущий агентский `read` читает локальные данные: `src/agents/history.mjs` использует `db.getMessage`, `src/controller.mjs` дополнительно ищет проекцию виджета. Аргументы сейчас `{messageIds, chatId?}`; inline-адрес не поддерживается. В `src/storage/retention.mjs` обычная история очищается по порогу 30 дней от получения, как описано в `docs/storage.md`. Это проверенные исходники исходного checkout проекта, а не выполненная интеграция inline.

Принятый контракт чтения описан в §33: содержимое исходной заготовки не сохраняется ради `read`; чтение появляется по мере наших подтверждённых редактирований и явно различает частичные данные и неопределённость доставки. Серверного чтения по этому адресу это не добавляет. В исходниках inline-read ещё не реализован; живые проверки не проводились.

## 28. Принято: действия кнопок и сохранение inline-содержимого после редактирования

Принята модель на основе предложения пользователя: до публикации хранить действия кнопок, а не полный результат ради последующего чтения. Агент задаёт кнопки с text, action и необязательными key/group; правила доступа задаются словарём message.permits (§50). action содержит самодостаточное поручение для будущего нажатия, например «Активировать виджет Wordle на этом сообщении»; его выполнение не требует восстановить текст карточки или контекст прежнего модельного хода. Отключение кеша, глобальная одноразовость группы, приём/доставка события, конверт button, частичный inline-read и API подготовки приняты в соответствующих разделах; сроки хранения продолжают обсуждаться.

### Реестр подготовленных кнопок

Контроллер сохраняет записи `{botId, agentId, btnId, tipId, key, permits, action, group, createdAt, expiresAt}` непосредственно перед отправкой страницы с этими результатами, по §43. Сам set_inline_results оставляет подготовленные действия в памяти и не регистрирует их в БД. `agentId` нужен для маршрутизации к подготовившему результат агенту независимо от пользователя нажатия; `botId` задаёт область доступа. Непрозрачный случайный `btnId` помещается в callback data; `tipId` общий для клавиатуры одной заготовки и не является адресом фактической публикации. Приняты 30 дней от первой регистрации перед выдачей, без продления от нажатий и повторов страницы (§51). После утраты/истечения записи кнопка не вызывает агента. Форма permits и логические key/group приняты в §50.

### Принято: глобальная одноразовость группы заготовки

Одинаковую заготовку могут отправить несколько раз. Принято глобальное закрытие группы по `{botId, tipId, group}` при первом допустимом принятом нажатии, например удалением её btn-записей. Оно запрещает дальнейшие нажатия группы во всех публикациях этой заготовки. Отдельное закрытие по inlineMessageId для независимых запусков копий не выбирается. Новая заготовка с новым tipId имеет собственные группы.

Для inline-выдачи принят `cache_time: 0`. По проверенному описанию `answerInlineQuery.cache_time` управляет серверным кешированием результата, а не ограничением числа его публикаций или нажатий. Отключение кеша дополняется закрытием группы в нашей базе. Гарантия относится к одному принятому действию группы заготовки, даже если появилось несколько её публикаций, а не к единственному отправленному сообщению. Опора на `chosen_inline_result` для строгого расходования в момент публикации не подходит из-за необязательности feedback. См. [answerInlineQuery](https://core.telegram.org/bots/api#answerinlinequery) и [inline feedback](https://core.telegram.org/api/bots/inline#4-inline-feedback).

При отсутствии group действие остаётся повторяемым по правилам обычных кнопок; повтор одной доставки callback.id всё равно отсекается. Для кнопки с group принято сохранять событие и закрывать группу в одной транзакции по §30: если приём не состоялся, группа не расходуется. Текущая обычная очередь агента хранится в памяти; долговечная запись для inline-нажатия является проектируемым расширением, а не уже работающей гарантией. Закрытое состояние не должно исчезать, пока действуют соответствующие btn-записи, иначе старое нажатие снова станет допустимым. Ошибка агента не открывает группу автоматически по §29.

### Обработка и событие агенту

Сначала проверить действующую регистрацию адреса сообщения. Если оно подключено к виджету, callback обрабатывает его текущий маршрут с точными проверками кнопок и view; старый btnId не возвращает его к первоначальному action. Для обычной сохранённой inline-публикации проверить её владельца, актуальную клавиатуру и закрытые группы. Текущий владелец адреса не заменяется агентом из конфликтующего токена.

Для публикации без сохранённого содержимого btnId разрешает найти действие и агентский маршрут; несовпадение автора запроса и пользователя нажатия само по себе не запрещает публичную кнопку. Если запись не найдена, истекла или permits не разрешают нажатие, подтвердить callback без текста, не вызывать агента и не расходовать группу. Успешный приём создаёт принятое событие button с eventId, btnId, tipId, action, inlineMessageId, пользователем from и полем btnGroup для заданной group (§32). Название события не обещает первое в истории нажатие только потому, что текста сообщения ещё нет в базе.

Telegram предупреждает, что callback data может не соответствовать текущим кнопкам сообщения. Поэтому для неизвестной публикации такой вызов означает приём сохранённого действия для адреса из callback, без утверждения, что всё сообщение имело ожидаемый текст или клавиатуру. Публичный токен не считается общим доступом к личному агенту. Это ограничение первичного вызова остаётся и в предложении пользователя, но больше не используется для реконструкции якобы прочитанного содержимого.

### Сохранённое содержимое и read

Принят `read({inlineMessageId})` по сохранённым inline-данным контроллера с формой ответа §33. До известного содержимого возвращается явная ошибка недоступности. Подтверждённая полная замена записывает известное представление и владельца. Подтверждённая частичная правка обновляет только известные компоненты: одна замена reply_markup не раскрывает прежний текст или медиа. Если исходного полного снимка нет, read явно сообщает неполноту и возвращает только известные поля, не выдумывая остальное. Неопределённый результат сохраняет последний подтверждённый снимок с отметкой неопределённости; неизвестный кандидат не становится текущим содержимым. Отдельный физический файл базы для этого не требуется.

Если снимок уже полный, частичные успешные правки применяются к нему, сохраняя остальные известные поля. Права чтения проверяются по владельцу. Сохранённое inline-сообщение остаётся адресом inline: наличие снимка не раскрывает chatId назначения и не разрешает пользоваться чужим чатом. Логику прав, групп и доставки событий можно переиспользовать с обычными сообщениями, сохраняя различие адресов. После очистки снимка нельзя считать старые группы снова открытыми или обходить существующую регистрацию виджета. Срок жизни активных widget view и их проекций остаётся по ранее принятым правилам независимо от истории и реестра первоначальных стартовых кнопок.

### Проверки и открытые детали

Проверить `cache_time: 0`, две публикации одной заготовки и глобальное закрытие группы после нажатия в любой из них; остальные группы и другой tipId не затрагиваются. Проверить конкурентные нажатия разных людей, повтор callback.id и отказ очереди без расходования группы. Проверить маршрутизацию к исходному агенту, публичные/ограниченные кнопки, истечение 30 дней и перезапуск. Для read проверить отсутствие исходной карточки, только известную клавиатуру после частичной правки, полный снимок после полной замены и неопределённый результат. Сохранённый снимок не позволяет старой кнопке обойти актуальный реестр или владение. Поведение пересылок/копий всё ещё требует живой проверки.

В этом разделе приняты `cache_time: 0`, глобальная одноразовость группы, отсутствие автоматического открытия при ошибке (§29), транзакционное сохранение события (§30), передача по приёму очередью агента (§31), конверт button (§32) и частичный inline-read (§33). API подготовки принят в §38, запись кнопок только перед выдачей — в §43, схема кнопок и permits — в §50, сроки хранения — в §51. Ссылки: [CallbackQuery](https://core.telegram.org/bots/api#callbackquery), [редактирование](https://core.telegram.org/bots/api#editmessagetext). Прежняя идея сохранять полную заготовку и выдавать её как источник read не выбирается.

## 29. Принято: сбой после принятого нажатия

После надёжного приёма нажатия закрытая группа автоматически не открывается при ошибке агента или инструментов. Результат мог быть частичным: виджет мог создаться, а подключение или подтверждение операции — не завершиться. Восстановление прежней группы разрешило бы повторно запустить исходное действие, в том числе в другой публикации той же заготовки.

Агент получает ошибки инструментов по согласованным правилам и решает, как продолжить: исправить существующий виджет, повторить подключение к исходному сообщению или подготовить новую кнопку с новыми идентификаторами и нужным действием повтора. Предыдущая группа остаётся закрытой. Платформа не добавляет универсальную видимую кнопку «Повторить» и не создаёт автоматически новую игру после ошибки. По принятому §31 очередь агента является границей передачи: после её приёма автоматическое восстановление исходного события или прерванного хода не требуется. Допустимую потерю компенсирует новое поручение пользователя и новая карточка.

Проверки будущей реализации: ошибки создания, подключения и обновления не восстанавливают старые btn-записи, в том числе если частичный результат уже существует. Явная новая кнопка имеет новые идентификаторы и не оживляет прежнюю группу. Повторное подключение существующего виджета не требует автоматически создавать ещё один; правила восстановления stopped и delivery_unknown сохраняются.

## 30. Принято: атомарное сохранение принятого нажатия

Для кнопки с group сохранять событие агенту и закрывать глобальную группу в одной транзакции базы. После проверок прав и допуска выбрать ровно одного победителя, сохранить botId, eventId, callbackId, agentId, action, пользователя, адрес публикации и идентификаторы кнопки/группы, удалить btn-записи этой группы, затем зафиксировать транзакцию. Только после фиксации подтверждать приём и передавать событие рабочей очереди. При ошибке транзакции ни группа, ни событие не изменяются; при отказе приёма группа не расходуется.

Сохранённая запись позволяет после перезапуска обнаружить принятое событие, ещё не поставленное в очередь агента, и продолжить передачу. Это отдельная долговечная запись для данного пути, а не обещание, что существующая очередь всех обычных событий уже переживает перезапуск. Подтверждение callback не заменяет транзакционное сохранение события. Успешный приём очередью агента завершает обязанность передачи по §31; её дальнейшая обработка и сохранность не гарантируются. Повторная доставка callback не должна создать новую запись/вызов, конкурентное нажатие проигравшего не расходует другие группы.

Граница «передано агенту» принята в §31: приём в его очередь. После этого запись не используется для повторной доставки из-за отсутствия подтверждения runtime или завершения хода; для дедупликации при необходимости может сохраняться служебная отметка. Этот механизм обеспечивает согласованность приёма нажатия и закрытия группы, но не гарантирует строго однократные внешние действия модели при любой аварии. Уже поставленное в очередь действие автоматически не повторяется; принятое правило §29 о закрытой группе сохраняется.

Проверки будущей реализации: сбой до фиксации оставляет группу открытой и не создаёт событие; сбой после фиксации до оперативной очереди сохраняет одно событие и закрытую группу. Перезапуск обнаруживает ещё не переданную запись. Конкурентные нажатия и повтор callbackId не создают дополнительные события; отказ приёма не закрывает группу без сохранённого события.

## 31. Принято: приём очередью агента завершает передачу

Событие считается переданным агенту, как только принято в его очередь. Дополнительное подтверждение модельного runtime, начало выполнения action, завершение хода или создание виджета не требуются. Сохранённая запись ожидает только постановки в очередь, а не успешного выполнения поручения.

После приёма очередью автоматическая повторная доставка исходного события не выполняется: ни из-за ошибки агента, ни из-за перезапуска, ни из-за отсутствия результата. Риск того, что очередь потеряется или агент не обработает событие, пользователь явно принял как некритичный. Пользователь может заново дать поручение и опубликовать новую карточку с новыми идентификаторами; старая группа остаётся закрытой.

Сложный протокол подтверждения приёма модельным runtime и восстановления неизвестного результата его вызова не вводится. События, которые ещё не были приняты очередью, остаются в области транзакционного сохранения §30; отказ очереди не выдаётся за успешную передачу. Здесь не добавляется гарантия долговечности самой обычной очереди агента.

Проверки будущей реализации: очередь приняла событие, но обработчик не запущен — передача уже завершена. Последующая ошибка, потеря очереди или перезапуск не воспроизводят исходное событие и не открывают группу. Не требуется ждать runtime/завершения хода. Отказ очереди не помечает событие переданным; сохранённая ещё не поставленная запись остаётся доступна для передачи. Новая подготовленная карточка имеет независимый tipId и может быть использована после неудачи прежней.

## 32. Принято: конверт inline-нажатия для агента

Используется существующий агентский тип `eventType: 'button'`, расширенный вариантом inline-адреса и сохранённым `action`. Пример:

```json
{
  "eventType": "button",
  "eventId": "event-123",
  "inlineMessageId": "inline-message-id",
  "from": {"userId": 456, "name": "Борис"},
  "action": "Активировать виджет Wordle на этом сообщении",
  "btnId": "button-123",
  "tipId": "tip-123",
  "btnGroup": "start"
}
```

`inlineMessageId` — адрес для действий над публикацией, не адрес личного чата агента. Обычные messageId/chatId назначения не выдумываются; у текущих обычных button-событий их адресная форма сохраняется. `from` обозначает нажавшего пользователя, а не автора заготовки; при наличии можно сохранить username по текущему соглашению событий. `action` берётся из сохранённой записи кнопки, нажатие не подменяет его присланным текстом. `btnGroup` соответствует group кнопки и отсутствует у негрупповой. `btnId`/`tipId` дают связь с определением действия, `eventId` — с сохранённым событием. Не требуется добавлять фиктивный key или text, если у inline-кнопки задан только action и подпись не сохранена.

Событие не утверждает, что содержимое сообщения доступно через read, и не содержит фиктивного `event.view`: widget view мог ещё не появиться. Агент может выполнить самодостаточное action и подключить созданный виджет через `set_widget_view` с `target: {inlineMessageId}`. Точные проверки маршрута, permits, группы и очереди выполняются контроллером до постановки; название button не означает обход уже существующей widget-регистрации. События игровых кнопок подключённого виджета остаются в его runtime и автоматически не передаются модели.

По текущим `docs/message-events.md` и `src/controller.mjs` обычные модельные button-события уже используют eventType, from и btnGroup; key/text описывают их нынешний обычный callback. Принятый inline-вариант расширяет проектируемый контракт; поддержки в исходниках пока нет. Обычные события сохраняют текущую форму, включая необязательные topicId, username и historyGap; новые идентификаторы и action не объявляются уже присутствующими в их текущей реализации. Проверки будущей реализации: правильный пользователь и владелец маршрута, сохранённый action, полный inline-адрес без подставленного chatId/messageId, отсутствие btnGroup без группы и отсутствие ложного обещания read/готового view.

## 33. Принято: частичный результат inline-read

Альтернативный вызов `read({inlineMessageId})` сохраняет оболочку текущего read `{messages: [...]}` и возвращает один элемент по этому адресу. Если содержимого нет в хранилище, элемент содержит inlineMessageId, `error: 'message_not_found'` и пояснение, что сохранённое содержимое недоступно; это не подтверждает удаление сообщения из Telegram. До наших правок содержимое стартовой заготовки не реконструируется по action.

Если известна только часть представления после подтверждённой правки, возвращаются известные поля с `partial: true`. Пример после замены только клавиатуры:

```json
{
  "messages": [{
    "inlineMessageId": "inline-message-id",
    "partial": true,
    "reply_markup": {"inline_keyboard": []}
  }]
}
```

Отсутствующий text здесь означает отсутствие сведений о тексте, а не пустую строку. При полном известном представлении `partial: false`; данные возвращаются с сохранённым форматированием/rich-содержимым и клавиатурой. Неизвестные chatId, messageId, автор и время Telegram-публикации не выдумываются. Доступ проверяется по владельцу сохранённой публикации.

Неопределённость доставки независима от полноты снимка: после неподтверждённой правки возвращается последнее подтверждённое представление с `deliveryUnknown: true`. Даже полный снимок в таком случае не обещает совпадения с текущим экраном. После подтверждённой правки отметка неопределённости снимается по принятым правилам публикации; чтение само ничего не отправляет и не сбрасывает. Точная политика хранения снимков и дополнительные метаданные могут быть уточнены отдельно.

Проверки будущей реализации: одна запись в messages с правильным inline-адресом; отсутствие сохранённых данных даёт message_not_found с точным пояснением. Правка только клавиатуры даёт partial: true без выдуманного text; полное известное представление даёт partial: false. Неизвестная доставка не подменяет подтверждённые поля, а отмечается отдельно. Проверить чтение владельцем, отказ другому агенту и неизменность прежнего обычного read.

## 34. Принято: edit по inline-адресу без исходного содержимого

Расширить существующий `edit` альтернативным адресом `inlineMessageId`, например `edit({inlineMessageId, text: 'Запускаю Wordle…'})`. Для обычной карточки до подключения виджета отсутствие полного снимка не запрещает явно заданную правку поддерживаемого компонента. Контроллер сохраняет подтверждённые известные данные для принятого read; при неизвестном результате не выдаёт предложенную правку за подтверждённое содержимое.

Выбор адреса однозначен: либо текущие messageId/chatId с ограничением §35, либо inlineMessageId, без смешивания и фиктивного chatId. Право правки определяется сохранённой связью публикации с подготовившим кнопку агентом, установленной при принятии допустимого callback; сам inlineMessageId не является общим разрешением. Эту связь нужно уметь хранить независимо от полного текста сообщения и от уже удалённых btn-записей группы. Чужая привязка не перехватывается. Решение касается обычной inline-карточки; подключённый widget view продолжает управляться через принятый контракт виджетов.

Агент передаёт полное новое значение изменяемого компонента, а не просит контроллер угадать или дополнить неизвестный текст/rich-блоки. Преобразования типов принимает или отклоняет Telegram; неудачная правка не заменяется новой отправкой. Оболочка результата edit сохраняет смысл updated/failed/unknown с inlineMessageId вместо обычного адреса. В текущих `src/messages/actions.mjs` и wiki edit требует известный оригинал и обычный messageId; принятая inline-ветка является расширением, не описанием уже работающей поддержки.

## 35. Принято: запрет правок via_bot через обычный адрес

Если сохранённое Telegram-сообщение имеет `via_bot`, агент не может редактировать его через chatId/messageId. Правило действует для любого via_bot, включая нашего бота, независимо от наличия прав писать в чат и от того, найден ли уже виджет. `via_bot` — поле Telegram Message с ботом, через которого отправлено сообщение; это не признак `from.is_bot`. См. [Message](https://core.telegram.org/bots/api#message).

Запрет охватывает текст, подпись, медиа, rich-содержимое, обычную inline-клавиатуру, rich-кнопки и локальную правку permits без Telegram-вызова. Проверка выполняется до любых внешних эффектов и изменений локальных прав/кнопок. Для недоступного сохранённого оригинала обычный edit по-прежнему не разрешается: отсутствие записи не доказывает отсутствие via_bot. Подтверждённый признак via_bot нельзя терять при локальном обновлении снимка.

Чтобы не обойти запрет подключением рендера, `set_widget_view` также не подключает и не заменяет view по target: {chatId, messageId} сообщения с via_bot. Для управления такой публикацией агент использует inlineMessageId с принятой проверкой владельца; знание обычного адреса или самого inlineMessageId не даёт права перехватить чужую публикацию. Если достоверно известна существующая чужая привязка, сохраняется принятая ошибка конфликта с ownerAgentId, widgetId и viewId. По одному via_bot эти идентификаторы не угадываются.

Это ограничение агентских операций с обычным адресом. Рендер уже зарегистрированного view и отключение его кнопок контроллером продолжают работать через контракт виджетов; прямой edit подключённого widget view не становится разрешённым ни по одному адресу. Ранее созданные виджеты и их миграция сохраняются по §9.

Удаление сообщения через обычный адрес остаётся доступным по существующим правам удаления. Оно не даёт права редактировать или перехватывать виджет. При подтверждённом удалении сообщения с известной привязкой отвязывается только соответствующий view, с принятой обработкой onViewDelete; остальные view, общий state и таймеры сохраняются.

В текущем `src/messages/actions.mjs` такой проверки via_bot пока нет; локальный permits-only edit имеет отдельную раннюю ветку, которую тоже нужно закрыть. В `src/controller.mjs` есть запрет обычного edit активного виджета, но он не заменяет новую проверку: inline-публикация может ещё не иметь локальной привязки по обычному адресу. Проверки будущей реализации: отказ для своего и чужого via_bot до побочных эффектов; отказ permits-only и подключения через обычный target; сохранение разрешённых inline-операций владельца, рендера и миграции прежних виджетов; удаление с обычными правами и отвязкой одного view; отсутствие запрета по одному from.is_bot.

### Пример опубликованного inline-сообщения, полученного другим ботом

Пользователь предоставил 2026-10-17 update от raw_bot: обычный `message` с `chat.type: 'private'`, `message_id: 5652038`, `from.is_bot: false`, `text: 'test'`, `entities: [{offset: 0, length: 4, type: 'italic'}]` и `via_bot: {id: 107705060, is_bot: true, first_name: 'Markdown Bot', username: 'bold'}`. Это предоставленное наблюдение, не наш живой тест.

Пример подтверждает нужное различие: отправитель — пользователь, через @bold подготовлено содержимое, а сообщение получил бот назначения raw_bot с обычным адресом и форматированием. Для принятого запрета достаточно сохранённого message.via_bot, без локального widgetId или inlineMessageId. Проверка только from.is_bot этот случай пропустила бы. В текущем проекте saveMessage сохраняет Message целиком в JSON, а обычный read возвращает его поля, включая via_bot и entities, если такой update получен и сохранён.

В примере нет inline_message_id; via_bot указывает бота, но не даёт связь с конкретной inline-публикацией в его хранилище. Получение этого message ботом назначения не означает, что @bold получил такой же update или узнал chatId/messageId. Это также не меняет состав InlineQuery: entities относятся к уже опубликованному сообщению, а не к запросу во время набора. Доставку обычного message в другие типы чатов этот частный пример не проверяет.

## 36. Принято: viaBot в кратких сообщениях

В общем преобразовании shortMessage добавить необязательное поле `viaBot`, чтобы агент сразу видел, через какого бота подготовлено сообщение. При наличии message.via_bot.username значение — username без @, например `viaBot: 'bold'`. Если via_bot отсутствует, поле не добавляется. Если via_bot есть, но username не передан, использовать `viaBot: true`, сохраняя сам признак; username является необязательным полем Telegram [User](https://core.telegram.org/bots/api#user).

Соответствующая часть краткого сообщения с вымышленными идентификаторами:

```json
{
  "eventType": "message",
  "messageId": 7,
  "from": {"userId": 123, "name": "Example", "username": "example_user"},
  "viaBot": "bold",
  "textPlain": "test",
  "hasEntities": true
}
```

Это фрагмент: остальные текущие поля, включая date, сохраняются. from продолжает обозначать фактического отправителя по текущим правилам, viaBot — источник подготовки содержимого. Поле строится из метаданных Telegram, а не из текста сообщения или упоминания @бота. Оно не подтверждает наличие виджета, его владельца или право управления публикацией. Контроллер применяет запрет §35 по сохранённому message.via_bot независимо от того, видел ли агент краткое представление.

Добавление в общий shortMessage распространяется на новые сообщения, message_edited и краткие результаты history/search. Полный read продолжает возвращать исходный объект via_bot. В текущем src/telegram/short-message.mjs поле ещё не реализовано. Проверки будущей реализации: username без @, отсутствие поля без via_bot, fallback true без username, сохранение from и одинаковая проекция во всех перечисленных источниках кратких сообщений.

## 37. Принято: одно текущее inline-поручение пользователя

Область текущего поручения — `{botId, userId}`. Разные пользователи и разные боты независимы. Не предполагается, что один пользователь одновременно готовит несколько inline-сообщений у одного бота; неизвестный чат назначения не используется как часть ключа.

Новый начальный inline-запрос создаёт новую версию поручения и немедленно прекращает обслуживание прежней, ещё до прохождения новой версией двухсекундного порога. Это относится и к повторному обращению с тем же текстом: ответы по совпадению текста не переиспользуются (§43). Запрос следующей страницы с курсором продолжает текущую версию; повторная доставка того же Telegram-запроса не создаёт нового поручения. Один Telegram inline_query.id не считается идентификатором всей сессии: курсоры и работа агента связываются с внутренней версией. Возврат к прежнему тексту после другого текста также создаёт новую версию.

Для прежней версии:

- Если поручение ещё ожидает передачи агенту, по возможности удалить именно его событие из очереди либо пометить недопустимым. Остальные события агента не очищать. Перед фактической передачей проверять актуальность повторно: одного удаления из видимой очереди недостаточно, если событие уже выбрано для отправки.
- Если поручение уже передано агенту для исполнения, не останавливать ход и не отправлять автоматическую команду отмены. Изменение inline-текста не откатывает уже выполненные действия агента и не удаляет созданные им виджеты.
- Если агент позже возвращает подготовленные варианты, кнопки или действия для устаревшей версии, игнорировать этот результат. Не добавлять его кнопки/действия в базу и не выдавать его в новой либо старой пагинации. У инструмента подготовки результата должен быть проверяемый идентификатор версии; привязывать поздний ответ к текущему запросу по одному userId нельзя.
- Ожидание готовности старой выдачи прекращается. На запрос её старого курсора возвращать завершённую пустую страницу без next_offset, не запускать агентскую работу повторно и не переключать пользователя обратно на старую версию. Уже отданные ранее строки выдачи не считаются удалёнными с экрана.

Новое поручение отдельно проходит принятый порог 2 секунды и передаётся агенту не более одного раза на версию. Поэтому одна обслуживаемая версия не означает, что в агенте гарантированно нет ещё завершающейся работы от старой версии.

Проверка актуальности и приём результата в память согласуются с заменой текущей версии; устаревший результат не принимается. Перед выдачей страницы актуальность проверяется повторно, и только затем кнопки/действия включённых в неё результатов регистрируются в БД (§43). Результат с отказом из-за устаревшей версии не превращается в новую отправку и не направляется обычным сообщением в личный чат автоматически.

Граница с уже выданными результатами: ранее выданные карточки и зарегистрированные для них кнопки не отзываются автоматически при новом наборе. Пользователь уже мог опубликовать такую карточку; действуют ранее принятые permits, одноразовость группы и срок хранения. Новое правило отсекает позднюю подготовку и дальнейшую выдачу старой версии, не инвалидируя ранее опубликованные сообщения. Заготовки, которые достоверно ещё не выдавались, не требуют сохранения ради старой версии.

В текущем src/agents/queue.mjs уже есть admit-проверка при выборе ожидающих событий; очистка clear удаляет всю очередь и для точечной отмены не подходит. Передача runtime выполняется после выбора асинхронно, поэтому будущая интеграция должна закрыть промежуток дополнительной проверкой непосредственно перед передачей. Специального inline-протокола версий в текущих исходниках нет.

Проверки будущей реализации: смена текста до порога, во время ожидания очереди, между выбором и передачей runtime, во время работы агента, перед сохранением результата и перед выдачей страницы. Старое поручение не передаётся, если успели отменить; начатый ход не прерывается; поздние кнопки/действия не записываются. Старые курсоры завершаются и не возрождают версию; повтор страниц не запускает поручение дважды; возврат к прежнему тексту получает новую версию; другие пользователи/боты и обычные события очереди не затронуты; ранее выданные карточки сохраняют действующие кнопки.

## 38. Принято: передача готовых inline-вариантов агентом

Агент получает идентификатор внутренней версии поручения requestId и передаёт весь готовый список одним вызовом отдельного инструмента:

```js
set_inline_results({
  requestId,
  results: [{
    title: 'Wordle',
    description: 'Опубликовать игру с кнопкой запуска',
    message: {
      text: 'Wordle',
      buttons: [{
        text: 'Начать',
        action: 'Активировать виджет Wordle на этом сообщении',
        group: 'start'
      }]
    }
  }]
});
```

title и description относятся к списку выбора, message — к сообщению, которое пользователь отправит после выбора. message необязателен: при отсутствии контроллер подставляет нейтральное сообщение с крестиком (§42). Поддерживаются текст/rich-содержимое и кнопки с принятыми action, permits и group. Для медиа действуют запрет прямой загрузки и явная подготовка file_id по §39. Контроллер назначает btnId, tipId и технические callback-данные; агент их не подделывает.

Проверить принадлежность requestId вызывающему агенту и актуальность версии до приёма результата. Для устаревшего запроса инструмент явно сообщает, что запрос устарел, и ничего не регистрирует. Успешно принятый результат переводит выдачу из ожидания в готовый набор в памяти; до этого завершение модельного хода не завершает ожидание (§40). В БД кнопки сохраняются не этим вызовом, а непосредственно перед выдачей страницы с ними (§43). Набор возвращается на соответствующем запросе пагинации. Инструмент не отправляет обычное сообщение в чат и не даёт агенту неизвестный адрес назначения: выбор и публикацию выполняет пользователь. Принятый контракт ещё не реализован.

## 39. Принято: файлы и изображения через явную отправку в буферный чат

Целевой сценарий: `@бот сгенерируй изображение котика`. После принятого запуска агент генерирует изображение, сохраняет его разрешённым способом и передаёт готовый фото-вариант. Пока работа идёт, обслуживается прежняя пагинация ожидания. На очередном запросе после готовности пользователь получает фото для выбора и отправляет его в исходный чат. Длительность генерации не требует удерживать один Telegram inline-запрос всё время; автоматическое появление результата без очередного запроса клиента не обещается.

Для создаваемых файлов принимается явная последовательность действий агента. set_inline_results не принимает uploads, attach:// и локальные пути, в том числе внутри rich-медиа; такие аргументы отклоняются, а не превращаются в автоматическую отправку. Запрет относится к подготовке inline-результата, обычный send сохраняет поддержку загрузки. Новая обёртка для файлов или скрытая буферная загрузка контроллером не вводятся.

Пользователь сообщает агенту, какой доступный буферный чат использовать. Это указание не обходит текущие проверки прав отправки и чтения. Если буфер не указан, агент отправляет файл в свой личный диалог с автором inline-поручения, используя chatId этого пользователя и disable_notification: true. Это пользователь, чьё inline-поручение обслуживается, а не неизвестный чат назначения будущей публикации и не другой человек, нажавший кнопку. Такая отправка — обычное видимое сообщение в ЛС; отсутствие звука не делает его скрытым. Наличие личного агента и доступ к его диалогу проверяются по ранее принятым правилам.

Агент выполняет следующие шаги:

1. Создаёт файл в разрешённой области. Для результата генерации изображения использует уже существующую регистрацию и save_image по текущему контракту проекта.
2. Обычным send отправляет photo либо document в выбранный буфер. Для буфера по умолчанию явно передаёт disable_notification: true. Сохраняет messageId из результата; текущий send возвращает messageIds, а не полный объект с file_id.
3. Вызывает обычный read({chatId: bufferChatId, messageIds: [messageId]}) и извлекает file_id из нужного объекта вложения. Для фото выбирает подходящий размер из photo; для файла — document.file_id. file_unique_id вместо file_id не используется. Ошибки send/read проверяются до подготовки выдачи; неподтверждённая отправка не повторяется автоматически.
4. Вызывает set_inline_results с подтверждённым file_id и file_sources, указывающим bufferChatId, messageId и тот же fileId. Тип вложения сохраняется: photo для фото, document для документа. Источник должен оставаться сохранённым и доступным на момент проверки; произвольный file_id без доказанного происхождения не принимается.

Пример аргументов после успешных send и read, с условными значениями идентификаторов:

```js
set_inline_results({
  requestId,
  results: [{
    title: 'Котик',
    message: {
      photo: 'CONFIRMED_PHOTO_FILE_ID',
      caption: 'Котик',
      file_sources: [{
        chatId: bufferChatId,
        messageId: bufferMessageId,
        fileId: 'CONFIRMED_PHOTO_FILE_ID'
      }]
    }
  }]
});
```

В подсказку агенту и описание инструмента включить порядок: «В inline-результат нельзя загружать новые файлы. Если нужно создать файл или изображение, сначала сформируй и сохрани его, отправь обычным send в буферный чат, прочитай отправленное сообщение и используй полученный file_id с file_sources. Буфер берётся из указания пользователя; по умолчанию отправляй автору поручения в ЛС без звука (disable_notification: true). Прямые uploads, attach:// и локальные пути в set_inline_results запрещены. Проверяй ошибки каждого шага; завершение генерации не означает успешную отправку или готовую inline-выдачу».

Контроллер проверяет принадлежность requestId и доступность file_sources, затем преобразует подтверждённое фото в [InlineQueryResultCachedPhoto](https://core.telegram.org/bots/api#inlinequeryresultcachedphoto), документ — в [InlineQueryResultCachedDocument](https://core.telegram.org/bots/api#inlinequeryresultcacheddocument). file_id должен относиться к текущему боту и соответствующему типу Telegram-вложения. Это обычное преобразование inline-результата, без дополнительной загрузки. Фото для просмотра и исходник как document выбираются агентом по задаче. Ограничения URL-варианта InlineQueryResultDocument не переносятся автоматически на cached document.

Политика буфера принята в §52: автоматического удаления сообщений после выдачи, отмены или истечения запроса нет, временные файлы и история подчиняются общей очистке. Собственный HTTPS-сервис для загрузки созданных файлов не нужен. Внешние URL и остальные нативные виды inline-медиа включаются по §56 с ограничениями конкретных Telegram-типов. Одна или несколько картинок могут быть разными вариантами выбора; самостоятельный тип альбома одним выбором не добавляется сверх нативных возможностей Telegram.

Правила §37 применяются и к генерации: уже начатую работу не обрывать, но устаревшее изображение не выдавать и не регистрировать его кнопки. Если агент уже знает, что поручение устарело, он не начинает буферную отправку ради него; set_inline_results в любом случае повторно проверяет актуальность версии. Уже состоявшаяся буферная отправка не откатывается автоматически при изменении текста. Хранение готовой выдачи и курсоров принято в §43, информационные ответы — в §41, правила буфера и утраты источника — в §52.

Проверки будущей реализации: явный буфер пользователя и буфер по умолчанию с правильным chatId автора и disable_notification: true; обычный send сохраняет uploads, но set_inline_results отклоняет их и вложенные локальные ссылки без отправок; photo/document получают соответствующий file_id через read; file_sources проверяет доступ, сообщение и тип; ошибки буферной отправки не дают фиктивной готовности и не вызывают слепой повтор; устаревший результат не выдаётся; инструкции агента содержат все шаги. Отдельно проверить вид фото в смешанной выдаче со служебными текстовыми строками на разных клиентах. Код и живые проверки пока не выполнены.

## 40. Принято: ожидание явного inline-результата независимо от хода агента

После передачи поручения состояние ожидания хранится у inline-поручения requestId и не выводится из busy/idle агента, завершения модельного хода или наличия работающего процесса. Пока не принят успешный set_inline_results для этой версии, запросы следующих страниц получают «Агент думает» и продолжение пагинации по действующим правилам барабана. Статус означает отсутствие подготовленного ответа и не утверждает, что модель прямо сейчас выполняет ход.

Допустим сценарий: агент начал генерацию либо другую фоновую задачу, сохранил requestId для продолжения и закончил текущий ход. Позже продолжение у того же агента получает результат, при необходимости отправляет файл в буфер и вызывает set_inline_results с исходным requestId. До успешного приёма этого результата барабан остаётся в ожидании. Фоновой работе необходимо явно передать requestId; автоматически привязывать её ответ к последнему поручению пользователя нельзя. Новый текст по §37 отменяет обслуживание прежней версии и делает её поздний результат устаревшим.

Попытка вызова set_inline_results не равна готовности: ошибка аргументов, недоступный file_sources или неуспешный приём результата в память не переводят актуальное поручение в готовое. Регистрация кнопок в БД откладывается до выдачи (§43). Обычный текст финального ответа агента также не подменяет вызов инструмента. Само завершение хода без результата не вызывает автоматическую повторную постановку того же поручения, уведомление об ошибке или отправку в ЛС.

Каждый Telegram inline-запрос по-прежнему получает отдельный ограниченный по времени ответ; одно соединение не держится до завершения фоновой задачи. При отсутствии новых запросов страницы сервер не обещает обновить уже показанную выдачу. Успешный set_inline_results делает результаты готовыми для подходящего текущего или следующего запроса страницы. Время ожидания одной страницы и общий час жизни версии — разные параметры; хранение только в памяти, expiresAt = createdAt + 1 час и потеря при перезапуске приняты в §43. Уточняется обработка невосстановимого сбоя. Обычный отказ/уточнение агент может вернуть через set_inline_results (§41). Завершение хода само по себе истечением срока или сбоем не считается.

В подсказку агенту добавить: «Inline-ответ завершается явным set_inline_results. Если переносишь подготовку в фоновую задачу, сохрани и передай ей requestId, затем вызови инструмент после готовности результата. Окончание твоего хода не завершает inline-поручение».

Проверки будущей реализации: ход завершился без set_inline_results — ожидание продолжается; обычный финальный текст не превращается в вариант; фоновое продолжение того же агента завершает исходную версию; ошибочный вызов не закрывает ожидание; смена текста до окончания фоновой задачи отсекает старый результат; конец хода не создаёт повторного агентского события; отсутствие запросов клиента не имитирует доставку готовой страницы. Код и живые проверки пока не выполнены.

## 41. Принято: уточнения через обычный set_inline_results

Пример: пользователь просит добавить корону на своё фото, агент проверяет доступные фото профиля и не находит подходящего. Пояснение «Фото профиля не найдены. Передайте своё фото мне в ЛС» передаётся обычным инструментом готовых результатов, без отдельного промежуточного API:

```js
set_inline_results({
  requestId,
  results: [{
    title: 'Нет фото',
    description: 'Фото профиля не найдено, отправьте мне в ЛС',
    message: {
      text: 'dummy'
    }
  }]
});
```

title/description видны в списке выбора, даже если пользователь ничего не публикует. message не обязан совпадать с пояснением. `dummy` технически допустим как непустой текст, но при выборе карточки отправится именно он. Агент может передать осмысленный текст либо опустить message и получить нейтральное сообщение по §42. Служебная строка не становится невыбираемой и не открывает ЛС нажатием. Это соответствует [InlineQueryResultArticle](https://core.telegram.org/bots/api#inlinequeryresultarticle).

Успешный set_inline_results с таким результатом завершает ожидание текущей версии по §40. На подходящем запросе страницы выдаётся пояснение и завершается пагинация; прежние строки ожидания не удаляются. Агент сам решает, подготовить сообщение, файл, уточнение или пояснение об отказе; отсутствие фото не должно оставлять барабан бесконечно в ожидании, если агент уже решил, что ему нужны дополнительные данные.

Пользователь читает пояснение и самостоятельно переходит в личный диалог с тем же ботом, где файл принимается обычным сообщением. Само получение фотографии не оживляет завершённый requestId и не даёт права повторно открыть уже закрытую пагинацию; новый inline-ввод подчиняется §37. Продолжение задачи и повторная подготовка выдачи требуют отдельного поручения/согласованного сценария продолжения; автоматическое прикрепление любого следующего файла к старому запросу не принимается.

Верхнюю кнопку с start_parameter не используем как динамический канал уточнений. Проверено по исходникам 2026-10-17: [Android](https://github.com/DrKLO/Telegram/blob/master/TMessagesProj/src/main/java/org/telegram/ui/Adapters/MentionsAdapter.java#L859-L863) не заменяет уже установленный switch_pm, [Desktop](https://github.com/telegramdesktop/tdesktop/blob/dev/Telegram/SourceFiles/inline_bots/inline_results_widget.cpp#L377-L400) читает присланные параметры и на следующих страницах. Поэтому утверждение «Telegram вообще запрещает менять кнопку» слишком категорично, но опираться на одинаковое обновление во всех клиентах нельзя. Предыдущая рекомендация динамически менять её для этого сценария снимается. Принятый исходный переход при отсутствии агента (§25) сохраняется.

В подсказку агенту добавить: «Если inline-поручение нельзя закончить без уточнения, верни пояснение обычным set_inline_results. Используй title/description для инструкции пользователю; помни, что выбор результата отправляет message в исходный чат. При необходимости попроси передать файл в ЛС. Отдельного set_inline_status для этого нет».

Проверки будущей реализации: уточнение завершает ожидание так же, как обычный результат; title/description показываются без публикации; выбор строки отправляет именно message.text, включая dummy в приведённом примере; отсутствие динамической смены верхней кнопки не мешает выдаче пояснения; поздний результат другой версии отсекается; фотография из ЛС сама не возобновляет завершённую выдачу. Код и живые проверки пока не выполнены.

## 42. Принято: нейтральный крестик без кнопок

Для служебных пунктов барабана принято нейтральное сообщение `{text: '✖️'}` без кнопок. Агенту разрешено опускать message в set_inline_results: контроллер подставляет тот же нейтральный message без клавиатуры. title/description остаются пояснением для выдачи, и выбор всё равно публикует крестик в исходный чат. Обычный заданный агентом message и его кнопки не заменяются автоматически.

Пример уточнения без явно заданного публикуемого содержимого:

```js
set_inline_results({
  requestId,
  results: [{
    title: 'Нет фото',
    description: 'Фото профиля не найдено, отправьте мне в ЛС'
  }]
});
```

Системную кнопку «Удалить» и отдельный обработчик для неё не вводим. Причина: у [deleteMessage](https://core.telegram.org/bots/api#deletemessage) обязательны chat_id и message_id, параметра inline_message_id нет. [CallbackQuery](https://core.telegram.org/bots/api#callbackquery) от inline-публикации даёт inline_message_id вместо message с обычным адресом. Нейтральное сообщение не обещает автоматического удаления; пользователь может удалить его средствами своего Telegram-клиента.

В подсказку агенту добавить: «message можно опустить: при выборе результата будет отправлен нейтральный крестик ✖️ без кнопок. Для содержательного сообщения или клавиатуры задай message явно».

Проверки будущей реализации: отсутствие message даёт крестик без клавиатуры; явный message и его кнопки сохраняются; служебные строки барабана используют тот же шаблон; нажатие результата действительно публикует крестик; системная кнопка удаления не создаётся. Код и живые проверки пока не выполнены.

## 43. Принято: временный запрос в памяти, без восстановления

По решению пользователя inline-поручение и готовая выдача хранятся только в памяти контроллера. Постоянный кеш запросов и ответов по тексту не вводится; после перезапуска обслуживание не восстанавливается. Прежний вариант с сохранением в базе на 24 часа не используется. Это относится к подготовке выдачи, а не к уже выданным кнопкам, принятым button-событиям, зарегистрированным widget view или inline-снимкам после наших правок: их согласованные правила хранения сохраняются.

### Ожидание и готовый ответ

- Если запросы страниц прекратились, контроллер не знает, закрыл ли пользователь выдачу. Продолжает ждать set_inline_results до истечения срока обслуживания или нового начального запроса.
- Если агент закончил ход без результата, ожидание продолжается в пределах общего часа жизни версии. После expiresAt новые строки «Агент думает» не добавляются. Начатая агентская работа не прерывается, а запоздалый результат не принимается для утраченного запроса.
- При успешном set_inline_results готовые варианты и определения кнопок остаются в памяти до страницы, на которой их можно выдать, до того же expiresAt либо до нового начального запроса. Получение результата не продлевает срок и ещё не создаёт записей кнопок в БД.
- После успешной отправки страницы буфер полного ответа можно освободить. Обработка повторов и неопределённого подтверждения не должна заново создавать одноразовые группы; небольшие служебные метки допустимы в памяти в пределах жизни версии. Отдельный кеш ответов для следующих одинаковых вопросов не вводится.

Принят один общий час: expiresAt = createdAt + 1 час, где createdAt — создание внутренней версии при начальном запросе. Например, результат пришёл через 50 минут — его можно выдать ещё 10 минут. Прокрутка, конец модельного хода, переход в фон и готовность результата expiresAt не меняют. Это предельный срок с большим запасом; отдельного дополнительного часа после готовности нет.

### Запись кнопок при выдаче

Под «скроллом» понимается запрос страницы по действующему курсору, в том числе возможная автоподгрузка клиента. Когда в ответ на такой запрос возвращаются готовые варианты:

1. Проверить текущую версию, владельца и срок; выбрать включаемые в страницу варианты.
2. Сохранить в БД кнопки/действия именно этих вариантов и завершить транзакцию.
3. Только после успешной фиксации вызвать answerInlineQuery с соответствующими btnId/tipId.

Если запись не удалась, страницу с неработающими кнопками не отправлять, обслуживание версии прекратить и готовый буфер освободить по §49. Страница без кнопок не требует регистрации кнопок. Уже выбранный для ожидания запрос страницы может получить готовый ответ, если тот успел прийти до его отправки: дополнительное движение пользователя не требуется.

Для повторных или одновременных допустимых запросов до прекращения обслуживания использовать прежние идентификаторы и сведения об уже выполненной регистрации. Не вставлять удалённые после нажатия записи снова и не открывать закрытую группу. При ошибке answerInlineQuery обслуживание версии прекращается по §49, повторной выдачи для неё не будет. Запись, попавшая в БД до неудачной/неопределённой отправки Telegram, остаётся до обычной очистки реестра: результат мог быть доставлен. Восстанавливать ради неё запрос или удалять её сразу как гарантированно неиспользованную не требуется.

Смена запроса или истечение в процессе подготовки страницы согласуется с проверкой непосредственно перед регистрацией/отправкой. Уже переданные Telegram результаты не отзываются, их кнопки живут независимо от потерянного буфера. Отдельного сохранения текста исходного запроса или полного ответа в БД ради этой выдачи не требуется.

### Перезапуск, новый запрос и старые курсоры

Перезапуск теряет и ожидание, и готовый невыданный ответ. Поздний set_inline_results получает явный отказ «запрос недоступен/устарел» и не создаёт кнопок; связывать его с новым запросом того же текста нельзя. Автоматического восстановления или повторной постановки агентского поручения нет. Это принятие возможной потери уже подготовленного результата.

Новый начальный inline-запрос с пустым offset создаёт новую версию, даже если текст совпал: прежний буфер освобождается, поручение снова проходит барабан. Запрос страницы с непустым курсором продолжает привязанную к нему версию и не очищает её буфер. Повторная доставка того же Telegram-запроса отсекается как дубликат, а не считается новым обращением. Формат курсоров остаётся отдельной деталью; потерянный/истёкший/чужой курсор нельзя трактовать как новый начальный запрос.

Для утраченного или истёкшего курсора предлагается пустая завершающая страница без next_offset, без нового ожидания и без повторного запуска агента. Это конкретизация «перестаём добавлять ожидание»; отдельная карточка об истечении не обязательна. Уже выданные кнопки остаются в БД после перезапуска, смены версии и освобождения готового буфера. Обычный контекст/история работы агента не становятся кешем inline-выдачи и этим решением не изменяются.

Проверки будущей реализации: до запроса готовой страницы нет записей её кнопок в БД; перед передачей Telegram они уже зафиксированы; ошибка БД не выдаёт кнопки; повтор страницы не создаёт новые ID и не оживляет закрытые группы. Закрытие окна не отменяет запрос, но новый начальный запрос освобождает старый буфер; тот же текст обрабатывается заново; скролл и дубликат доставки не сбрасывают версию. Перезапуск теряет ожидающий/готовый запрос, старый set_inline_results отклоняется, ранее выданные кнопки продолжают работать. Проверить общий expiresAt для ожидания и готового ответа: результат через 50 минут доступен ещё 10 минут, срок не продлевается активностью или готовностью. Код и живые проверки пока не выполнены.

## 44. Принято: первоначальное inline-событие агенту

Принят отдельный eventType: 'inline', с устойчивым requestId внутренней версии, полным текстом поручения в query, expiresAt в ISO-формате и необязательным chatType. from в первоначальное событие не включается: поручение всегда получает личный агент автора inline-запроса, то есть текущего собеседника по ЛС. expiresAt показывает уже принятый общий час от создания версии; очередь агента и фоновые задачи не получают нового срока.

```json
{
  "eventType": "inline",
  "requestId": "inline-request-123",
  "query": "Сгенерируй изображение котика",
  "chatType": "supergroup",
  "expiresAt": "2026-10-17T13:00:00Z"
}
```

chatType берётся из нативного InlineQuery.chat_type без придумывания нового классификатора: sender, private, group, supergroup или channel. Если Telegram не передал тип, поле отсутствует; значение не угадывается по агентскому ЛС и не подменяется private. Это тип чата, в котором вызван inline-запрос, а не доказанный адрес фактической публикации; он может помочь агенту выбрать содержание и оформление. chatId, messageId и inlineMessageId не добавляются до публикации. requestId не является Telegram inline_query.id отдельной страницы. Значения и необязательность проверены по [InlineQuery](https://core.telegram.org/bots/api#inlinequery) 2026-10-17.

Контроллер продолжает использовать нативный from.id для проверки автора, выбора личного агента, ключа botId/userId и буферной отправки по умолчанию. Удаление from из модельного события не отменяет этих проверок. Оно касается только первоначального inline-события; from в button остаётся, поскольку кнопку может нажать другой человек (§32).

Событие передаётся выбранному личному агенту после принятого условия запуска барабана и только один раз на версию. В общую инструкцию агенту включить: автор — текущий собеседник по ЛС; chatType описывает место вызова и не даёт доступа к его переписке; ответить через set_inline_results с исходным requestId; сохранять этот ID для фонового продолжения; обычный send использовать для необходимых действий, включая разрешённую буферную отправку файлов, а не как автоматическую замену inline-ответа.

## 45. Принято: окончательный результат и повторные вызовы

Первый успешно принятый set_inline_results окончателен для requestId. Весь список проверяется до приёма: если ошибочен хотя бы один вариант, вернуть ошибку без частичного результата; актуальный запрос остаётся в ожидании, агент может исправить аргументы. После успеха принимается один набор в памяти, без немедленной записи кнопок в БД, как уже решено в §43.

Повторный вызов для ещё действующего requestId после приёма результата возвращает `{status: 'already_set'}` без замены, добавления вариантов и регистрации новых кнопок. Это относится и к другому содержимому повторного вызова: статус означает «результат для этого запроса уже принят», а не «ваш новый список совпал с прежним». Для первого успешного приёма возвращается `{status: 'accepted'}`. Конкурентные успешные вызовы упорядочиваются: принимается один. Потеря подтверждения инструмента допускает безопасный повтор с явным already_set.

Пустой results считается допустимым окончательным ответом без агентских вариантов. Контроллер добавляет одну служебную строку с title «Работа завершена», нейтральным message `{text: '✖️'}` без кнопок и пустым next_offset. На подходящем запросе страницы показывается эта строка и завершается пагинация; ожидание больше не выдаётся. Выбор строки публикует только крестик. Уже показанные служебные строки не удаляются. Если агент хочет пояснить причину, он может передать обычный информационный вариант без message, как согласовано в §41–42.

После выдачи и освобождения полного буфера достаточно оставить до expiresAt небольшую метку «результат принят», чтобы повтор инструмента не создал новый набор. Это не кеш полного ответа и не восстановление после перезапуска. Истёкший, отменённый или потерянный при перезапуске requestId возвращает явную ошибку недоступности, а не accepted/already_set; проверка владельца сохраняется.

Проверки будущей реализации: ошибка одного варианта не принимает остальные; исправление после ошибки возможно; повтор после успеха не меняет результат независимо от содержимого; два одновременных вызова дают одного победителя; повтор после выдачи не создаёт новые кнопки. Пустой список даёт ровно одну строку «Работа завершена» с крестиком без кнопок, прекращает ожидание и заканчивает пагинацию; просроченный и чужой requestId не получают успех. Код и живые проверки пока не выполнены.

## 46. Принято: точка отсчёта и живая калибровка порога

Измерение привязывается к конкретному курсору: непосредственно перед вызовом answerInlineQuery, который отдаёт страницу с этим next_offset, сохранить в памяти серверное время начала отправки issuedAt. При получении следующего запроса с этим курсором вычислить паузу от issuedAt до времени получения запроса. Время доставки пользователю неизвестно; порог остаётся принятой эвристикой с допустимыми ложными срабатываниями, а не доказательством ручной прокрутки.

- Пауза меньше 2 секунд: вернуть ещё страницу приглашений прокрутить с новым курсором и собственной точкой отсчёта.
- Пауза не меньше 2 секунд: если версия ещё текущая, не истекла и не передавалась агенту, однократно передать поручение в очередь и перейти к ожиданию результата.
- Само истечение 2 секунд без следующего запроса страницы не запускает агента.
- Привязка версии, пользователь и срок проверяются до измерения/действия. Одновременные запросы не должны передать поручение дважды. Повтор доставки того же Telegram-запроса не создаёт новую точку отсчёта и новый запуск.

Отсчёт начинается до ожидания ответа Telegram на answerInlineQuery: запрос следующей страницы может прийти раньше завершения этого ожидания. Ошибка/неопределённый результат отправки прекращает обслуживание этой версии (§49); старые и повторные курсоры обслуживаются по §48, без второго запуска. Это не сдвигает общий expiresAt версии.

Пример: страница с курсором A начала отправляться в 12:00:00; запрос A пришёл в 12:00:00.3 — выдаём новую страницу с курсором B. Если B начал отправляться в 12:00:00.4, а запрос B пришёл в 12:00:03, пауза 2.6 секунды допускает запуск. После запуска дальнейшие страницы обслуживают ожидание, не переоценивая условие запуска.

Порог 2 секунды сохраняется по принятому после живых замеров решению пользователя: нужен запас на задержки и сбои сети. В реализации используется единый параметр порога. Подтверждённая автоподгрузка Desktop занимала 160–196 мс; в других опытах встречались быстрые запросы до 945 мс без надёжного разделения автоматики и ручной прокрутки. Нижняя безопасная граница не установлена, проверять меньшие значения для принятого решения не требуется. Этот запас не исключает ложного запуска при ещё более медленной автоподгрузке. Полные условия и ограничения выборки фиксируются в отчёте о калибровке; офлайн-тесты не заменяют наблюдения клиента.

Дополнительно принято откалибровать количество служебных строк, при котором клиент перестаёт автоматически запрашивать следующую страницу барабана. Проверить Desktop, Android и iOS на разных устройствах, размерах окна/экрана и масштабах интерфейса; записать число строк, автоподгрузки и момент необходимости ручной прокрутки. Число пунктов начальной страницы пока не выбрано; отдельно наблюдать поведение после однострочных страниц «Агент думает», не объявляя его уже проверенным. Подобранное значение должно опираться на замеры, а не предположение об одинаковом экране у всех клиентов.

Предел общего числа страниц не вводится. Обслуживание ограничено уже согласованными общим часом, сменой версии и ошибками; калибровка размера страницы не является лимитом количества страниц.

Ожидание готовности страницы до 5 секунд принято отдельно в §47. Проверки будущей реализации: быстрые страницы не запускают поручение, пауза ровно на выбранном пороге допускает запуск, отсутствие запросов не запускает таймером, каждый новый курсор имеет собственный issuedAt, одновременные/повторные запросы не запускают работу дважды. Код и живые проверки пока не выполнены.

## 47. Принято: ограниченное ожидание готовности при запросе страницы

Запрос страницы после запуска агентского поручения обслуживается так:

1. Если результат уже готов, сразу зарегистрировать необходимые кнопки и вернуть готовые варианты по §43. Пустой агентский список даёт «Работа завершена» по §45.
2. Если результата нет, асинхронно ожидать его до 5 секунд с момента получения этого запроса страницы. Это ограниченное ожидание одной страницы, не цикл новых агентских событий и не продление общего часа.
3. Если set_inline_results принят до окончания ожидания, ответить готовыми вариантами сразу, не дожидаясь всех 5 секунд. Проверить актуальность и срок перед регистрацией кнопок и отправкой.
4. Если за 5 секунд результата нет, вернуть один служебный пункт «Агент думает» с message ✖️ без кнопок и курсором продолжения. Следующий запрос страницы проходит ту же схему; весь ход агента одним запросом Telegram не удерживается.

Смена версии, истечение expiresAt или потеря запроса прекращают ожидание страницы: обслужить её по принятому правилу старого курсора, без новой строки ожидания и без повторного запуска агента. Продолжительность ограничена также оставшимся временем жизни версии. Гонка готовности с таймером не должна породить два ответа на один Telegram inline_query.id; после выбора ответа ожидающая подписка/таймер освобождается.

5 секунд — предварительное значение для этого механизма. Обязателен отдельный живой эксперимент: проверить, успевает ли Telegram принять такие ответы на поддерживаемых клиентах с учётом задержек, досрочную отдачу готовых вариантов и переход к следующей странице после ожидания; успешность не объявляется гарантированной до проверки. Этот параметр независим от предварительных 2 секунд допуска поручения агенту (§46). До передачи поручения агенту страницы приглашения прокрутить не получают дополнительной пятисекундной задержки. Эксперимент ещё не проводился.

Пример: пользователь запросил следующую страницу, ответ агента появился через 0.8 секунды — готовые варианты уходят через 0.8 секунды. Если ответа нет, через 5 секунд возвращается «Агент думает». Отсутствие новых запросов после этого не создаёт самостоятельных отправок страниц.

Проверки будущей реализации: готовый результат без задержки, раннее пробуждение, ожидание до предела с новым курсором, отмена/истечение во время ожидания, один ответ при гонке таймера и готовности, отсутствие повторных событий агенту и лишней задержки до его запуска. Код и живые проверки пока не выполнены.

## 48. Принято: повторные и устаревшие курсоры

Каждый выданный непрозрачный курсор связывается с текущей внутренней версией, владельцами botId/userId и сохранённым issuedAt. На входе проверять принадлежность, наличие версии в памяти, срок и то, что она не заменена новым начальным запросом. Известный контроллеру курсор текущей версии не обязан быть последним выданным, чтобы запрос был допустимым; его повтор не создаёт новую версию.

Допустимый повтор обслуживать по текущему состоянию версии, без сохранения истории полных страниц: до запуска действует проверка порога этого курсора, после запуска — ожидание §47, при готовности — отдача результата с прежними идентификаторами, после уже завершённой выдачи — пустая завершающая страница. Не обещать повтор байт-в-байт ранее отданной страницы. Повторный запрос не передаёт уже принятое поручение агенту, не регистрирует кнопки заново и не открывает использованные группы.

Потерянный после перезапуска, истёкший, отменённый, чужой или неизвестный непустой курсор получает пустую страницу без next_offset. Он никогда не становится новым начальным запросом и не сбрасывает текущую версию другого поручения. Новый начальный запрос по-прежнему определяется пустым offset. Дубликат доставки того же Telegram-запроса отсекается отдельно от повторного обращения по тому же курсору с новым query id.

Состояние передачи агенту и регистрации кнопок меняется последовательно для версии; одновременные запросы не должны запустить два поручения или повторно зарегистрировать результат. Сетевое ожидание страницы не должно блокировать обработку смены версии и истечения срока. Ошибка/неопределённое подтверждение answerInlineQuery прекращает обслуживание по §49; последующие курсоры этой версии получают пустую завершающую страницу и не переоткрывают успешно израсходованную группу.

Проверки будущей реализации: повтор действующего старого курсора, разные query id с одним курсором, дубликат того же query id, чужой/случайный/истёкший курсор, курсор прежней версии после нового начального запроса, одновременная прокрутка до/после запуска и повтор после готовой выдачи. Текст запросов и полные ответы в БД не сохраняются. Код и живые проверки пока не выполнены.

## 49. Принято: ошибка answerInlineQuery или записи кнопок прекращает обслуживание

При любой ошибке answerInlineQuery, включая транспортную неопределённость, контроллер прекращает обслуживание соответствующей внутренней версии requestId. Правило одинаково для приглашения прокрутить, страницы «Агент думает» и готовых результатов. Автоматической повторной отправки и восстановления этой версии нет. Начатая работа агента не прерывается; ожидающее поручение по возможности снимается с очереди, как при отмене версии.

Если ошибка произошла при выдаче ожидания, поздний set_inline_results больше не принимается и кнопки из него не записываются в БД. Если агент успел вернуть результат в память, но выдача ещё не состоялась, такой буфер освобождается. Утрата может случиться даже после успешного ответа самого инструмента агенту; это принятое следствие завершения обслуживания без постоянного хранения.

Если кнопки уже записаны перед отправкой готовой страницы, они остаются в БД независимо от вида ошибки: Telegram мог доставить результат. Их callback обрабатывается по обычному реестру, без требования действующего inline-запроса. Закрытые группы не восстанавливаются. Если результата никто не получил, записи могут остаться невостребованными до штатной очистки реестра.

Отмена привязывается к requestId неудачного вызова, а не просто к текущему пользователю: запоздалая ошибка старой страницы не отменяет уже начатый новый запрос. Проверка закрытия перед приёмом результата, регистрацией кнопок и отправкой страницы предотвращает новые действия старой версии; уже выполненные записи/отправки не откатываются. Старые курсоры получают пустой завершающий ответ по §48; если такой ответ сам завершится ошибкой, он не затрагивает другое действующее поручение. Новый начальный запрос может начать обычный барабан заново.

При ошибке записи кнопок в БД до answerInlineQuery также прекратить обслуживание этой версии, освободить готовый буфер и отклонять поздний set_inline_results. Страницу с готовыми результатами не отправлять. Транзакция неуспешной регистрации откатывается; уже существующие записи других либо ранее выданных результатов не удаляются. Не отправлять страницу с предложением повторить попытку и не вводить отдельный цикл восстановления. Ошибка БД сама по себе не прерывает уже начатую агентскую работу и не отменяет другую текущую версию.

Проверки будущей реализации: ошибка при приглашении прокрутить и ожидании закрывает только соответствующую версию; поздний результат отклоняется без новых записей; ранее готовый буфер освобождается. Ошибка после фиксации кнопок не удаляет их, потенциально доставленная кнопка продолжает работать. Ошибка БД до фиксации закрывает версию без отправки готовой страницы и без частично зарегистрированных кнопок. Ошибка старой версии не отменяет новую; повтор курсора не оживляет обслуживание; нет автоматических повторов и новых агентских событий. Отдельно проверить гонки результата/фиксации/смены версии/ошибки. Код и живые проверки пока не выполнены.

## 50. Принято: раскладка кнопок и прежний формат permits

Проверено по [InlineKeyboardMarkup](https://core.telegram.org/bots/api#inlinekeyboardmarkup): inline_keyboard — массив рядов, каждый ряд — массив кнопок. В [InputRichBlockButtons](https://core.telegram.org/bots/api#inputrichblockbuttons) один блок описывает один ряд из 1–8 кнопок; несколько рядов задаются несколькими blocks типа buttons. Это разные места размещения: нижняя клавиатура сообщения и кнопки внутри rich-содержимого.

Сохранить ранее обсуждавшееся поле message.buttons как сокращённую запись нижней клавиатуры, с матрицей рядов по той же модели. Ранее показанный плоский buttons: [button, ...] поддержать как сокращение одного ряда; новые примеры делать с явными вложенными массивами. Для rich-сообщения сохранять обычные блоки buttons, каждый со своим одномерным списком. Единую матрицу не вкладывать внутрь отдельного rich buttons-блока.

Для action-кнопки приняты text, необязательный логический key, необязательный group и самодостаточный action. key нужен для правил доступа и читаемой идентичности; это не генерируемый btnId. Для проверки permits составляется прежний логический callback: key без группы или [group]key при её наличии. Сам Telegram получает непрозрачный btnId, назначенный контроллером; key/group/action и правила доступа находятся в служебной записи. Проверку выполнять по восстановленным из неё данным, а не по произвольному содержимому callback.

Пример message для set_inline_results:

```js
{
  text: 'Выберите игру',
  buttons: [
    [
      {text: 'Wordle', key: 'wordle', group: 'start',
       action: 'Активировать виджет Wordle на этом сообщении'},
      {text: 'Nerdle', key: 'nerdle', group: 'start',
       action: 'Активировать виджет Nerdle на этом сообщении'}
    ],
    [{text: 'Правила', key: 'rules',
      action: 'Объяснить правила игр Wordle и Nerdle'}]
  ],
  permits: {
    '[start]*': [123],
    'rules': null
  }
}
```

Сохранить текущий формат и смысл message.permits из src/messages/callbacks.mjs: словарь логических callback-ключей/префиксных шаблонов в null либо массив userId. Точный ключ приоритетнее шаблона, среди шаблонов выигрывает наиболее длинный префикс; '*' — общий fallback. null разрешает всем, [123] — только указанным ID, [] — никому; отсутствие подходящего правила при заданном словаре запрещает. Отсутствующий/null permits разрешает всем. Для inline применять проверку независимо от известного chatType. В текущей реализации обычных сообщений permits проверяются на неперсональном маршруте, личные callback имеют отдельную авторизацию, а канал отклоняет обычную обработку; это не объявляется готовой поддержкой нового inline-пути.

В примере пользователь 123 может выбрать Wordle или Nerdle, любой участник может нажать «Правила». Первое допустимое принятое нажатие группы start закрывает обе стартовые action-кнопки во всех публикациях этой заготовки по уже принятому правилу; rules без группы остаётся повторяемой.

key необязателен: без него контроллер назначает внутренний логический ключ; для точного правила доступа агент задаёт key явно. Общие '*' и групповые '[group]*' правила применимы и без явно заданного key. Это сохраняет прежние примеры action-кнопок без ключа. ## 51. Принято: сроки выданных кнопок и inline-снимков

Срок обслуживания запроса (§43), срок первоначальных action-кнопок и срок сохранённого содержимого опубликованного сообщения разделяются:

- Запись подготовленной кнопки действует 30 дней от первой регистрации перед выдачей соответствующей карточки. Повтор страницы, нажатия, чтение и редактирование сообщения срок этой записи не продлевают. Повтор регистрации того же btnId не восстанавливает израсходованную группу. Истёкшая кнопка подтверждается без текста и без события агенту, даже если физическая очистка БД ещё не прошла.
- Снимок обычного inline-сообщения хранится 30 дней от последней нашей подтверждённой правки. Подтверждённая частичная правка продлевает срок снимка, сохраняя признак partial и только известные поля. read и неопределённый результат отправки срок не продлевают. После очистки read возвращает message_not_found; это отсутствие локального содержимого, а не доказательство удаления сообщения в Telegram.
- Адресное владение и маршрутизация не должны исчезать раньше действующих кнопок или привязки виджета. После очистки содержимого допустимо оставить минимальную запись владельца без текста: пока есть действующая зависимость, а также на 30 дней от последней подтверждённой правки или принятого callback этого адреса. Сам read срок не продлевает. Это сохраняет обычную правку владельцем без полного снимка и не даёт чужому агенту перехватить адрес посредством старого токена.
- Виджеты, их view и необходимые рабочие проекции не очищаются по сроку истории или первоначальной стартовой кнопки. Если Wordle запущен до её истечения, его игровые кнопки продолжают обрабатываться виджетом. Очистка истории не отвязывает view, не открывает закрытые группы и не удаляет уже принятое, ещё не переданное событие.

Пример: стартовая карточка выдана 1 октября, Wordle подключён 2 октября. Истечение записи «Начать» через 30 дней от выдачи не останавливает игру. Для обычной карточки без виджета новая подтверждённая правка 20 октября продлевает хранение известного содержимого ещё на 30 дней, но не оживляет первоначальную стартовую кнопку.

Очистка буферных сообщений/файлов и утрата file_sources согласованы отдельно в §52. Проверки будущей реализации должны различать логическое истечение и фоновое удаление, срок снимка и владения, сохранение активного view, частичные/неопределённые правки, повтор страницы и закрытой группы, а также перезапуск контроллера. ## 52. Принято: буферные сообщения и утрата источника файла

Сообщение остаётся в выбранном пользователем буферном чате либо в ЛС автора, куда отправлено без звука. Удаление возможно пользователем или агентом по обычному запросу и с обычными правами; завершение inline-поручения само по себе его не удаляет.

Проверено в исходной версии проекта: src/storage/retention.mjs и docs/storage.md задают очистку сохранённых сообщений старше 30 дней от первого получения и временных файлов/зарегистрированных источников генерации старше 24 часов по mtime; фоновая очистка запускается каждые 24 часа. Истечение локальной записи источника не объявляется истечением Telegram file_id и не вызывает удаления уже опубликованных сообщений. ## 54. Принято: рекурсивная заморозка view в render

В render(state, view) передаётся отдельный снимок view, рекурсивно замороженный через Object.freeze: id, target, props и все вложенные объекты/массивы доступны только для чтения. Одного Object.freeze(view) недостаточно, поскольку он не замораживает вложенные значения. Замораживается снимок, а не служебная запись контроллера; отдельные прокси или перехватчики записи не вводятся. Общее state не замораживается.

Для попытки изменения действует обычная семантика JavaScript: в строгом коде запись в замороженное свойство вызывает TypeError; в нестрогом присваивание может быть проигнорировано. Гарантия контракта — невозможность изменить снимок, а не обязательное исключение для любой формы записи. Неперехваченное исключение обрабатывается как обычная ошибка рендера через onError и lastError. Если код обработчика сам перехватил исключение и вернул допустимый результат, рендер может завершиться штатно. Сохранённая привязка и параметры не изменяются ни в одном случае.

Это предотвращает скрытое изменение настроек одной публикации из render и влияние такого изменения на следующие рендеры. Состояние игры остаётся общим state; новый запрет на изменение state этим решением не вводится. Параметры представления меняет агент через уже принятое повторное подключение сообщения: создаётся новый view с новым id, с ожиданием текущего рендера и сохранением старого при неуспехе замены.

Пример нового обработчика игры: view.props.part === 'results' выбирает табло, view.props.part === 'game' — игровое поле. Присваивание view.props.part = 'game' внутри render не переключает сохранённое табло: это запрещённая запись. Для смены режима агент вызывает set_widget_view с новым props. Предоставленный Wordle не адаптируется под эти параметры: его прежний render(state) игнорирует второй аргумент и работает без изменения исходника.

Снимок соответствует конкретному вызову. При первом рендере перед отправкой у target ещё нет messageId; после успешной отправки следующий вызов получает новый снимок с полным адресом при том же view.id. Ранее переданный объект не дополняется задним числом. Снимки event.view сохраняют уже принятые правила фиксации источника при поступлении события.

Проверки будущей реализации: заморозка корня и вложенных объектов/массивов props, запись/удаление полей target, отсутствие изменения сохранённой привязки и других view, обычная обработка неперехваченной ошибки рендера, первый неполный и последующий полный target, а также совместимость прежнего render(state) Wordle. Код и живые проверки пока не выполнены.

## 55. Принято: сохранить текущие таймауты runtime

Проверено в исходной версии проекта: src/widgets/contract.mjs задаёт teardownMs = 5000, heartbeatMs = 5000, silenceMs = 10000 и sampleMs = 500. В manager.mjs единый таймер ограничивает запрос retire; runtime.mjs отправляет heartbeat каждые heartbeatMs, host.mjs проверяет превышение silenceMs. Принято сохранить эти значения и их назначение:

| Параметр | Значение | Назначение |
| --- | --- | --- |
| teardownMs | 5 секунд | Общий бюджет штатного завершения при retire: ожидание текущей работы, onStop и освобождения ресурсов внутри runtime |
| heartbeatMs | 5 секунд | Интервал отправки heartbeat из runtime |
| silenceMs | 10 секунд | Допустимая пауза с последнего принятого heartbeat; авария при превышении |
| sampleMs | 500 мс | Интервал фоновой проверки runtime |

Бюджет retire отсчитывается от начала запроса на завершение и не начинается заново на каждом этапе. По его превышению применяется уже принятая общая аварийная остановка всех виджетов этого runtime. Работа с Telegram для отключения кнопок после аварии остаётся best effort и не должна задерживать принудительное завершение процесса. Обнаружение нарушения heartbeat происходит при очередной проверке, а не гарантированно ровно через 10 секунд.

teardownMs ограничивает процедуру завершения. Отдельный универсальный пятисекундный срок обычного обработчика или рендера этим решением не вводится: асинхронная операция может ждать дольше при работающем heartbeat. Если потребовалось её завершение через retire, действует указанный общий бюджет. Сохранение текущих чисел не меняет отдельно принятые интервалы inline-барабана и правила подтверждения callback.

Проверки будущей реализации: единый бюджет retire без продления при переходе к onStop, нарушение heartbeat при очередной выборке, одна аварийная остановка и одно уведомление при одновременном срабатывании проверок, сохранение очередей пустыми и остановленных статусов, отсутствие влияния на другие runtime. Код и живые проверки пока не выполнены.

По тому же критерию полноценные платежи требуют отдельного расширения, а не одной сериализации invoice. Источники: [InputInvoiceMessageContent](https://core.telegram.org/bots/api#inputinvoicemessagecontent), [answerPreCheckoutQuery](https://core.telegram.org/bots/api#answerprecheckoutquery).

Неподдержанный тип или поле, требующее отсутствующей подсистемы, должны давать понятную ошибку валидации до принятия результата; нельзя молча заменять такую нагрузку обычным текстом. Явно исключены game, callback_game, InputInvoiceMessageContent и платёжные кнопки/сценарии; обход через вложенные нативные поля не допускается. Общий адаптер сохраняет проверки file_sources/прав, регистрацию action-кнопок, permits и назначение служебных идентификаторов контроллером. Передача нативных полей не создаёт обход этих правил. Самостоятельная интеграция Telegram Games или платежей в текущую работу не входит.

Исходники Wordle и его игровых зависимостей остаются неизменными. Обязательная проверка — работа текущего обработчика на старой версии, миграция тех же сохранённых регистраций/состояния и управление через новый API. Несколько view такого Wordle показывают полную существующую карточку и общий активный выбор; отдельные игровые поля, клавиатуры и пассивные табло в этот обработчик не добавляются. Воспроизведение старого поведения и отсутствие скрытой правки игры важнее демонстрации новых props на этом примере. О проблемах обратной совместимости предупреждать пользователя по §9.

Это принятые требования и выявленные границы сложности, а не выполненная реализация. Нужны проверки всех включённых семейств результатов и их дополнительных полей, внешних URL и file_id, отказа неподдержанным интеграциям без частичного принятия, совместимости простого message-формата и миграции неизменённого Wordle.

## 57. Принято: пользователь сам возвращается новым inline-запросом

После настройки личного агента, включения агента или передачи фотографии/файла в ЛС пользователь сам возвращается в нужный чат и начинает новый inline-запрос. Специальную кнопку возврата, сохранение исходного текста ради повторного запуска и автоматическое продолжение прежнего requestId не реализовывать. Исходный переход в ЛС при отсутствии доступного агента (§25) сохраняется.

Новый начальный запрос проходит обычный барабан, получает новую версию и при необходимости заменяет ещё обслуживаемый старый запрос по §37. Уже завершённое поручение не оживает от настройки агента или поступления фотографии. Агент может использовать доступные ему данные из ЛС в рамках обычного контекста и прав; отдельный кеш исходного inline-поручения для этого не нужен.

Это принятое правило. При проверке сценария настройки и передачи фото убедиться, что новый inline-запрос работает обычным образом, старый requestId не возобновляется автоматически, а переход в ЛС сам по себе не создаёт повторного поручения.

## 58. Обязательная проверка: смешанные типы inline-результатов

Пользователь отдельно потребовал проверить возможность смешивать разные типы сообщений в одной inline-выдаче, если документация не гарантирует это явно. По проверенной схеме [answerInlineQuery](https://core.telegram.org/bots/api#answerinlinequery) results имеет тип массива InlineQueryResult, элементы которого описываются разными нативными типами. Требование однородности не указано; отдельная гарантия одинакового клиентского поведения всех сочетаний не найдена. В [MTProto inline results](https://core.telegram.org/api/bots/inline) дополнительно есть gallery-режим, поэтому одного принятого HTTP-запроса недостаточно для приёмки интерфейса.

Проверить два независимых сценария на доступных Desktop/Android/iOS: разные типы на одной странице, а также переход от уже показанных article-строк барабана к готовой странице с фото/видео/документами и другими включёнными типами. Переставить типы местами, проверить список/галерею, видимость и порядок вариантов, пагинацию и фактическое содержимое сообщения после выбора каждого типа. Отдельно проверить rich-содержимое и кнопки. Точная матрица и замеры входят в план реализации и выполняются вместе с калибровкой таймеров и числа prompt rows.

Это требование к живой проверке, а не уже подтверждённая совместимость клиентов. При отказе API или проблеме отображения сообщить конкретный тип/сочетание/клиент пользователю и согласовать необходимое изменение поведения; не подменять медиа текстовой карточкой скрыто и не объявлять успешную нормализацию доказательством Telegram acceptance.

## Separate compiler process (accepted during execution)

The user accepted separating compilation after the live Wordle memory failure. Each build now runs in a temporary owner sandbox with the same filesystem/network profile and its own monitored tree. Builds serialize per owner; snapshots return through the bounded authenticated transport and the process is terminated after each request. The widget runtime has no compiler import or build RPC. A compiler error does not stop running widgets; owner revocation/close also cancels compilation and fences queued build results. Existing runtime memory/heartbeat/teardown limits remain unchanged; compiler trees use the same limits independently. Concurrent compilation can therefore temporarily add memory/processes beyond the resident widget runtime quota. No global cap was introduced.
