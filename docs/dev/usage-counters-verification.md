# Usage accounting: decisions and live verification

Historical feasibility verification, recorded before implementation. Probe date: 2026-10-11 UTC. See the [implementation verification](master-usage-verification.md) for the completed feature.

## Accepted scope

Master bot monitoring compares child bots. Stable identity is the Telegram bot ID. Removed bots retain statistics and remain in service totals, marked `removed`.

Per-bot UTC aggregates: lifetime total, every calendar year, current month plus 11 previous months, current day plus 29 previous days, current hour plus 23 previous hours. Update all applicable buckets atomically. `Total from` reports collection start; no `partial` label for first periods. Current open buckets show `in progress`. Unknown/expired periods are not zero usage.

Store runtime-reported input, output, cached input, reasoning output, cache-write input and total tokens. Cache/reasoning are details, not additional tokens to add to total. Image counters are generation starts and bytes of successfully generated native files, not file copies or Telegram sends. Native image failure contributes a start but no generated bytes.

Commands: `/usage` lists lifetime totals per bot; `/usage all` sums all bots; `/usage @BOT` shows one lifetime total; `/usage @BOT hours|days|months|years` includes available nonzero period buckets. Period options do not apply to `all`. Normal lists sort by input tokens; comparisons sort by input-token increases.

Reply `/usage` to an unedited, non-forwarded report from the master bot compares lifetime counters. Parse exact numbers from report text, including exact image bytes; do not store report snapshots. Approximate elapsed time uses Telegram message dates. No `As of` line. A reply to a command has no prior counters. Preserve Telegram bot IDs in reports for identity matching. Truncate only between complete blocks, and compare only complete displayed bots. Counter decreases produce a reset/unavailable comparison rather than negative consumption.

## Probe environment and safety

Alpine Docker, ordinary uid 1000, Node 24.18.1, Codex 0.159.3. Uses the production named `tg-agent` permission layout: minimal reads, isolated writable wiki, denied `.git` and sibling temp directories, own writable temp, enabled network, unattended approvals denied. Same authenticated Codex home; no auth/token contents read or printed. Separate test threads, no Telegram requests or production database modifications. The regular test bot remains running.

Harness: [usage-counters.mjs](../../test/live/usage-counters.mjs). Analysis: [usage-report.mjs](../../test/live/usage-report.mjs). Private runtime report includes only timestamps, runtime IDs, counters and image file size, not prompts, full image results, base64 or secret values.

## Full live sequence

Two short root turns; one native subagent and wait; close/reopen App Server and resume root; explicit compaction, wait for its turn completion; another root turn; one native image generation.

The corrected full run passed, with 14 usage notifications across two threads. Offline assertions passed on Windows against the sanitized live report. Aggregate across root and child: input 192,091; output 302; total 192,393; cached input 173,696; reasoning output 8; cache-write input 0. These are probe measurements, not a benchmark or pricing estimate.

| Observation | Evidence and implication |
|---|---|
| Per-thread cumulative counters | Root first two totals 14,559 then 30,378. `last` is one request, not necessarily the whole agent turn. |
| Several requests in one turn | Child phase had three root updates plus one child update; image phase had four root updates. |
| Child usage is separate | Child 15,137 tokens; root final total 177,256. Each thread's distinct request totals sum to its own cumulative total; root excludes child expense. |
| Duplicate ownership events | Child-start activity appeared twice for the same thread; ownership registration must be idempotent. |
| Resume replay | Resume re-emitted root cumulative total 78,302 before increasing it to 95,126. Do not add replayed totals. |
| Compaction | Cumulative total remained 95,126. `last.totalTokens` became 6,624 with zero input/output; summing `last` would misclassify this as expense. |
| After compaction | Next root cumulative total increased to 110,957, preserving the previous baseline. |
| Image start/completion | One stable item ID with started/completed notifications. Native file existed immediately at completion and measured 983,017 bytes. |
| Category relationships | Reported total equals input + output; cached input <= input; reasoning <= output. |
| Replay accounting | A per-thread monotonic cumulative baseline ignored a second replay of the entire report without changing aggregates. This is an offline accounting experiment, not a product implementation test. |

The first run failed because the harness started the next turn after compaction's item completion but before compaction's turn completion. Corrected the harness and ran a fresh full sequence successfully. No product change was made.

An additional fresh-session probe requested one child with `fork_context:true`. It completed with separate child counters: initial cumulative and last request both 15,714 tokens, without inherited parent expense. Offline assertions passed. This probe requested the flag in the prompt; it did not independently capture the native spawn arguments, so it is not proof of every fork implementation's behavior. Fresh root runs also began with independent zero-based baselines, rather than carrying the previous session's totals.

## Implementation implications and limits

- Maintain durable cumulative baselines keyed by native thread ID and persistent ownership by Telegram bot ID; account root and children exactly once. Updating baselines and bucket counters must share a transaction.
- On resuming an existing session when collection is newly enabled, establish a baseline instead of importing all historical usage into the current hour. Newly created sessions start from zero. Empty/changed contexts use a new native thread ID.
- Read native image size in the controller at completion, before cleanup or export; deduplicate start and completion accounting independently by thread/item ID. Missing/unreadable file contributes no bytes; internal diagnostics should distinguish missing data from a genuine zero-byte result.
- If a runtime counter decreases, do not silently add the full value or subtract from aggregates. Diagnose the reset/compatibility event and establish a new baseline conservatively.
- Data is as complete as the runtime notifications: transport crashes may lose final updates; account reported partial expense even if the turn fails. Perfect billing completeness is not established.
- Compaction's own billed cost cannot be inferred from this stream: cumulative counters did not expose an increase in this probe. Do not claim it is free.
- Exact image-generator tokens, credits or money are not supplied by the inspected image item schema. Count starts and generated bytes only.
- Actual `/usage`, SQLite storage migration, retention, report parsing, master permission checks and rendering remain future implementation work. No live Telegram acceptance is claimed for them.

## Reproduction

Run as the normal server user, with configured Codex login and an unused private probe directory:

```sh
node test/live/usage-counters.mjs CONFIG_JSON PRIVATE_PROBE_DIRECTORY
node test/live/usage-report.mjs PRIVATE_PROBE_DIRECTORY/report.json
```

This makes real model requests and one image request. Temporary owned threads are deleted best-effort after the run. Generated assets stay under native temporary storage and its existing cleanup lifecycle; do not change the shared Codex home's retention policy for this probe.

Optional additional probe (no image generation): pass `fork` as the third harness argument, then `fork` as the second analysis argument.
