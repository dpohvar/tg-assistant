# Прерывание текущей работы агента

Статус: пользовательское поведение согласовано, включая отмену, возобновление, роли, переполнение и откат кнопок. Реализация не начата; оставшаяся инженерная детализация фиксируется в плане. Согласованное управление контекстом описано отдельно в [context-management-design.md](context-management-design.md).

## Задача

Дать пользователю возможность прервать длительную работу и передать исправление до следующего запуска агента. Контекст, файлы и ожидающие события сохраняются. Cancel отличается от существующего stop, который выключает агента, очищает ожидающую очередь и удаляет контекст после завершения работы.

## Согласовано: отмена текущей работы

- `/agent cancel [AGENT_ID]` немедленно удерживает dispatch и steer выбранного агента, затем запрашивает прерывание текущего основного хода и связанных вычислений.
- Состояния различают отмену в процессе и подтверждённую паузу. Сообщение о завершении отмены отправляется только после подтверждения остановки работы; неизвестный исход не выдаётся за завершение.
- Thread и его история не удаляются, agentEnabled не меняется. Поздние вызовы инструментов отменённого запуска отклоняются. Остановка связанных субагентов и исполняемых команд требует отдельной проверки; прерывание только корневого хода не считается достаточным доказательством.
- Уже выполненные записи файлов, отправленные сообщения и внешние действия не откатываются. Начатый внешний вызов может завершиться после запроса отмены; его подтверждение или неизвестный исход нужно сохранить.
- Ожидающие события остаются на месте. Cancel считается ожидаемым управляющим исходом и не проходит через обычный agent_failed с очисткой очереди.
- Уже переданный агенту пакет не возвращается автоматически в очередь как новый запрос. При возобновлении агенту передаётся факт прерывания с привязкой к исходной работе и указанием пересмотреть её по новой инструкции. Нельзя объявлять прерванную scheduled task выполненной или автоматически повторять её эффекты.
- Новое событие, снимающее паузу, включается в тот же пакет вместе с накопленными событиями; агент должен учесть весь пакет до новых действий. Если оно пришло ещё во время отмены, обработка начинается только после подтверждённой остановки прежнего запуска.
- Исправление принимается даже при заполненной обычной очереди за счёт согласованного вытеснения самого старого ожидающего chat-элемента. Дополнительное управляющее место и неограниченная очередь для этого не нужны.
- Пауза отмены сохраняется после перезапуска сервиса. Сама обычная очередь пока остаётся RAM-only; cancel не добавляет гарантию её сохранности после сбоя.

## Согласовано: что снимает паузу

Паузу снимает следующее новое допустимое событие любого источника. Отдельная защита от возобновления из-за WebSocket не требуется: пользователь допускает повторный `/agent cancel`.

Уже ожидающие события сами паузу не снимают. Команды просмотра статуса и правил сами не снимают паузу; `/agent start` позволяет снять её явно. Ограничение возобновления только пользовательским вводом не вводится.

## Уточнение FIFO и текущих лимитов

В проверенной реализации одна очередь агента уже хранит элементы в порядке постановки (FIFO) и передаёт накопленные элементы одним пакетом после фиксированного окна 200 ms. Это не обработка строго одного события за ход. Лимит десять применяется только к ожидающим элементам с source=chat: обычные сообщения, отдельные события правки, собранные альбомы, обычные callback и `/say`. Альбом занимает один элемент, хотя передаёт несколько событий; уже переданный пакет лимит не занимает.

Источники schedule, agent (включая agent_error), websocket, widget, inline, guest и inline_button не учитываются в лимите десять. Это не отменяет их собственные проверки доступа, дедупликацию, сроки действия и объединение повторов. Текущая полная очередь отклоняет новый chat-элемент; согласованное изменение ниже заменяет отказ вытеснением. Переход к одному событию за модельный ход не согласован.

## Согласовано: вытеснение при переполнении

- Лимит остаётся равным десяти ожидающим chat-элементам на агента и действует постоянно, включая обычную работу и паузу после cancel.
- При поступлении нового допустимого chat-элемента в заполненную очередь удаляется самый старый ожидающий элемент именно с source=chat, затем новый добавляется в конец. Остальные элементы сохраняют взаимный порядок. Уже переданная работа не вытесняется.
- Неограниченные этим лимитом источники не вытесняются ради chat-элементов и сами не вызывают вытеснение chat-элементов.
- Собранный альбом остаётся одним элементом: при вытеснении удаляется весь ожидающий альбом, а не отдельная его фотография.
- При вытеснении обычного Telegram-сообщения или отдельного события его правки контроллер отмечает historyGap для следующего подходящего передаваемого события этого чата/темы. Сохранённое сообщение не удаляется из истории. Для вытесненного альбома применяется то же правило.
- Это правило охватывает и личные чаты: текущая реализация historyGap, ограниченная group/supergroup, должна быть расширена для пропусков из-за вытеснения.
- При вытеснении `/say` контроллер сразу пытается заменить текст подтверждённого preparedReply сообщением об ошибке, например: `Request was removed from the queue because newer messages arrived. Please send it again.` Ответ остаётся приватным тому же получателю; публичного fallback нет.
- Вытесненный `/say` не создаёт historyGap обычной переписки: его текст отсутствует в обычной истории и не должен попадать туда через уведомление. Повторная доставка исходного Telegram update не возвращает вытесненный запрос в очередь.
- Если подготовленного ответа нет или его изменение не подтверждено, сохраняется технический исход без объявления успешного уведомления, автоматической повторной отправки или публичного fallback.
- Вытеснение выполняется только при успешном принятии нового события. Ошибка проверки доступа, подготовки или атомарной фиксации нового события не должна удалять старое.
- Окно сбора 200 ms не продлевается из-за вытеснения старого элемента. Вытеснение отличается от обычного clear, отмены и утраты доступа; приватная ошибка `/say` относится именно к переполнению.

## Согласовано: разблокировка кнопок при вытеснении callback

- Для вытесненного ожидающего обычного callback контроллер отменяет собственное предварительное закрытие соответствующей группы выбора. Отдельное приватное уведомление нажавшему вместо этого не требуется.
- До предварительного закрытия сохраняются исходное представление кнопок группы и привязка закрытия к конкретному принятому событию. При вытеснении восстанавливаются исходные callback_data, доступность, подписи и отметки выбора этой группы; она удаляется из closed только после подтверждённого восстановления.
- Откатывается только закрытие, принадлежащее вытесненному событию. Если сообщение удалено, группа заменена или её состояние уже изменено другим действием, старый снимок не применяется. Текст сообщения, другие группы, более новые изменения и актуальные permits не откатываются.
- Проверка актуальности и изменение сообщения выполняются последовательно с другими операциями над тем же сообщением. Для rich и reply_markup требуется применять восстановление к текущему представлению, а не отправлять целиком старый снимок сообщения.
- Если изменение Telegram не удалось или его результат неизвестен, группа не объявляется подтверждённо открытой; технический исход сохраняется без слепого повторения и без создания нового сообщения.
- Обычные callback без группы не закрывают кнопки автоматически, поэтому восстанавливать их при вытеснении не требуется. Inline-кнопки и callbacks виджетов имеют отдельные маршруты и в этот откат не входят.
- Восстановление применяется только к ожидающему событию, которое ещё не передавалось агенту. Уже обработанный выбор и его последствия этим механизмом не отменяются. После успешного восстановления пользователь может нажать кнопку заново; создаётся новое событие с обычными проверками доступа.

## Согласовано: доступ и жизненный цикл cancel

Технические подробности реализации не должны менять следующие правила.

1. Доступ — как у существующих stop/clear: текущий агент в ЛС доступен user+, в группе manager+; явный AGENT_ID требует admin/owner этого бота. Новые формы `*` и `in CHAT_ID` не добавляются автоматически.
2. Повторный cancel идемпотентен и оставляет очередь на паузе. У включённого существующего агента без активной работы cancel также ставит очередь на паузу. Выключенного агента команда не включает; отсутствующий agent/thread ради отмены не создаётся.
3. Паузу снимает следующее поступившее допустимое событие любого источника после запроса отмены, с обработкой только после подтверждённой остановки прежней работы. Уже ожидающие события сами паузу не снимают. `/agent start` дополнительно позволяет явно снять паузу и обработать накопленное без нового сообщения. Команды просмотра паузу не снимают; отдельные pause/resume не вводятся.
4. Cancel отменяет ожидающее сжатие и сохранённый continuation отменённой работы. Уже начатое сжатие завершается под удержанием очереди; автоматическое продолжение после него не запускается. При неизвестном исходе очередь не освобождается до сверки. Stop/clear/замена правил/удаление имеют приоритет и не позволяют старому продолжению оживить агента. Cancel не останавливает все постоянные ресурсы вроде виджетов и соединений.
5. Пауза и факт отмены сохраняются после перезапуска сервиса. Перезапуск сам не снимает паузу и не повторяет отменённую работу. Это не добавляет сохранность обычной RAM-очереди.

Существующая `/rules set` заменяет правила со сбросом контекста. Cancel не меняет этот контракт: обычная поправка в чате и замена AGENTS.md имеют разные последствия.

При подготовке реализации решаются инженерные вопросы: подтверждение прерывания основного хода/субагентов/команд, сериализация переходов состояния, формат факта отмены для модели, сохранение исходов уже начатых операций и привязка незавершённых scheduled/delegated запросов. План должен включать проверки соответствующих гонок.

## Техническая основа и проверки

В проверенной базе origin/main 9fd0fd9 Codex adapter уже использует turn/interrupt внутри удаления сессии; нужен отдельный путь с сохранением thread. AgentQueue поддерживает удержания, а Lifecycle — отклонение устаревших вызовов. Обычный путь ошибки очищает очередь и поэтому не подходит для ожидаемой отмены.

Проверки будущего контракта: подтверждённое прерывание основного хода/связанных работ, сохранение thread и ожидающих событий, запрет поздних эффектов, приём поправки при полной очереди, гонка поправки с подтверждением отмены, сохранение фактов уже выполненных действий, scheduled/delegated lifecycle и отмена старого compaction continuation. Специальная фильтрация фоновых источников для возобновления не требуется.

Для переполнения проверяются смешанная очередь chat/служебных источников, сохранение порядка и лимита, вытеснение целого альбома, historyGap в ЛС/группе/нужной теме, отсутствие historyGap и публичной утечки для `/say`, редактирование ровно его preparedReply, отсутствие воскрешения вытесненного события, отказ нового enqueueCommitted без потери старого и непродление срока batching. Для кнопок проверяются восстановление исходной группы и возможность нового выбора, сохранность других групп/текста/permits, отсутствие отката заменённой группы и обработка отказа/неизвестного результата Telegram.
