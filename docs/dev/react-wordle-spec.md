# Wordle, Nerdle и редактор базы на React

Статус: React runtime и миграция Wordle, Nerdle и редактора разрабатываются в отдельном worktree `feat/react-widgets`; групповой и inline Wordle и групповой редактор проверены на тестовом боте, Nerdle в клиенте ещё не проверен. Основа миграции — последний предоставленный wordle.zip, а не старый tar.gz. Связанные документы: [концепция движка](react-widgets-design.md), [план](plans/2026-10-26-react-widgets-wordle.md), [историческая проверка прежнего Wordle](wordle-migration-verification.md).

## Объём

Перевести три действующих entrypoints предоставленного комплекта на настоящий React: widget.tsx (Wordle), nerdle.tsx (Nerdle), dictionary-admin.tsx (редактор). Источник — wordle.zip, 486183 байта, SHA-256 `53d0690df1b0ba9522073134903a60b9a42c2eede7f973afbdff579f41ccf88b`. При исполнении повторно проверить hash/состав и работать с его новой рабочей копией; исходный ZIP не менять. Результат — обновлённый комплект с теми же действующими entrypoint-путями для установки и отдельный distributable ZIP с manifest. Старый tar.gz и его offline fixtures — только исторические доказательства.

Сохранить свежие правила, selected pools всех пяти длин, актуальные удаления/отключённый Use, артефакты базы Nerdle, titleSuffix и настройку уведомлений. Исторические widget-v1/v2/native/fallback и emoji diagnostics не переводить в альтернативные рабочие движки; при упаковке сохранить их только как архивные исходники, обновив active-entrypoint instructions. Новые store/Runtime не используют legacy ctx/render/actions. Прежние работающие экземпляры и их состояния автоматически не переносятся.

Быстрые команды !widget/* и зарегистрированные !exec/*-скрипты отложены. Публикация идёт существующими инструментами агента с обновлённым React-контрактом. Обычные inline/guest-адреса и ручная публикация виджета входят в объём; новый механизм inline-скриптов не требуется.

## Подтверждённые уточнения

1. **Завершение всего раунда — внешними силами.** Например, агент ежедневно завершает прежний раунд и создаёт следующий. Победа/поражение отдельного игрока не заканчивает общий раунд. Расписание/ротация не встраиваются в виджет; внешний агент использует согласованный инструмент изменения store. Автоматического завершения по списку участников не добавлять.
2. **«Прогресс» — все принятые слова игрока.** От 0 до 6 строк в одной ячейке таблицы, в порядке попыток. Shared до завершения показывает только цветные клетки каждой строки; individual и завершённый shared — буквы с underline/mark, разделённые одним пробелом. Зелёная буква внутри mark также выделяется жирным. При 0 попыток ячейка пустая, не заполняется выдуманной чёрной строкой. Текущий незавершённый input сюда не попадает.

Все дальнейшие задачи используют эти ответы; согласование этих двух пунктов больше не является блокировкой плана.

## Конфигурация и состояния

`create_widget.props` задаёт сериализуемые props Runtime: `title` (по умолчанию название entrypoint), `titleSuffix`, `length` (Wordle 5, Nerdle строго 8), `wordMode` (`individual` или `shared`; прежний индивидуальный режим — по умолчанию), `notify` и прикладную конфигурацию доступа. Лимит попыток — 6, тайм-аут общего inline-ввода — 60_000 мс. Политика фиксируется в store при начале раунда; смена Runtime props не должна незаметно менять слово или длину уже начатой игры. Общая модель и компоненты применяются к обоим игровым entrypoints, при этом Nerdle использует собственный валидатор и клавиатуру.

Один widgetId содержит один раунд; внешний агент может создать следующий экземпляр и перемонтировать выбранные публикации новым компонентом, сохранив прежнюю итоговую таблицу там, где требуется. Встроенной суточной ротации нет. Выбор ответа происходит вне React render и вне draft-recipe. Для shared ответ выбирается и сохраняется один раз; для individual — при первом входе конкретного игрока, повторный вход его не меняет. В Wordle случайный ответ берётся только из соответствующего N-select файла, допустимая догадка проверяется по объединению broad/select. Пустой selected pool — понятная ошибка, без fallback на broad. Изменения редактора влияют на будущий выбор/проверку, но не меняют уже загаданный ответ. Случайность и время поступают в чистую модель как параметры. Детерминированные ответы для тестов задаёт fixture.

Минимальное сохраняемое состояние:

```ts
type WordMode = 'individual' | 'shared';
type PlayerStatus = 'playing' | 'won' | 'lost';
type WordleState = {
  round: {
    status: 'open' | 'finished';
    title: string;
    length: number;
    wordMode: WordMode;
    sharedAnswer: string | null;
    finishedAt: number | null;
  };
  players: Record<string, {
    userId: number;
    name: string;
    username: string | null;
    joinedAt: number;
    answer: string | null;
    guesses: string[];
    input: string;
    status: PlayerStatus;
    startedAt: number | null;
    finishedAt: number | null;
  }>;
  sharedSessions: Record<string, {
    activeUserId: number | null;
    expiresAt: number | null;
  }>;
};
```

В shared ответ находится только в `round.sharedAnswer`; `player.answer` равен null. В individual ответ — у игрока. Статусы движка и статусы игры различаются. Словарь/кеш неизменяемых слов может быть общим модулю; живые игроки, таймеры и store не могут храниться в изменяемой модульной переменной.

`startedAt` устанавливается при первом принятом Enter с допустимым словом, не при открытии игры, вводе первой буквы или отклонённом слове. `finishedAt` игрока — при победе или исчерпании шести попыток. Длительность = finishedAt − startedAt; отображается только у завершившего свою игру. Паузы входят в длительность. Глобальное завершение не превращает всех незавершивших игроков в проигравших и не выдумывает им длительность.

## Компоненты и публикации

Все четыре компонента — именованные экспорты одного авторского модуля `widget.tsx`; default Runtime передаёт конфигурацию через Context и управляет завершением/очисткой. Store задаётся одним bare-вызовом defineStore с version: 1. Повторное монтирование не создаёт второй store и не выбирает новое слово.

### Обычная группа: два сообщения

1. `Players`: заголовок/название и таблица. Это обычная публичная вьюха.
2. `GameInput`: отдельная публичная вьюха, отправленная reply на подтверждённый messageId `Players` в том же чате/топике. Сначала публиковать Players, дождаться подтверждения и затем отправлять GameInput; не угадывать ID первого сообщения.

Публичный `GameInput` содержит rich-кнопку «Начать / продолжить игру». Нажатие открывает личный overlay с именем игрока, шестью строками поля, таблицей цветных rich-клавиш и кнопками Backspace/Delete/Enter. Rich-кнопка «Закрыть» удаляет только этот overlay; прогресс игрока остаётся. Overlay использует фактический event.from.id; ход другого участника не блокирует игрока. Повторное открытие после Telegram Revert создаёт новое приватное сообщение вместо редактирования скрытого старого overlay.

Таблица Players и launcher GameInput — разные сообщения: обновление таблицы не должно закрывать overlay клавиатуры. Публичная проекция launcher не зависит от изменяющегося поля игрока; обычные ходы не редактируют launcher. Личное поле обновляется в overlay и хранится в общем store по userId.

Столбцы Players: «Игрок», «Прогресс», «Длительность». Нет столбцов «Слово», «Попытки», количества жёлтых/зелёных клеток. Попытки сохраняются для правил и сортировки. Игрок появляется в таблице при входе; до принятого слова прогресс и длительность пустые.

Подтверждённый формат прогресса:

- Shared и открытый раунд: каждое принятое слово отдельной строкой из `⬛️`, `🟨`, `🟩`, без букв, подсказок/всплывающих текстов с ответом и скрытых полей с ответом в callback_data.
- Individual: все принятые слова отдельными строками; верные позиции — `<mark>`, буква не на месте — `<u>`, отсутствующая — обычная буква. Нет отдельного счётчика цветов.
- После завершения раунда: буквы и форматирование видны и для shared.

Нормализация Ё→Е и алгоритм оценки повторяющихся букв сохраняются. Жёлтый соответствует underline, зелёный — mark, чёрный — отсутствующей букве. Публичные props/проекции/кнопки не содержат скрытого shared-ответа. Общий store остаётся доступным авторизованному агенту-владельцу для управления; это не обещание скрыть ответ от владельца.

Сортировка по кортежу: ранг (won=0, lost=1, playing=2), число принятых попыток по возрастанию, длительность по возрастанию для завершивших; затем joinedAt и userId для детерминированного равенства. Незавершённая длительность не считается нулевой победной длительностью. Зелёные/жёлтые клетки в сортировке не участвуют.

### Общий публичный ввод без оверлеев

`GameInputShared` разрешён только при `wordMode: 'individual'`. Он показывает одного активного игрока, его имя/поле/клавиатуру и кнопку «Назад/закрыть». Участники ходят по очереди; активный пользователь проверяется на каждом действии. Чужое нажатие не меняет поле и не продлевает занятую сессию.

Сессия ввода задаётся на конкретную view.id, не одной глобальной activeId на все публикации. В `GameShared` дочерний GameInputShared использует ID внешней вьюхи. По последнему действию активного пользователя сохраняется deadline = now + 60_000. Back/close возвращает меню. После истечения deadline поле и клавиатура остаются на экране как игра на паузе: серые клавиши имеют callback, но нажатия ничего не меняют; кнопка «В меню» доступна всем и возвращает общую кнопку начала. Попытки/поле сохраняются, поражение не объявляется. Точное истечение проверяется до обработки нового хода, включая после рестарта. Таймер effect очищается при unmount; устаревший timer проверяет прежние userId/deadline и не ставит на паузу новую сессию.

`GameShared` возвращает Players, затем GameInputShared в одном сообщении. Это inline/guest-вариант публикации. Оба shared-компонента при общем загаданном слове дают понятную ошибку рендера до публикации — такой режим не должен публично раскрывать личный ввод. Они также могут использоваться по известному обычному адресу; наличие inlineMessageId не даёт chatId или права обычной отправки.

Inline-кнопки участников маршрутизируются по платформенной идентичности вьюхи; произвольный inlineMessageId из callback не переписывает сохранённый канонический адрес. Участнику не нужен собственный агент, чтобы играть в уже опубликованный виджет: применяются правила виджета и доступность его владельца.

Одновременные overlay и shared-представления одного игрока читают один input/guesses из store; отдельный протокол разрешения конфликтов двух экранов в этой итерации не вводится. Синхронные действия применяются к актуальному store, долгий await не должен записывать захваченный старый input. Другие игроки независимы.

### Завершение раунда

Авторизованный внешний агент/сценарий явно переводит round.status в finished с finishedAt через update_widget_store. Это операция полной замены store без expectedRevision; внешняя ротация должна учитывать это согласованное свойство. Во время живой приёмки завершать без параллельного ввода. Дополнительная публичная кнопка завершения не добавляется.

При завершении Players показывает название, загаданное слово и таблицу с буквенным прогрессом. В individual нет одного общего ответа: предлагается компактный список «игрок — ответ» над таблицей, без возвращения столбца «Слово». Это оформление — допущение плана, которое пользователь может скорректировать.

Все активные игровые кнопки во всех публичных представлениях становятся disabled, callback-обработчики повторно проверяют finished и отвергают опоздавший ход. Закрываются все игровые overlays; общий ввод освобождается, timers очищаются. Завершение не удаляет widget/store или обычные сообщения: итоговая таблица сохраняется после рестарта. Гонка завершения с открытием overlay не должна оставлять новое активное наложение после finished.

## Проверки приёмки

- Два пользователя одновременно играют в одной обычной группе через разные overlays, при одном общем слове; обновление таблицы не закрывает клавиатуры.
- До завершения общего раунда в Players нет букв/ответа, включая результаты победителя/проигравшего; после завершения появляется ответ и буквенный прогресс.
- Individual обычный режим: отдельные слова, форматированные буквы, правильное время начала/окончания и сортировка.
- Inline/guest GameShared: два участника по очереди, рабочие кнопки второго участника, освобождение по Back и 60 секундам; shared-word режим отклоняется.
- Перезапуск с действующей общей сессией и затем с истёкшей; store/слова/попытки сохраняются, overlays закрываются, прежние события не переигрываются.
- После finish все публикации не принимают ходы и остаются результатами после рестарта.
- Nerdle: математически точная проверка, нормализация знаков, автодополнение после =, оба представления игры и итоговые результаты после рестарта.
- Редактор: поиск/страницы/Add/Remove/Use, изменения broad/select и audit, влияние на новые игры при неизменности текущих ответов, отсутствие потери выключенных Use при упаковке.

Тесты модели используют фиксированные словарь/часы/выбор ответов и не требуют внешнего архива. Перенос настоящих assets свежего ZIP отдельно проверяется offline и в ограниченной live-приёмке. Ни один пункт этого списка пока не отмечен выполненным.

## Nerdle: сохраняемые правила

Использовать свежий nerdle-math.mjs: точные рациональные значения на BigInt внутри вычислений, приоритет операций и запрет eval/Function/float-сравнений. В сохраняемый JSON входят строки уравнений/результаты ходов, не BigInt. Нормализовать ×/÷/− в */-, соблюдать ровно один =, запрет ведущих нулей, требования к правой части/длине 8/операции слева, корректно отклонять деление на ноль и неверные равенства.

Сохранить appendEquationKey: при вводе = дописывать точный целочисленный результат, только если уравнение укладывается в длину и проходит проверку; иначе сохранять введённый = без выдуманного результата. classic_equations.txt и source metadata — часть комплекта. Публичный интерфейс/overlay/shared fallback и завершение используют общие React-компоненты и правила раунда, а не копию legacy shared.mjs.

## Редактор базы: React без потери свежих изменений

Отдельный entrypoint dictionary-admin.tsx с одним defineStore и экспортированным Editor. Перенести текущие режимы 4/5/6/7/8/✏, input/pages/notice и auditChatId в instance store; не делить живой input между экземплярами из-за module reuse. Информация о текущей странице может быть общей у view одного редактора, как сейчас; отдельный пользовательский overlay для редактора не требуется. Актуальные файлы архива, а не старые количества слов/списки поручений из истории AGENTS.md, являются исходным состоянием базы.

- Обычный текст слов в списке, не Wordle custom font. Поле и клавиатура сохраняют оформление свежего приложения. 20 слов на страницу, ±1/±20 страниц, безопасное ограничение индексов после редактирования.
- Поиск с 0–8 символами ввода; каждая * / ⭐ — ровно одна неизвестная русская буква. Шаблон сопоставляется целиком, ищет соответствующую длину 4–8; пустой ввод не показывает всю базу. Старое описание «ноль и более букв» из истории не переносить.
- Add добавляет слово в broad и select с включённым Use. Remove удаляет из обеих баз. Disable Use оставляет/переносит слово в broad, enable добавляет в select. Use устанавливает записанное желаемое состояние, а не инвертирует при повторном нажатии. Изменение повторно сверяет выбранное слово с актуальной страницей/input; устаревшее нажатие не меняет другой результат.
- Права из свежего DICTIONARY-ADMIN.md: существующие кнопки доступны всем пользователям с валидным Telegram userId, в том числе Add/Remove/Use. Публикация нового экземпляра или вьюхи — по явной просьбе application admin/owner после свежей проверки роли. Не заменять это требованием manager/Telegram-admin и не возвращать role check каждому клику.
- Mutable dictionary files находятся в workspace и не вшиваются в immutable bundle. Межпроцессный lock, временные файлы/rename, rollback при неудаче и аудит requested/committed/rolled_back сохраняются. Идентичность файлов читать с BigInt stat и наносекундными timestamps; кеш инвалидируется по реально изменившимся broad/select. Несколько editor instances не теряют изменения друг друга.
- Audit пишет действующего пользователя, действие, слово, время и затронутые ключи в настроенный журнал чата. Источник auditChatId — явно переданный конфиг либо известный обычный target; inlineMessageId не декодируется и не выдумывает чат журнала. Нет настроенного/известного audit chat — понятная ошибка до файловой мутации.
- Прерывание native render после успешного изменения файла не должно молча инвертировать Use при повторе. Ошибка persistence/render не даёт ложного сообщения об успешной правке. Запросы файлового изменения выполняются из handlers, не React render/recipe.

Инструкции комплекта переписать компактно под новый SDK, сохранив конечные политики свежих AGENTS.md/DICTIONARY-ADMIN.md без копирования устаревших transcript-правил или локальных ID в публичный пример. Прикладной список заблокированных участников Wordle сохранить как конфигурацию установки, не распространить автоматически на Nerdle/редактор. Локальные USER_ID и chatId в публичных fixtures заменяются тестовыми значениями.
