# Guest-message routing investigation

Status: historical capability investigation completed; both runners are stopped and scoped cleanup is complete. On 2026-10-19 the user removed URL markers and implicit guest reply-owner routing from version 1, then confirmed that an explicit mention inside a reply invokes the sender's own personal agent. The authoritative current scope is [explicit invocation and widget publication](guest-message-concept.md); earlier reply-owner routing is [deferred](guest-message-reply-routing-future.md). The marker/reply results below are historical evidence, not current requirements. Member-personal fallback was also rejected. The feature worktree now implements the guest handler and its automated checks; full guest-widget live acceptance remains pending.

## Current release boundary

Version 1 answers explicit guest invocations only. A reply without an explicit mention is ignored; a reply with an explicit mention is a new request to the sender's own personal agent, never to an inferred earlier owner. If context is insufficient, the selected agent may answer with a clarification. No routing URL markers are inserted. Member bots retain ordinary group-agent behavior and never fall back to a personal agent. Widget publication remains required. The accepted `set_widget_view` extension uses `send: {guestRequestId}`, prepares the first render, publishes it directly through `answerGuestQuery`, then records ownership and binds the returned inline ID. An optional prepared activation card remains a separate agent-chosen flow. Current evidence establishes the returned inline ID, callback match, inline edit and existing source-level APIs; it does not establish this new API extension, its first-render conversion or an end-to-end guest publication of Wordle. No new live probe was started for this scope revision.

For ordinary answers the current design now extends `send({guestRequestId,...content})` rather than adding `answer_guest`. Existing send body fields are reused for types/options representable by a native guest result, with ordinary sending unchanged. The guest-send adapter, destination validation and source/button integration are implemented and covered by automated tests in the feature worktree; live adapter acceptance is separate from the earlier raw-result probes. The active concept lists unsupported ordinary-send types and the required conversion checks.

The user accepted independent sent invocations: every call has its own guest request handle and destination, shares the existing personal-agent queue without replacing older calls, and completes/expires independently. The user also accepted unanswered invocations as normal: no forced response, placeholder, private failure warning, reminder or automatic rerun merely for ending a turn without an answer. Explicit publication-tool failures still need an honest structured result. Neither policy has been implemented or subjected to the corresponding new live checks.

Timing research on 2026-10-19 found no numeric answer deadline in the official `answerGuestQuery` documentation, Guest Mode overview, or relevant inspected Bot API/TDLib forwarding-method paths and schema comments. This does not prove an unlimited remote-server lifetime. Existing probes tested successful answers and recovery, not the maximum supported answer delay. The user subsequently accepted common 30-day local retention; concrete server timing and request recovery remain technical work. No numerical server waiting guarantee or live maximum-delay result is claimed.

## Earlier requested behavior (historical probe scope)

- A new guest mention invokes the sender's personal agent.
- A reply to a guest answer continues with the agent responsible for that answer, including when another user replies.
- Further replies must retain the original conversation owner; the latest caller is not automatically its owner.
- A new mention from a user with no personal agent receives no answer. The user explicitly accepted silence for this case.
- The actual sender remains identifiable independently of the selected agent. A public participant's message does not inherit the agent owner's private authority.
- Latest simplification: an added bot uses only ordinary chat-agent dispatch; if the chat agent is absent or disabled/stopping, agent requests are silent. No personal fallback for ordinary member messages. Guest personal routing is reserved for a nonmember bot. This supersedes the member-personal scenario tested below, without changing the recorded historical observations.

## Address control and recovery

The first poller stopped before its deadline when a `getUpdates` read failed with `telegram_transport_failed`. This was a transport failure after the previously successful checks, not evidence that guest replies stopped working. Its original response/participant registry remained on disk. The user reported two unanswered address-control replies during that interruption.

The disposable runner was corrected to retry transient polling reads using the same offset, with bounded backoff and the original lifetime bound. Message sends and uncertain guest answers are not automatically retried. A resume option restores response identities, participant aliases and observed addresses, retains the same run marker and preserves queued Telegram updates instead of resetting the backlog. A fault-injection check reproduced the original early exit (one answer instead of seven) and passed after the read-retry correction. A separate network-free resume check confirmed both pending updates were consumed with restored participants and the old plain fixture, with no queue reset.

The resumed live runner recovered both already-sent address-control replies without requiring the users to repeat them. Both replied to the sixth response, identified by the unique diagnostic fixture. The quoted chat identifier matched, but the quoted `message_id` differed between A and B. B's ID matched the earlier B reply to that same response. This is direct evidence that a single shared `(guestChatId,messageId)` lookup cannot safely identify that publication across these two callers in the tested basic group. It does not establish the behavior of every supergroup or client. No opaque inline ID was inferred or decoded.

Evidence precision: the original observations recorded the presence of `date` in the incoming and quoted Messages, but not its actual values. Equality of the quoted publication date across these two callers has therefore not been measured. The Message contract describes that field as the original message's Unix send time; verifying its equality and relating it to request/confirmation times needs a further date-aware control. The recorded address, sender/caller labels, exact fixture match and field-presence comparisons above do not depend on assuming equal dates.

Telegram accepted answers to both recovered guest queries. That establishes successful API answers after recovery; the user's earlier no-answer report described the stopped interval, and no additional client-display confirmation for the recovered answers was requested.

The final cumulative result is 11 marked guest inputs, 10 confirmed guest answers, seven followups and one deliberate no-agent silence, plus one callback and one confirmed inline edit. There were no recorded per-message processing failures. The earlier polling transport failure is recorded separately above and must not be hidden by that zero message-error count. The resumed poller was stopped gracefully after the requested checks and released the shared poller lock. No production controller/model was started and no agent database was changed.

## Conclusion

Guest updates and guest answers support the requested two-person conversation mechanics in this tested group. Opaque tokens in our own response keyboard were delivered in reply context and provide a concrete candidate for retaining the selected agent across caller changes. The underlying message must still be verified as our guest response, and token ownership/scope must be checked before granting any production authority.

Plain guest replies are delivered too, but the experiment used a unique diagnostic text marker to preserve ownership. Neither the latest caller metadata nor one global ordinary message address solved ownership for the tested multi-turn, cross-user plain chain. A production correlation policy must be designed explicitly before arbitrary button-free responses are supported. Bot/profile capability coexistence does not resolve the client's composer ambiguity between a leading inline query and a sent mention.

## Identity questions

The [guest answer](https://core.telegram.org/bots/api#answerguestquery) returns [SentGuestMessage](https://core.telegram.org/bots/api#sentguestmessage), containing an inline message ID. An incoming [Message](https://core.telegram.org/bots/api#message) may carry `reply_to_message`, `guest_bot_caller_user`, `guest_bot_caller_chat` and `reply_markup`; nested reply context is not a complete conversation history. The probe compares these paths directly.

Matching unique fixture text is a diagnostic fallback only. It must not be promoted into production ownership proof. An opaque keyboard token is a candidate correlation mechanism whose actual presence in incoming guest replies still needs to be observed. Caller metadata alone may identify the latest caller rather than the original agent owner after multiple turns. Never decode an opaque inline ID or assume that a guest chat ID shares the ordinary bot-chat namespace.
