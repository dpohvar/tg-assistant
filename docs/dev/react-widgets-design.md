# React-виджеты: рабочая концепция

Статус: основная концепция React-виджетов разработана и согласована пользователем. Подготовлен [план реализации](plans/2026-10-26-react-widgets-wordle.md) с [миграцией Wordle, Nerdle и редактора из свежего wordle.zip](react-wordle-spec.md). Выполнение не начато. Документ фиксирует принятые решения и технические уточнения; это не описание реализованного движка. Исторические альтернативы явно отмечены ниже. Быстрые inline/guest-команды и зарегистрированные скрипты отложены пользователем: они не являются зависимостью React-движка или плана миграции. Обычные inline/guest-вьюхи входят в объём и используют существующий транспорт.

Текущая реализация описана в [Widgets](../widgets.md): собственный JSX, `render(state, view)`, обработчики и сохраняемое JSON-состояние, без React. [Базовая идея оверлеев](widget-overlays-design.md) сохраняется отдельно. В React-варианте рассматриваем пересмотр движка целиком, а не обязательное сохранение его внутреннего устройства.

## Цель и выбранное направление

- Виджет соответствует работающему приложению, вьюха — точке монтирования компонента в Telegram-сообщение.
- Вьюха характеризуется компонентом и props. Оверлей является личной вьюхой поверх публичной.
- Рассматриваем настоящий React с обычными `useState`, `useEffect`, `useRef` и пользовательскими компонентами.
- Локальное состояние React после рестарта процесса теряется. Постоянные данные приложения живут в общем сохраняемом store вместо отдельных `usePersistentState`.
- Принята полная замена движка: старые экземпляры отключаются и удаляются, совместимость с legacy и автоматический перенос старых игр не требуются.
- Сохраняем один процесс среды виджетов на агента; процесс на вьюху не создаётся.
- Основное направление API состояния обсуждено и пользователь перешёл к следующему вопросу: собственный сохраняемый store, SDK-хуки `useSelector(selector)` и `useDispatch()` с функцией изменения draft, регистрация вызовом `defineStore` без экспорта. Ранее рассмотренный Redux-вариант оставлен для сравнения и как основание старого эксперимента изоляции, а не как обязательная зависимость нового API. Детали очереди, ошибок и selector equality ещё уточняются отдельно. Отдельный пользовательский API Reselect не требуется.

Предложенная архитектура React: один корневой React root на экземпляр виджета, все его вьюхи и оверлеи внутри общего дерева с Provider. По уточнению пользователя корневой `Runtime` должен оборачивать вьюхи собственными Context Provider, чтобы предоставлять им общие ресурсы, включая WebSocket. Он не должен быть служебным соседом вьюх: соседний Provider не передаст им контекст. Конкретное устройство renderer и точек монтирования ещё предстоит спроектировать.

## Общие библиотеки и изоляция приложений

React и renderer загружаются один раз в процессе агента. У каждого виджета независимы store, дерево компонентов, локальное состояние и жизненный цикл.

Пользователь предложил переиспользовать один скомпилированный и загруженный модуль для нескольких экземпляров одного виджета в этом процессе. Сборку и описание модуля можно кешировать по версии исходников и совместимым параметрам сборки. Живые данные экземпляра остаются в его store, hooks, refs и Context Provider; модульные изменяемые переменные с socket, таймером или живым Redux store нельзя считать изолированными по экземплярам. Общими могут быть определения компонентов, контекстов, reducers/action creators и статические данные. Это направление переработки загрузчика, не реализованный механизм разделения модулей.

Платформа поставляет закреплённые совместимые версии React и renderer как доступные только для чтения зависимости sandbox. Сборщик оставляет импорты React внешними и направляет их в эту поставку; реализация React не копируется в каждый bundle виджета. Renderer и компоненты используют один модуль React. Импорты `react`, `react/jsx-runtime` и поддерживаемых дополнительных точек входа разрешаются согласованно. Изменения resolver и проверок сборки необходимы; одной настройки `external` поверх текущего plugin недостаточно.

Динамическая композиция компонентов разрешена. Рекомендация хранить общие данные один раз относится к словарям, ресурсам и состоянию приложения, а не к запрету динамического создания React-элементов. Содержимое изображений не следует удерживать в состоянии, если достаточно `file_id` или другого разрешённого указателя.

## Объявление приложения

Отдельная обёртка `defineWidget(...)` в авторском файле не нужна. Модуль объявляет сохраняемый store через `defineStore(...)` и экспортирует компоненты для точек монтирования.

`defineStore` объявляет описание store, а не глобальный живой store для всех запусков файла. Для общей загрузки модуля описание должно быть переиспользуемым между экземплярами; движок создаёт реальный store для каждого widgetId после загрузки его собственных данных. Один экземпляр использует одно описание store. Привязка живого store к первому экземпляру при выполнении общего модуля не подходит. Начальное состояние не должно давать экземплярам разделяемые изменяемые ссылки.

Пользователь отверг обязательный `export const store` и предпочёл единственный вызов `defineStore(...)` на уровне файла. Экспорт описания не требуется: вызов регистрирует описание в метаданных загружаемой версии модуля. Эта регистрация не создаёт живой store и не привязывается к первому widgetId. После кеширования модуля для нового экземпляра не требуется повторно выполнять исходный файл. Живой store и persistence bridge принадлежат движку и создаются для каждого экземпляра отдельно.

Предлагаемый внутренний механизм: загрузчик/сборщик предоставляет модулю функцию `defineStore`, заранее привязанную к записи именно этой версии сборки. Она добавляет описание в эту запись, а загрузчик кеширует вместе exports компонентов и метаданные. Не используется процессная переменная «текущий виджет» или «последний импортированный модуль»; параллельные загрузки должны иметь раздельные записи. Конкретная реализация такого SDK-binding ещё не проверена прототипом.

Принято по уточнению пользователя: `defineStore` можно вызвать не более одного раза в течение инициализации загружаемой версии модуля. Повторный вызов и вызов после окончания инициализации выбрасывают ошибку. Если вызова не было, после завершения инициализации регистрируется стандартное описание с `version: 0` и `initialState: {}`. Граница относится к версии общего модуля, а не ко всему процессу агента и не к первому widgetId. Компоненты, effects и обработчики выполняются уже после этой границы и не могут доопределять store. Вызов из вспомогательной функции во время инициализации допустим при соблюдении ограничения одного вызова.

Стандартное `{}` является начальным состоянием нового экземпляра, а не командой сбрасывать существующие данные при каждом запуске. Сохранённый store версии 0 восстанавливается напрямую; при сохранённой версии выше объявленной, в том числе выше стандартной 0, действует прежнее правило отказа без понижения и потери данных. Переход с сохранённой версии 0 на явную более новую версию использует обычный механизм миграции; отсутствие записи отличается от сохранённого `{}` по наличию исходного состояния, а не только по номеру версии.

Регистрация является значимым действием для сборщика и не должна удаляться как неиспользуемый pure-вызов. Если общий модуль не загрузился, неполные метаданные нельзя использовать для создания экземпляров или подменять успешной стандартной инициализацией. Возвращаемое значение сохранять в переменную не нужно; в старом Redux-варианте можно оставить `const counter = defineStore(...)` ради action creators, но экспорт всё равно необязателен.

Именованные экспорты компонентов позволяют выбрать, что монтировать во вьюхе. Они не публикуются автоматически. Внутренние компоненты экспортировать необязательно. Для восстановления публичной вьюхи сохраняется имя выбранного экспорта и восстанавливаемые props.

Принято уточнение: для восстанавливаемой обычной вьюхи корневой компонент экспортируется файлом виджета, а props строго сериализуемые. Сохраняется имя экспорта, а не исходник функции или её замыкание. Внутренние компоненты и layout не обязаны экспортироваться. Для эфемерной вьюхи, созданной из кода виджета, эти ограничения сняты: корень и props остаются только в памяти и не восстанавливаются после рестарта. При обращении агента через JSON-инструмент, включая монтирование на эфемерное сообщение, по-прежнему требуются экспортное имя компонента и сериализуемые props. Проверка отсутствующего/неоднозначного экспортного имени уточняется при формализации SDK.

### Сериализация по типу вьюхи и способу создания

| Сценарий | Компонент и props | После рестарта |
| --- | --- | --- |
| Обычная восстанавливаемая вьюха | Экспортируемый корень и сериализуемые props | Восстанавливается по сохранённому описанию |
| Эфемерная вьюха или оверлей из кода виджета | Живой React-узел, в том числе неэкспортируемый компонент и props с callbacks/ссылками | Отключается, React-узел не восстанавливается |
| Монтирование агентом на эфемерное сообщение | Имя экспортированного компонента и JSON props на границе инструмента | Также отключается; сериализуемый вход не вводит автоматическое восстановление |

Для эфемерных вьюх сохраняется достаточно адресных метаданных для отключения и запроса удаления после рестарта, но не требуется запись компонента/props в БД. Ссылки на живые ресурсы не переносятся в общий сохраняемый store; cleanup и освобождение ссылки на ноду остаются частью unmount. Повторный mount() без аргументов доступен, пока регистрация и сохранённая в памяти нода ещё существуют.

Принято: `create_widget` принимает `props` экземпляра, сохраняет их и передаёт в default-компонент Runtime при запуске и восстановлении. Они также строго сериализуемые. Это конфигурация экземпляра, отдельная от props каждой вьюхи и от store. Управляемое `children` по-прежнему предоставляет движок; пользовательские props не заменяют дерево вьюх.

Управляющая операция запуска приложения со стороны агента остаётся: нужны файл, владелец и ID экземпляра. Обсуждение убирает фабрику из авторского кода, а не платформенный жизненный цикл `create_widget`.

## Состояние, вьюхи и фоновый ресурс приложения

Уточнение пользователя: отсутствие вьюх не должно удалять состояние виджета. Wordle можно отключить в одном чате и подключить в другом с теми же данными; постоянно работающий таймер для этого не требуется. Для обратного отсчёта достаточно сохранять абсолютный срок завершения, а каждой активной вьюхе иметь собственный таймер перерисовки. Перезапуск локального таймера не меняет исходный срок.

Общее WebSocket-соединение — другой случай: ресурс принадлежит экземпляру приложения, а не каждой вьюхе. Нужен жизненный цикл создания и освобождения, независимо от сохранённого store. Сам socket, listeners и retry-таймеры не сериализуются в store.

### Runtime как обёртка вьюх и Provider общего ресурса

Пользователь предложил `export default function Runtime()`, который создаёт ресурс и оборачивает точку вывода вьюх в собственный Context Provider. Это заменяет прежнюю идею служебного компонента, обязательно возвращающего `null`. Принято: default export является необязательным корневым компонентом приложения; имя функции `Runtime` нужно для читаемости, а не для поиска именованного экспорта. Если default export отсутствует, движок использует стандартный Runtime, возвращающий `children` без дополнительных пользовательских Context Provider. Обязательные платформенные контексты, включая Redux Provider, сохраняются.

Принято: движок передаёт управляемое дерево вьюх через обычный prop `children`, без специального `<views />`. Вьюхи и оверлеи располагаются под пользовательскими Provider в одном React-дереве, даже если публикуются в разные Telegram-сообщения; отдельный React root на сообщение не обеспечит наследование контекста.

```tsx
function DefaultRuntime({children}) {
  return children;
}
```

Платформенный Provider выбранного собственного store остаётся ответственностью движка и оборачивает весь экземпляр, включая `Runtime`. Сам `Runtime` не является Telegram-вьюхой, не имеет текущего `useView()` и не создаёт сообщение. Он получает сохранённые сериализуемые props из create_widget, например `url`, и использует обычный `useEffect` для запуска и cleanup для остановки ресурса. Отдельные обязательные `onStart`/`onStop` не требуются.

```tsx
const WsCtx = createContext(null);

export default function Runtime({children, url}) {
  const [ws, setWs] = useState(null);

  useEffect(() => {
    setWs(null);
    const socket = new WebSocket(url);
    let active = true;

    const opened = () => {
      if (active) setWs(socket);
    };
    const closed = () => {
      if (active) setWs(current => current === socket ? null : current);
    };

    socket.addEventListener("open", opened);
    socket.addEventListener("close", closed);

    return () => {
      active = false;
      socket.removeEventListener("open", opened);
      socket.removeEventListener("close", closed);
      socket.close();
    };
  }, [url]);

  return <WsCtx value={ws}>{children}</WsCtx>;
}

export function FeedView() {
  const ws = useContext(WsCtx);
  const [last, setLast] = useState("Waiting for data");

  useEffect(() => {
    if (!ws) return;
    let active = true;
    const receive = event => {
      if (active) setLast(String(event.data).slice(0, 2000));
    };
    ws.addEventListener("message", receive);
    return () => {
      active = false;
      ws.removeEventListener("message", receive);
    };
  }, [ws]);

  return (
    <tg-message type="text">
      {last}
      <tg-keyboard>
        <tg-button-row>
          <tg-button
            type="callback_data"
            onClick={() => {
              if (ws?.readyState === WebSocket.OPEN) ws.send("ping");
            }}
          >
            Ping
          </tg-button>
        </tg-button-row>
      </tg-keyboard>
    </tg-message>
  );
}
```

Это пример предлагаемого React API для текстового потока, не выполненный сетевой тест и не готовая реализация reconnect. Сокет публикуется в Context только после `open`; при закрытии значение очищается. Само изменение `socket.readyState` не является React state update, поэтому одного `setWs(new WebSocket(...))` недостаточно для реактивного отображения готовности соединения. Синтаксис `<WsCtx value={...}>` соответствует React 19+, что следует учесть при закреплении версии платформы. Основа: [createContext](https://react.dev/reference/react/createContext), [useEffect](https://react.dev/reference/react/useEffect).

Локальный `last` намеренно показывает независимую подписку компонента; он теряется при размонтировании. Данные, которые должны переживать отсутствие вьюх и рестарт, по-прежнему сохраняются в общем store. Для них основную подписку следует держать в `Runtime` и делать явный dispatch. Подписка вьюхи получает события только во время её присутствия и может пропустить данные до установки listener; для полной истории/снимка нужен протокол источника или общий потребитель приложения. Прямые сетевые sends не входят в транзакцию сохранения Redux и сами по себе не получают гарантий доставки или повторов.

В текущем движке уже есть отдельный [пример WebSocket](examples/widgets/websocket-display.tsx) с `onInit`/`ctx.enqueue`; он не использует React.

Предлагаемый порядок работы:

1. Контроллер выбирает кешированную сборку/модуль, восстанавливает отдельный store и запускает собственное React-дерево экземпляра с единственным корневым `Runtime`.
2. Effect создаёт ресурс; Provider передаёт его всем вьюхам/оверлеям этого экземпляра. Другой экземпляр того же модуля создаёт собственные store, Runtime и ресурс.
3. Компоненты могут подписываться на события и отправлять данные напрямую через полученный socket. Если входящие данные меняют сохраняемый store, запись и публикация вьюх должны соблюдать общую координацию сохранения и событий. Границы очереди для внешних callback ещё предстоит определить.
4. Отключение вьюхи очищает её собственные effects. Оно не равно удалению приложения или данных.
5. При явной остановке приложения, штатной замене его кода или штатном завершении runtime движок размонтирует служебный компонент, вызывая cleanup. При возобновлении запускается новый effect с восстановленным store.

При аварийном завершении процесса cleanup не гарантирован; нельзя использовать его как единственное место сохранения игровых данных. Соединение после рестарта создаётся заново; восполнение пропущенных событий и повторная подписка зависят от протокола сервера. Старое поколение ресурса после остановки не должно менять store нового поколения.

Обычные перерисовки и `view.mount(..., {force: true})` не должны перемонтировать корневой `Runtime`. Поддержание стабильных keys вьюх остаётся обязанностью движка. Должна быть одна логическая точка вывода управляемого дерева вьюх на экземпляр, а не две независимые копии тех же сообщений. [React useEffect](https://react.dev/reference/react/useEffect) может повторять setup/cleanup при смене зависимостей и в диагностическом Strict Mode: требуется корректное освобождение ресурсов, а не обещание единственного вызова setup за жизнь приложения.

Принято: Runtime продолжает работать при нуле вьюх, включая effects, таймеры и общее соединение. Удаление последней вьюхи не приостанавливает и не перемонтирует Runtime; store сохраняется. Его остановка связана с удалением, перезапуском или ошибкой экземпляра, а не числом точек монтирования. Для частых сообщений WebSocket нужно координировать темп записи и Telegram edits; каждый пакет не обязан порождать отдельное редактирование. Retry/backoff самого сетевого ресурса, пределы буфера и восстановление подписки остаются техническими вопросами и не разрешают автоматические повторы Telegram edit.

## Сохраняемый store: вариант с Redux

Предлагаемый интерфейс:

```tsx
const counter = defineStore({
  version: 1,
  initialState: {value: 0},
  reducers: {
    add(state, amount: number) {
      state.value += amount;
    },
  },
});
```

- `reducers` принимают draft состояния и непосредственно payload. Обёртка адаптирует это к Redux Toolkit/Immer и создаёт стандартные action creators в `counter.actions`.
- В компонентах остаются `useSelector` и `useDispatch`; пример: `dispatch(counter.actions.add(1))`.
- Provider устанавливает движок над приложением. Автор не пишет `configureStore`, SQL и подписку для сохранения.
- Общий store принадлежит виджету и не зависит от числа активных вьюх.
- Сохраняется весь store. Локальные хуки React, refs, кеши, функции, подключения и таймеры не сохраняются как часть store.
- Данные store должны удовлетворять платформенному контракту сериализации. Диагностические сообщения Redux Toolkit не заменяют реальную проверку и отказ при недопустимых данных.
- Константы и статические ресурсы могут оставаться в коде/файлах приложения, не дублируясь в store каждой вьюхи.

## Выбранное направление без Redux: селекторы и функции изменения

Пользователь предложил не объявлять reducers/action creators в описании store, а передавать в dispatch обычную функцию изменения, и завершил обсуждение основного API этого пункта. Это выбранное направление проектирования, не реализованный SDK. Общие требования к изоляции экземпляров, сохранению JSON, миграциям, Runtime и восстановлению вьюх сохраняются. Подробные ограничения и поведение ошибок ниже остаются предложениями, если не были отдельно согласованы.

По предложению пользователя используются имена `useSelector` и `useDispatch`: они описывают операции и не требуют реализации через Redux. Хуки импортируются из платформенного SDK, не из `react-redux`; `dispatch` принимает recipe, а не Redux action object. Первоначальные длинные имена заменены; подробности обработки событий и ошибок ещё требуют согласования.

```tsx
defineStore({
  version: 1,
  initialState: {value: 0},
});

const getCounterValue = state => state.value;
const add = amount => state => { state.value += amount; };
const reset = () => state => { state.value = 0; };

export function Counter() {
  const value = useSelector(getCounterValue);
  const dispatch = useDispatch();

  return (
    <tg-message type="text">
      Count: {value}
      <tg-keyboard>
        <tg-button-row>
          <tg-button type="callback_data" onClick={() => dispatch(add(-2))}>
            -2
          </tg-button>
          <tg-button type="callback_data" onClick={() => dispatch(add(2))}>
            +2
          </tg-button>
          <tg-button type="callback_data" onClick={() => dispatch(reset())}>
            Reset
          </tg-button>
        </tg-button-row>
      </tg-keyboard>
    </tg-message>
  );
}
```

Предлагаемый контракт:

- `defineStore(...)` регистрирует только переиспользуемое описание версии и initialState/миграции в записи модуля; присваивание и экспорт не требуются. Общий модуль может объявлять селекторы и фабрики функций изменения, но живой store остаётся отдельным на каждый widgetId. Хуки получают его через платформенный Provider экземпляра; процессной переменной «текущий виджет» не требуется.
- `useSelector(selector)` читает выбранные данные из неизменяемого снимка. По умолчанию сравнение результата селектора — `Object.is`; изменение другого поля само по себе не должно инициировать рендер подписчика этого селектора. Это не запрет других причин рендера, например изменения props или Context. Новый объект из селектора считается новым значением; правила дополнительного equality аргумента/мемоизации пока не выбраны.
- Подписку можно строить на [useSyncExternalStore](https://react.dev/reference/react/useSyncExternalStore), обеспечив стабильный снимок и subscribe. Сам hook не принимает selector; для корректной фильтрации и кеширования есть независимый от Redux [адаптер withSelector](https://github.com/facebook/react/blob/main/packages/use-sync-external-store/src/useSyncExternalStoreWithSelector.js). Конкретный выбор адаптера остаётся внутренним решением движка.
- `useDispatch()` возвращает стабильную функцию, привязанную к экземпляру. `dispatch(recipe)` применяет recipe к актуальному состоянию этого экземпляра, а не к снимку предыдущего React render.
- Recipe получает draft, например через [Immer produce](https://immerjs.github.io/immer/produce/). Он синхронный, без возвращаемого значения и внешних побочных эффектов; async/await, I/O и вложенный dispatch внутри recipe не разрешаются. `dispatch(add(2))` и `dispatch(state => { state.value += 2; })` равнозначны. Сеть выполняется снаружи, затем её результат передаётся отдельным dispatch.
- Исключение recipe отбрасывает его draft и сохраняет прежний снимок. Это не обещание отката других dispatch того же обработчика, уже выполненного Telegram-запроса, WebSocket send или локального React-состояния.
- Успешный dispatch синхронно обновляет снимок в памяти после проверки допустимости результата. Группировка нескольких dispatch, запись в БД, revisions и разрешение Telegram-публикации после сохранения по-прежнему координируются движком; `dispatch` не означает немедленной долговечной записи. Ошибка БД рассматривается отдельно от ошибки recipe.
- В БД записывается только состояние и его версия, не селекторы, замыкания или функции изменения. Необработанные recipes не сериализуются как очередь команд для восстановления после рестарта. Принято: очередь событий и незавершённые обработчики после аварии не переигрываются; сохраняется только подтверждённый снимок store. Диагностика и границы сохранения уточняются отдельно.

Плюс варианта — короткий авторский API без таблицы reducers, action types и Redux-обёртки. Цена — собственная ответственность платформы за подписки/селекторы, применение draft, проверки и координацию persistence. Сами эти обязанности частично уже нужны для Telegram-платформы независимо от выбранной библиотеки. Immer и готовый selector-адаптер позволяют не переписывать их механизмы с нуля.

Предыдущий прототип изоляции проверяет именно вариант с Redux и явным экспортом описания. Он не является проверкой выбранного направления; отдельный прототип без Redux и регистрации без экспорта пока не запускался.

## Инициализация и миграции

Принято: отдельный объект миграций не нужен. Если требуется преобразование сохранённых данных, `initialState` задаётся функцией `(oldState, oldVersion) => currentState`.

```tsx
const counter = defineStore({
  version: 3,

  initialState(oldState, oldVersion) {
    if (oldState === undefined) {
      return {counter: {value: 0}, history: [], step: 1};
    }

    let state = oldState;
    if (oldVersion < 2) {
      state = {counter: {value: state.value}, history: []};
    }
    if (oldVersion < 3) {
      state = {...state, step: 1};
    }
    return state;
  },

  reducers: {
    increment(state) {
      state.counter.value += state.step;
    },
  },
});
```

Правила:

| Ситуация | Действие |
|---|---|
| Новый экземпляр | Вызвать функцию с `undefined, 0` либо использовать объект `initialState` |
| Сохранённая версия ниже объявленной | Вызвать функцию с сохранёнными данными и их версией |
| Версии совпадают | Восстановить сохранённое состояние напрямую |
| Сохранённая версия выше версии кода | Отказать до вызова функции, без автоматического понижения |

`version` — номер формата пользовательских данных, а не версия React, исходного файла или схемы БД контроллера. Для простого случая обсуждено необязательное поле с начальным значением `1`. Изменение интерфейса само по себе не требует повышения версии. Если версия данных повышается, объект `initialState` не заменяет необходимую функцию преобразования.

Функция должна быть чистой и не изменять исходный снимок. Она возвращает целевое состояние сразу из поддерживаемой старой версии; внутренние последовательные шаги — выбор автора. Результат проверяется, данные и новая версия записываются атомарно. При ошибке прежние сохранённые данные остаются неизменными; автоматического сброса в начальное состояние нет.

## Связь store с БД и Telegram

Сейчас контроллер уже хранит JSON в `widgets.state`, проверяет владельца и поколение и принимает сохранение через bridge из sandbox. Для нового движка это основа интеграции, а не готовая реализация Redux persistence. Версию данных и дополнительные служебные метаданные ещё потребуется встроить в схему.

Обсуждённый порядок:

1. Загрузить сохранённое состояние и выполнить необходимую инициализацию/миграцию.
2. Создать Redux store с восстановленными данными.
3. Подключить компоненты к store через Provider.
4. Обрабатывать события последовательно; `dispatch` синхронно меняет состояние в памяти.
5. Проверить и сохранить итоговое состояние события.
6. Разрешить публикацию соответствующей версии содержимого в Telegram после подтверждения сохранения.

Несколько dispatch в одном обработчике могут объединяться в один сохраняемый снимок. Обычный `dispatch` не означает немедленной долговечной записи. Завершение обработки события должно включать сохранение. Независимая асинхронная запись из `store.subscribe` без координации с публикацией не обеспечивает требуемый порядок.

Предложение для дальнейшего уточнения: при ошибке БД не публиковать новое содержимое и остановить экземпляр до восстановления. Атомарность ошибок обработчика, очереди, effects, локального React-состояния и Redux ещё не спроектирована. Старый механизм отката состояния нельзя считать автоматически применимым к React.

## API компонентов

Пользователь предложил разделить контекст по назначению; обсуждение продолжается на этой основе:

| Хук | Назначение |
|---|---|
| `useTelegram()` | Разрешённые операции с Telegram, знакомые агенту: `send`, `read`, `edit` и другие |
| `useWidget()` | Управление текущим виджетом, его точками монтирования и жизненным циклом |
| `useView()` | Текущая вьюха со свойствами и методами |
| `useViews()` | Реактивная коллекция вьюх собственного виджета |

Для адресных операций приложения принято симметричное направление API:

```tsx
widget.getViews();
widget.getView(targetOrId);
await widget.mount(targetOrId, <Main />);
await widget.mount(targetOrId, <Main />, {force: true});
await widget.unmount(targetOrId);
await widget.closeOverlays(targetOrId);
widget.delete();
```

`widget.mount(target | id, node, options?)` заменяет ранее предложенный `widget.createView`. `widget.unmount(target | id)`, `widget.closeOverlays(target | id)` и `widget.getView(target | id)` принимают такой же способ выбора вьюхи. Вспомогательные названия `getViews()` и `delete()` остаются предложениями.

Предлагаемая детализация контракта адресных методов:

| Метод | Действие |
|---|---|
| `widget.mount(targetOrId, node, options?)` | Для существующей собственной вьюхи — установить компонент и props по правилам `view.mount`; допустимый target может также создать новую вьюху. Вернуть `Promise<View>` |
| `widget.unmount(targetOrId)` | Отключить выбранную вьюху по правилам `view.unmount`; неизвестную не создавать |
| `widget.closeOverlays(targetOrId)` | Закрыть дочерние оверлеи выбранной публичной вьюхи, сохранив её; у оверлея детей нет |
| `widget.getView(targetOrId)` | Вернуть актуальную собственную вьюху либо `null`, без создания и сетевых побочных эффектов |

Уточнения, предложенные для безопасной адресации:

- `id` означает ID вьюхи; адрес сообщения передаётся объектом target, без смешения с числовым `messageId`.
- Неизвестный ID в `mount` — ошибка, а не основание восстановить удалённую вьюху. Создание по target допускается только в разрешённых случаях публикации/прикрепления.
- Полный target существующего сообщения однозначно выбирает адрес. Для эфемерного адреса необходимо учитывать получателя. Форма создания нового сообщения и неоднозначные неполные адреса требуют отдельной спецификации; `getView` не должен выбирать произвольную вьюху чата.
- Target чужого виджета не предоставляет права его заменить. Все операции ограничены текущим виджетом и разрешениями владельца.
- Новый оверлей по-прежнему открывается через `event.overlay`; `widget.mount` не должен обходить условия создания эфемерного ответа. Уже зарегистрированный оверлей можно выбрать по ID или полному разрешённому адресу.
- Опция `{force: true}` у `widget.mount` имеет ту же семантику, что у `view.mount` и `event.overlay`: смена React-экземпляра, без создания дубликата существующей вьюхи.
- Чтение отсутствующей вьюхи возвращает `null`; отсутствие при `unmount`/`closeOverlays` предлагается считать пустой операцией. Точные возвращаемые значения изменяющих методов, кроме предложенного результата `mount`, ещё предстоит определить.

`getViews()`/`getView()` нужны для актуального чтения в обработчике. `useViews()` подписывает React-компонент на изменения. Предложено возвращать из `useViews()` массив для обычных `filter`/`map`, а поиск по ID/адресу вынести в `getView`; окончательный тип коллекции ещё не выбран. В исходной идее оверлеев использовался словарь `ctx.views`.

Данные `useView()` соответствуют снимку рендера. Методы выполняются по идентификатору вьюхи и проверяют её актуальность. После `await` свежие данные можно запросить у `widget`. Контекст и методы не должны неявно обращаться к вьюхам другого виджета.

Хуки вызываются в компонентах/пользовательских хуках. Telegram-запросы и команды изменения вьюх выполняются обработчиками или effects, не во время рендера. Обычным вспомогательным функциям нужные объекты передаются аргументами.

## Объект view и названия операций

Для React-варианта выбранное направление названий — `mount`/`unmount`, вместо прежних `update`/`close`. Термин «Назад» не должен скрывать отключение публичной вьюхи.

```tsx
view.id;
view.props;
view.target;
view.message;
view.parent;
view.user;

await view.mount(<Counter />);
await view.mount(<Counter />, {force: true});
await view.unmount();
view.getOverlays();
await view.unmountOverlays();
await view.closeOverlay();
```

- `view.mount(element, {force = false} = {})` устанавливает корневой компонент и props в существующую точку монтирования. Это намеренное изменение самой этой вьюхи; правила сохранения экземпляра приведены ниже.
- Принято: `view.mount()` без аргументов оставляет последнюю установленную корневую ноду и props и инициирует попытку синхронизации сообщения. Это не отправка нового сообщения и не подмена renderer. Если вьюха в `error`, применяется согласованное повторное монтирование поддерева; если исправна, вызов сам по себе не сбрасывает hooks. После удаления регистрации вьюхи восстановление по её прежнему handle невозможно. Если корневая нода никогда не была установлена, вызов без аргументов возвращает понятную ошибку.
- `view.unmount()` отключает текущую вьюху независимо от её типа. Для публичной вьюхи закрываются дочерние оверлеи, компоненты размонтируются, сообщение остаётся с отключёнными кнопками. Для личной эфемерной вьюхи размонтируются компоненты и запрашивается удаление эфемерного сообщения; это относится также к самостоятельной личной вьюхе.
- `view.user` содержит информацию о получателе личной эфемерной вьюхи; для публичной вьюхи равно `null`. Это не автор последнего нажатия и не игрок, выбранный через props.
- `view.parent` у оверлея ссылается на публичного родителя; у публичной вьюхи равно `null`.
- `view.getOverlays()` возвращает актуальных дочерних оверлеев. У самого оверлея детей нет.
- `view.unmountOverlays()` отключает дочерние оверлеи, сохраняя родителя.

Принят безопасный алиас:

```tsx
view.closeOverlay = async () => {
  if (view.user !== null) {
    await view.unmount();
  }
};
```

Он закрывает текущую личную эфемерную вьюху либо ничего не делает для публичной вьюхи. При добавлении самостоятельных эфемерных вьюх без родителя алиас закроет и их, поскольку условие проверяет `user`, а не `parent`. Других пользователей не затрагивает. Поэтому одна кнопка допустима в обоих типах вьюх:

```tsx
<Button onClick={() => view.closeOverlay()}>Назад</Button>
```

## Сохранение экземпляра и принудительное перемонтирование

Согласовано: `mount` не должен безусловно размонтировать прежний компонент. В существующей вьюхе действуют следующие правила:

| Изменение | Результат |
|---|---|
| Тот же корневой тип компонента и `key`, изменились только props | Обновить props и выполнить обычный React update, сохранив экземпляр и его локальное состояние |
| Изменился корневой тип компонента | Размонтировать старое поддерево и смонтировать новое |
| Изменился корневой React `key` | Выполнить обычную для React замену экземпляра |
| Передан `{force: true}` | Принудительно заменить всё корневое поддерево, даже при том же компоненте, `key` и props |
| Вьюха находится в `error` | Повторно смонтировать её поддерево независимо от совпадения компонента, `key` и props; явный `{force: true}` не требуется |
| Вызван `view.mount()` без аргументов | Сохранить последнюю установленную ноду/props и повторно синхронизировать сообщение; для `error` выполнить восстановительное монтирование |

```tsx
// Прежний экземпляр PlayerList получает новые props.
await view.mount(<PlayerList page={2} />);

// Новый экземпляр PlayerList с начальным локальным состоянием.
await view.mount(<PlayerList page={2} />, {force: true});
```

При обычном update сохраняются `useState` и `useRef` остающихся компонентов. Effects с изменившимися зависимостями могут выполнить cleanup и setup без размонтирования — это обычное поведение React. Изменившиеся дочерние типы и `key` также подчиняются обычным правилам React; сохранение корневого экземпляра не запрещает обновление его поддерева.

При принудительной замене выполняется cleanup effects старого поддерева, заново создаются локальное состояние и refs, запускаются effects нового поддерева. Общий сохраняемый Redux store приложения не сбрасывается.

`force` относится к жизненному циклу React-компонентов. Идентичность вьюхи, её адрес Telegram, родитель и получатель сохраняются. Это не команда `view.unmount()` с последующим созданием новой вьюхи, не требование отправить новое сообщение и не принудительный запрос редактирования неизменившегося сообщения. Для публичного родителя оверлеи закрываются по прежнему правилу — перед фактическим редактированием его содержимого в Telegram.

Принято: `view.mount(node)` для вьюхи в `error` сбрасывает её границу ошибки и выполняет свежую попытку монтирования, даже с прежними props. Локальные hooks/refs создаются заново; общий store, ID вьюхи и адрес сообщения сохраняются. После успешного React commit вьюха выходит из `error`; если рендер снова падает, остаётся в `error`. Ошибка Telegram-доставки обрабатывается отдельно и не превращает успешный React render в восстановленную доставку. То же правило действует при адресном `widget.mount(id, node)`. Это восстановление отдельной вьюхи при работающем Runtime, а не скрытый перезапуск всего виджета, находящегося в `error`.

Основа поведения: [идентичность и сброс состояния React](https://react.dev/learn/preserving-and-resetting-state), [жизненный цикл effects](https://react.dev/reference/react/useEffect).

## Открытие оверлея

Кнопка открывает личный интерфейс через полученное событие:

```tsx
<Button onClick={event => event.overlay(<PlayerList />)}>
  Посмотреть игры
</Button>
```

В публичной вьюхе это создаёт/обновляет оверлей нажавшего пользователя. Внутри оверлея переключает его существующий корневой компонент, сохраняя публичного родителя и получателя. Вложенный оверлей не создаётся. Возможность создания связана с событием, а не с произвольным выбранным получателем.

Сигнатура: `event.overlay(element, {force = false} = {})`. Для существующего оверлея действуют те же правила сохранения экземпляра, изменения компонента/`key` и принудительного перемонтирования, что для `view.mount`. Если оверлея ещё нет, создаётся один новый экземпляр; `force` не создаёт дополнительный оверлей.

```tsx
<Button onClick={event => event.overlay(<PlayerList />, {force: true})}>
  Open a fresh list
</Button>
```

Публичный компонент не заменяется этим действием. Намеренное изменение публичного экрана выполняется через `view.mount(...)`.

## Сохраняемые правила оверлеев

Из [базовой концепции](widget-overlays-design.md) сохраняются механики, а не прежние имена API:

- Один оверлей на пользователя в каждой публичной вьюхе; всего два уровня иерархии.
- Очистка после 20 минут неактивности получателя; действия пользователя продлевают срок, автоматический рендер и таймерное переключение — нет.
- Размонтирование очищает эффекты, подписки и привязки обработчиков. Закрытые кнопки не должны обслуживаться; прогресс в общем store сохраняется.
- Перед фактическим редактированием публичного родителя отключаются все его оверлеи. Если результат рендера прежний, редактирование и очистка не выполняются.
- Ошибка последующего редактирования родителя не восстанавливает автоматически закрытые оверлеи.
- Telegram может не доставить удаление или самостоятельно потерять эфемерный интерфейс; видимое состояние клиента не является надёжным подтверждением существования оверлея.
- Новый движок пока ориентирован на HTTP Bot API; интеграция MTProto отложена. Гостевой режим сохраняет существующие ограничения.

## Отдельная эфемерная вьюха

Принято: включить самостоятельные эфемерные вьюхи в новый движок. Их создание из кода виджета необходимо. Агенту также разрешается смонтировать новую вьюху на доступное эфемерное сообщение, передавая экспортное имя компонента и сериализуемые props. Это не означает произвольного права новой эфемерной отправки: контекст разрешения и точные формы send/target ещё уточняются. Нижеописанные конкретные сигнатуры создания из кода остаются предложениями.

Исследован вопрос: можно ли отправить новое личное эфемерное сообщение в группе и прикрепить к нему виджет. На уровне Bot API это допускается: эфемерное сообщение можно редактировать и снабжать inline-клавиатурой по адресу `chat_id`, `receiver_user_id`, `ephemeral_message_id`. Сам «виджет» является привязкой на стороне платформы, не отдельным типом сообщения Telegram. Текущий движок прикрепление к эфемерным сообщениям не поддерживает; React-вариант тоже ещё не реализован. Отдельная живая проверка самостоятельного эфемерного виджета не проводилась.

Условия новой отправки в обычной группе/супергруппе:

- Бот-администратор может отправить сообщение указанному участнику без свежего нажатия.
- Бот без прав администратора использует подходящее действие пользователя в пределах 15 секунд: callback либо ответ на входящее эфемерное сообщение. Параметр `replace_callback_query_message` не включается для отдельного нового сообщения.
- Это не устанавливает право отправки в гостевой чат без бота; ранее исследованное ограничение HTTP Bot API остаётся.
- Доставка и существование эфемерного интерфейса не гарантированы; Telegram может удалить его самостоятельно.

Основания: [условия отправки](https://core.telegram.org/bots/api#ephemeral-messages-and-commands), [параметры эфемерного сообщения](https://core.telegram.org/bots/api#ephemeralmessageparameters), [редактирование содержимого и клавиатуры](https://core.telegram.org/bots/api#editephemeralmessagetext).

В принятой модели три разновидности:

| Вьюха | `user` | `parent` |
|---|---|---|
| Публичная | `null` | `null` |
| Личное наложение на публичную | Получатель | Публичная вьюха |
| Отдельное личное эфемерное сообщение | Получатель | `null` |

Это расширяет ранее принятую модель, где любая личная вьюха была оверлеем. Сохраняем точный принятый алиас: `view.closeOverlay()` проверяет `view.user !== null` и вызывает `view.unmount()`. Следовательно, отдельное личное сообщение тоже закрывается. Проверку `parent` вместо `user` автоматически не вводим; она означала бы изменение ранее выбранного контракта.

Создание/прикрепление предлагается проводить через общий `widget.mount`, с передачей получателя для новой отправки либо полного сохранённого эфемерного адреса для прикрепления. Точные формы target, политика числа самостоятельных личных вьюх, TTL и поведение `event.overlay` на их кнопках ещё не выбраны. Возможность прямой отправки сразу готового рендера позволит избежать промежуточной текстовой заготовки.

### Новая личная вьюха из кнопки и по таймеру

Принято уточнение пользователя: новые самостоятельные сообщения создаются только через widget.mount(target, node). Метода event.mount нет. Event.view.mount обновляет текущую вьюху, а event.overlay управляет наложением. Адресный widget.mount по ID существующей вьюхи сохраняет ранее выбранную семантику обновления, а target новой отправки создаёт новую вьюху. Поля target ниже согласованы пользователем.

Для новой эфемерной отправки из нажатия принят явный target:

```tsx
await widget.mount(
  {
    chatId,
    receiverUserId: event.from.id,
    callbackQueryId: event.callbackQueryId,
  },
  <PlayerList />,
);
```

Принято: наличие receiverUserId задаёт эфемерную отправку; отдельный флаг ephemeral:true не требуется. CallbackQueryId предоставляет контекст свежего нажатия, не становится частью постоянного адреса вьюхи и не сохраняется как бессрочное разрешение. В объекте события используется event.callbackQueryId. ChatId должен быть известным разрешённым адресом; его нельзя получать декодированием inlineMessageId.

Вариант низкоуровневого target для отправки без события:

```tsx
async function remind(widget, chatId, receiverUserId) {
  return await widget.mount(
    {chatId, receiverUserId},
    <Reminder />,
  );
}
```

Такой вызов может выполнять обработчик таймера. Бот должен быть администратором указанной обычной группы/супергруппы, пользователь — участником. Свежий callback не передаётся и не требуется. Старое событие нажатия не служит бессрочным разрешением для будущих отправок; таймеры, ожидаемые после рестарта, требуют отдельной модели восстановления расписания.

Принято различать создание и выбор существующего адреса: `{chatId, receiverUserId}` без ID сообщения обозначает новую личную отправку; полный target с `ephemeralMessageId` либо ID зарегистрированной вьюхи обозначает конкретную существующую вьюху. Несколько самостоятельных сообщений одному пользователю не выбираются по неполному target автоматически; чтение/отключение требует однозначного адреса.

В обоих сценариях renderer формирует первое сообщение сразу из компонента, контроллер передаёт ephemeral_message_parameters с receiver_user_id и без replace_callback_query_message:true, затем сохраняет подтверждённый эфемерный адрес в привязке вьюхи. При создании по кнопке туда же добавляется свежий callback_query_id. Предполагаемый результат обоих вызовов — Promise<View> по принятому контракту ожидания Telegram и исходов ошибки; у новой вьюхи user равен получателю, parent === null. Подтверждение API не обещает видимую доставку клиенту.

Повторный вызов создания создаёт ещё одно сообщение: неполный target не является ключом переиспользования уже отправленной личной вьюхи. Для обновления сохраняется возвращённый View и вызывается view.mount(node) либо widget.mount(view.id, node). Прикрепление к существующему эфемерному сообщению использует полный target {chatId, receiverUserId, ephemeralMessageId} с проверкой доступности/владения. Самостоятельная вьюха не привязана жизненным циклом к сообщению, на котором нажали кнопку; она принадлежит тому же widgetId и удаляется вместе с виджетом.

Принятые различия операций:

- event.overlay(node) на публичной вьюхе создаёт или обновляет единственное наложение для нажавшего пользователя; публичный родитель остаётся прежним.
- event.overlay(node) из существующего оверлея переключает его текущую ноду/props через mount, не создавая вложенного слоя.
- Новое отдельное сообщение создаётся через widget.mount с target новой отправки. Event.mount исключён из API.
- event.view.mount(node) обновляет текущую вьюху, не меняя её публичность и получателя.

Принято: event.overlay на самостоятельной эфемерной вьюхе, у которой user !== null, но parent === null, отклоняется с понятной ошибкой. Telegram запрещает replace_callback_query_message:true для callback из уже эфемерного сообщения; создание вложенного наложения не обещается. В отличие от оверлея у такой вьюхи нет публичного родителя. Для переключения текущего личного сообщения используется event.view.mount. Все личные вьюхи не приравниваются к оверлеям; безопасный closeOverlay по условию user !== null остаётся ранее принятым алиасом.

Принято: самостоятельные эфемерные вьюхи очищаются после 20 минут неактивности получателя, как оверлеи. Действия пользователя продлевают срок, фоновые edits/timers — нет. Несколько самостоятельных сообщений одному пользователю допустимы; правило одного оверлея на пользователя в публичной вьюхе к ним не применяется. Лимит общего числа вьюх относится к техническим ограничениям движка, а не к неявному объединению отправок. После рестарта все эфемерные вьюхи отключаются по уже принятому правилу; node и props из кода не обязаны быть сериализуемыми. Описанные сценарии основаны на документированных возможностях Bot API, а не на live-тесте нового renderer.

### Методы самостоятельной эфемерной вьюхи

Рассматривается существующая личная вьюха с `user !== null` и `parent === null`.

| Метод | Поведение |
|---|---|
| `view.unmount()` | Размонтировать компоненты с cleanup, отключить обслуживание и регистрацию вьюхи и запросить удаление её эфемерного сообщения |
| `view.closeOverlay()` | Выполнить тот же `unmount()`, поскольку `view.user !== null`; публичную вьюху этот алиас по-прежнему не отключает |
| `view.mount(node, options?)` | Обновить компонент/props в том же эфемерном сообщении по общим правилам, сохранив адрес, ID вьюхи и получателя; новое сообщение не отправляется |

У `mount` сохраняются правила: прежний тип и `key` — update без сброса локального состояния; новый тип/`key` либо `{force: true}` — перемонтирование поддерева. Общий Redux store не сбрасывается ни при перемонтировании, ни при отключении отдельной вьюхи.

После отключения самостоятельной личной вьюхи никакое публичное родительское сообщение не открывается: родителя нет. `mount` через старую ссылку не должен автоматически создавать новое сообщение; для новой отправки используется операция создания новой вьюхи. `getOverlays()` у такой вьюхи возвращает пустую коллекцию в рамках текущей двухуровневой модели.

## JSX на основе Telegram Rich HTML

Принято: сделать JSX максимально близким к [Rich HTML Telegram](https://core.telegram.org/bots/api#rich-html-style), добавив React-обработчики. Пользователь согласился с правилами тегов, событий, атрибутов и преобразования rich-содержимого. Прежний пример ниже с отдельными компонентами `Message`, `Text`, `Button` остаётся ранним эскизом, а не требованием сохранять эти имена. Реализация нового renderer ещё не начата.

В текущем собственном JSX уже есть преобразования многих Rich HTML тегов в rich blocks. Это задел для нового renderer, но он не использует React и не поддерживает предложенные замыкания `onClick` в качестве нового интерфейса событий.

Предлагаемый синтаксис:

```tsx
export function Counter() {
  const value = useSelector(state => state.value);
  const dispatch = useDispatch();
  const view = useView();

  return (
    <>
      <h2>Counter</h2>
      <p>Value: <b>{value}</b></p>
      <tg-button-row align="left">
        <tg-button
          type="callback_data"
          style="primary"
          onClick={() => dispatch(counter.actions.add(1))}
        >
          +1
        </tg-button>
        <tg-button
          type="callback_data"
          style="link"
          onClick={() => view.closeOverlay()}
        >
          Back
        </tg-button>
      </tg-button-row>
    </>
  );
}
```

Корневой React Fragment в примере группирует rich-блоки одного сообщения, уже заданного вьюхой. Отдельный обёрточный тег для сообщения может не требоваться. Это не HTML для React DOM: host-теги обрабатывает наш Telegram renderer.

Принципы предлагаемого интерфейса:

- Сохранить названия тегов и по возможности атрибутов из Telegram: `p`, `h1`–`h6`, форматирование, списки, таблицы, media, `tg-button`, `tg-button-row` и другие поддерживаемые rich-теги. Соблюдать ограничения вложенности и доступности Bot API, не обещая поддержку произвольного browser HTML/CSS.
- Для callback-кнопки автор задаёт `type="callback_data"` и `onClick`. Renderer регистрирует функцию в среде виджета, создаёт служебное `callback_data` и связывает ответ Telegram с нужной вьюхой/обработчиком. Функция в Telegram и БД состояния не сериализуется.
- Поле `data` вручную не требуется при `onClick`. Совместное использование явного `data` и `onClick`, а также возможность опускать `type` пока не определены.
- `style="link"` является строковым стилем Telegram, а не CSS-объектом React DOM. По [контракту RichMessageButton](https://core.telegram.org/bots/api#richmessagebutton) стиль `link` разрешён только callback-кнопкам.
- Кнопки URL, копирования, inline query и другие клиентские типы сохраняют собственные поля Telegram. Наличие таких кнопок не означает получение callback; `onClick` для несовместимого типа предлагается отклонять явно.
- JSX выражения и пользовательские компоненты работают обычным способом. Например, компонент `PlayerRow` может вернуть `tr`, а внутри использовать `tg-button`. Соблюдаются синтаксические правила JSX: закрытые/самозакрывающиеся теги, значения выражений в `{...}` и boolean props.
- Предлагается преобразовывать дерево непосредственно в `rich_message.blocks` и отдельный реестр обработчиков. Буквальная сериализация всего дерева в HTML не обязательна; структурированные блоки также являются документированным входом [InputRichMessage](https://core.telegram.org/bots/api#inputrichmessage).
- React `key` и ссылки/обработчики не должны утекать как обычные атрибуты Telegram. Типы intrinsic JSX-тегов должны описывать Telegram-атрибуты и добавленные обработчики, в том числе строковый `style`.

Личная навигация сохраняется в событиях:

```tsx
<p>
  <tg-button
    type="callback_data"
    style="link"
    onClick={event => event.overlay(<PlayerList />)}
  >
    View games
  </tg-button>
</p>
```

Повторный React render обычно создаёт новое замыкание `onClick`. Это само по себе не должно вынуждать безусловно менять wire callback ID и редактировать неизменившееся публичное меню: такое редактирование закроет его оверлеи. Стабильность ID кнопок, смена обработчиков при commit, отсечение устаревших кнопок и восстановление после рестарта требуют отдельной спецификации.

### Обычный HTML и Rich HTML

По документированным контрактам это пересекающиеся, но не одинаковые языки. Обычный [HTML style](https://core.telegram.org/bots/api#html-style) используется для форматирования текста, Rich HTML — для структурированного rich-сообщения.

| Возможность | Обычный текстовый HTML | Rich HTML |
|---|---|---|
| Базовое форматирование `b`/`strong`, `i`/`em`, `u`/`ins`, `s`/`strike`/`del` | Да | Да |
| `code`, `pre`, ссылки `a href`, `tg-spoiler`, `tg-emoji`, `tg-time` | Да | Да, с собственными правилами контекста и атрибутов |
| `blockquote`, включая `expandable` | Да | Да; rich поддерживает также дополнительную структуру, например `cite` |
| `p`, заголовки, списки, таблицы, `details`, `hr` | Нет | Да |
| `mark`, `sub`, `sup`, формулы, якоря и сноски | Нет | Да |
| Media-блоки, галереи, карты | Нет в теле текста | Да |
| `tg-button` внутри содержимого | Нет | Да |
| `span class="tg-spoiler"` | Документированный вариант | В rich-документации этого варианта нет; общий вариант — `tg-spoiler` |
| `br` | Не входит в документированные теги; для текста используются переводы строк | Поддерживается, например внутри цитаты |

Нельзя обещать буквальное надмножество обычного HTML только из-за большего числа rich-тегов. Отличаются также правила вложенности, именованные HTML entities и интерпретация некоторых ссылок.

Обычное сообщение тоже может иметь кнопки, но они передаются отдельно в `reply_markup.inline_keyboard`, а не размещаются в его HTML-тексте. В частности, [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton) не поддерживает стиль `link`; для rich callback-кнопки этот стиль допустим.

Для нового движка предложено иметь общее ядро JSX-форматирования, но разные целевые преобразования: обычный текст с entities либо rich blocks. Способ явного выбора формата и описание обычной inline-клавиатуры пока не выбраны. Не следует молча трактовать rich-теги как эквивалентное обычное форматирование или автоматически терять неподдерживаемые элементы.

## Типы сообщений и клавиатура под сообщением

Пользователь требует поддерживать не только rich: обычный текст, dice, отдельные фото, видео, аудио, анимации, location и liveLocation, включая кнопки под сообщениями. Это требование к охвату нового движка; доступность конкретного типа в обычном, inline, гостевом и эфемерном адресе определяется Telegram отдельно.

Текущий движок уже имеет native send/edit-планирование для многих таких типов; это можно учитывать при переработке, но готовой React-интеграции нет.

### Предложение явного корня сообщения

Предлагается общий контейнер `tg-message`, определяющий native тип одного сообщения. Точные имена контейнера, атрибутов и клавиатуры ещё не приняты:

| `type` | Результат |
|---|---|
| `text` | Обычный текст с форматированием HTML style / entities |
| `rich` | Rich-сообщение с Telegram Rich HTML / blocks |
| `photo` | Отдельное фото |
| `video` | Отдельное видео |
| `audio` | Отдельное аудио |
| `animation` | Отдельная анимация |
| `dice` | Отправленный Telegram случайный бросок |
| `location` | Статичная геолокация |
| `liveLocation` | Геолокация с обновляемыми координатами |

Следующий предлагаемый выбор для окончательной формы JSX: сделать tg-message обязательным корнем одной вьюхи, выбирать native тип явно через type, использовать tg-caption для native media и tg-keyboard/tg-button-row для внешней клавиатуры. Rich-кнопки внутри содержимого и внешняя клавиатура остаются разными контекстами. Несовместимый с типом сообщения тег/атрибут должен давать понятную ошибку, а не молча исчезать; автоматическое определение типа или неявная публикация нескольких сообщений не предлагаются. Существующие примеры rich-фрагментов без tg-message остаются иллюстрацией содержимого до выбора обязательности корня. Это рекомендация к согласованию, а не уже принятое ограничение.

Пример native фото с подписью и клавиатурой:

```tsx
export function PhotoCard({photoId}) {
  const view = useView();

  return (
    <tg-message type="photo" src={photoId}>
      <tg-caption><b>Photo</b> with a formatted caption.</tg-caption>
      <tg-keyboard>
        <tg-button-row>
          <tg-button
            type="callback_data"
            onClick={event => event.overlay(<PlayerList />)}
          >
            View games
          </tg-button>
          <tg-button type="callback_data" onClick={() => view.closeOverlay()}>
            Close
          </tg-button>
        </tg-button-row>
      </tg-keyboard>
    </tg-message>
  );
}
```

`src` в предложении адресует native media, а не HTML-картинку. Поддерживаемые file ID, публичные URL и разрешённые локальные источники должны согласовываться с контрактом контроллера и ограничениями адреса. Подпись `tg-caption` использует форматирование обычного текста, не произвольные rich-блоки.

Другие типы выбираются явно:

```tsx
<tg-message type="video" src={videoId} />;
<tg-message type="audio" src={audioId} />;
<tg-message type="animation" src={animationId} />;
<tg-message type="dice" emoji="🎲" />;
<tg-message type="location" latitude={latitude} longitude={longitude} />;
<tg-message
  type="liveLocation"
  latitude={latitude}
  longitude={longitude}
  live_period={900}
/>;
```

Для rich-содержимого тот же явный корень может оборачивать принятые HTML-теги:

```tsx
<tg-message type="rich">
  <h2>Results</h2>
  <p>
    <tg-button
      type="callback_data"
      style="link"
      onClick={event => event.overlay(<PlayerList />)}
    >
      View games
    </tg-button>
  </p>
</tg-message>
```

Это позволяет отличить native фото от `<img>` в rich-блоке, native live location от rich-карты, обычный текст от rich. Ранее показанные фрагменты без корня остаются примером содержимого rich; станет ли это сокращением, ещё не решено. Одна вьюха по-прежнему представляет одно Telegram-сообщение; набор отдельных сообщений создаётся несколькими вьюхами.

### Кнопки внутри rich и под сообщением

- `tg-button` внутри rich-параграфа/таблицы и `tg-button-row` внутри rich-тела преобразуются в rich-кнопки/блоки.
- `tg-keyboard` обозначает внешнюю inline-клавиатуру и преобразуется в `reply_markup.inline_keyboard`. Она может применяться к text, rich и запрошенным native типам, где Telegram принимает соответствующую клавиатуру.
- Внутри внешней клавиатуры `tg-button-row` задаёт ряд, `tg-button` — кнопку. Используется тот же механизм `onClick` и событий, что для rich-кнопок.
- Атрибуты проверяются по контексту: например, `style="link"` относится к rich callback-кнопкам и не поддерживается обычным [InlineKeyboardButton](https://core.telegram.org/bots/api#inlinekeyboardbutton). Rich-выравнивание ряда также нельзя автоматически переносить на внешнюю клавиатуру.

### Объединение нескольких tg-keyboard

Принято по предложению пользователя: если итоговое React-дерево одной вьюхи содержит несколько tg-keyboard, их ряды объединяются в одну внешнюю inline-клавиатуру сообщения.

- Порядок определяется обходом итогового host-дерева в порядке содержимого. Ряды каждой клавиатуры добавляются целиком после рядов предыдущей; кнопки внутри ряда сохраняют свой порядок. Последний ряд одной клавиатуры не склеивается с первым рядом следующей.
- Клавиатуры могут возвращаться разными пользовательскими компонентами и находиться внутри Fragment или layout. Tg-keyboard извлекается как внешняя клавиатура, а не как видимый блок rich-тела. Сбор ограничен текущей вьюхой: клавиатуры других вьюх/оверлеев того же Runtime не смешиваются.
- На каждом render вычисляется итог текущего дерева; клавиатуры не накапливаются между render. Удаление компонента удаляет его вклад, пустой вклад не добавляет рядов.
- Одинаковые подписи кнопок не являются основанием для удаления дублей. Идентичность кнопок и callback ID следует принятому React-контракту, а не позиции в плоском объединённом массиве.
- Итоговая клавиатура проверяется как одна native клавиатура. При недопустимом размере/содержимом возвращается понятная ошибка, без молчаливого обрезания или отправки дополнительных сообщений.

Пример: первая клавиатура содержит ряды [A, B] и [C], вторая — [D, E]. В результате три ряда: [A, B], [C], [D, E]. Это позволяет компоненту игры добавить свои действия, а компоненту навигации — ряд «Назад», не требуя общей ручной сборки клавиатуры.

### Жизненный цикл native типов

- Принято для выбранного гибрида rich/sticker/dice: dice и sticker можно впервые опубликовать только как новое сообщение. Первое прикрепление компонента с таким результатом к уже существующему Telegram-сообщению — ошибка рендера, даже если сообщение внешне того же типа. Это не запрет повторного render уже созданной этим движком native-вьюхи или её восстановления по сохранённой публикации.
- После отправки тело native dice/sticker фиксировано. Неизменный native-узел при следующем render допустим и не требует новой отправки. Изменение параметров dice (например, emoji), замена самого sticker, переход в другой тип или исчезновение native-узла с пустым телом — ошибка рендера. Сравниваются нормализованные параметры native-содержимого, а не ссылка на JSX-объект или экземпляр функции компонента; серверный dice.value не является входным параметром.
- Внешняя клавиатура — отдельная изменяемая часть: можно добавлять, изменять и убирать её, продолжая рендерить прежний dice/sticker. Поэтому useDice может обновить зависимые кнопки после получения результата. Компонент, возвращающий только клавиатуру без прежнего native-узла, не выражает сохранение dice/sticker и даёт ошибку смены тела.
- Несовместимая проекция целиком отклоняется до native edit; вместе с ней не применяется даже новая клавиатура. Ошибка обрабатывается как обычная ошибка рендера этой вьюхи: прежнее сообщение остаётся, вьюха получает error, Runtime и другие вьюхи продолжают работу. Автоматического удаления, замены сообщения или нового броска нет. Для нового native сообщения нужен явный widget.mount с новым адресом отправки.
- Обычный React render не должен повторно отправлять сообщение или заново бросать dice. Telegram выбирает значение при отправке [sendDice](https://core.telegram.org/bots/api#senddice); результат является данными ответа, а не задаваемым значением JSX. Для нового броска требуется новая отправка/вьюха. Предложение доступа к серверному результату описано ниже.
- `{force: true}` перемонтирует компоненты React, но не является требованием нового native сообщения или повторного броска и не снимает ограничения тела. Mount() и восстановление прежней зарегистрированной публикации допускают только совместимый native-результат.
- Для `liveLocation` обновление координат планируется через [editMessageLiveLocation](https://core.telegram.org/bots/api#editmessagelivelocation). Период отсчитывается Telegram от отправки; повторный render не должен сам по себе начинать новый отсчёт. Остановку трансляции и восстановление после рестарта нужно явно описать.
- Для эфемерного [sendLocation](https://core.telegram.org/bots/api#sendlocation) `live_period` должен быть нулевым: native live location там недоступна. `sendDice` не предоставляет параметров эфемерной отправки. Совместимость остальных сочетаний требует матрицы, а не обещания любого типа для любой вьюхи.
- Переход компонента React на другой native тип не означает, что Telegram разрешит редактирование того же сообщения. Используются допустимые native операции; невозможная смена типа должна возвращать понятную ошибку без автоматического удаления и новой отправки. Это соответствует прежнему принципу текущего движка.

## Сравнение JSX с корнем сообщения и без него

По запросу пользователя варианты рассматриваются параллельно; позднее добавлен третий — только rich-сообщения. Ни обязательный tg-message, ни замена onSent на useMessage, ни отказ от native типов управляемых вьюх пока не выбраны. Предыдущая принятая семантика onSent остаётся исходным вариантом, пока не согласовано её изменение. Форма JSX и способ чтения подтверждённого сообщения — независимые оси: useMessage технически возможен с любым из синтаксисов.

### Вариант A: явный tg-message

```tsx
<tg-message type="photo" src={photoId}>
  <tg-caption>Kitten</tg-caption>
  <tg-keyboard>{buttons}</tg-keyboard>
</tg-message>;
```

Плюсы: native тип очевиден в одном месте, пересечение text/rich не требует эвристики, есть естественный контейнер специфичных полей сообщения. Минусы: дополнительная обёртка, для простого текста больше служебного JSX, и type, src и вложенные узлы всё равно требуют проверки совместимости. Явный type не даёт права на недопустимую смену native типа существующего сообщения.

### Вариант B: тип по результату React render

Эскиз с отдельными native-тегами, не принятыми окончательно:

```tsx
<>
  <tg-photo src={photoId} />
  <tg-caption>Kitten</tg-caption>
  <tg-keyboard>{buttons}</tg-keyboard>
</>;
```

Предлагаемые строгие правила, необходимые вместо свободной эвристики:

- Тип определяется по итоговому host-дереву вьюхи после выполнения React-компонентов, а не по имени пользовательской функции или простому обходу children до render. React Children не раскрывает результат вложенных компонентов: [React Children](https://react.dev/reference/react/Children).
- Ровно один native media-узел вроде tg-photo/tg-dice задаёт соответствующий тип; tg-caption и tg-keyboard относятся к этому сообщению. Несколько native сообщений в одной вьюхе отклоняются, а не превращаются молча в несколько публикаций или альбом.
- Для пересечения обычного текста и rich нужен детерминированный выбор. Кандидат: только общие текстовые теги дают text, наличие rich-only структуры даёт rich. Отдельный img всегда rich-блок; native фото задаётся tg-photo. Альтернативная трактовка одиночного img как native фото тоже возможна, но требует отдельного выбора и не должна меняться неявно от соседнего элемента.
- Автоматический вывод типа не разрешает неподдерживаемую смену native типа опубликованного сообщения. Изменение содержимого, меняющее выбранный тип, проходит ту же проверку допустимого edit. Неоднозначное или несовместимое дерево даёт ошибку, а не скрытый fallback.

Плюсы: меньше обязательной оболочки, простые компоненты возвращают содержимое напрямую, native-представления естественно разделяются по тегам. Минусы: нужны правила классификации, добавление rich-элемента может менять выводимый тип, а информация о типе распределяется по дереву. Отказ от tg-message не отменяет типизацию и валидацию сообщения; она переносится в анализ host-узлов. Конкретные правила выше — предложения, не уже согласованный контракт.

### useMessage вместо onSent: отдельный выбор

Предлагаемая семантика хука — явная реактивная подписка на последнее подтверждённое сообщение текущей вьюхи:

```tsx
const message = useMessage();
const diceValue = message?.dice?.value ?? null;
```

До подтверждения первой публикации возвращается null. После успешной новой публикации или подтверждённого обновления доступных данных подписанный компонент перерисовывается. Хук не отправляет сообщение и не бросает dice сам; первый render без результата создаёт исходное сообщение, получение dice.value вызывает render зависимой клавиатуры того же сообщения. После рестарта обычной вьюхи хук сразу читает восстановленные подтверждённые данные, без новой отправки.

Это явная подписка автора через хук, а не пересмотр принятого пассивного свойства view.message: чтение последнего само по себе по-прежнему не инициирует render. Подход можно построить на стабильном immutable snapshot и подписке, как у [useSyncExternalStore](https://react.dev/reference/react/useSyncExternalStore). Неизменные данные не должны создавать новый snapshot и лишние уведомления; одинаковая native-проекция не создаёт новый edit. Возможный selector для useMessage, состав snapshot при native методе без полного Message и частота уведомлений требуют уточнения.

useMessage читает состояние, onSent обозначает новую отправку. Для построения клавиатуры дайса хук короче и не дублирует значение в useState. Для одноразового начисления очков это не эквивалент события: после восстановления useEffect снова может увидеть сохранённое сообщение. Защита от повторного игрового эффекта должна опираться на сохраняемые данные приложения, а не на предположение, что появление message всегда означает новую отправку. Рендер/эффект, который меняет сообщение при каждом подтверждении edit, может создать цикл; engine dedup одинакового результата не устраняет произвольную логическую обратную связь автора.

### Обратная связь useMessage: альтернативы подписки

Пользователь указал проблему полного реактивного Message: вызов useMessage подписывает компонент на подтверждение edit, а недетерминированный render выдаёт новое содержимое, порождая следующий edit и повторное уведомление. Пример — useMessage вместе с Math.random в результирующем параграфе. Даже стабильная идентичность неизменного snapshot не разрывает цикл, если каждое успешно доставленное содержимое действительно отличается.

Math.random в render не соответствует [правилу идемпотентности React](https://react.dev/reference/rules/components-and-hooks-must-be-pure), однако требование чистого render само по себе не является защитой SDK от циклов обратной связи. Чистая функция, которая намеренно меняет результат на основании прошлого подтверждённого сообщения, тоже может образовать цикл. Рекомендация к обсуждению — не предоставлять по умолчанию подписку на весь Message.

Рассматриваются три подхода:

1. Оставить полную подписку и считать такие циклы ошибкой приложения. Самый общий интерфейс, но даже неиспользуемый результат useMessage подписывает компонент и может создать лишний сетевой цикл.
2. Требовать selector у useMessage: например, useMessage(message => message?.dice?.value ?? null). Рендер уведомляется только при изменении выбранного значения. Это универсальный способ, но selector, возвращающий весь изменяющийся Message, снова создаёт прежний риск.
3. Разделить пассивное чтение, узкую реактивную подписку и событие. Последний Message читается через уже согласованное пассивное view.message. Предложенный пользователем useDice возвращает [value, emoji] и подписывается только на эти данные. UseOnMessage регистрирует обработчик подтверждения, не инициируя render автоматически.

Принято выбранное разделение для текущего гибрида rich/sticker/dice: пассивное view.message, узкий реактивный useDice и события useOnMessage. Полная автоматическая подписка на весь Message не вводится.

Принятая семантика useDice:

- До подтверждённого результата текущей вьюхи возвращать [null, null]. Вызов хука сам не отправляет dice, тип по-прежнему задаёт native-узел JSX.
- После первой публикации обновить пару из подтверждённого Message.dice; результат и emoji являются данными Telegram, а не новым вычислением render.
- Подтверждение редактирования одной клавиатуры не меняет пару и не инициирует render подписчика. Snapshot пары должен быть стабильным при одинаковых значениях, а не новым массивом на каждое чтение.
- При восстановлении обычной dice-вьюхи читать прежнюю сохранённую пару без нового броска. Наличие данных не считается новым событием отправки. Вьюха без dice возвращает [null, null], а не результат другого сообщения.

Принято пользователем: useOnMessage(callback) вызывается после подтверждённой новой отправки и каждого успешного редактирования сообщения вьюхи, включая изменения клавиатуры. В отличие от полной подписки useMessage, регистрация обработчика сама по себе не инициирует render. Изменения state/store внутри callback являются явным решением автора; возможная петля «edit → callback → изменение state → edit» допускается как ошибка дизайна приложения, аналогично циклу useEffect. Автоматическое подавление таких событий только ради разрыва петли не вводится. Повторный render без native edit, смена функции callback, регистрация обработчика и восстановление прежнего сообщения сами по себе не воспроизводят подтверждение публикации. Для native результата без полного Message нужно уточнить честную форму аргумента callback без выдуманных полей.

Эта альтернатива не обещает exactly-once побочных действий при аварии. Она ограничивает автоматическую связь подтверждения доставки с React render и сохраняет различие между читаемыми данными сообщения и событием новой публикации. Спецификация и runtime-прототип новых хуков ещё не реализованы.

### Предварительное сравнение

| Критерий | Явный tg-message | Вывод типа без tg-message |
| --- | --- | --- |
| Обычный короткий текст | Больше служебного JSX | Компактнее |
| Ясность text/rich/native | Тип указан явно | Зависит от правил и тегов |
| Медиа и клавиатура | Общий контейнер | Соседние host-узлы в пределах одной вьюхи |
| Произвольные React-компоненты | Поддерживаются | Поддерживаются; вывод по результату render |
| Ошибки классификации | Несовместимость type и children | Неоднозначность и смена выводимого типа |
| useMessage | Совместим | Совместим |
| Сложность интеграции | Нужен renderer и валидатор | Дополнительно нужен строгий классификатор |

Предварительная рекомендация для обсуждения: useMessage как явная подписка полезен в обоих вариантах. Вариант без tg-message можно предпочесть ради компактности, если принять однозначные native-теги и правила text/rich, а не произвольное угадывание по картинке/ссылке. Окончательный выбор принадлежит пользователю; runtime и живые проверки этих альтернатив ещё не реализованы.

### Вариант C: вьюха всегда rich

Предложен пользователем, пока не принят: renderer управляет только rich-сообщениями. Корневой tg-message не требуется, тип по содержимому не угадывается. Любой компонент может дать rich-содержимое; img всегда является rich-фото. Иные native сообщения можно отправлять обычным API из обработчиков/Runtime, но они не становятся управляемыми вьюхами этого renderer.

Преимущество относительно B — исчезает классификация native/text/rich, а относительно A — разделение авторских компонентов на «готовое сообщение с оболочкой» и «только содержимое». Все компоненты составляют одно rich-дерево, которое завершается границей вьюхи. Обычный текст оформляется как rich-текстовый блок; пустой или неподдерживаемый результат всё равно требует понятной валидации.

Проверены актуальные официальные схемы [InputRichBlock](https://core.telegram.org/bots/api#inputrichblock), [InputRichMessage](https://core.telegram.org/bots/api#inputrichmessage), [sendRichMessage](https://core.telegram.org/bots/api#sendrichmessage), [RichMessageButton](https://core.telegram.org/bots/api#richmessagebutton) и текущие native-планировщик/JSX проекта. Rich содержит блоки photo, video, animation, audio, voice_note, document, map, collage/slideshow и buttons. Поэтому обычные карточки, Wordle, таблицы, медиа-каталоги, музыкальные/голосовые карточки, документы и статичная карта не требуют native типа вьюхи. Внешний reply_markup также предусмотрен sendRichMessage; ограничение только rich не означает запрет обычной inline-клавиатуры под сообщением. Доступность каждого действия кнопки по типу чата остаётся ограничением Telegram.

Разница сценариев и возможные обходы:

| Сценарий | Что меняется при rich-only renderer |
| --- | --- |
| Нативный dice с результатом | В rich-дереве нет dice-блока. Как предложил пользователь, обработчик вызывает sendDice, читает возвращённый Message.dice и записывает значение в store; интерфейс игры остаётся rich. Сам dice не становится View |
| Native live-location | Отдельная отправка и последующие edit/stop через API с сохранением адреса и нужного расписания. Rich-карту можно перерисовывать, но нельзя автоматически считать это native live-location с её сроком/событиями |
| Нативные poll/quiz | Нет rich-poll. Голосование на callback-кнопках возможно как интерфейс приложения, но это другая модель голосования. Отдельный sendPoll сохраняет native poll, однако для poll_answer/изменений самого опроса нужна маршрутизация событий в экземпляр; одной возможности отправки недостаточно |
| Sticker, video note и live photo | Отдельных rich-блоков этих native типов нет. Можно отправить скриптом; подмена картинкой/обычным видео не сохраняет точный native объект и его взаимодействия |
| Contact и venue | Можно показать текст/ссылку телефона, карту и адрес. Это не полноценная native contact/venue-карточка; при необходимости она отправляется отдельно |
| Монтирование в существующее native сообщение | Обычный rich edit не предоставляет универсального преобразования photo/video/poll/dice в rich. Такие сообщения нельзя обещать превратить в rich-вьюху на том же адресе; нужны поддерживаемый target или новая rich-публикация |
| Привычное отдельное медиа/альбом | Rich-галерея и native отправка остаются разными объектами. Точное клиентское поведение сохранения, пересылки и индексации rich-медиа не подтверждено этим исследованием; не считать предполагаемые визуальные различия доказанными потерями |

Для последнего ограничения важен контракт [editMessageText](https://core.telegram.org/bots/api#editmessagetext), который адресован текстовым, rich и game сообщениям. Для dice подтверждён возврат Message методом [sendDice](https://core.telegram.org/bots/api#senddice). Отдельная отправка должна иметь известный разрешённый chatId: наличие inlineMessageId или guest-вьюхи само по себе не даёт права отправлять произвольное новое сообщение в чат без бота. Это ограничение API, а не новое ограничение, введённое rich-only.

Native-сообщение, отправленное скриптом, не получает автоматически view.mount/useMessage, JSX-кнопки, подписки на события, cleanup и восстановление адреса как зарегистрированная вьюха. Если ему нужны виджетные кнопки/события или управление после рестарта, эту связь нужно спроектировать отдельно; иначе rich-вьюха служит панелью управления, а скрипт явно управляет внешним сообщением по сохранённому адресу. При варианте C useMessage относится к rich-вьюхе; результат стороннего sendDice читается из ответа API и не подменяет сообщение этой вьюхи.

Вывод исследования: основные UI-сценарии сохраняются, включая медиа. Основная потеря — автоматическое управление специальными native объектами как самими вьюхами и универсальность прикрепления к уже существующим сообщениям. Полный отказ от таких сообщений в API не предлагается. Вариант C существенно упрощает контракт renderer и выглядит подходящим для Wordle/инструментальных интерфейсов, если перечисленные границы приемлемы пользователю. Ни новый renderer, ни визуальная эквивалентность rich/native не проверялись живьём в рамках этого исследования.

### Вариант D: rich плюс native sticker и dice

Новый вариант на рассмотрении по предложению пользователя: сохранить отсутствие tg-message и поддержать три вида управляемого сообщения — rich, sticker и dice. У sticker/dice допускается внешняя inline-клавиатура. Викторины, live photo, видеокружки и контакты в renderer не включаются. Принято отдельное решение: native live-location пока не реализовывать, четвёртый тип вьюхи ради неё не добавлять. Пользователь не видит необходимого сценария, который нельзя покрыть rich-сообщениями. Поддержка произвольного дополнительного native типа не подразумевается.

Предлагаемая однозначная классификация: специальный native-узел tg-sticker или tg-dice плюс внешняя клавиатура дают соответствующий тип; остальное допустимое содержимое образует rich. Img всегда rich-фото. Несколько специальных native-узлов или смесь native sticker/dice с обычным rich-телом должны отклоняться, поскольку это не одно поддерживаемое сообщение с подписью. Конкретные имена тегов ещё не приняты. UseMessage особенно полезен для чтения результата управляемого dice, но выбор хука вместо onSent по-прежнему открыт.

#### Rich map и native live-location

Проверены [InputRichBlockMap](https://core.telegram.org/bots/api#inputrichblockmap), [RichBlockMap](https://core.telegram.org/bots/api#richblockmap), [Location](https://core.telegram.org/bots/api#location), [editMessageLiveLocation](https://core.telegram.org/bots/api#editmessagelivelocation) и [stopMessageLiveLocation](https://core.telegram.org/bots/api#stopmessagelivelocation).

Документация rich-map описывает карту с центром location, масштабом, размерами и подписью, но не устанавливает для rich-сообщения контракт native live-location. Методы edit/stop live-location адресуют само live-location-сообщение, не выбранный rich-блок; параметра выбора такого блока в них нет. Для проекта нельзя обещать, что они работают с rich-map так же, как с отдельной native геопозицией.

Важная неоднозначность схемы: общий тип Location действительно содержит необязательные live_period, heading и proximity_alert_radius. Одна ссылка на этот тип в InputRichBlockMap не подтверждает создание трансляции или совместимость с методами edit/stop; эти поля документированы для активных native live locations. Поведение передачи таких полей именно в rich-map отдельно живьём не проверялось. Исследование не следует выдавать за экспериментальное доказательство того, что каждое дополнительное поле игнорируется или отклоняется.

Карту в rich можно обновлять заменой rich-содержимого, а прекращение обновлений реализовать логикой приложения. Это не обещает native срок трансляции, её остановку через stopMessageLiveLocation или уведомления о приближении. Принято: native live-location отложена, её реализация и живое исследование совместимости с rich-map в текущий объём не входят. Rich-карты и обычное обновление их координат остаются допустимым содержимым. Это решение об охвате renderer, а не изменение общего контракта разрешённых Telegram API-вызовов. Остальные детали гибридного синтаксиса и useMessage ещё требуют окончательного согласования.

## Пример авторского модуля

Это эскиз будущего Telegram API. Пакет `@tg-assistant/react`, компоненты и интерфейсы ниже ещё не реализованы. Пример не следует выдавать за работающий виджет текущего движка.

```tsx
import {
  defineStore, useSelector, useDispatch, useView,
  Message, Text, Button,
} from "@tg-assistant/react";

const counter = defineStore({
  initialState: {value: 0},
  reducers: {
    add(state, amount: number) {
      state.value += amount;
    },
  },
});

export function Main() {
  return (
    <Message>
      <Text>Counter</Text>
      <Button onClick={event => event.overlay(<Counter />)}>
        Open counter
      </Button>
    </Message>
  );
}

export function Counter() {
  const value = useSelector(state => state.value);
  const dispatch = useDispatch();
  const view = useView();

  return (
    <Message>
      <Text>Count: {value}</Text>
      <Button onClick={() => dispatch(counter.actions.add(1))}>+1</Button>
      <Button onClick={() => view.closeOverlay()}>Back</Button>
    </Message>
  );
}

export function Summary() {
  const value = useSelector(state => state.value);
  return <Message><Text>Count: {value}</Text></Message>;
}
```

Предполагается публичный неизменный `Main`, отдельный обновляемый `Summary` и личные `Counter`. Компонент `Counter` также можно монтировать публично: `closeOverlay()` тогда ничего не отключает.

## Доказательства и ограничения оценок

### Изоляция store при общей загрузке модуля

По просьбе пользователя выполнен узкий [исполняемый прототип](../../test/manual/react-store-isolation.mjs) с [экспериментальной обёрткой](../../test/manual/react-store-isolation-prototype.mjs) и общим [модулем виджета](../../test/manual/react-store-isolation-fixture.mjs). Это не production SDK. Использованы настоящие React 19.2.0, React Redux 9.2.0 и Redux Toolkit 2.9.0; зависимости установлены только в игнорируемый каталог эксперимента, без изменения package.json/lock проекта. Для React-проверки использован react-test-renderer; это не Telegram renderer.

В эксперименте `defineStore` создаёт общее описание/action creators, а `configureStore` вызывается для каждого экземпляра отдельно. Начальное или восстановленное состояние копируется вместе с вложенными объектами; объектный шаблон initialState заморожен. Внешний Provider получает store соответствующего экземпляра. Сохранение привязано к конкретному widgetId в SQLite `:memory:`.

Пять проверок прошли:

- Повторный import возвращает тот же модуль и описание; два экземпляра имеют разные живые store и вложенные данные, изменения A не затрагивают B или общий initialState.
- Настоящие useSelector/useDispatch и один общий объект Context обслуживают два React root независимо; асинхронный callback A меняет только A, записи SQLite также разделены. Восстановление A сохраняет данные и не меняет работающий B.
- [Модуль без default export](../../test/manual/react-store-isolation-default-fixture.mjs) работает через стандартный Runtime, сохраняя Redux Provider.
- Функция initialState/миграции выполняется для конкретного экземпляра и его версии; текущее состояние восстанавливается без повторной инициализации, более новая сохранённая версия отклоняется.
- Неэкспортированное или неоднозначное описание отклоняется; aliases одного описания не создают несколько store.

Прототип подтверждает осуществимость изоляции с явным экспортом описания — ранее рассмотренным, но отвергнутым пользователем авторским контрактом. Правило этого экспериментального загрузчика об ошибке неэкспортированного описания не переносится в новый дизайн. Прототип не проверяет выбранную регистрацию вызовом defineStore при загрузке модуля, реальный bridge, долгие обработчики, аварийное восстановление или Telegram-доставку. Синхронная подписка для SQLite в эксперименте не заменяет согласованный порядок сохранения и публикации production движка. Основа интеграции прежнего эксперимента: [configureStore](https://redux-toolkit.js.org/api/configureStore), [Provider](https://react-redux.js.org/api/provider).

### Другие эксперименты и оценки

[Браузерный пример React/Redux](../../test/manual/react-redux-counter.jsx) с [runner](../../test/manual/react-redux-counter.mjs) проверен в браузере: общий счётчик двух представлений, dispatch из обоих, уменьшение, сброс, отрицательное значение и потеря состояния при перезагрузке. Это не Telegram renderer, не persistence в SQLite и не проверка нового движка.

Оценки дополнительного расхода React были предварительными: 5–20 МиБ на общую библиотеку/renderer в процессе и 0,05–0,5 МиБ на простую активную вьюху, отдельно от данных и буферов. Это бюджет для обсуждения, а не измерение. Прежние [замеры Node](widget-memory-verification.md) и [реального Wordle](wordle-migration-verification.md) относятся к разным средам и метрикам; их нельзя выдавать за измерения React. Собственный renderer и нагрузочный прототип необходимы для выбора лимитов.

### Результат отправки: view.message и общий onSent

Рассмотрен сценарий пользователя: сообщение содержит dice, а кнопки под ним зависят от выпавшего значения. Telegram возвращает `Message` с `dice.value` в ответе на `sendDice`; ждать отдельного update не требуется. Клавиатуру можно изменить отдельно через [editMessageReplyMarkup](https://core.telegram.org/bots/api#editmessagereplymarkup).

Пользователь согласовал `view.message`, но отклонил неявный повторный рендер при получении результата отправки. Поле содержит доступный только для чтения снимок последнего известного подтверждённого сообщения Telegram. До первого подтверждения `message === null`; это не оптимистичная копия желаемого JSX и не гарантия знания последующих внешних изменений в Telegram. Обновление подтверждённых данных сообщения само по себе не должно подписывать компонент на повторный рендер.

Принято: общий prop `onSent(message)` для всех поддерживаемых типов сообщений, вместо отдельного `onDice`. Он обозначает уже успешную отправку. Ошибка отправки не вызывает `onSent`; render, edit, прикрепление к существующему сообщению и штатное восстановление вьюхи также не создают искусственного события отправки. Ошибка обработчика не вызывает повторной отправки уже опубликованного сообщения. `ref.current.ready` не является выбранным контрактом; effects сохраняют обычную семантику React.

Обычный [useEffect](https://react.dev/reference/react/useEffect) выполняется после React commit; сам по себе он не ожидает сетевые операции контроллера. В экспериментальном [react-reconciler](https://github.com/facebook/react/blob/main/packages/react-reconciler/README.md) есть механизм `waitForCommitToBeReady`, позволяющий задержать commit, но это не готовая гарантия отправки Telegram перед effects. Отложенный commit может быть отменён; если к тому времени отправка уже выполнена, нужно согласовывать внешнее сообщение с отменённым React-деревом. При общем root это также связывает завершение commit остальных вьюх с сетевым ожиданием. Это архитектурный вывод, не результат прототипа.

Для отправки, возвращающей `Message`, обработчик получает его доступный только для чтения подтверждённый снимок после сохранения результата в записи вьюхи. К этому моменту обновлён и `view.message`; для dice значение читается из `message.dice.value`. Обработчик выполняется вне render/commit как событие контроллера для актуального host-узла. Если конкретный способ публикации не возвращает полный `Message`, необходимо отдельно определить доступный результат и типизацию: нельзя обещать неизвестные поля или выдумывать полный ответ. Ниже пример согласованного направления API обычной отправки, пока не реализованного новым движком.

```tsx
export function DiceGame() {
  const view = useView();
  const [value, setValue] = useState(
    () => view.message?.dice?.value ?? null,
  );

  return (
    <tg-message
      type="dice"
      emoji="🎲"
      onSent={message => setValue(message.dice.value)}
    >
      {value !== null && (
        <tg-keyboard>
          <tg-button-row>
            <tg-button
              type="callback_data"
              onClick={event => event.overlay(<RollDetails value={value} />)}
            >
              {value === 6 ? "Claim your prize" : `Keep ${value}`}
            </tg-button>
          </tg-button-row>
        </tg-keyboard>
      )}
    </tg-message>
  );
}
```

Порядок для новой вьюхи:

1. Пока результата нет, компонент рендерит dice без зависимых кнопок.
2. Контроллер отправляет dice, сохраняет подтверждённые адрес и данные результата в записи вьюхи, обновляет `view.message` и передаёт подтверждённый `Message` в `onSent`.
3. Обработчик явно вызывает `setValue`, вызывающий обычный React render с известным `dice.value`. До обновления state подтверждение отправки само по себе не вызывает render компонента.
4. Планировщик меняет только клавиатуру существующего сообщения. Повторный render, перезапуск приложения и `force: true` не бросают dice заново.

`onSent` обозначает подтверждение новой отправки, а не render, обновление клавиатуры, обычный edit или прикрепление компонента к уже существующему сообщению. Простое перемонтирование React-компонента не должно порождать новую отправку или её событие. Ошибка публикации не создаёт успешного `onSent`; политика ошибок остаётся общей для отправки сообщений. Ошибка самого обработчика после успешной отправки не превращает её в неуспешную и не должна инициировать повторную отправку. Гарантии доставки/повторного выполнения событий при аварии нужно определить вместе с общим механизмом событий, без обещания exactly-once.

Перед штатным восстановлением React-дерева контроллер загружает сохранённое сообщение вьюхи. Начальный `useState` в примере читает его `dice.value`, поэтому перезапуск или `force: true` восстанавливает нужную клавиатуру без новой отправки и без искусственного воспроизведения `onSent`. Если требуются игровые побочные эффекты вроде начисления очков, нельзя выдавать чтение сохранённого результата за новый бросок. Для заменённого/размонтированного узла нельзя вызывать устаревшее замыкание `onSent`; выбор актуального обработчика и отмена ожидания согласуются с жизненным циклом вьюхи.

Результат сохраняется с вьюхой, а не только в `useState`, чтобы после штатного восстановления использовать тот же бросок и восстановить недоставленную клавиатуру. Между отправкой дайса и добавлением зависимых кнопок допустим короткий период без клавиатуры. При неопределённом исходе отправки нельзя вслепую повторять `sendDice`; восстановление после сбоя между внешней отправкой и записью в БД требует общей политики ошибок публикации. Гарантия ровно одной отправки этим предложением не вводится.

Обновления должны сходиться к стабильному результату: одинаковый JSX не порождает новый edit, а обновление служебных callback-привязок само по себе не должно бесконечно менять клавиатуру. При необходимости общих игровых итогов автор может перенести значение в Redux отдельным действием из обработчика, но для построения кнопок достаточно локального state и сохранённого результата вьюхи.

Значение известно серверу до завершения клиентской анимации dice. Поэтому кнопки могут появиться во время анимации; Bot API не сообщает момент окончания анимации на каждом клиенте. Ожидание завершения анимации не является частью предложенного контракта.

## Восстановление после рестарта

Для обычного рестарта с тем же кодом приняты следующие правила восстановления. Отдельно ниже зафиксирована модель незавершённых событий при аварии; технические границы приёма событий и переключения поколений уточняются в плане.

- Восстанавливать общее сохранённое состояние и подтверждённые данные сообщений; существующие правила версии/миграции сохраняются.
- Создавать новое дерево Runtime и вьюх. Локальные hooks/refs не сохраняются, effects запускаются заново, сетевые ресурсы создаются повторно. Cleanup возможен при штатном завершении, но не гарантирован при аварии.
- Для восстанавливаемой обычной вьюхи хранить стабильное имя экспортированного корневого компонента, сериализуемые props и полный адрес прежнего сообщения. Внутренние компоненты могут оставаться неэкспортированными. Несериализуемые корневые props допустимы только у эфемерных вьюх из кода, не восстанавливаемых после рестарта.
- Повторно привязывать компонент к тому же сообщению, без новой отправки и без события useOnMessage о прежней отправке. Неизменный native результат не требует редактирования. Dice использует прежнее сохранённое значение и не бросается заново.
- Принято: при рестарте отключать все эфемерные вьюхи, включая оверлеи и самостоятельные личные сообщения, а не восстанавливать их React-деревья. Отключать прежние обработчики, запрашивать удаление эфемерных сообщений и давать пользователю открыть интерфейс заново. Видимая доставка удаления не гарантируется. Игровые данные в общем store не теряются; локальный экран не восстанавливается. Это относится и к эфемерной вьюхе, смонтированной агентом с сериализуемыми входными данными.

Для очистки нужно сохранять достаточно адресных метаданных эфемерных вьюх, чтобы после рестарта запросить их удаление; это не требование сохранять renderer, props или локальные hooks. Закрытие эфемерных вьюх не означает удаления публичных вьюх или общего store. Прежнее правило только для оверлеев расширено на самостоятельные эфемерные вьюхи.

Восстановление старых callback ID, момент приёма первых событий после рестарта и переход на изменённый исходный код рассматриваются отдельно; нельзя считать их решёнными только сохранением store или повторным рендером.

### Авария и незавершённые события

Принято для первой версии: автоматического переигрывания событий нет.

- Уже принятые движком нажатия, reply и реакции, оставшиеся в очереди, после аварии не восстанавливаются. Обработчики, начатые до остановки процесса, не запускаются повторно; продолжения их Promise не восстанавливаются. Это правило локальной очереди, а не указание отбрасывать ещё не принятые Telegram updates.
- Восстанавливаются последний успешно сохранённый store и регистрации обычных вьюх. Сохранённые промежуточные изменения до await остаются; несохранённые изменения, локальные hooks и refs теряются. Восстановление не откатывает уже совершённые внешние действия.
- Runtime и обычные вьюхи монтируются заново, effects выполняются по обычной семантике React. Соединения и подписки создаются повторно. Одноразовые игровые действия в effect требуют проверки сохранённого состояния приложения, если их нельзя повторять.
- Восстановление сообщения не является новой отправкой и не вызывает useOnMessage для прежней отправки или edit. Утерянный вызов обработчика этого хука не воспроизводится автоматически. Dice использует сохранённый результат; существующее сообщение не заменяется новым ради восстановления.
- Незавершённые requestAgent старого поколения отменяются по общим правилам; ожидания и запросы не восстанавливаются автоматически. Приложение может явно решить создать новый запрос по восстановленному store.
- Если внешняя операция успела выполниться перед аварией, её результат может остаться неизвестным. Нет гарантии exactly-once, автоматического отката или повторения такой операции. Пользователю иногда потребуется повторить действие; повтор после рестарта является новым действием, а не продолжением прежнего обработчика.

Это согласованный контракт нового движка, а не уже реализованный механизм или проверка аварийного восстановления. Порядок сохранения ревизий и публикаций, диагностика неопределённого исхода и тесты точек отказа описываются при реализации.

### Обновление исходного кода

Принято: применение новой версии кода является полным перезапуском React-дерева выбранного экземпляра, сохраняя его widgetId, общий store и адреса публичных вьюх. Локальные hooks/Context сбрасываются, Runtime/effects запускаются заново, оверлеи закрываются по правилу рестарта. Автоматическое сохранение hooks по аналогии с Fast Refresh не подразумевается.

Принято: сборку новой версии и проверку наличия экспортированных корневых компонентов восстанавливаемых обычных вьюх выполнять до остановки действующей версии. Для отключаемых при обновлении эфемерных вьюх экспорт корня не требуется. Несобираемый модуль или отсутствие нужного экспорта отклоняют обновление до переключения. Актуальное состояние и миграция должны согласовываться с остановкой/завершением событий старого поколения; точные границы и обработка длительных действий относятся к следующему вопросу очереди. Сбой активации после внешних побочных эффектов не получает автоматической гарантии отката всего приложения.

Принято: обновление применяется к выбранному экземпляру, не переключая остальные экземпляры автоматически. Они продолжают пользоваться прежней кешированной версией модуля до собственного обновления. Триггер применения новой версии, поведение при ошибке миграции/БД/нового effect и порядок переключения ещё требуют согласования.

### Кеширование сборки при загрузке из файла

Принято: при загрузке виджета из файла проверять манифест всех входов сборки, содержащий пути, mtime, размеры и хеши содержимого. Совпадение содержимого и параметров позволяет переиспользовать сборку; одна смена mtime не требует компиляции. Изменение или исчезновение входа требует пересборки; новый манифест сохраняется только после успеха. Учитываются версии SDK/компилятора и настройки разрешения импортов, включая влияющий package.json. Пользователь первоначально предложил MD5; алгоритм хеша и остальные внутренние детали ниже ещё уточняются.

Согласованное разделение метаданных файла и идентичности кода:

| Проверка | Действие |
|---|---|
| Содержимое входов и параметры сборки прежние | Переиспользовать готовую сборку и, в пределах подходящего процесса/области владельца, уже загруженный модуль |
| Изменился только mtime, хеш содержимого тот же | Обновить метаданные, не компилировать заново |
| Изменился хеш содержимого, включая случай прежнего mtime | Повторно собрать либо взять уже известную сборку для этого полного fingerprint |
| Изменились SDK, compiler/plugin/options или разрешение зависимостей | Считать прежний кеш неподходящим |

mtime не является доказательством совпадения содержимого: время может сохраняться при копировании/восстановлении, а точность зависит от файловой системы. Для строгой проверки при загрузке из файла нужно подтверждать хеш прочитанных байтов, а не пропускать его только из-за совпадения stat. Простая смена времени без смены кода не должна требовать компиляции.

Принято по уточнению пользователя: отслеживать все файлы, участвовавшие в сборке, а не только entry-файл. Основой списка является `metafile.inputs` из [esbuild](https://esbuild.github.io/api/#metafile). Поля записи файла: нормализованный путь, mtime, размер и хеш фактически прочитанного содержимого. При следующей загрузке из файла проверяется весь манифест; изменение или исчезновение входа требует новой сборки либо уже известного подходящего полного fingerprint. После успешной пересборки манифест заменяется новым списком входов. Неуспешная сборка не должна перезаписывать последнюю пригодную запись кеша.

Дополнительно в fingerprint входят используемые SDK-ресурсы, параметры и версии toolchain. Список входов следует дополнять данными resolver/plugin: одного списка старых inputs недостаточно при изменении разрешения import. Например, добавление файла с более приоритетным расширением либо смена package.json может изменить результат, не изменив прежние файлы. Конкретный формат такого дополнения ещё предстоит спроектировать.

Для выбора алгоритма рекомендуется использовать SHA-256 последовательно с текущим [build.mjs](../../src/widgets/build.mjs), где он уже формирует snapshotId из готового bundle. Это не готовый кеш исходников до компиляции: входной fingerprint и snapshotId результата выполняют разные роли. Пользователь предложил MD5; окончательный выбор алгоритма ещё не согласован.

Кеш должен учитывать область владельца/агента, каноничный entry path и контекст разрешения импортов. Хешировать и компилировать следует согласованный снимок источников; обнаруженное изменение во время подготовки требует повторной проверки. Параллельные запросы одной и той же версии должны разделять одну выполняющуюся сборку, не создавать отдельную компиляцию на каждую вьюху. Кеш результата не требует держать esbuild в процессе React runtime или постоянно запущенный compiler ради метаданных.

Проверка актуальности относится к загрузке/обновлению виджета из файла. Обычный React render, dispatch и открытие оверлея не являются поводом читать и компилировать исходники заново. Совпадающая сборка может обслуживать новый независимый экземпляр; её повторное использование само по себе не переключает другие уже работающие экземпляры и не стирает их hooks. Если реально новая версия применяется к существующему экземпляру, действует согласованный полный перезапуск этого экземпляра. Границы применения при создании новой вьюхи, лимиты кеша и удаление неиспользуемых версий остаются уточнениями.

Реальный compile path был прочитан, но этот кеш и его граничные случаи прототипом не проверялись. Это дизайн, не заявленная новая возможность текущего движка.

## Асинхронные обработчики и очередь

После согласования кеширования следующий пункт — уточнить последовательность событий при async/await. Конкретный сценарий: пользователь нажимает кнопку, обработчик ждёт сеть, в это время приходят другое нажатие, таймер или событие общего WebSocket.

Принято: не удерживать исключительную очередь всего виджета до завершения Promise обработчика. Синхронный участок выполняется последовательно; при await другие события этого экземпляра могут обрабатываться. После разрешения Promise продолжение может вызвать dispatch к актуальному store, но захваченные до await значения автоматически не обновляются. Долгий запрос одного игрока не блокирует все вьюхи и возможность обработать отмену. Это уточнение прежней идеи последовательной обработки.

При таком выборе:

- Один синхронный `dispatch(recipe)` неделим относительно других recipe и применяется к актуальному снимку store. Между разными dispatch, разделёнными await, состояние может измениться.
- Промежуточные изменения до await могут сохраняться и публиковаться до завершения всего обработчика. Значит, нужно явно определить границы сохранения синхронных участков/ревизий, а не считать весь async callback одной транзакцией. Независимые некоординированные записи из subscribe по-прежнему не подходят.
- Порядок сохранения и Telegram-публикации задаёт движок; новый async режим не отменяет запрет публикации несохранённой ревизии.
- Ошибка после await не откатывает автоматически уже сохранённые промежуточные изменения или внешние действия.
- Автоматический запрет повторного запуска, отмена запроса, таймауты и судьба продолжения после отключения вьюхи требуют отдельной политики. Операции старого поколения после перезапуска/обновления не должны менять новый store или его сообщения.

Ожидание полного Promise каждого обработчика с блокировкой всех остальных событий не выбрано. Принятая модель ещё не реализована новым движком; границы checkpoint, отмена и таймауты требуют технической детализации.

## Идентичность кнопок и устаревшие нажатия

Принято: отделять обычный render от замены логической кнопки и следовать идентичности узлов React, включая ключи родительских поддеревьев:

- Пока сохраняется тот же смонтированный узел кнопки, сохранять его непрозрачный callback ID. При React commit обновлять ссылку на актуальное замыкание onClick. Новая функция в JSX сама по себе не требует редактировать Telegram-сообщение или закрывать оверлеи.
- После удаления кнопки, смены её key или размонтирования соответствующего компонента отклонять новые нажатия на прежний ID. Не назначать этот ID другой кнопке по совпавшему индексу.
- Для динамических списков использовать семантические key, например playerId. Если логическое назначение кнопки изменилось, автор меняет key; одна смена props не означает новую идентичность.
- Key достаточно поставить на внешнем элементе, который возвращает map: например, `players.map(p => <PlayerRow key={p.id} player={p} />)`. Единственной кнопке на стабильной позиции внутри PlayerRow собственный key не требуется. При перемещении родителя кнопка сохраняется; удаление родителя или смена его key размонтирует и её. Изменение типа/структуры внутри поддерева подчиняется обычным правилам React. Это не наследование значения key дочерним элементом и не глобальный ключ: идентичность определяется всем положением в React-дереве.
- На отклонённое нажатие давать короткий ответ `Button is no longer active.`. Уже запущенный async обработчик не отменяется автоматически только из-за удаления его кнопки; отмена работы и отключение вьюхи обсуждаются отдельно.
- После рестарта или обновления кода обработчики прежнего поколения не могут менять новый экземпляр. Вариант восстановления — обновить публичные клавиатуры новыми callback ID и отклонять прежние; точный механизм восстановления ещё не выбран.

Пример: в списке удалили игрока A и на его место переместился B. Ключи по playerId не позволяют старому нажатию на A вызвать обработчик B. При обычном обновлении счёта существующая кнопка остаётся активной и вызывает актуальный обработчик.

Нужно согласовать активацию новых привязок с подтверждением Telegram edit и гонками доставки: React commit сам по себе не доказывает, что пользователь уже видит новую клавиатуру. Контракт принят, но ещё не реализован; конкретный механизм восстановления callback ID после рестарта остаётся предложением.

## Ошибки и границы отказа

Принято: изолировать необработанную ошибку рендера на уровне вьюхи, если общий Runtime продолжает работать. Название состояния ошибки — `error` и для вьюхи, и для экземпляра виджета; `stopped` не используется как название аварийного состояния. Вьюха в `error` остаётся зарегистрированной и допускает восстановление через mount. Намеренный unmount — отдельная операция. Отказ сохранения store переводит экземпляр в `error`. Детали ошибок действий и доставки ниже остаются предложениями, если не согласованы отдельно.

- Ошибка recipe отклоняет изменения этого dispatch. Ошибка обработчика завершает только этот вызов; ранее выполненные dispatch и внешние действия не откатываются. Движок регистрирует ошибку, остальные события продолжают работать. Автоматический повтор всего обработчика не выполняется, поскольку он мог уже отправить сообщение или выполнить другой внешний эффект.
- Принято: необработанная ошибка рендера отдельной вьюхи изолируется границей этой вьюхи и переводит её в `error`. Остальные вьюхи и Runtime продолжают работать, последнее успешно опубликованное сообщение остаётся. Прежние обработчики упавшего поддерева деактивируются. Восстановление — обычный `view.mount(node)`, автоматически выполняющий повторное монтирование без обязательного force. Автор может разместить собственную React error boundary внутри вьюхи; обработанная ей ошибка не требует платформенного `error`.
- Принято: ошибка общего Runtime, которую не обработала внутренняя граница, останавливает React-экземпляр этого виджета и переводит виджет в `error`. Сохранённый store не удаляется, другие виджеты агента не останавливаются. Ошибки async callback требуют отдельного перехвата движком; нельзя обещать, что React error boundary ловит их все.
- Принято: отказ сохранения общего store переводит виджет в `error`, останавливает новые изменения и публикации экземпляра до восстановления согласованного состояния. Несохранённая ревизия не публикуется. Уже ожидающие async продолжения не могут обойти остановку новым dispatch или API-вызовом. Откат локальных hooks и уже совершённых внешних действий не обещается. Точный механизм восстановления и блокирования операций требует детализации.
- Ошибка Telegram-публикации не откатывает сохранённый store и не перезапускает весь обработчик. Повторять допустимо конкретную операцию доставки с учётом вида ошибки; неопределённый исход новой отправки не даёт основания слепо отправлять её снова. Подтверждённое view.message не заменяется неподтверждённым результатом. Политика временных ошибок, недоступного сообщения и уведомлений агенту ещё уточняется.

Граница отказа вьюхи, общего Runtime и сохранения принята. Предлагаемая детализация: ошибка одного действия не должна автоматически останавливать весь виджет. Низкоуровневый crash процесса агента, лимиты ресурсов и восстановление других экземпляров относятся к отдельному уровню изоляции.

### Сбой сохранения store

Принято: если согласованное сохранение ревизии не удалось и движок не может подтвердить её долговечность, переводить экземпляр виджета в `error`, вместо введения отдельного длительно ожидающего состояния. До разрешения исхода записи не принимать новые изменения и не публиковать эту ревизию. Останавливать React-дерево и деактивировать поколение обработчиков; другие экземпляры не затрагиваются. Уже начатые внешние операции могут завершиться, их автоматический откат не обещается.

При восстановлении читать фактически сохранённый store из БД, заново создавать Runtime и вьюхи по правилам рестарта. Несохранённые изменения в памяти и локальные hooks не восстанавливаются. При неопределённом исходе commit сначала выяснять, какая ревизия действительно сохранена; нельзя автоматически считать, что запись точно не состоялась, или слепо повторять исходный обработчик.

Это заменяет ранее предложенное ожидание восстановления БД без остановки экземпляра. Локальная ошибка recipe или недопустимые данные dispatch отклоняют сам dispatch и не считаются инфраструктурным отказом записи всего виджета. Лимиты повторов заведомо безопасных операций хранения и способ запуска восстановления ещё требуют технической детализации.

### Ошибки доставки Telegram

Принятые правила для публикаций, управляемых renderer:

- Ошибка доставки не откатывает сохранённый store и не запускает повторно обработчик или recipe. Подтверждённый view.message сохраняет последний известный результат.
- Принято: одна попытка редактирования, без автоматических повторов после ошибки. Последующее восстановление через mount является новой явной попыткой. Нельзя обходить правило циклом повторных render того же неуспешно доставленного состояния. Отсутствие изменений при подтверждённо совпадающем результате не требует лишнего native edit по прежнему правилу сравнения результата.
- Принято: если ошибка явно подтверждает удаление или недоступность сообщения, удалять регистрацию вьюхи, размонтировать её поддерево и деактивировать обработчики. Дочерние оверлеи отключаются и закрываются по обычным правилам очистки. Общий store, Runtime и другие вьюхи остаются. Это не дополнительный delete чужого/недоступного сообщения и не создание замены. После удаления нужен явный mount по новому допустимому target, а не восстановление прежнего viewId.
- Для остальных ошибок доставки предлагается `error` только соответствующей вьюхи и отключение её обработчиков, без остановки Runtime и других вьюх. `view.mount()` с сохранённой нодой или mount с новым node инициирует восстановление и одну попытку синхронизации с актуальным store. Классификация ошибок должна отличать явную недоступность от временного сбоя или неизвестного результата; произвольная ошибка HTTP 400 не означает удаление сообщения.
- Не создавать новое сообщение автоматически вместо удалённого или недоступного. При неизвестном исходе первой отправки не выполнять слепой повтор, способный создать дубликат; сохранять неопределённость адреса/доставки и требовать её разрешения до новой отправки. Обычный mount ошибочной вьюхи не должен обходить это ограничение.
- Ошибки доступны в диагностике с widgetId, viewId, операцией и причиной. Принято ограничение автоматических уведомлений, описанное ниже; пользователь требует не будить агента каждым повтором ошибки. Возвращаемый результат mount при ошибке доставки ещё уточняется.

Пример: store уже содержит счёт 10, но Telegram показывает 9. Ошибка edit не возвращает store к 9. После явной попытки восстановления сообщение получает актуальное значение, которое к тому времени может быть больше 10. Граница React commit и подтверждения публикации сохраняется: успешный React render ещё не доказывает доставку. Автоматические повторы отвергнуты; детали классификации ошибок и уведомлений ещё обсуждаются.

### Уведомления агенту

Принято: сочетать уведомление о переходе в ошибочное состояние с общим ограничением частоты на агента. Первую ошибку направлять сразу; пока вьюха остаётся в том же `error`, не генерировать повторные обращения к агенту. Собирать новые ошибки в агрегат и направлять последующие сводки не чаще одного раза в пять минут на агента, только при наличии новых записей. Повторный неудачный mount и несколько одновременно упавших вьюх тоже входят в этот лимит; одно лишь правило перехода в `error` не защищает от циклов восстановления.

Сводка содержит виджеты/вьюхи, причины и счётчики, полная диагностика остаётся доступной без самостоятельного запуска агента. Частота согласована; точный состав событий (включая автоматическое удаление недоступной вьюхи) и механизм агрегации ещё уточняются. Этот лимит касается уведомлений, а не возврата ошибки непосредственному вызывающему коду.

## Полная замена старого движка

Принято пользователем: полная замена без переходного запуска legacy. При переходе на новый движок старые экземпляры отключаются и удаляются. Их регистрации, состояние, очереди и привязки вьюх не переносятся в React-экземпляры; старые обработчики, таймеры и фоновые задачи прекращают работу. Поддержка старого авторского формата не входит в новый runtime.

Для опубликованных сообщений используется семантика текущего `delete_widget`: сообщения остаются, кнопки отключаются по возможности, старые callback больше не вызывают обработчики. Удаление виджета не трактуется как массовый delete сообщений Telegram. Исходные пользовательские файлы не являются регистрациями виджетов и не удаляются автоматически.

Автоматическая миграция Wordle и продолжение прежних игр не требуются. Нужные приложения, включая Wordle, переписываются на новый React API и создаются как новые экземпляры. Миграции версии store остаются механизмом для последующих версий уже новых React-приложений.

Процедуру отключения и удаления legacy нужно реализовать как часть перехода: исключить запуск старых экземпляров до очистки, учесть незавершённые действия и возможность повторного старта после прерванной очистки. Эта запись фиксирует дизайн будущего перехода; удаления в текущем окружении не выполнялись.

## Пустой результат рендера

Пользователь предпочитает визуально пустое сообщение ошибке, если вся вьюха вернула null/пустой Fragment. Это пересматривает предложенный ассистентом отказ на пустом результате; пустые дочерние компоненты в любом случае допустимы.

Для обычного sendMessage пустая строка отклоняется с Message text is empty: проверено чтением официального Client.cpp и контракта метода. Это не ограничение rich-параграфа: живая проверка ниже дала другой результат. [sendMessage](https://core.telegram.org/bots/api#sendmessage), [InputRichBlockParagraph](https://core.telegram.org/bots/api#inputrichblockparagraph), [Bot API implementation](https://github.com/tdlib/telegram-bot-api/blob/master/telegram-bot-api/Client.cpp).

Принято после живой проверки: нормализовать пустой rich-render в {blocks: [{type: "paragraph", text: ""}]}, сохраняя регистрацию вьюхи и её React-дерево. Не нужны пробелы или специальные символы. Скрытый переход к обычному text-сообщению вместо rich не выполняется. Render с одной клавиатурой использует ту же нормализацию тела.

В ограниченном живом HTTP Bot API прогоне f95b08 через `test/manual/empty-rich-probe.mjs` проверены создание sendRichMessage и редактирование editMessageText обычного сообщения в тестовой группе. Контрольный непустой rich-параграф принят. Результаты без клавиатуры:

| Rich payload | Создание | Редактирование |
| --- | --- | --- |
| blocks: [] | RICH_MESSAGE_EMPTY | RICH_MESSAGE_EMPTY |
| Один paragraph с text: "" | Принято, пустой text сохранён в ответе | Принято, пустой text сохранён в ответе |
| paragraph с пробелом, NBSP, U+2800 или U+200B | Все четыре приняты | Все четыре приняты |

В том же прогоне пустой paragraph успешно отправлен отдельным эфемерным сообщением без клавиатуры; затем к нему добавлена inline-кнопка. Второе эфемерное сообщение создано с контрольным непустым телом и успешно отредактировано через editEphemeralMessageText в пустой paragraph с клавиатурой. Приватная отправка использовала свежий callback владельца; бот был обычным участником группы. Edit вернул подтверждение успеха без полного Message, поэтому содержимое после него подтверждено визуальной проверкой, а не выдуманным снимком ответа API.

Пользователь предоставил изображения обычного пустого сообщения и обоих приватных вариантов. Во всех трёх случаях тело визуально пустое; Telegram оставляет небольшой отступ/высоту и служебные элементы сообщения, что пользователь принял. Это живая проверка native API и одного клиента; другие клиенты, оверлей поверх публичного сообщения и новый React renderer здесь не проверялись. Остальные эфемерные варианты whitespace не запускались, поскольку пустой paragraph работает без подстановок. Runner ограничен временем, не меняет команды/членство бота и при завершении удаляет только свои сообщения, восстанавливает подписку updates и освобождает общую блокировку.

Прогон завершён успешно: собственные обычные и эфемерные сообщения удалены, подписка updates восстановлена, общая блокировка освобождена; ошибок очистки нет. Production-код и текущая wiki не менялись, новый React renderer не реализовывался.

Принято по уточнению пользователя: после публикации dice/sticker пустой render является ошибкой рендера, а не сохранением native-объекта со снятой клавиатурой. Чтобы убрать только кнопки, компонент должен продолжить возвращать прежний native-узел и убрать клавиатуру. Для ещё не опубликованной вьюхи пустой результат создаёт rich-placeholder; последующий переход такой уже опубликованной вьюхи к dice/sticker тоже отклоняется. Нужно сразу рендерить native-узел при создании новой native-вьюхи. Правила неизменяемого тела и отдельно изменяемой клавиатуры сведены в разделе жизненного цикла native типов; это решение дизайна, не новая живая проверка или реализованный React renderer.

## Связь виджета с агентом-владельцем

Пользователь запросил две возможности: передать сообщение агенту-владельцу и попросить у него ответ с тайм-аутом и/или отменой через AbortController. Это расширяет существующий односторонний notify_agent({text}), который отправляет событие widget_message с widgetId в очередь владельца. В текущем runtime запрос-ответ не реализован.

Принят публичный API нового Widget handle:

```tsx
await widget.notifyAgent({text: "The player finished the game."});

const reply = await widget.requestAgent(
  {
    text: "Prepare a hint. Return JSON with a hint field.",
    data: {playerId: "42", attempts: ["CRANE"], screen: "game"},
  },
  {timeoutMs: 120_000, signal: abortController.signal},
);
```

Принятый контракт:

- Получатель всегда агент-владелец widgetId; sender не задаёт чужой agentId. Первый аргумент имеет форму {text, responseSchema?, data?}: text обязателен, data — произвольное JSON-значение с параметрами из состояния/обработчика. Это обычное авторизованное событие виджета, а не системная инструкция с повышенными правами.
- Только первый аргумент requestAgent должен быть строго сериализуемым в JSON: он передаётся агенту на обработку. Необязательное поле можно не передавать; явные undefined, функции, Symbol, BigInt, NaN/Infinity, циклы и непрозрачные объекты не допускаются. Нужны обычные JSON-объекты/массивы и примитивы, без молчаливой потери полей или преобразования ресурсов в {}. Проверка выполняется до постановки события в очередь; первый аргумент фиксируется как независимый JSON-снимок вызова, последующие изменения исходных объектов не меняют событие. Второй аргумент {timeoutMs?, signal?} содержит локальные настройки ожидания, не передаётся агенту и может содержать AbortSignal.
- NotifyAgent подтверждает постановку в обычную очередь агента, а не завершение его работы. RequestAgent также ставит событие в очередь, но возвращает Promise с JSON-ответом.
- Контроллер создаёт requestId и передаёт агенту widgetId, requestId, текст/данные и срок, если задан. Агент отвечает новым инструментом answer_widget_request({requestId, result}). Обычный финальный текст хода не является ответом на RPC: ход агента может обрабатывать несколько разных событий. Контроллер проверяет владельца и поколение запроса.
- TimeoutMs и AbortSignal можно использовать по отдельности или вместе; требуется хотя бы один способ ограничения ожидания. Тайм-аут отсчитывается с принятия запроса, включая время в очереди. Срабатывает первый из ответа, тайм-аута или abort. Если signal уже отменён при вызове, событие в очередь не ставится.
- Тайм-аут/abort завершают ожидающий Promise понятной ошибкой и делают requestId неактивным. Если событие ещё в очереди, оно удаляется из неё: отменённый запрос не запускает ход агента. Уже переданное агенту событие отозвать нельзя; работающий ход принудительно не прерывается, поскольку он может выполнять другие задачи. Поздний ответ возвращает инструменту понятную ошибку недействующего запроса и не меняет store/вьюхи.
- Ожидание ответа не удерживает исключительную очередь/lock экземпляра и не мешает нажатиям, таймерам, агентским операциям и публикациям. Инструмент создания/mount не должен ждать завершения requestAgent из effects/подписок: иначе запрос к тому же агенту способен взаимно заблокировать его текущий tool call.
- При удалении, ошибке, перезапуске или смене поколения виджета запросы прежнего поколения отменяются. Живые Promise не восстанавливаются после рестарта; приложение при необходимости создаёт новый запрос по своему сохранённому состоянию. Источник в конкретной вьюхе сам по себе не задаёт её размонтирование как отмену работы: автор может связать это с AbortController.
- Ответ является данными, не исполняемым кодом и не автоматической командой отправки в Telegram. Применение ответа через dispatch, обновление вьюх или другие действия явно задаёт виджет. Непойманная ошибка ожидания обрабатывается по общим правилам callback, без автоматического повторного запроса.

Детальные схемы событий, результата и ошибок, а также лимиты очереди ещё уточняются. Уведомления по явному запросу приложения не следует молча считать теми же автоматическими error-сводками с пятиминутным лимитом; общий механизм нагрузки описывается отдельно. Реализация пока не начиналась.

### Схема ответа

Принято необязательное поле responseSchema с JSON Schema в первом аргументе requestAgent, отдельно от текста задания и data. TimeoutMs и signal остаются во втором аргументе как локальные параметры ожидания:

```tsx
const reply = await widget.requestAgent(
  {
    text: "Prepare a hint for the player.",
    data: {playerId: "42", attempts: ["CRANE"]},
    responseSchema: {
      type: "object",
      properties: {hint: {type: "string"}},
      required: ["hint"],
      additionalProperties: false,
    },
  },
  {timeoutMs: 120_000},
);
```

Агент получает схему вместе с событием; контроллер проверяет result в answer_widget_request до разрешения Promise. Без responseSchema допускается любой корректный JSON. Схема задаёт контракт данных для конкретного запроса, не меняет общую схему инструмента агента и не требует поддержки structured output конкретной моделью.

Принята политика ошибок: некорректная или неподдерживаемая схема отклоняется до постановки события в очередь. Несоответствующий ответ возвращает агентскому инструменту ошибку с путём поля и причиной; запрос остаётся активным, агент может исправить ответ до исходного срока. Тайм-аут при этом не продлевается, новый запрос агенту автоматически не создаётся. Диалект/поддерживаемые возможности JSON Schema и ограничения сложности уточняются при спецификации; сетевое разрешение внешних ссылок не предполагается.

## Быстрые команды публикации: отложенное дополнение

Отложено по решению пользователя при переходе к плану реализации React-движка. Ниже сохраняются ранее обсуждённые решения как отдельная будущая идея; реализовывать их вместе с React-виджетами не нужно. Это отдельный механизм быстрых inline/guest-команд с префиксом ! и зарегистрированными скриптовыми обработчиками, без хода агента. Встроенные команды публикации виджетов — одно из его применений; общий API регистрации скриптов ещё не выбран.

По предложению пользователя для !widget/new и !widget/view выбран сценарий с карточкой «Подключить виджет»:

- В inline-выдаче пользователь выбирает и отправляет карточку. Набор запроса, подготовка выдачи и публикация карточки сами по себе не создают экземпляр виджета или вьюху.
- В guest-режиме отправленная команда получает аналогичную карточку с кнопкой, без немедленного создания экземпляра/вьюхи.
- Нажатие кнопки обрабатывается зарегистрированным кодом без агента. Для !widget/new создаются новый экземпляр из указанного файла и вьюха выбранного экспортированного компонента с JSON props. Для !widget/view создаётся только вьюха уже существующего экземпляра.
  - Предлагается монтировать вьюху на саму опубликованную карточку, заменяя её виджетом. Это уточнение адресации ещё обсуждается. Сохраняются ограничения native типа и транспорта: наличие карточки не разрешает превратить существующее сообщение в dice/sticker или открыть guest-оверлей без поддерживаемого маршрута.

Принято: прикладную политику доступа определяет сам зарегистрированный скрипт. Он проверяет USER_ID при inline-вызове и заново при каждом нажатии кнопки; в guest-вызове аналогично доступен достоверный автор входящего запроса. При подготовке выдачи это вызывающий пользователь, при callback — фактически нажавший участник, который может отличаться от автора запроса. ID берётся из события Telegram, а не из дописанных параметров или пользовательского JSON. Прежний успешный inline-вызов сам по себе не авторизует последующий callback. Скрипт вправе разрешить только владельца, список пользователей или более широкую аудиторию; обязательное правило «кнопку нажимает только автор» не вводится.

Проверка прикладного USER_ID не заменяет платформенную изоляцию: контроллер проверяет регистрацию/доступность обработчика и ограничивает доступ его контекстом владельца. Разрешение нажать кнопку не даёт доступа к произвольным чужим файлам/виджетам. Выбор владельца обработчика и конкретная политика встроенных !widget-команд ещё требуют детализации.

Нужно согласовать владельца, повторные/одновременные нажатия, повторную публикацию одной карточки, срок жизни определения, ошибки частичного создания и детали замены карточки. Долговечность определения кнопки следует отделить от RAM-срока inline-запроса: опубликованная карточка должна адресовать своё действие, а не зависеть от chosen_inline_result. Публичные схемы и runtime не реализованы; предложение !exec/<id> с дописываемыми параметрами остаётся отдельным обсуждением.

## Управление виджетами через API агента

Требования пользователя: агент получает список своих виджетов и квоту, читает статус экземпляра и его вьюхи, включая статус каждой вьюхи, имя компонента и props; создаёт и удаляет виджеты; создаёт, изменяет и удаляет вьюхи; редактирует общий store. Это обязательные возможности нового движка. Они не означают доступ к чужим экземплярам или произвольное выполнение исходного кода из JSON аргументов инструмента.

Принят следующий набор инструментов и их назначение. Детальные схемы ответов и ошибок ещё уточняются; expectedRevision в текущую итерацию не входит.

| Инструмент | Принятый контракт |
| --- | --- |
| `list_widgets` | Краткие записи своих экземпляров: ID, описание, status, число вьюх; квота `limit`, `used`, `available` в том же ответе, без отдельного запроса |
| `get_widget` | Status, источник/сборка, описание, store со schema version, все зарегистрированные вьюхи и диагностические ошибки |
| `create_widget` | Создать экземпляр по handler-файлу и описанию, передать сериализуемые props в Runtime; начальное состояние задаёт defineStore; вьюхи автоматически не публикуются |
| `update_widget` | Обновить исходник/описание экземпляра и предоставить явное восстановление ошибочного экземпляра; изменение кода подчиняется согласованному полному перезапуску дерева |
| `delete_widget` | Удалить экземпляр, его store, очереди, ресурсы и регистрации вьюх; публичные сообщения остаются с отключёнными кнопками по возможности |
| `set_widget_view` | Создать вьюху через `send` или `target`, указав именованный экспорт `component` и JSON `props`, включая прикрепление к доступному эфемерному сообщению; либо изменить существующую по `viewId`, сохраняя ID и адрес. Повторная синхронизация без смены ноды соответствует view.mount() |
| `delete_widget_view` | Отключить и удалить регистрацию конкретной вьюхи по viewId с обычной семантикой unmount |
| `update_widget_store` | Атомарно заменить JSON-состояние конкретного экземпляра переданным state, без expectedRevision и проверки конфликта со снимком, ранее прочитанным агентом |

`get_widget` покрывает получение списка и деталей вьюх: ID, status, корневой компонент, props, target, parentViewId, получатель личной вьюхи, последняя ошибка. Для обычных вьюх и агентского ввода используется экспортное имя корня. Эфемерные вьюхи из кода могут иметь неэкспортируемый корень и несериализуемые props; диагностическое имя функции не является mount-идентификатором. Принято: в диагностическом JSON-представлении props функции заменять строкой `[Function]`, не сериализовать замыкание. Это описание для агента, а не снимок, пригодный для точного восстановления или обратного mount; живые значения внутри runtime не изменяются. Обработка других непрозрачных ресурсов/циклов и ограничения размера описания уточняются технически. Чтение не должно выполнять пользовательский render или сбрасывать ошибку. Сохранённые props Runtime также доступны при чтении экземпляра.

Принято для `set_widget_view`: при создании ровно один send/target, при изменении viewId вместо нового адреса публикации. Смена props того же компонента сохраняет hooks, замена компонента/key или force перемонтирует по общим правилам. Неуказанные поля существующей вьюхи сохраняются; props, если переданы, заменяют объект целиком. Детальная схема key/force и точный результат инструмента ещё требуют согласования. Произвольную функцию или JSX агент через аргументы инструмента не передаёт — выбирает экспорт из файла.

### Внешнее редактирование store

Принято: `update_widget_store({widgetId, state})` передаёт полный JSON-снимок и заменяет им store. По решению пользователя expectedRevision пока не реализуется, конфликта со снимком, ранее прочитанным агентом, не проверяется. Замена остаётся атомарной и координируется с dispatch текущего экземпляра; это не независимая запись в БД в обход живого store.

Изменения, произошедшие между чтением агентом и заменой снимка, могут быть перезаписаны переданным state. Это следствие выбранной полной замены без проверки версии, а не основание вводить скрытую проверку или обязательный токен. Внутренние revisions для порядка сохранения/публикации остаются техническим механизмом движка и не равны schema version из defineStore. Агент не меняет schema version этой операцией: изменение схемы выполняется через код/миграцию.

Изменение проходит проверку JSON и согласованное сохранение до публикации, уведомляет подписки useSelector без обязательного перемонтирования дерева. Локальные hooks не сбрасываются. Операция не должна воспроизводить пользовательские кнопки, вызывать onSent или заново отправлять одноразовые сообщения. Точное поведение инструмента при `error` общего Runtime, возвращаемые ошибки и работа с очень большим store ещё уточняются. JSON Patch или запись отдельных путей можно рассмотреть отдельно; пока они не являются требованием.

## Прямые операции Telegram над управляемым сообщением

Принято: прямой edit/delete сообщения через API, доступный агенту или useTelegram, снимает привязку вьюхи. Её регистрация удаляется, React-поддерево размонтируется, старые обработчики отключаются; общий store и другие вьюхи остаются. Дочерние оверлеи очищаются по общим правилам. Renderer не должен затем перезаписать сообщение, которое автор намеренно отредактировал напрямую.

Внутреннее редактирование самого renderer не считается такой внешней операцией и не удаляет собственную вьюху. Координацию прямого вызова с уже начатой публикацией и точный момент снятия привязки при неуспехе native запроса нужно формализовать. Очистка привязки не должна поверх успешной внешней правки повторно редактировать её содержимое/клавиатуру устаревшим результатом. Это платформенная координация вызовов API, а не обещание получать от Telegram события любых внешних изменений сообщения.

## Подписки на события вьюхи

Принято правило маршрутизации: если у вьюхи есть активный обработчик reply, ответ получает только виджет, без параллельной доставки обычному агенту. Ошибка обработчика сама по себе не является основанием повторно передать тот же reply агенту.

Принято: публичный API — React-хуки useOnReply(callback, {disabled?: boolean}) и useOnReaction(callback, {disabled?: boolean}) с автоматической отпиской. AddEventListener/removeEventListener не предоставляются автору как API вьюхи; низкоуровневый реестр listener остаётся внутренним механизмом SDK.

Принятые правила:

- Каждый хук относится к текущей вьюхе, как useView. Несколько компонентов могут зарегистрировать обработчики одного события; подписка не инициирует React render. Обработчик сам вызывает dispatch/setState или нужное действие.
- Disabled по умолчанию false. При disabled:true активной подписки нет: callback не вызывается, и эта подписка не перехватывает reply у обычного маршрута. Если хотя бы один useOnReply данной вьюхи включён, применяется принятое правило доставки только виджету. Если включённых обработчиков нет, действуют обычные правила маршрутизации, а не принудительный вызов агента в обход команд/разрешений.
- Хук вызывается безусловно по правилам React; условие включения передаётся в disabled. SDK сам регистрирует и снимает подписку при изменении disabled, размонтировании компонента, удалении вьюхи или остановке поколения.
- SDK обновляет ссылку на актуальный callback при commit. Новая inline-функция на каждом render не должна накапливать обработчики или требовать от автора deps-массив только для свежего замыкания. Функции не сериализуются; hooks заново создают подписки после восстановления обычных вьюх.
- Нет автоматического всплытия от оверлея к публичной вьюхе или рассылки всем вьюхам. Возможность явной подписки на другую вьюху из Runtime рассматривается отдельно и не следует автоматически из этих хуков текущего контекста.
- Ошибку синхронного callback и rejection возвращённого Promise перехватывает движок по правилам ошибок обработчиков. Await не удерживает исключительную очередь всего экземпляра. Созданные автором самостоятельные Promise без возвращения/обработки не получают автоматической гарантии перехвата.
- Ответ может содержать текст или файл; listener должен получить исходное сообщение/его доступные данные, а не только строку. Reaction обозначает изменение реакции, включая снятие/замену. Анонимные агрегированные счётчики не содержат достоверного автора; их нельзя выдавать за индивидуальный лайк. Точная схема payload и объединение/разделение видов reaction ещё обсуждаются.

Пример подписки на ответ:

```tsx
useOnReply(event => {
  dispatch(state => {
    state.lastReply = event.message.text ?? null;
  });
}, {disabled: !acceptReplies});

useOnReaction(handleReaction, {disabled: !acceptReactions});
```

Внутренний механизм может служить общей основой принятых useOnMessage/useOnReply/useOnReaction; автор не управляет removeEventListener вручную. Различия данных и семантики событий остаются явными: useOnMessage — исходящая публикация/редактирование, useOnReply — входящий ответ, useOnReaction — изменение реакции.

Подписка не расширяет то, что Telegram доставляет боту: для reaction updates требуются права администратора и явно включённые allowed_updates; анонимные счётчики могут приходить с задержкой. [Telegram Update](https://core.telegram.org/bots/api#update), [MessageReactionUpdated](https://core.telegram.org/bots/api#messagereactionupdated). Для inline/guest без известного исходного адреса нельзя обещать маршрутизацию reply по одному inlineMessageId. Команды контроллера сохраняют приоритет.

Технически нужно согласовать фиксацию активных подписок с маршрутизацией и уже принятой очередью событий. Изменение disabled после приёма reply не должно приводить к его повторной доставке сразу в другой маршрут. Принята общая модель аварии: уже принятые reply/reaction в очереди и незавершённые обработчики после рестарта не восстанавливаются и не переигрываются. Схемы payload, порядок вызова нескольких обработчиков и обработка гонок маршрутизации ещё уточняются; выбор публичных хуков закрыт.

## Завершение mount и частично применённые изменения

Принято: await mount ждёт подтверждения Telegram, а не только React commit. Если редактирование не требуется, потому что native результат уже подтверждён и совпадает, лишний запрос не выполняется. Принцип возврата при ошибке: reject либо View в error в зависимости от этапа и того, применились ли изменения к вьюхе. Пользователь подтвердил следующую таблицу исходов.

Принятая детализация:

| Этап и исход | Результат операции |
| --- | --- |
| Валидация не пройдена до принятия новой ноды/props: например, нет обязательного экспорта, props несериализуемы там, где это требуется, или адрес не разрешён | reject; существующая вьюха не заменяется |
| Новая нода/props уже приняты в зарегистрированную вьюху, но render или попытка доставки завершились ошибкой, не требующей удаления | resolve с View в error; принятая нода сохранена для последующего mount() |
| Доставка подтвердила, что сообщение удалено или недоступно; регистрация вьюхи удалена по принятому правилу | reject с диагностикой удаления вьюхи; нельзя возвращать пригодный к mount handle несуществующей регистрации |
| Telegram подтвердил синхронизацию | resolve с действующей вьюхой и подтверждённым адресом/сообщением в пределах результата native метода |

Для неизвестного исхода новой отправки и отказа БД после внешней публикации нужно сохранять отдельную диагностику частичного результата. Reject сам по себе не должен обещать, что внешних действий точно не было, или разрешать автоматическую повторную отправку. Схема ошибки и реализация принятия ноды/регистрации уточняются в плане в рамках принятой таблицы.

## Приоритет следующих обсуждений

Следующие вопросы влияют на авторский API и поведение приложения. Это повестка обсуждения, не новые принятые решения:

1. **Фоновая жизнь приложения и основной API store.** Обсуждение первого пункта завершено пользователем: default Runtime с `children`, стандартная обёртка при отсутствии default, регистрация defineStore в окно инициализации и SDK-хуки useSelector/useDispatch. Общий store сохраняется между отключением и подключением вьюх. Подробности фоновых ресурсов и конфигурации экземпляра сохраняются в технических уточнениях; новый вариант регистрации/подписок предстоит проверить прототипом.
2. **Восстановление и обновление исходного кода.** Приняты закрытие всех эфемерных вьюх при рестарте, восстановление сохранённого store/обычных вьюх, отказ от переигрывания уже принятых событий и незавершённых обработчиков после аварии, полный перезапуск выбранного экземпляра при обновлении и кеш по манифесту входов/содержимому/параметрам сборки. Effects запускаются заново; внешние действия не откатываются. Технически уточняются алгоритм хеша, формат зависимости resolver, идентификация корневого компонента/props и ошибки переключения.
3. **Асинхронные события и старые кнопки.** Принято не удерживать очередь экземпляра на время await; отдельный dispatch неделим и работает с актуальным store. Приняты стабильный callback ID для сохраняющегося React-узла кнопки, актуальный обработчик и отклонение нажатий на удалённые узлы, включая размонтирование родительского поддерева. Границы сохранения, гонки публикации, восстановление callback ID и отмена/таймауты требуют технической детализации.
4. **Ошибки и границы отказа.** Приняты отдельный `error` для упавшей вьюхи, `error` экземпляра при отказе общего Runtime или сохранения, восстановление через mount, вызов `view.mount()` без node, одна попытка edit и удаление регистрации явно недоступного сообщения. Автоматические повторы отвергнуты. Приняты уведомление о первой ошибке и последующие агрегированные сводки не чаще раза в пять минут на агента. Детали остальных ошибок доставки и обработчиков уточняются. Запрет публикации несохранённых данных не является автоматическим откатом локального React-состояния.
5. **Совместимость.** Принята полная замена: старые экземпляры отключаются и удаляются, legacy runtime не сохраняется, автоматического переноса старых игр нет. Нужные приложения переписываются и создаются заново; процедуру очистки предстоит реализовать.
6. **API агента.** Приняты перечисленные инструменты управления экземплярами, квотами, вьюхами и store, адресация компонента по экспорту и полная замена store. expectedRevision отложен пользователем; внешней проверки конфликта версий в этой итерации нет. Детальные схемы результатов и ошибок остаются техническим уточнением.

Полный перечень технических уточнений остаётся ниже. Реализация и живая проверка нового renderer пока не начаты.

## Оставшиеся решения перед планом реализации

Основные выбранные контракты выше не открываются заново. Из подробного списка ниже на пользовательский API и объём первой версии ещё влияют:

1. Корневые компоненты и props: экспорт и сериализация требуются для обычной восстанавливаемой вьюхи и агентского JSON-ввода. Для эфемерных вьюх из кода компонент/props остаются в памяти и могут быть несериализуемыми. Props create_widget сохраняются и передаются в default Runtime. Для диагностики функций принят маркер [Function]; остальные ресурсы описываются технически без обещания сериализации.
2. Работа при нуле вьюх: принято, что Runtime и его effects продолжают работать; store сохраняется. Этот выбор закрыт.
3. Окончательная форма Telegram JSX: рабочее направление — гибрид rich/sticker/dice с клавиатурой и без обязательного tg-message, с сохранёнными альтернативами для сравнения. Native live-location отложена; rich-карты остаются. Приняты useOnMessage после новой публикации/каждого успешного edit, пассивное view.message и useDice с парой [value, emoji]. Пустой rich-render нормализуется в один пустой paragraph: native создание/редактирование обычного и эфемерного сообщения и внешний вид подтверждены. Dice/sticker создаются только новым сообщением; изменение тела или пустой render после их публикации — ошибка. Повторный render неизменного native-узла и изменение его клавиатуры допустимы. Затем свести host-теги, клавиатуру и хуки в авторскую спецификацию.
4. Самостоятельные личные эфемерные вьюхи включены; агенту разрешено прикреплять вьюху к доступному эфемерному сообщению с экспортным именем и сериализуемыми props. После рестарта все эфемерные вьюхи отключаются. Новые самостоятельные сообщения создаёт только widget.mount, event.mount отвергнут. Приняты receiverUserId/callbackQueryId в target, полный адрес с ephemeralMessageId для существующего сообщения и ошибка event.overlay на самостоятельной личной вьюхе. Принята очистка после 20 минут неактивности получателя, без продления от фоновых updates.
5. Прямые edit/delete: принято удалять привязку вьюхи. Остаётся технически согласовать гонки операций и ошибку внешнего вызова; внутренние edits renderer не снимают привязку.
6. Завершение операций: приняты ожидание подтверждения Telegram и таблица разделения reject/View(error) по применению изменений. Состав event и алиасы методов ещё нужно окончательно свести в единый контракт.
7. Аварийное восстановление: принято не восстанавливать локальную очередь уже принятых событий и не перезапускать начатые обработчики. Восстанавливаются сохранённый store и обычные вьюхи; effects выполняются заново, эфемерные вьюхи отключаются. Выбор закрыт; остаются технические границы сохранения и испытания точек отказа.

Внутренние алгоритмы кеша, поколений, хранения и лимитов можно детализировать в плане и прототипах, не превращая каждое техническое решение в отдельный пользовательский выбор. Перед реализацией нужны цельные проверяемые примеры и согласованный объём первой версии; текущий документ всё ещё является дизайном.

## Технические уточнения и открытые вопросы

1. Стратегия перехода определена: полная замена и удаление старых экземпляров без автоматической миграции. Уточнить процедуру однократной очистки, отключение старых callback и восстановление после прерывания этой процедуры; подготовить новый Wordle как пример, если он войдёт в объём реализации.
2. Точный контракт renderer и сохранение точек монтирования: для обычных вьюх экспорт и сериализация обязательны, для эфемерных из кода не требуются; агентский ввод всегда использует экспорт и JSON props. Уточнить lookup экспортов, aliases/обёртки, валидацию и диагностику живых props; внутренние компоненты/layout динамически компонуются обычным React.
3. Runtime продолжает работать при отсутствии всех вьюх — принято. Props из create_widget являются сохраняемой сериализуемой конфигурацией экземпляра. `children`, default Runtime и его стандартная замена при отсутствии экспорта приняты. Уточнить cleanup, reconnect и координацию внешних callback с сохранением данных. Принят максимум один defineStore в окно инициализации модуля; повторный/поздний вызов — ошибка, отсутствие вызова даёт описание версии 0 с `{}`. Проверить привязку регистрации к версии модуля, кеширование, параллельную загрузку и сохранение вызова сборщиком. Старый прототип проверял другой способ обнаружения описания.
4. Тип `useViews()`, вспомогательные методы `widget`, ошибки и возвращаемые значения изменяющих операций. Имена адресных методов выбраны: `mount`, `unmount`, `closeOverlays`, `getView`; формы target для создания/прикрепления, поведение повторного отключения и устаревших ссылок нужно формализовать. Для симметрии можно переименовать предложенный `view.unmountOverlays()` в `view.closeOverlays()`; это ещё не принято.
5. Связь событий с обработчиками-замыканиями, их версии при обновлении публикаций, восстановление после рестарта и защита от старых кнопок. Для кнопки используются event.from/view/callbackQueryId/overlay; точную схему нужно свести в SDK. Приняты useOnReply/useOnReaction с disabled и автоматической отпиской вместо публичного addEventListener; при активном reply-обработчике событие получает только виджет. Уточняются payload и гонки изменения подписки.
6. Реактивные снимки данных view со ссылкой `parent` и методами: стабильность идентичности, сериализация между процессами и работа после `await`.
7. Изменения store из кнопок, timers, сетевых callback и effects; порядок очереди, контроль revisions, сохранение и публикация, ошибки recipe/reducer, обработчика и БД, checkpoint долгого действия и невозможность обычного отката локального React-состояния.
8. Для выбранного направления SDK-хуков `useSelector` и `useDispatch` с draft-recipes уточнить равенство результата selector, ограничения функции изменения, ошибки и границы сохранения. После аварии уже принятые события и незавершённые обработчики не переигрываются — принято. Ранее проверенный Redux-прототип не доказывает работоспособность новой реализации без Redux.
9. Конкретные разрешённые данные store, правила нормализации, лимиты снимка и версия формата в схеме контроллера.
10. Прямой edit/delete удаляет привязку вьюхи — принято. Уточнить координацию с публикацией renderer и ошибкой native запроса; внутренний edit renderer не удаляет привязку. Правила адресации по умолчанию нельзя считать определёнными только наличием текущей вьюхи.
11. При рестарте все оверлеи закрываются — принято. Уточнить очистку сохранённых адресов и отказ от старых callback при недоставленном удалении, native Revert и последующий автоматический рендер, повторное использование ephemeral ID. Конфликт игры одного пользователя через обычное и гостевое представления остаётся отложенным.
12. Закреплённые версии React/reconciler, их обновления, безопасность sandbox, использование памяти, корректное размонтирование и испытания настоящей доставки Telegram.
13. Отдельные эфемерные вьюхи без публичного родителя включены — принято; создание новых самостоятельных сообщений только через widget.mount, event.mount отсутствует. Агенту разрешено монтировать на доступное эфемерное сообщение с сериализуемым описанием. Приняты receiverUserId/callbackQueryId в target и ошибка event.overlay на самостоятельном личном сообщении; уточнить техническую схему и лимиты/TTL. Принятый алиас closeOverlay закрывает такую личную вьюху по условию user !== null. Новый renderer ещё не реализован.
14. Rich HTML как язык JSX принят вместе с React `onClick` и преобразованием в rich blocks; это пока не реализовано. Остаются точный набор host-тегов/атрибутов, корень сообщения, сокращения callback-кнопок, явный `data` вместе с `onClick`, типизация и политика стабильных callback ID. Для обычных текстовых сообщений отдельно выбрать переключение формата и JSX-представление внешней клавиатуры: обычный HTML не совпадает с rich.
15. Выбранное направление renderer — rich/sticker/dice с клавиатурой, вместо первоначального широкого набора native сообщений. Native live-location отложена; rich-карты допускаются. Dice/sticker впервые создаются только новым сообщением, после публикации тело неизменно; пустой render или смена параметров тела дают ошибку рендера, изменение клавиатуры допустимо. Уточнить окончательный JSX, источник media и матрицу адресов. Пассивное view.message сохраняется, принята событийная подписка useOnMessage на новую отправку и каждый успешный edit, допускающая явные циклы, созданные обработчиком. Полная реактивная подписка useMessage не вводится; useDice принят. Уточнить результат для способов публикации без полного Message. Принято не воспроизводить утерянные вызовы useOnMessage после аварии; восстановление прежней публикации не создаёт новое событие отправки. Обычная семантика effects сохраняется, ref.current.ready не выбран. Новый движок не реализован.
16. Приняты widget.notifyAgent/requestAgent, корреляция инструментом answer_widget_request, timeout/AbortSignal и отсутствие удержания lock при ожидании. Отменённое событие удаляется из очереди, если ещё не передано агенту; запросы прежнего поколения отменяются. Только первый аргумент requestAgent строго JSON: {text, responseSchema?, data?}; второй {timeoutMs?, signal?} содержит локальные настройки ожидания. ResponseSchema проверяется контроллером, ответ можно исправить до исходного срока. Реализация не начиналась.

Открытые вопросы не являются препятствием для продолжения обсуждения. Они отделены от принятых решений, чтобы документ не создавал ложного впечатления завершённой спецификации.
